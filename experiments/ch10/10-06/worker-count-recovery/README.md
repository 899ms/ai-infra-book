# 10-6：恢复时改变DataLoader worker数量

从原来2个worker保存的检查点恢复为1个或4个worker，**12次恢复全部保持原训练轨迹**：420次后续真实更新中，每步输入字节位置、loss和梯度范数完全相同；每次最终模型、Adam、CPU RNG、DataLoader Generator及packing状态与原不中断基线逐项精确一致，包含114个张量。

固定3个seed（1061/1062/1063）、第17／41步两个检查点、恢复worker数1／4，形成12个条件，每条件执行一次。共12个训练进程和30个实际读取数据的worker，全部正常退出且无残留。原始2-worker基线、保存前缀和检查点直接复用，未重新训练基线。

| worker数量 | 最终训练消费游标 | 最终派发游标 | 模型与优化器状态 |
|---:|---:|---:|---|
| 原基线2 | 32 | 36 | 参考 |
| 恢复为1 | 32 | 34 | 每次精确一致 |
| 恢复为4 | 32 | 40 | 每次精确一致 |

游标表示下一条记录编号。派发游标随预取数量变化，是执行进度观察量，不是已提交训练的逻辑位置；它不应覆盖消费游标。各worker实际完成读取的数量可有差异，原始日志全部保留，不要求退出时预取队列同一内容。

## 固定条件与证据

M2 Max本机CPU，Python3.14.7、Torch2.14；原124672参数byte Transformer、两层、width64，无dropout。主进程2线程，worker1线程，spawn、prefetch_factor2、顺序DataLoader。每步128个next-byte目标，64步为完整轨迹；17步保存后恢复47步，41步保存后恢复23步，总420新增更新。数据和模型源码均为原封存副本。

第17／41步的packing残留分别181／6 bytes。恢复保留残留、从消费游标重读未消费记录；原检查点的四条未消费预取记录在全部恢复中都实际重新读取。模型和两份Generator状态继续按原实现恢复。`run_worker.py`相对原件只增加worker参数、替换DataLoader的worker数并记录该参数，未调整优化器或精确一致门槛。

这是确定性读取、顺序返回和无随机增强条件的机制实测。不同worker数改变的不是数据语义，所以可以保持逻辑轨迹；随机增强、worker局部随机流、无序返回及完整大模型I/O争用不由本实验覆盖。实际墙钟和RSS保留为运行记录，单次固定顺序不能支持worker数量性能排名。

`reference/`含三个不中断基线、六个检查点前缀及原执行记录；`provenance.json`固定所有复用原件SHA。`results/`含每个恢复的派发／读取／消费日志、逐步输入与训练结果、最终完整状态、PID、退出和资源采样。预登记条件见`PROTOCOL.md`，正式运行源码SHA保存在`results/environment.json`。

## 独立复现

使用相同Torch版本，在本目录副本内指定不存在的输出目录：

```sh
python -B launch.py --out new-results
python -B analyze.py --out new-results
```

不依赖相邻实验目录、GPU或calculations。分析器从源文件位置独立重建每步输入，检查每步结果、全部模型和优化器状态、实际worker数量、消费顺序、原预取记录重读及实际派发游标。只检查loss不足以证明恢复一致，本实验同时核对完整状态。`python -B verify.py`用于核对现有封存及重新分析结果逐字一致。
