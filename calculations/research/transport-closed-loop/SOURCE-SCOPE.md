# 双向参考网络：来源与独立审查范围

本目录的 `sources.lock.json` 固定 RFC9000、RFC9002 和 RFC Editor 已验证 Errata7539。原件从已固定的 `../transport-feedback/sources/` 复制，每份目标重新计算字节数和 SHA256；没有把复制日期称为规范修订日期。当前 sender 代码仍读取原 feedback 来源锁，新增本地锁用于本次独立审查证据。

实际复读的适用段落为 RFC9000 §4.1–4.2（STREAM 最高 offset 和绝对限额）、§13.2.1–13.2.5（ACK 生成、频率、范围、host delay）、§13.3（信息重传而非复用 PN），RFC9002 §4.2、§5.3、§6.1–6.2.4、§7，以及 Verified Errata7539。后者要求 RTT 方差使用更新前的 SRTT，再更新 SRTT，正文未经勘误的次序不能用作另一种同等合法解释。

每包立即 ACK 是显式选择的参考策略。RFC9000 §13.2.2 给出至少每两包反馈的通常建议并允许其他策略，不意味着真实实现总是每包立即 ACK。ACK-only 不生成 ACK；MAX 更新为 ack-eliciting，必须在双向线上账本中保留其反馈。单包 ACK 范围和固定 64B QUIC 控制包只是声明布局，未验证实际 QUIC 帧编码器。

ACK Delay 为接收端有意等待生成反馈的时间。本例在收到包时立即生成，取零；ACK 后续排队/串行被视为所声明的外部链路服务，并进入发送者测得的 RTT。RFC9000 §13.2.5 并不普遍允许忽略端点有意施加的 pacer 或发送缓冲等待；如果这些队列改为端点可控的 ACK 延迟，需要重新明确并实现测量边界。28B UDP/IPv4 和 32B QUIC 头/帧/tag 为本例声明预算，不代表所有包/地址族的普遍开销。

发送时间在实际串行开始记录；链路序列化结束再加单向传播。接收端区间、发送端 ACK 确认区间和实际消费各自独立。模型开始依赖上传完整有序区间，不依赖最后上传 ACK 到达。普通 ACK 不增加 MAX_DATA/MAX_STREAM_DATA；实际消费生成 MAX，发送方仅在其到达后使用额度。

PTO 授权实际 probe，不在超时时直接宣布旧包丢失。新 PN 可以携带旧 STREAM offset；线上重发字节重复计费，唯一业务区间只计一次。第一版选参考 NewReno；CUBIC/BBR 状态实现的存在不意味着它们已经接入此网络，更不意味着完整 Linux TCP 或生产 QUIC。

预先手算来自 `root-oracles.py/json`，独立 checker 在实际执行候选后逐包核这些确定时刻，并核每方向线速、非重叠、反馈因果、PN、区间及线上字节。第 3 例保留 MAX ACK 占用上行 23/307 秒的修正说明。有限队列规则、ACK 丢失恢复、媒体/取消、多流、控制器适配和全部 C68 仍须逐项验证，不能由五个小例或一条 30MB 成功路径推断完成。
