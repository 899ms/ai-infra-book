# 第 2 章 模型架构

第一章把一次模型执行分解为容量、计算与数据读取，并借助硬件的关键数字估算时间下界。这样的估算可以迅速排除一些方案，却还留下一个问题：所代入的计算量和数据量从哪里来？“一个 8B 模型”只说明参数数量的大致范围，没有说明每个 token 使用哪些参数、上下文保存在什么地方，也没有说明不同工作之间的先后关系。

本章从一个 token 的数值表示开始，沿着一层网络追踪它如何变成下一个 token 的分数，再计算这条路径的容量 $M$、运算量 $F$ 和读写量 $R$。计算图用节点表示运算，用边表示运算之间传递的数据。先认识图上的对象，才能知道资源预算中的每个数字来自哪里。

我们使用 Qwen3-8B 作为贯穿例子。这是一个约含 81.9 亿参数的语言模型，重复执行 36 层网络来处理文本。先完整理解这一种模型，再改变上下文的保存方式、每个 token 使用的参数集合和层间连接，比较 Qwen3.6-35B-A3B（下文简称 Qwen3.6）、DeepSeek V4-Flash 与 Kimi K3 的资源需求。

计算运算量时，一次乘法加一次加法计为 2 FLOPs。存储量采用 GB 和 GiB：$1\ \mathrm{GB}=10^9\ \mathrm{bytes}$，$1\ \mathrm{GiB}=2^{30}\ \mathrm{bytes}$。BF16 是每个数占 16 位的浮点表示，每个元素占 2 字节，因此将张量的元素数乘以 2，就得到它的存储大小。

## 2.1 计算图与前向执行

张量是按一个或多个维度排列的数值数组：向量只有一个维度，矩阵有两个维度。模型用向量表示每个 token 的特征，把多个位置的向量按行排成矩阵。理解模型资源需求，首先要把计算节点和数据依赖分开。一个节点执行矩阵乘法或其他变换，一条边表示后续节点需要前面的结果。节点的工作量决定需要多少处理能力，边上的张量决定数据量，边的方向则决定哪些工作能够同时推进。三者共同描述模型，单看参数量无法替代其中任何一项。

本章的计算图先描述数学运算和数据依赖。实际执行时，框架会把这些运算交给设备程序；一个运算可能拆成多个程序，多个运算也可能合在一起执行。图上的一条张量边只说明后续需要这份数据，不表示它一定要在 CPU 与 GPU 之间复制。第四章说明数据放在哪里，第五章再解释程序怎样提交、数据怎样传入传出。

### 2.1.1 序列依赖与因果计算图

要计算执行时间，先要知道哪些运算能够同时开始。考虑四个 token、三层网络，把位置画在横轴、层数画在纵轴。循环神经网络（RNN）把前一位置的状态传给后一位置，位置状态满足 $h_t=f(x_t,h_{t-1})$。其中 $x_t$ 是当前输入，$h_t$ 是处理到当前位置时保存的状态，$f$ 是使用模型权重进行的变换。当前结果依赖前一位置，所以同一层沿位置串行推进。即使四个输入已经全部到达，第 $t$ 个位置仍要等待第 $t-1$ 个位置。

![循环神经网络的依赖。相同颜色的圆点表示各位置的计算，箭头指向需要前一结果的节点；同层位置沿横向逐次推进。](ch02/figure-2-1-dependencies.svg)

*图 2-1　循环神经网络的依赖。相同颜色的圆点表示各位置的计算，箭头指向需要前一结果的节点；同层位置沿横向逐次推进。*

Transformer 用注意力机制让一个位置读取其他位置的信息；“因果”表示当前位置只能使用自身及此前位置的信息。因果 Transformer 的依赖形式不同。第 $l$ 层计算某个位置时，通过注意力读取上一层中该位置及其之前各位置的表示。只要输入 token 已知，并且上一层的相应表示已经完成，同一层不同位置的计算就不需要再等待本层前一个位置的输出。因果掩码是一张允许访问关系表，它屏蔽当前位置之后的信息。按查询与被查询位置排列，这张表呈三角形；它限制信息来源，却不要求所有已知位置逐个执行。网络深度方向的依赖仍然存在：下一层使用这一层的结果。

![因果 Transformer 的层间依赖。各查询读取上一层中允许访问的位置；上一层完成后，同一层的已知输入位置可以并行计算。](ch02/figure-2-causal-dependencies.svg)

*图 2-2　因果 Transformer 的层间依赖。各查询读取上一层中允许访问的位置；上一层完成后，同一层的已知输入位置可以并行计算。*

沿图中的箭头追踪，便能区分两种等待：RNN 在同层等待前一位置，因果 Transformer 在下一层等待所需的上一层结果。已知输入能否并行，取决于这些依赖，而不是“序列”这个名称。生成新的 token 又增加了另一条依赖：下一次调用的输入由本次输出确定。

编码器把已知输入转换为表示，解码器根据允许访问的信息逐步产生输出。现代因果语言模型常用只含解码器的结构（decoder-only），本章采用这一结构。处理已知输入时，同层位置可以并行；生成时，第一个输出确定后才能成为下一次输入。因此，输入处理沿网络深度推进，生成还增加了跨调用的串行依赖。[^source-10]

### 2.1.2 模型配置与张量结构

先把一个计算节点展开。设输入有 $m$ 行，每行 $k$ 个特征，输出宽度为 $n$：

$$
X\in\mathbb R^{m\times k},\qquad W\in\mathbb R^{k\times n},\qquad Y=XW\in\mathbb R^{m\times n}.
$$

每个输出元素是长度为 $k$ 的点积，输出共有 $mn$ 个元素，因此

$$
N_W=kn,\qquad F=2mkn,\qquad M_W=b_Wkn.
$$

$N_W$ 是权重参数数，$b_W$ 是每参数字节数。行数 $m$ 翻倍，运算量翻倍，权重大小保持不变；输出宽度 $n$ 翻倍，权重与运算都翻倍。这两个变化分别对应“同一模型处理更多输入”与“模型的一层变得更宽”。下面的模型表都可以用这条规则逐行计算。

先只看 Qwen3-8B 的一条数据路径。一次**前向执行**是使用当前权重从输入算到输出的过程；隐藏向量是网络内部传递的特征表示，其维度给出每个位置保存多少个数。**前馈网络**（feed-forward network，FFN）对每个位置分别做特征变换；**注意力**则在位置之间选择并汇总信息。这两类运算交替组成网络的一层。

Qwen3-8B 包含 $L=36$ 层，隐藏维度为 $d=4096$，FFN 中间维度为 $f=12288$；注意力把特征分成多组并分别建立位置间的关系，每一组称为一个头。这里有 32 个查询头和 8 组供查询使用的键值头（KV 头），每头 128 维；2.1.3 将沿查询、键和值的路径解释它们。词表包含 151936 个 token，词嵌入是一张把 token 编号映射为向量的查找表，输出头则把末层向量变成每个候选 token 的分数。两者各自保存一份权重。各层参数与这两份词表矩阵相加，模型共有约 81.9 亿个参数。[^source-1]

一次前向执行从 token ID（词元在词表中的整数编号）开始。词嵌入为每个 ID 查出一个 4096 维向量，向量依次经过 36 层注意力与 FFN，最后经过归一化和词表投影产生 logits，即尚未转换为概率的候选 token 分数。归一化按向量的统计量调整各特征的尺度，保持逐层计算的数值范围。词嵌入按 ID 选择行，一个 token 取出一条向量，整个词表则作为常驻数据供不同 token 查询。词表输出头则将隐藏向量与词表矩阵相乘；只生成下一个 token 时，通常只需要最后一个输入位置的 logits。

设同时处理 $B$ 条等长请求，每条本次输入 $P$ 个已知 token。投影和 FFN 可以把它们的输入表示为 $X\in\mathbb{R}^{BP\times4096}$，即 $m=BP$ 行。每条请求只补入一个 token 时，$m=B$。第一种情形容易形成行数较大的矩阵，第二种在小 batch 下接近矩阵与向量的乘法。权重相同，输入形状却明显不同。

下面比较两种输入形状：一条请求一次处理 8192 个输入位置，以及一条已有 8192 个上下文位置的请求再处理一个新位置。用 $B$ 表示请求数，$S$ 表示调用前已有的上下文长度，$P$ 表示本次输入长度，$d$ 表示隐藏维度。前者取 $B=1,S=0,P=8192$，后者取 $B=1,S=8192,P=1$。

| 配置项 | Qwen3-8B 参数 | 对资源需求的直接影响 |
| --- | ---: | --- |
| 层数 $L$ | 36 | 重复的计算、逐层状态与深度依赖 |
| 隐藏维度 $d$ | 4096 | 子层输入输出与投影尺寸 |
| FFN 中间维度 $f$ | 12288 | 三个 FFN 矩阵的权重与计算 |
| $Q$／KV 头数 | 32／8 | 查询计算与上下文保存宽度 |
| 头维度 $d_h$ | 128 | 每个头的点积与状态宽度 |
| 词表大小 $V$ | 151936 | 嵌入和输出头规模 |

**例题 2-1：从矩阵尺寸求一层的参数量与运算量。** Qwen3-8B 的查询和输出投影宽度为 4096，键和值投影宽度为 1024，FFN 中间维度为 12288。求四个注意力投影与三个 FFN 矩阵的参数量，以及处理 $m$ 行输入的运算量。

**解：** 查询与输出各使用一个 $4096\times4096$ 矩阵，键和值各使用一个 $4096\times1024$ 矩阵，三个 FFN 矩阵各有 $4096\times12288$ 个参数。因此，

$$
\begin{aligned}
N_{\mathrm{proj}}&=2\times4096^2+2\times4096\times1024=41{,}943{,}040,\\
N_{\mathrm{FFN}}&=3\times4096\times12288=150{,}994{,}944,\\
F_{\mathrm{linear}}&=2m(N_{\mathrm{proj}}+N_{\mathrm{FFN}})=385{,}875{,}968m.
\end{aligned}
$$

注意这里尚未使用上下文长度：这些矩阵对每一行做相同的变换。下一节的查询与上下文交互才会引入与位置对数相关的计算。将两类工作分开，就能预测“增加输入行”和“让每行看到更长上下文”为什么有不同的代价。

| 符号 | 含义与使用范围 |
| --- | --- |
| $B,P,S$ | 请求数、本次每请求输入位置数、已有上下文长度 |
| $m=BP$ | 投影处理的总行数；普通 decode 时 $P=1$，故 $m=B$ |
| $d,f$ | 主干隐藏宽度、前馈网络中间宽度 |
| $n_Q,n_{\mathrm{KV}},d_h$ | 查询头数、KV 头数、每头维度 |
| $N_{\mathrm{pair}}$ | 每层跨全部请求的有效因果位置对数，不含头数 |
| $t_e$ | 专家 $e$ 收到的行数；无丢弃路由时 $\sum_e t_e=mk_{\mathrm{top}}$ |
| $m_{\mathrm{out}}$ | 真正执行词表头的行数；只预测每请求末位置时为 $B$ |

计算整模型时，先按每行矩阵尺寸求单次运算量，再乘这一类层的数量。词表头另外按实际输出位置数 $m_{\mathrm{out}}$ 计算；生成下一 token 时，每条请求只需最后一个位置的分数。归一化、激活与数据查表各有自己的运算方式，下面沿数据流说明它们的作用。

### 2.1.3 注意力计算与位置表示

先跟踪一个位置。模型从它的隐藏向量产生三种表示：**查询** $Q$ 用来提出“当前需要什么信息”，**键** $K$ 用来与查询计算匹配分数，**值** $V$ 是被选中后汇总到输出的信息。三者都由同一位置的输入经过不同的权重矩阵产生。线性投影就是这样的矩阵乘法：把输入特征变换到另一组坐标。

![同一位置的输入经不同投影产生查询、键和值。注意力先用查询与键计算位置间关系，再用这些关系汇总值。](ch02/figure-2-qkv-objects.svg)

*图 2-3　同一位置的输入经不同投影产生查询、键和值。注意力先用查询与键计算位置间关系，再用这些关系汇总值。*

采用数学右乘记号，输入 $X$ 分别乘三个权重矩阵，得到 $Q$、$K$、$V$。$Q$ 的总宽度为 $32\times 128=4096$，$K$ 和 $V$ 的总宽度各为 $8\times 128=1024$。因此，$W_q$ 为 $[4096,4096]$，$W_k$ 和 $W_v$ 各为 $[4096,1024]$。代码中的线性层常以 $(d_{\mathrm{out}},d_{\mathrm{in}})$ 保存权重；换成数学右乘记号后，输入宽度在前、输出宽度在后，便可逐项对照下面的表格。

上述投影产生了 $Q$、$K$、$V$，但尚未让当前位置与上下文交换信息。接下来将 $Q$ 拆成 32 个头，把 $K$、$V$ 拆成 8 个头。每组四个 $Q$ 头共用一个 KV 头。对一个 $Q$ 头，查询向量与允许访问位置的 $K$ 做点积，将点积除以头宽的平方根，使分数尺度随头宽保持稳定，然后屏蔽未来位置。Softmax 把允许位置的分数 $s_j$ 变成正数并归一化，系数为 $a_j=e^{s_j}/\sum_i e^{s_i}$；这些系数之和等于一，决定各上下文位置贡献多少信息。这里的“注意力权重”是本次输入算出的系数，区别于训练后保存的模型参数。随后用这些权重对 $V$ 加权求和。各 $Q$ 头的结果拼接后，经 $[4096,4096]$ 的输出投影 $W_o$ 返回隐藏空间。

用矩阵记号写出一个头的计算：

$$
A=\operatorname{Softmax}\!\left(\frac{QK^{\mathsf T}}{\sqrt{d_h}}+\mathcal M\right),\qquad O=AV.
$$

$A$ 是各查询对上下文位置的权重，$\mathcal M$ 是因果掩码，$d_h$ 是头维度。点积决定哪些位置与当前查询相关，Softmax 将分数转成加权系数，再用这些系数汇总值向量。Qwen3 在点积前还进行 **查询与键归一化（QK Norm）**和**旋转位置编码（Rotary Position Embedding，RoPE）**：前者调整各头查询与键的数值尺度，后者通过随位置变化的旋转，使点积包含相对位置信息。

![两段上下文形成长方形加三角形。蓝色为三个新位置分别读取两个旧位置，绿色为新输入内部的因果访问，空白为被屏蔽的未来位置。](ch02/figure-2-causal-pairs.svg)

*图 2-4　两段上下文形成长方形加三角形。蓝色为三个新位置分别读取两个旧位置，绿色为新输入内部的因果访问，空白为被屏蔽的未来位置。*

现在数清有多少个点积。输入 $P$ 个新位置、已有 $S$ 个上下文位置时，第 $i$ 个新位置可访问 $S+i$ 个位置，其中 $i=1,\ldots,P$。把每个查询允许访问的上下文逐行相加，就得到一个长方形加一个三角形：

$$
N_{\mathrm{pair}}=B\left(PS+\frac{P(P+1)}{2}\right)
$$

每个位置对上，一个 $Q$ 头的 $QK^{\mathsf T}$ 点积约需 $2d_h$ FLOPs，随后 $AV$ 的贡献又约需 $2d_h$ FLOPs。合计所有 $Q$ 头，$QK^{\mathsf T}$ 与 $AV$ 的有效矩阵运算量为：

$$
F_{\mathrm{attn}}=4n_Qd_hN_{\mathrm{pair}}=16384N_{\mathrm{pair}}
$$

在没有已有上下文的 prefill 中，序列长度加倍时，投影的输入行数变为两倍，全注意力的位置对数则约为原来的四倍，因为新加入的位置也要与此前的上下文交互。计算这些位置对有两种常见路径：完整矩形乘法先产生所有分数再屏蔽上三角，因果分块则跳过上三角。分块还可以把评分、归一化和 $V$ 汇总接在一起，让分数在片上被使用后释放。第五章将沿这条数据流解释如何减少中间结果的显存读写。

因此，保持 $BP$ 不变只能保持投影行数不变，不能保持上下文交互不变。例如，把一条长输入拆成两条互不相见的短输入，原来跨越分界的那些位置对就消失了。相反，仅在同一请求前面增加上下文，会增加每个新位置的点积数，输入投影的行数却保持不变。

### 2.1.4 前馈网络与前向计算量

注意力负责跨位置的信息交互，FFN 则对每个位置的特征执行非线性变换。SwiGLU 是一种带门控的前馈结构：一条分支变换输入特征，另一条分支为它生成逐元素的调节量。它采用 SiLU 激活函数 $\operatorname{SiLU}(x)=x/(1+e^{-x})$，用非线性变换改变特征间的组合方式。Qwen3-8B 使用这种结构：输入分别经过 gate 与 up 两条升维投影，其中 gate 分支应用 SiLU，再与 up 分支逐元素相乘，最后通过 down 投影降回隐藏维度：

$$
\operatorname{FFN}(X)=\left[\operatorname{SiLU}(XW_{\mathrm{gate}})\odot(XW_{\mathrm{up}})\right]W_{\mathrm{down}}
$$

式中 $\odot$ 表示对应元素相乘；gate 是门控分支，up 是升维分支，down 是降维投影。它们产生的中间向量称为激活。gate 与 up 将每行从 $d$ 维升到 $f$ 维，down 再降回 $d$ 维。三个矩阵因此合计 $3df$ 个参数，处理 $m$ 行需 $6mdf$ FLOPs。Qwen3-8B 取 $d=4096,f=12288$，FFN 约有 1.51 亿个参数，BF16 权重占 288 MiB。升维后较宽的激活也需要临时空间，但只在相应计算期间存活。

![SwiGLU 的两条升维分支。gate 经 SiLU 后调节 up 的对应元素，乘积再由 down 投影降回主干维度。](ch02/figure-2-ffn-gates.svg)

*图 2-5　SwiGLU 的两条升维分支。gate 经 SiLU 后调节 up 的对应元素，乘积再由 down 投影降回主干维度。*

注意力的 QKV 与输出投影合计约 4194 万个参数。将它与 FFN 的约 1.51 亿相加，FFN 占这些主要投影参数的约 78%，因此短上下文的计算中，三个 FFN 矩阵占据很大份额。随着输入变长，FFN 随位置数线性增长，全注意力则随 $P(P+1)/2$ 增长。两种增长率使计算重心随上下文长度移动。

残差连接把一个子层的输入保留下来，在该子层完成变换后，与输出逐元素相加。这样，一条路径执行新变换，另一条路径直接传递已有表示。下面把注意力、前馈和两次残差连接连成完整的一层。

## 2.2 自回归生成与资源核算

单次前向给出了计算模块的组成，完整生成还需要确定调用次数和状态寿命。同一份权重可能在一个请求中被使用数百次，KV 则一边读取一边增长。最终保存的字节数与累计访问的字节数因此可以相差几个数量级。

### 2.2.1 Prefill、Decode 与状态复用

模型收到一段已知输入后，可以同时计算多个位置的表示。这一阶段称为 prefill。由最后位置的 logits 选择首个输出 token 后，下一次调用把这个 token 作为新输入，得到再下一个输出；这种逐步扩展的阶段称为 decode。两者使用同一个模型，但前者有多个已知输入位置，后者在普通串行生成中每条请求只增加一个位置。

如果每生成一个 token 都把整个前缀重新送入模型，旧位置的投影与 FFN 会重复执行。因果模型中，旧位置不能看到后来加入的 token；在权重、位置与相关计算条件不变时，旧位置产生的 $K$、$V$ 可以保留。后续查询读取这些上下文 $K$、$V$，并补入当前位置的新 $K$、$V$，就避免了旧位置的大量重算。

缓存把“重新计算旧位置的表示”变成“保存并访问旧位置的状态”。未来位置会产生自己的 $Q$，用它对旧位置的 $K$ 评分，再以分数汇总 $V$，所以长期保存的是 $K$ 和 $V$。旧查询已经完成了自己的任务，下一步使用新的查询。第八章再将这套同请求复用扩展到跨请求共享。

Qwen3-8B 的 BF16 KV 每个上下文 token 占：

$$
\begin{aligned}c_{\mathrm{KV}}&=2L n_{\mathrm{KV}}d_h b_{\mathrm{KV}}\\&=2\times36\times8\times128\times2\ \mathrm{bytes}\\&=144\ \mathrm{KiB}.\end{aligned}
$$

第一个 2 分别对应键和值；$L$ 层各保存 $n_{\mathrm{KV}}$ 组宽度为 $d_h$ 的向量，每元素占 $b_{\mathrm{KV}}$ 字节。于是，保存 $H$ 个上下文位置需 $M_{\mathrm{KV}}=c_{\mathrm{KV}}H$。Qwen3-8B 的 $H=8192$ 对应 1.125 GiB，再处理一个新输入位置就追加 144 KiB。层数或 KV 头数减半，增长速度也减半；batch 增加则为每个独立请求增加一份上下文。[^source-13]

### 2.2.2 内存占用与数据访问量

KV 说明了缓存如何用存储换取少做计算。要判断这种交换对系统意味着什么，还需要把 KV 与权重、临时数据放在一起比较。为此，我们把数据分成权重、上下文状态和临时数据三类。区分的依据是用途与寿命，而不只是它们都占用显存。

| 数据类别 | 保存与复用 | 本章主要核算项 |
| --- | --- | --- |
| 权重 | 通常在多次调用间保持不变 | 常驻字节、被访问的权重集合、批内复用 |
| 上下文状态 | 随请求保留，持续追加或更新 | 有效容量、每步读取、写入及更新计算 |
| 临时数据 | 随算子和阶段产生、消亡 | 张量尺寸、接口数据量、同时存活范围 |

Qwen3-8B 全部 BF16 权重约占 16.38 GB，即 15.26 GiB。模型加载后，这份数据供多个请求反复使用。一次前向中，嵌入按 token ID 查行，层内投影与 FFN 使用对应矩阵，末端词表头计算输出分数。访问哪些权重，因而由计算图中的具体操作决定。

对于 $[m,d]\times[d,f]$，每一行都使用同一个权重矩阵。将权重块读入片上存储后，可以依次用于多行输入，让一次读取支撑更多乘加。处理行数 $m$ 增加，计算量随之增加，整份矩阵的容量保持不变。第五章将进一步解释片上容量与分块怎样决定一份权重能够复用多少次。

临时数据占用多少内存，取决于哪些张量同时存在。前一层释放缓冲后，后一层可以复用同一块空间；算子融合还可以让部分中间值只保存在寄存器或片上存储中。因此，计算读写量时要数清每次访问，计算内存峰值时则要找出同时存活的张量。第五章将结合具体程序分析。

保存量回答“这一时刻有哪些数据仍要使用”，访问量回答“执行过程中使用了它们几次”。例如，一步 decode 若将整段旧上下文读一遍，逻辑读取量为 $c_{\mathrm{KV}}H$；连续执行多步，就要逐步累计。确定这些访问实际经过哪一级存储后，才能将相应的 $R$ 除以该接口的带宽。

**例题 2-2：增加 batch 后，上下文读取量何时超过权重读取量？** Qwen3-8B 每批将所需共享权重读取一遍，数据量约为 15.14 GB，嵌入按请求查行另计。每请求的 8K BF16 上下文为 1.125 GiB，假定各请求独立、旧上下文各读一次。

**解：** 每批共享权重读取量记为 $R_W$，各请求的上下文独立，则上下文读取量为 $Bc_{\mathrm{KV}}H$。两者相等时

$$
B_* = \frac{R_W}{c_{\mathrm{KV}}H}.
$$

以 $R_W=15{,}136{,}811{,}008$ 字节、$c_{\mathrm{KV}}=147456$ 字节代入，$H=8192$ 时最小整数 batch 为 13；$H=2048$ 时为 51。上下文缩短到四分之一，跨过共享权重所需的请求数约增至四倍。较长上下文更早耗尽批内权重复用带来的收益，因为每个新增请求都会增加一份独立上下文的读取。[^source-12]

沿第一章的数据路径看，加载把权重从存储送到 GPU 显存，执行再把所需权重送到计算单元。KV 和层间激活也可在设备内部保存与使用。相同的逻辑访问因此可以留在片上、经过 HBM，或跨设备传输；第四章将给这些路径分别配置容量与带宽。

### 2.2.3 完整生成的计算与状态累积

上一节比较了一步执行中的读取量。一个完整回答会重复执行许多步，同一份上下文也随之被读取许多次。现在固定一个普通串行生成请求：$B=1$，已恢复前缀为 $S$，本次输入 $P\ge1$ 个 token，最终返回 $G\ge1$ 个 token。令 $H=S+P$。prefill 处理新输入并产生首输出，随后执行 $n_d=G-1$ 次 decode。最后返回的 token 尚未重新送入模型，所以请求结束时并不自动为它保存 KV。

图 2-7 中的每一行都比上一行多一个已填色方块：先前追加的位置现在也成为上下文。第 $j$ 次 decode（$j$ 从 0 开始）执行前，上下文长度为 $H+j$。于是，若每次 decode 将此前的上下文各读取一遍，累计读取量为：

$$
R_{\mathrm{old}}=c_{\mathrm{KV}}\sum_{j=0}^{n_d-1}(H+j)=c_{\mathrm{KV}}\left[n_dH+\frac{n_d(n_d-1)}{2}\right]
$$

decode 追加状态为 $c_{\mathrm{KV}}n_d$；若保留整个上下文，最终有效 KV 为 $c_{\mathrm{KV}}(H+n_d)$。本次请求的全部新增 KV 还应包含 prefill 写入的 $c_{\mathrm{KV}}P$。已有前缀的恢复与传输单独核算。求和中的每一项都对应一次 decode 开始时已有的上下文：早出现的位置参与更多后续查询，晚出现的位置参与较少查询。

**例题 2-3：一份上下文为什么会被读取一千多 GiB？** 求一个请求结束时的状态与生成期间累计已有上下文状态的读取量。

**解：** 取 $S=0$、$P=8192$、$G=1025$，则 $n_d=1024$，累计访问 8,912,384 个上下文位置。每个位置占 144 KiB，因此累计读取约 1224 GiB。生成期间只新增 144 MiB KV，结束时共保存约 1.27 GiB。累计读取量是最终保存量的近千倍，因为较早生成的上下文被后续查询反复使用。

同一条调用链也决定累计计算。线性投影和 FFN 在每次 decode 中处理一行，上下文交互则随 $H+j$ 增长。设每步固定矩阵工作为 $F_0$、每个上下文位置的交互工作为 $a$，便有

$$
F_{\mathrm{decode,total}}=n_dF_0+a\left[n_dH+\frac{n_d(n_d-1)}2\right].
$$

输出变长时，固定工作按 $n_d$ 增长，生成中新出现的上下文又形成二次增长项。返回一个 token 时 $G=1$、$n_d=0$，只有 prefill；这一特殊情形也说明为什么完整回答包含 $G-1$ 次后续 decode。

图 2-7 沿生成步数累加读取，图 2-8 沿请求数累加读取。多条独立请求的状态容量与上下文访问分别相加，批内权重则共同使用。长度不同时，逐请求代入各自的 $H$ 与 $n_d$：长输出让已有上下文被更多次读取，输入越长，第一次 decode 需要访问的上下文就越多。对实际对话，可先从每轮输入、缓存命中与返回数重建这条调用链，[已保存的 Chat 长度核算](../calculations/results/sealed-chat-known-prefill.md)给出了具体代入过程。

## 2.3 上下文状态表示与访问机制

这里的上下文状态，是模型处理已有上下文后保存、供后续计算复用的表示，例如 KV 缓存或递推状态。上下文长度按 token 位置计数，状态容量按实际保存的字节数计量。

完整上下文 KV 的容量随序列长度增长，累计读取又随生成次数增加。架构可以从不同位置改变这笔需求：减少每个上下文位置的表示宽度，压缩或选择上下文条目，或者把上下文更新进固定大小的状态。这些选择影响的对象不同，也会产生不同的新增工作。比较时必须同时观察保存、选择、读取和更新。

### 2.3.1 多头注意力与 KV 共享

多头注意力允许不同查询子空间建立各自的上下文关联。在多头注意力（MHA）中，每个 $Q$ 头对应自己的 $K$、$V$ 头；多查询注意力（MQA）让所有 $Q$ 头共用一组 $K$、$V$；分组查询注意力（GQA）则把 $Q$ 头分组，每组共享一组 $K$、$V$。共享后，每个上下文位置需要保存的 $K$、$V$ 组数减少，上下文位置的数量保持不变。

先看一个只有四个查询头的单层例子。MHA 为四个查询头各存一份 $K$、$V$；GQA 可以让前两个查询头共享第一份 $K$、$V$，后两个共享第二份；MQA 则让四个查询头共用一份。若上下文长度和头宽相同，需要保存的 KV 份数依次为四、二、一。因此，GQA 在这个例子中把上下文保存量减半。四个查询头仍可给同一段上下文打出四组不同的分数，这正是“共享上下文表示”与“合并查询”之间的区别。

![固定四个查询头，分别为每头、每组和全部查询保存 KV。连线表示使用关系；共享上下文后，各查询仍分别产生自己的评分与输出。](ch02/figure-2-3-sharing.svg)

回到 Qwen3-8B：它让每四个查询头共用一组 KV，总计 32 个查询头、8 个 KV 头。如果给每个查询头单独保存 KV，容量会是当前配置的四倍；如果全部查询共享一组，则会是当前配置的八分之一。实际 GQA 配置保存 8192 个位置需要约 1.13 GiB。本节末的容量图固定上下文长度与头宽，只改变 KV 组数，因此柱高之比直接呈现共享比例。

共享 $K$、$V$ 改变了被查询的数据，32 个 $Q$ 头仍分别计算分数和加权输出。因此，KV 投影和保存量按组数减少，$QK^{\mathsf T}$ 与 $AV$ 交互仍按查询头数累计。一次读入的 $K$、$V$ 还可服务同组多个查询头，从而在实际计算中复用同一份数据。

可以直接由组数预测资源变化。将 $n_{\mathrm{KV}}$ 减半，键值投影参数和上下文状态容量都减半；查询头数 $n_Q$ 不变，查询与上下文交互的运算量仍按原来的头数累计。减少存储与减少计算是两个不同结果，只有沿各组件分别计算才能判断。

### 2.3.2 潜变量压缩与 MLA 执行路径

GQA、MQA 通过减少 KV 组数节省空间，多头潜变量注意力（Multi-head Latent Attention，MLA）则通过降低上下文表示的维度节省空间。可以先把输入投影为低维潜变量 $c$，再通过上投影得到用于注意力的 $K$、$V$。模型在训练中学习这些低维表示与上投影，生成时将上下文以 $c$ 的形式保存。

![两种计算路径改变上投影的位置。展开路径先恢复上下文键，紧凑路径先变换当前查询，再直接读取潜变量；结合律保证对应点积可以按这两种次序计算。](ch02/figure-2-mla-paths.svg)

*图 2-11　两种计算路径改变上投影的位置。展开路径先恢复上下文键，紧凑路径先变换当前查询，再直接读取潜变量；结合律保证对应点积可以按这两种次序计算。*

为什么可以只保存潜变量？设键的上投影为 $U_k$，上下文潜变量按行组成矩阵 $c$，展开键为 $K=cU_k$。矩阵乘法的结合律给出

$$
qK^{\mathsf T}=q(cU_k)^{\mathsf T}=(qU_k^{\mathsf T})c^{\mathsf T}.
$$

左边先为每个上下文位置恢复键，右边先变换当前查询。对单个新查询，右边只需做一次查询变换，随后直接与潜变量点积。值向量也可在加权汇总后再上投影：先汇总低维向量，再恢复输出维度。这样，随上下文位置重复的宽向量展开被移到了查询与汇总两侧。

本章采用 Kimi K3 的 **Gated MLA（门控多头潜变量注意力）**作实例；门控通过学习得到的系数调节注意力输出。紧凑路径保存 512 维潜变量和参与 $QK^{\mathsf T}$ 点积的 64 维额外分支；NoPE 表示该处不使用位置编码的设置，它保留该分支的计算维度，省去旋转位置编码。24 个 MLA 层、8192-token 上下文、BF16 下，保存量为 $24\times8192\times(512+64)\times2$，即 216 MiB。

展开缓存将潜变量先恢复为各头的 $K$、$V$，再保存这些向量；同样的 8192 个位置需要约 11.25 GiB。紧凑缓存则保存上投影之前的潜变量。两者的容量差异因此来自缓存位于线性变换的哪一侧：紧凑缓存每步变换当前查询，展开缓存直接读取各头的上下文向量。[^source-2]

![Kimi K3 的 24 层 MLA 在相同 8K 上下文、BF16 下的两种保存量。紧凑路径保存上投影前的表示，展开路径保存各头的键和值。](ch02/figure-2-mla-capacity.svg)

*图 2-12　Kimi K3 的 24 层 MLA 在相同 8K 上下文、BF16 下的两种保存量。紧凑路径保存上投影前的表示，展开路径保存各头的键和值。*

这个变换减小了每个上下文位置的保存宽度，但仍需为每个位置保存一条潜变量。因而容量和点积工作继续随上下文长度增长。若上下文很长，紧凑表示减少的读取更加显著；若上下文很短，查询变换本身的开销占比更高。接下来先改变保存和选择哪些上下文条目，再研究把上下文汇总到固定大小矩阵中的方法。

> **练习 2-3〔延伸〕：状态大小与累计读取**
>
> 取 Qwen3-8B、$B=1,S=0,P=8192$，分别返回 $G=513$ 和 $G=1025$ 个 token。求后续 decode 次数、最终 KV 大小和累计旧上下文读取量。解释输出数量接近翻倍时，新增状态、总状态与累计读取为什么有不同的比例。再将 KV 位宽减半，指出这三项中哪些随之减半。

### 2.3.3 局部窗口、上下文压缩与稀疏索引

减少上下文表示宽度之后，还可以改变保留哪些上下文、每次访问哪些上下文。局部窗口只关注最近的一段位置；压缩机制把若干位置合成较少的条目；稀疏选择先确定相关条目，再把它们送入主注意力。窗口决定保留的近期范围，压缩决定长期条目的数量，索引决定当前查询读取哪些条目。索引器先扫描用于选择的表示，再把选中的主状态交给注意力，两段访问分别产生工作。

DeepSeek V4-Flash 有 43 个主干层、4096 隐藏维度、64 个注意力头，每头维度 512。$Q$ 先从 4096 维投影到 1024 维，再得到 $64\times 512$ 维查询；共享 KV 从 4096 维投影到 512 维；输出采用分 8 组的低秩投影。投影宽度并不必然等于隐藏维度，各投影的输出维度决定了矩阵的第二维，不能一律写成 $d\times d$。

DeepSeek V4-Flash 使用两种压缩注意力：**压缩稀疏注意力（Compressed Sparse Attention，CSA）**先压缩上下文，再通过索引选取相关条目；**高压缩注意力（Heavily Compressed Attention，HCA）**把更多位置汇成较少的粗粒度条目，供查询访问。两者都用于减少长上下文的存储与访问量，区别在于压缩程度和是否进一步筛选条目。其主干包含 2 个纯窗口层、21 个 CSA 层和 20 个 HCA 层，窗口长度为 128。CSA 按压缩比 4 保存上下文，并维护索引；HCA 按压缩比 128 保存更粗的上下文。用 BF16 参考表示，CSA 每个完成的压缩条目含 512 维主状态，另有 128 维索引条目。已有 $S$ 个位置时，完成条目数按 $\lfloor S/4\rfloor$ 计算；尚未完成的压缩块还需独立缓冲。

一次 CSA 查询的主注意力最多读取窗口加 512 个压缩条目，但索引打分仍扫描已保存的压缩索引条目。在 $S=8192$ 时，一个 CSA 层保留 2048 个压缩条目：主注意力状态约 2 MiB、索引约 0.5 MiB，窗口约 0.125 MiB；主注意力选择的压缩条目最多约 0.5 MiB，索引扫描却仍需处理那 2048 个索引条目。HCA 则有 64 个完成条目，主注意力状态约 0.0625 MiB，并访问窗口状态与这组粗粒度压缩条目。

将 43 层相加，8192-token 上下文下的窗口、压缩上下文和索引约为 59.125 MiB；另有约 11.641 MiB 的 FP32（每元素 4 字节浮点格式）压缩器缓冲，合计约 70.8 MiB。最后查询的主注意力与索引数据量约 27.6 MiB。[状态分解](../calculations/results/state-deepseek-v4-flash-n8192-b1-native.md)将这些分项列开，因此能看出选择条目数、保存量和每步读取量并不相等。

### 2.3.4 线性注意力与有限状态递推

线性注意力通过重新组织查询、键和值的计算，避免显式计算所有位置对的注意力分数。在特征维度固定时，下面这种递推形式处理整段序列的运算量随序列长度线性增长，状态矩阵的大小保持不变。

外积把一个键向量与一个值向量的每对元素相乘，组成二维的关联表。考虑一个由键值外积累加得到的矩阵 $\mathcal S_t$。每个新位置到来时，先读取旧状态，再写入本位置的贡献，当前查询直接从状态矩阵读出结果：

$$
\mathcal S_t=\mathcal S_{t-1}+k_tv_t^{\mathsf T},\qquad o_t=q_t^{\mathsf T}\mathcal S_t.
$$

若键宽为 $d_k$、值宽为 $d_v$，状态始终有 $d_kd_v$ 个元素。位置增加改变的是矩阵内容，而不是矩阵大小。逐位置的上下文列表因此变成了一组累积的键值关联；查询通过这组关联得到输出。

![固定矩阵的递推更新。新键和值的外积加入旧状态，矩阵形状保持不变；查询使用更新后的状态计算输出。本图采用简单累加递推。](ch02/figure-2-recurrence.svg)

*图 2-16　固定矩阵的递推更新。新键和值的外积加入旧状态，矩阵形状保持不变；查询使用更新后的状态计算输出。本图采用简单累加递推。*

**Kimi Delta Attention（KDA）**是 Kimi 使用的一种门控递推注意力，用固定大小的关联矩阵保存上下文信息。它使用门控与 delta 更新；delta 在这里指依据当前预测误差写入修正量。状态更新不仅写入新信息，还根据当前键对既有状态的预测形成修正，并通过衰减控制旧信息保留。直观上，它更新的是一张固定大小的关联矩阵，而不是不断追加一张逐 token 列表。旧信息以汇总后的关联保留，当前键控制修正的位置，衰减门控制旧贡献继续存在的程度。

Kimi K3 每个 KDA 层有 96 个头，每头递推矩阵为 $128\times128$。按 FP32 保存，单层为 6 MiB，69 层为 414 MiB。一次 decode 读取旧矩阵、融合新信息并写回，理想一读一写就是 828 MiB。这个量不随上下文长度增长：短上下文时它是一笔显著的固定开销，长上下文时则避免了逐位置扫描持续扩大。

prefill 与 decode 的实现方式也不同。decode 使用单步递推；一段已知输入可以通过块式算法并行计算，再在块之间传递状态。块内中间量和块间状态会占用临时空间，因此最终递推状态的大小不足以预测 prefill 峰值。第五章按缓冲寿命分析这一问题。[^source-15]

### 2.3.5 混合注意力的状态构成

实际模型常把有限状态层与全局注意力层混合使用。这样既利用递推结构的上下文压缩，也保留部分直接访问全局上下文的能力。但整模型状态不再服从单一的“固定”或“线性增长”规则，而是多种分量之和。

Kimi K3 共 93 层，其中 69 个 KDA 层、24 个 MLA 层。8192-token 上下文、紧凑 BF16 MLA、FP32 递推状态及给定 BF16 短卷积槽位下，三项分别为 216 MiB、414 MiB 与 19.4 MiB，合计约 649.4 MiB。若使用参考展开缓存，MLA 一项就变为 11.25 GiB，整体随之改变。[^source-16]

Qwen3.6-35B-A3B 同样需要按层型计算。其 30 个线性注意力层加 10 个完整注意力层，使每请求每个上下文 token 的全局 KV 为 20 KiB，另有固定 FP32 递推状态 60 MiB，以及保存短卷积所需近期输入的 BF16 缓冲区 1.875 MiB。短卷积先混合邻近位置的信息，缓冲区让下一步更新可以复用这些输入。8192-token 上下文时，三项合计 221.9 MiB。这些状态来自注意力分支；接下来的混合专家（Mixture of Experts，MoE）分支准备多个前馈子网络，由路由器为每个 token 选择其中一部分执行，在同一主干上改变权重选择，两类机制共同组成完整模型。

这几条状态曲线的形状来自不同表示。Qwen3-8B 每增加一个位置，所有 GQA 层都追加 $K$、$V$；Kimi K3 只有 MLA 部分追加上下文，KDA 部分保持固定矩阵；DeepSeek V4-Flash 则在压缩块完成时增加条目。对长上下文，增长速度决定新增容量；对短上下文，递推矩阵等固定部分决定起始占用。

将固定递推状态与逐位置上下文相加，就得到混合结构的容量模型：

$$
M_{\mathrm{state}}(H)=M_{\mathrm{fixed}}+cH,\qquad H_* = \frac{M_{\mathrm{fixed}}}{c}.
$$

$H_*$ 表示两部分占用相等的上下文长度。Qwen3.6 的固定部分为 $61.875$ MiB，每位置增加 20 KiB，因此 $H_*=3168$；Kimi K3 的紧凑表示每位置增加 27 KiB，固定部分约为 433.4 MiB，交点约在 $16.4$$K$。低于交点时，缩短上下文只能节省较小部分；远高于交点时，减少每位置宽度对容量更有效。DeepSeek V4-Flash 则按完成的压缩块增加条目，曲线呈阶梯增长。

这些状态在执行中承担不同的信息访问：全局 KV 允许查询直接选择旧位置，递推矩阵通过更新保留上下文关系，压缩索引则在较少条目中寻找相关内容。2.6.3 将把资源比较接到具体检索任务。[^source-17]

>

## 2.4 条件计算与专家权重复用

前面几节通过共享、压缩和递推减少上下文状态。对另一个主要数据来源——模型权重——也可以问同样的问题：每个 token 是否必须使用模型中的全部参数？下面从 FFN 出发分析这一问题。

稠密 FFN 对每个 token 使用同一组矩阵；MoE 把容量分散给多个专家，由路由器为每个 token 选择少数专家。它使“模型保存多少参数”与“一个 token 激活多少参数”分离，也让 batch 内不同 token 的选择影响实际权重访问集合。

### 2.4.1 稠密前馈网络与专家路由

一个典型 MoE 分支先从输入计算路由分数，选择路由分数最高的 k 个专家（top-k），再把 token 送入选中专家，最后按路由权重合并输出。有共享专家时，还会有一条所有 token 都参与的分支。专家本身通常仍由 gate、up、down 三个矩阵构成，因此可以按 2.1.4 的 SwiGLU 计算逐个展开。

Qwen3.6-35B-A3B 的文本主干包含 40 层，隐藏维度 2048；每层 256 个路由专家，每 token 选 8 个，专家中间维度为 512，另有共享专家。一个路由专家包含 $3\times 2048\times 512=3,145,728$ 个参数，以 BF16 保存为 6 MiB。每层全部路由专家占 1.5 GiB，一个 token 选中的八个专家占 48 MiB。

设专家 $e$ 实际收到 $t_e$ 个 token，其 gate/up 是 $[t_e,2048]\times [2048,512]$，down 是 $[t_e,512]\times [512,2048]$，主要矩阵运算量为 $6t_e\times 2048\times 512$。将各专家的运算量相加，就得到全部路由专家的矩阵运算量。路由器先决定各个 $t_e$，选中专家执行三次投影，随后收集并加权合并结果；共享分支对全部输入行执行。

用 $E$ 表示路由专家总数、$k_{\mathrm{top}}$ 表示每 token 选中的专家数，单个专家有 $N_e$ 个参数，则每层保存 $EN_e$ 个路由专家参数，单 token 执行的专家矩阵工作约为 $2k_{\mathrm{top}}N_e$。增大 $E$ 扩充了可选择的参数集合；只有实际选中数或专家尺寸增加，才会直接增加这部分单 token 运算。Qwen3.6 的 A3B 名称体现激活规模，全部文本参数约为 346.6 亿，BF16 权重约为 69.321 GB。

### 2.4.2 激活计算与批内权重访问

**例题 2-4：相同专家计算量，权重读取为何相差 32 倍？** 对 Qwen3.6 的同一层，比较均匀分派和集中分派。

**解：** 即使激活参数相同，batch 内的权重读取也可能不同。假设 $B=64$，每个 token 选择 8 个专家，总共有 512 次 token–expert 分派。若均匀分到 256 个专家，每个专家平均接收 2 个 token，当前批次会访问全部路由专家；若所有 token 都集中到同 8 个专家，则每个专家接收 64 个 token，当前批次只访问 8 份专家权重。

设本批实际访问的不同专家数为 $U$。没有丢弃的路由满足 $\sum_e t_e=Bk_{\mathrm{top}}$，因此

$$
F_{\mathrm{expert}}=2N_e\sum_e t_e=2N_eBk_{\mathrm{top}},\qquad R_{\mathrm{expert}}=b_WN_eU.
$$

第一式按分派的总行数累计，第二式按被读入的不同权重累计。例中两种分派都有 512 行，矩阵运算量相同；但 $U$ 分别为 256 和 8，每层读取量分别为 1.5 GiB 和 48 MiB，相差 32 倍。40 层所有路由专家合计保存 60 GiB，集中路由每批选中的权重合计只有 1.875 GiB。

| --- | ---: | ---: | ---: |
| 均匀分配 | 256 | 2 | 1.5 GiB |
| 集中于同 8 个专家 | 8 | 64 | 48 MiB |

读取差额来自每份权重服务的输入行数：均匀分派时每专家只有两行，集中分派时每专家有 64 行。同一份权重支持的计算增加 32 倍，理想权重访问量便减少 32 倍。与此同时，原来要执行许多输入为两行的矩阵乘法，现在只需执行少数输入为 64 行的矩阵乘法；权重复用和计算效率因此都会受到影响。[^source-18]

Qwen3.6 在已有 8192-token 上下文的 $B=1$ decode 中约需 7.33 GFLOPs，小于 Qwen3-8B 的约 20.0 GFLOPs。这个整模型差额由几项结构共同形成：2048 维主干缩小投影，30 个线性层使用递推状态，MoE 每次只执行选中的专家及共享分支。总参数增长来自专家集合，当前工作则由实际经过的计算路径决定。

### 2.4.3 共享专家与潜空间计算

上述差距由专家接收的输入行数决定。接下来还要考虑专家本身的尺寸：共享专家处理全部输入，潜空间专家则先缩小输入维度。两者都会改变一个专家需要多少权重、执行多少运算。

DeepSeek V4-Flash 每层有 256 个路由专家，每 token 选 6 个，另有 1 个共享专家；路由专家中间维度为 2048。单专家的 gate/up 为 $[t_e,4096]\times [4096,2048]$，down 为反向尺寸，参数为 25,165,824。前三层采用哈希路由，后续采用评分路由：哈希路由按 token 确定专家，评分路由根据当前表示选择专家。

共享专家对全部 $B$ 行输入执行，路由专家则分别处理 $t_e$ 行。若共享专家有 $N_s$ 个参数，一层的专家矩阵运算量为 $2BN_s+2\sum_e t_eN_e$。DeepSeek V4-Flash 每 token 选择六个路由专家并执行一个共享专家，正是这两个部分相加；容量则需要保存全部 256 个路由专家和共享分支。

Kimi K3 每个 MoE 层有 896 个路由专家，每个 token 选择其中 16 个。输入先从 7168 维主干空间投影到 3584 维潜空间，再经过中间维度为 3072 的专家变换，合并后投影回主干空间。共享专家直接处理主干表示。降维减少了路由专家的矩阵尺寸，同时增加了进入和离开潜空间的两次投影。[^source-3]

如果专家分布在不同设备上，就要把输入 token 发送到对应设备，专家完成计算后再合并结果。通信量因此取决于专家放在哪里、输入由哪张设备持有。第六章讨论多卡划分，第九章介绍 CPU／GPU 放置，以及将注意力（attention）与前馈网络（FFN）交给不同资源的 AF 分离。本节先确定每个专家处理的 token 数、矩阵尺寸和权重读取量。

> **练习 2-6〔延伸〕：专家总量、激活与复用**

## 2.5 网络形状与计算组织

上下文状态与专家选择改变了主要数据集合，网络的深度、宽度和连接方式则进一步决定这些工作以什么形状、什么顺序执行。相近的参数预算不保证相同的执行图，甚至相近的矩阵 FLOPs 也可能伴随不同的缓冲寿命和串行步骤。

### 2.5.1 深度、宽度与专家粒度

先忽略词表和小向量参数。若 FFN 宽度与隐藏维度保持固定比例，稠密主干的参数量大致正比于 $Ld^2$。把隐藏维度减半、层数增至四倍，可以保持这部分参数量相近，却把逐层依赖加长了四倍。每个矩阵更小，但必须经过更多层；每层还要保存相应的上下文状态。参数总量相近并不能说明执行形状相近。

专家也有类似的等预算变化。单层路由专家的总参数为 $3Edf$，单 token 专家运算量为 $6k_{\mathrm{top}}df$。将专家数 $E$ 减半、中间维度 $f$ 加倍、选中数 $k_{\mathrm{top}}$ 减半，这两个量都不变。Qwen3-235B-A22B 的 128 个宽度 1536 的专家、每 token 选 8 个，可以与 64 个宽度 3072 的专家、每 token 选 4 个作这一对照。路由输出维度与每专家接收行数仍会改变，从而改变分组矩阵乘法的形状。

在 16-token 算例中，三种专家粒度的专家矩阵运算量保持相同，基线与 64 专家变体均约为 454 GFLOPs。专家数减半、单专家宽度加倍时，相同数量的权重被分成更少的大矩阵；专家数加倍、宽度减半时，则成为更多的小矩阵。路由器要为每个专家计算路由分数，因此其参数也随专家数变化。[专家粒度计算](../calculations/results/qwen235-granularity-baseline.md)将路由与专家矩阵分别累计，呈现同一专家参数总量如何形成不同的执行形状。

形状也决定多卡分工的最小单位。128 个专家可分成八组，每组 16 个；四个 KV 头按完整头分工时只能形成四份，八卡执行就需要复制部分 KV 或调整分组。第五章从矩阵分块分析执行效率，第六章将进一步把这些矩阵和状态分配到设备。

### 2.5.2 残差连接与跨层状态

除了层数和宽度，还要看各层怎样连接。残差连接把子层输入直接加到变换结果上，使原始信息和梯度具有跨层直通路径。普通残差计算 $x_{\ell+1}=x_\ell+f_\ell(x_\ell)$，其中 $f_\ell$ 是第 $\ell$ 个子层的变换，因此子层计算期间要保留输入 $x_\ell$，等变换结果产生后才能相加。若后续多个层还会引用同一表示，它的寿命就要延长到最后一次使用。连接方式由此直接决定哪些张量需要同时保存。

普通残差把不同深度的信息不断相加到同一条通路中。为了让层间信息有更多组合方式，同时保持深层网络中的信号传播稳定，DeepSeek V4-Flash 使用 **mHC（Manifold-Constrained Hyper-Connections，流形约束超连接）**。它把一条残差通路扩展成多条，并约束通路之间的混合系数；这里的“流形约束”具体表现为将残差混合矩阵的元素限制为非负、各行与各列的和接近 1。[^architecture-motivation]

该模型保存 4 路残差状态，每一路都是当前 token 的一份 4096 维中间表示。保留四路表示，是为了让后续层学习如何组合不同通路的信息。每个子层先将四路表示混合为 4096 维子层输入，执行注意力或 FFN，再把结果写回残差通路。因此，主体矩阵保持 4096 维输入，新增工作集中在进入和离开子层的混合与汇合。四路状态扩大了跨层表示，混合操作负责连接它们与原有子层。

处理 8192 个输入 token 时，mHC 的混合投影约需 555 GFLOPs，普通算术约需 149 GFLOPs。残差混合矩阵先经 **Sinkhorn 迭代**归一化，即交替将每行、每列除以各自的和，使行和与列和逐渐接近 1；这使多层混合中的数值尺度更稳定。归一化后的系数再用于组合各条残差通路；末端汇合这些通路，形成送入词表头的表示。因此，多路残差不仅增加要保存的表示，还增加每层的混合与归一化计算。[^source-4]

Kimi K3 希望当前层能够按需要选取不同深度的信息，而不只是接收逐层相加后的一个混合结果。它使用 **Attention Residuals（AttnRes，注意力残差连接）**，对较浅层的表示计算权重，再加权求和，形成当前层的输入。这种注意力沿网络深度选择信息，前面的序列注意力则在不同 token 位置之间选择信息。为减少保存和读取所有层输出的开销，块式实现把若干层组织成一块，保留供后续块选择的表示。[^architecture-motivation]

后面的层还要使用这些块表示，所以它们需要在本次前向中继续保存；前向结束后即可释放。上下文 KV 则要保留到后续生成步骤。两者的寿命不同：AttnRes 增加一次前向中的临时存储，KV 随请求跨多次调用保留。[^source-19]

### 2.5.3 多 token 预测与辅助计算

普通自回归主干根据当前上下文预测下一个 token。**多 token 预测（Multi-Token Prediction，MTP）**在此基础上增加后续多个位置的预测目标或辅助预测模块。训练时，这些额外目标促使当前表示包含对更远后续内容有用的信息；推理时，辅助模块可以先提出多个候选 token，再由主模型验证，以减少生成同样数量 token 所需的串行轮数。分析时必须区分三件事：训练时优化了哪些预测目标，发布的模型实际包含哪些模块，服务后端又启用了哪些模块。

**推测解码（speculative decoding）**先用较低开销生成候选序列，再让目标模型验证这些候选。用于推测解码时，MTP 根据当前主干特征预先生成后续 token，再交给目标模型验证。如果多个 token 通过验证，一轮就能产生多个有效输出；否则从最后一个通过验证的位置继续生成。因此，加速效果取决于草稿生成、目标模型验证各需多久，以及每轮有多少 token 被接受。第八章将计算这三者的关系。

DeepSeek V4-Flash 的 MTP 辅助块接收主干特征和 token ID，预测后续位置。对单个 token，即 $B=1,T=1$，一次辅助计算约需 1.80 GFLOPs，其中共享词表头约需 1.06 GFLOPs。共享词表头占这次计算的一半以上：虽然它不增加一份独立权重，每次调用仍要执行词表投影。[^source-5]

辅助预测提醒我们，一次前向执行、一次采样和一个有效输出可能是不同的单位。第三章将把编码、生成、迭代及实时输出组织成完整负载；第八章再计算草稿与验证的服务收支。

设一次普通 decode 耗时为 $T_d$，一轮推测解码的草稿和验证合计耗时为 $T_s+T_v$，平均得到 $a$ 个有效输出。每输出分摊时间为 $(T_s+T_v)/a$，有收益的条件是

$$
a>\frac{T_s+T_v}{T_d}.
$$

例如，普通 decode 为 20 ms，草稿与验证合计为 30 ms，平均每轮得到两个有效输出时，每输出分摊 15 ms；若只能得到一个，则需要 30 ms。多预测几个位置增加了单轮工作，只有足够多的输出被采用，才能抵偿这些工作。

下面把各类层的工作按数量累加，再加入模型入口与输出接口，得到整模型的需求。

前面已经可以计算一种层的参数、一次调用的运算和一条请求的状态。整模型只需把这些项按实际层型与次数相加：

$$
M_W=b_W\sum_gL_gN_g+M_{\mathrm{embedding}}+M_{\mathrm{head}},\qquad
F_{\mathrm{model}}=\sum_gL_gF_g+F_{\mathrm{head}}.
$$

$g$ 表示层型，$L_g$ 为该层型数量。MoE 的 $N_g$ 包含全部专家，$F_g$ 则使用各专家实际接收的行数。表 2-1 已建立 Qwen3-8B 的稠密基线；章末查阅表按同样方式展开 Qwen3.6、DeepSeek-V3、DeepSeek V4-Flash 和 Kimi K3，使每个合计都能回到具体矩阵。

阅读时可以按数据流走一遍：输入进入哪类注意力层，随后经过哪类前馈网络，最终如何得到词表分数。每张表按注意力、前馈与连接、输出接口分组；“层／调用数”给出整模型累计倍数，“矩阵 FLOPs”仍是该行单次成本。先选层型，再累加该层的注意力、前馈与连接工作，最后加入嵌入查行、末端归一化和词表头。

### 2.6.2 参数规模、数值精度与容量约束

分项计算给出了模型权重和每条请求状态的大小。现在把它们放进同一张显存容量表，就可以判断一台设备能同时保留多少条请求，以及量化权重能腾出多少空间。

对一张设备，先扣权重，再扣工作区和其他固定预留，剩余空间才能放请求状态。对普通等长、独立 KV 的简化情形，可写为：

$$
B_{\max}=\left\lfloor\frac{M_{\mathrm{device}}-M_{\mathrm{weight}}-M_{\mathrm{workspace}}}{M_{\mathrm{state/request}}}\right\rfloor
$$

分子是扣除固定驻留之后可用于请求的空间，分母是每条请求的状态。每增加一条请求，都要为它分配相应的状态空间；剩余空间放不下完整的一份状态时，就无法再增加请求，因此结果要向下取整。递推与卷积状态同样属于每请求数据，与 KV 一起计入分母。

以 24 GB 显存运行 Qwen3-8B BF16 为例，权重占 $16{,}381{,}470{,}720$ 字节，工作区预留 2 GiB，每条请求的 8K 上下文占 1.125 GiB。可容纳请求数为

$$
B_{\max}=\left\lfloor\frac{24\times10^9-16{,}381{,}470{,}720-2\times2^{30}}{1.125\times2^{30}}\right\rfloor=4.
$$

上下文变为 16K 时，每条请求占 2.25 GiB，同一空间只能放两条；变为 4K 时，则能放九条。整数跳变来自剩余空间必须足以容纳完整的一条状态，而不是只够存放其中一部分。

再看 DeepSeek-R1-Distill-Llama-70B，其参数量约为 705.5 亿。其 BF16 权重为 141.107 GB，每条 8192-token BF16 KV 为 2.5 GiB。在本例采用的分组量化方案中，保留嵌入、输出头和归一化等较高精度部分，并计入 scale 与打包尾部后，8-bit 方案约为 73.726 GB，4-bit 方案约为 39.500 GB。

4-bit 方案的 39.500 GB 来自低位宽矩阵、高精度保留项、scale 与打包的共同贡献，比将全部参数一律按半字节计算更大。显存容量为 80 GB（十进制）、固定预留 2 GiB 时，8-bit 方案可放 1 条 8K 请求，4-bit 方案可放 14 条。上下文从 8K 增至 32K 时，每请求 KV 增至四倍，4-bit 方案可同时容纳的请求数降到 3 条。压缩权重腾出的空间可以保存更多请求的上下文，但每条上下文越长，能同时容纳的请求就越少。[^source-23]

同样方法也能分析更大的部署。235B 的 BF16 权重约 470 GB，超过八张 24 GB 卡合计的 192 GB，而八张 80 GB 卡合计为 640 GB。后者为状态、工作区与复制留下约 170 GB 总余量；第六章将按具体分工把这笔总量分配到每张设备，得到逐卡预算。

容量先给出可放置的实例规模，长度与并发再决定实例要服务的工作。更低位宽释放空间，较短上下文允许更多请求同时驻留，批内复用则改变这些请求的执行成本。部署选择因此沿容量、访问与计算逐步展开，第三章将进一步加入请求的到达与时限。

### 2.6.3 请求条件与模型比较

最后把容量、调用链和任务质量合在一起。先根据设备容量排除无法放下的配置，再沿每个模型的实际计算方式累计请求工作，最后检查模型能否完成目标任务。相同参数量不保证相同计算量，相同 token 数也不保证相同文本内容；比较的输入应当由要回答的问题决定。

比较完整模型时，可以从两种输入出发。固定 $S,P,G,B$，得到相同调用长度下的资源需求，便于观察结构差异；固定文本和任务，则先经各模型的分词器得到输入长度，再检查输出。这两种对照分别回答“同样多的位置怎样计算”和“同一个任务需要怎样执行”。

先比较相同输入、输出长度下的资源需求。取 $S=0,P=128,G=4,B=1$，模型执行一次 prefill 和三次 decode，最终保存 131 个已处理位置。将这些调用的矩阵运算量相加，得到下表。[^source-8]

| 模型 | 完整请求矩阵运算量（TFLOPs） | 本次计算采用的实现方式 |
| --- | ---: | --- |
| Qwen3-8B | 1.83 | 有效因果矩阵运算量，最后位置输出头 |
| DeepSeek V4-Flash | 3.40 | 主干有效注意力／专家工作，参考索引计算 |
| DeepSeek V4-Pro | 12.72 | 独立 Pro 配置，按自己的层型和选择上限计算 |
| Kimi K3 | 27.13 | 展开 MLA 与块式 KDA 算法 |

这张表中的 Kimi K3 使用展开 MLA：上下文先恢复为各头的 $K$、$V$，再执行交互。前面的紧凑 MLA 则把上投影移到查询和汇总一侧。完整请求沿同一条选定路径累计 prefill 与三次 decode，上下文从 128 增到 131；这一路径的矩阵形状与状态表示共同决定各项运算量。

从一次调用扩展到完整请求之后，输入和输出的作用更加清楚。增加 $P$，主要增加一次输入处理的工作量，以及后续解码开始时的上下文长度；增加 $G$，则反复执行投影、专家与输出头，并多次读取上下文。长输入、短输出与短输入、长输出由此形成不同的资源组成，第三章将把这一区别放入持续到达的负载。

> **练习 2-8〔延伸〕：从多轮输入重建调用**
>
> 一轮输入总长 1443 个 token，其中前 1392 个命中缓存，返回 128 个 token。求 $S,P,G,n_d$、请求结束时的上下文长度，以及本轮新增 KV。比较完全重算与复用缓存时，投影行数、有效因果位置对数分别减少多少。若在第 501 个输入位置修改了内容，重新求最长可复用前缀与新输入长度。

固定文本时，不同分词器会产生不同的输入长度。例如，在八道短语检索题中，Qwen3-8B 与 DeepSeek V4-Flash 都正确找到了目标短语，但短文在 Qwen 中对应 523 或 524 个 token，在 DeepSeek V4-Flash 中对应 501 个；较长文本分别对应 2121 或 2122 个和 2036 个。相同文本保持了任务内容，模型各自的 token 数则决定了实际输入形状。

因此，比较模型需要同时回答两个问题：能否完成同一任务，以及完成任务需要多少资源。先按相同标准判断答案，再将各自的输入长度代入模型表，才能把结构差异与实际用途联系起来。[^source-9]

## 谬误与陷阱

**参数更多，每 token 计算就一定更多。** 总参数决定完整模型的容量；MoE 的选中专家、注意力层型和调用形状决定当前工作。对照表 2-A 与资源表，分别解释这两种大小。

**KV 缩小四倍，注意力计算就缩小四倍。** GQA 共享上下文表示，查询头仍分别评分；MLA 改变上下文宽度，也改变上投影的执行位置。先找被改变的矩阵与状态，再计算其余工作。

**状态不随上下文增长，状态访问就可以忽略。** 固定递推矩阵仍需更新；prefill 还可能产生临时块状态。容量、累计访问与峰值工作区分别回答不同问题。

**同 token 数就是公平的模型能力比较。** 输入和输出的 token 数适合比较资源结构；同文本任务还需固定评分、质量与执行条件，并允许不同分词器产生不同长度。

## 本章小结

本章把第一章的三个资源量展开为可计算的对象。矩阵尺寸给出权重容量与线性运算，查询—上下文位置对给出注意力交互，缓存寿命与调用次数给出保存和读取，专家分派决定每批使用多少份权重。面对新条件，先指出它改变了哪一个对象，再重新代入相应公式：增加 batch、延长上下文、扩大专家集合和增加选中专家数，会作用于不同的项。

读完本章，应能从新配置列出一次前向、一次 decode 和完整生成的需求，并解释长度或 batch 改变时哪些项增长。第三章将继续加入到达与工具依赖，使这些需求成为随时间变化的负载。
