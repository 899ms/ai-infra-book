# 第 3 章 推理与训练负载

假设一个服务平均每秒收到四个请求，每个请求输入 4,608 个 token、输出 1,152 个 token。第二章已经教我们按长度计算模型工作量。现在把平均工作量乘以每秒请求数，是否就能决定需要多少资源？

还不能。同样的平均数，既可能来自始终均匀的请求，也可能来自前一分钟集中处理长文档、后一分钟集中生成长回答的任务。一条 Agent 请求还会在模型与工具之间往返：GPU 暂时不生成，历史状态却可能继续占着显存。训练也有类似区别：处理相同数量的 token，序列长度、有效标签和更新次数不同，工作量与状态寿命就不同。

这一章把第二章的计算图放进时间线。我们先观察请求如何到达，再沿多轮对话、工具调用和实时媒体展开依赖，随后补上反向传播与 RL 循环。最后，才讨论这些负载怎样转成训练和长期服务预算。

## 3.1 从一次执行到持续负载

### 3.1.1 Prefill 与 Decode

沿用第二章的记号：$S$ 是已恢复前缀的长度，$P$ 是本次未缓存输入的长度，$G$ 是返回 token 数，$B$ 是同时参与执行的请求数。普通自回归生成中，prefill 处理本次输入并产生第一个输出；之后每次 decode 把上一个输出送回模型，生成下一个 token。因此，在 $P\ge1,\ G\ge1$ 的这个口径下，返回 G 个 token 只需要 $G-1$ 次额外 decode。

这一个位置的差别会影响累计工作和最终状态。已有 6,144 个前缀位置，再补入 2,048 个输入位置，prefill 后历史长度为 8,192。若随后返回四个 token，额外执行三次 decode，最终已处理历史为 8,195 个位置。第四个输出已经交给用户，却还没有再次进入模型。

Qwen3-8B 的 BF16 逻辑 KV 每位置占 144 KiB。在这个例子中，prefill 后需要 1.125 GiB 的历史载荷，后三步再增加 432 KiB。前缀命中省去了旧输入的重算，但新输入的注意力仍可能读取旧状态。命中长度回答“已有多少计算可以复用”，无法单独回答“本次还要读多少数据”。V4-Flash 也遵循调用之间的生成依赖，只是内部保存窗口、压缩条目和索引，不能沿用 Qwen 的每位置 KV 系数。[^model]

![图 3-1 同一模型的 Prefill 与 Decode](ch03/figure-3-1-stages.svg)

*图 3-1：普通串行生成的阶段与逻辑状态。横轴按调用次序排列，不代表实测时间；$S=6144,\ P=2048,\ G=4$。prefill 产生首输出，最后一个返回 token 尚未写入历史。*

两个阶段使用同一套权重，却提出不同的资源需求。以一组权重矩阵为例，prefill 的输入包含 $BP$ 行，单步 decode 只有 $B$ 行。输入位置较多时，一次权重读取可以服务较多乘加；低并发 decode 则可能为很少几个 token 读取整组权重。这是“prefill 常偏计算密集、decode 常偏带宽密集”的来源。

这里的“常”不能省掉。增加 $B$ 可以摊薄每个输出承担的权重读取，同时也增加计算和历史状态。上下文变长、专家分布改变、非矩阵工作增加之后，限制可能转移。第二章算出的矩阵形状与逻辑访问量是判断起点，实际数据读写和执行效率还要等第四、五章补齐。

> **实验 3-1 · 延伸：Prefill 与 Decode 的资源变化**
>
> 使用第二章相同模型的长度、batch 与前缀命中表，把输入较多和生成较多的两段工作分别汇总。保持总 token 数，再改变输入与输出的比例，检查计算、历史读取和状态增长。结果应分别列工作量与资源时间下界；没有测量时，不填完整请求延迟。

### 3.1.2 任务目标与评价指标

模型请求与用户任务通常不是一一对应的。回答一个问题可能只需一次生成，修复一个函数却可能需要读文件、改代码、运行测试、根据错误再修改。评估系统时，先写出什么算完成，再决定统计什么。

对流式文本请求，设请求到达时刻为 $t_a$，首个输出时刻为 $t_1$，最后输出时刻为 $t_G$。首 token 时间 TTFT 是 $t_1-t_a$，完整请求延迟是 $t_G-t_a$。若每个输出 token 都有时间戳，平均 TPOT 可写成 $\frac{t_G-t_1}{G-1}$，仅适用于 $G>1$。相邻 token 的间隔还应单独观察：同样的平均 TPOT，可能是一条平稳输出，也可能是几次长停顿后成批交付。

首个 token 到达客户端之前，服务可能还要完成排队、输入准备、主机到设备的数据传输、设备计算、结果回传和发送。哪些步骤实际发生，要看输入与状态原来放在哪里。GPU 上算出 token 的时刻不等于客户端收到它的时刻；后续输出间隔也可能受到主机调度和结果处理影响。记录阶段时间时应保留这些边界，存在重叠时不能直接相加。第五章会把设备提交、传输与完成时刻展开。

客户端有时按块接收多个 token，块间隔不能直接当作逐 token 间隔。reasoning 模型又增加了一个观察点：首个内部 token 出现时，用户未必已看到答案。因此，内部生成、用户可见输出和任务完成各自有时间边界。语音的首次播放还要再经过解码与设备缓冲，稍后讨论。

| 要回答的问题 | 需要的指标或记录 |
| --- | --- |
| 多久开始回应？ | TTFT；reasoning 另记首个有用输出 |
| 输出是否连续？ | 逐 token／逐块间隔及其分布 |
| 多久把事情做完？ | 完整请求时间、完整任务时间 |
| 每秒交付多少合格结果？ | 在质量与时限要求下的有效吞吐 |
| 得到一个成功结果花多少？ | 全部尝试的模型、工具和环境费用／成功任务数 |
| 等待期间还占着什么？ | 状态身份、大小、驻留位置和寿命 |

p95 也必须带着对象使用。本章的配套重放采用最近秩法：将 n 个观测从小到大排列，取第 $\lceil0.95n\rceil$ 个。四条请求的 p95 就是最大值；480 条请求的 p95 是第 456 个。不能把“请求完成 p95”“初次排队 p95”和“首响应 p95”混成一个尾延迟，也不能将各阶段 p95 相加得到全程 p95。

时间线还要保留没有计算的区间。一个工具在 CPU 上执行 10 秒，模型调用已经结束，KV 可能仍需等待下一轮复用。若期间保留 M 字节状态，其驻留量对时间的积分为 $10M$ byte·s。这个量有助于比较等待带来的容量占用，却不是 HBM 访问流量。记录不到实际缓存块的分配与释放时，可以算条件式驻留预算，但应把实测峰值留空。

费用也需要同样清楚的分母。API 单价是购买服务的价格，GPU 小时是设备投入，成功任务成本衡量用户最终得到的结果。它们不能互相代替。若一个批次没有任务成功，经验成功任务成本无法估计；不能因为模型生成了很多 token，就把成本除以这些 token，宣称完成任务很便宜。[^cost]

### 3.1.3 请求分布

先用四条请求做一个能手算的对照。四条请求分别在 0、0.5、1.0、1.5 ms 到达，由两个独立 worker 按 FIFO 处理；每个 worker 独占一条请求直到完成。教学服务时间固定为每个输入 token 1 μs、每次 decode 1 ms，没有批处理、抢占或前缀共享。

第一组每条输入 1,024、输出 128。第二组交替使用短请求“512 输入、64 输出”和长请求“1,536 输入、192 输出”。两组平均输入与输出完全相同，长短分布却不同。将长度代入相同规则，结果如下。[^trace]

| 四请求教学重放 | 均匀长度 | 长短同向配对 |
| --- | ---: | ---: |
| 平均输入／输出 token | 1024／128 | 1024／128 |
| 完整请求 p95 | 255.048 ms | 318.060 ms |
| 等待 p95 | 127.024 ms | 125.524 ms |
| 逻辑 KV 峰值 | 323.719 MiB | 468.000 MiB |

长请求推高了完整延迟与状态峰值，但等待 p95 略低。原因并不矛盾：短请求较早释放一个 worker，改变了后续请求的开始时刻；长请求自身的执行时间仍然更长。仅用一个平均值，或期待所有指标同向变化，都会漏掉这层关系。

这组结果依赖明确的服务模型。将 worker 换成共享同一 GPU 的连续批处理实例，或者加入容量准入，结果就需要重算。配套的 256 MiB KV 准入变体保持请求不变，按声明的最大输出长度预留状态，完整请求 p95 增至 510.596 ms；这是容量等待的影响，不能归因于模型算得更慢。[^admission]

生产请求还会随客户组成改变。ServeGen 的研究覆盖阿里云 Model Studio 的 12 个模型、约 35.4 亿请求。收集横跨四个月，各模型在表中的分析窗口是一周或一个月。研究观察到，同一客户的请求形状相对稳定，而不同客户的速率变化会改变整体长度分布。于是，“来自哪个客户”“在什么时候到达”“输入与输出怎样配对”成为负载描述的一部分。论文中的一个规划案例，真实负载需要 24 个实例，ServeGen 估计为 25，仅采用简化负载的 NAIVE 方法估计为 12；这个结果绑定当时的 Qwen2.5-14B、A100、vLLM 配置和时限要求。[^servegen]

回到章首每秒四个请求的例子。定义 A 为输入 8,192、输出 256，B 为输入 1,024、输出 2,048。每份记录持续两分钟，A、B 各 240 条。一份始终均匀混合；另一份前一分钟 $A:B=9:1$，后一分钟变成 1:9。两份均值相同，但每秒新输入和后续 decode 的需求变成了三种情况。

| 时间窗 | 新输入 token/s | 后续 decode 步/s |
| --- | ---: | ---: |
| 均匀混合 | 18,432 | 4,604 |
| 时段变化，前一分钟 | 29,900.8 | 1,736.8 |
| 时段变化，后一分钟 | 6,963.2 | 7,471.2 |

输出总量每秒为 4,608 个 token，后续 decode 却只有 4,604 步，因为每秒四个请求的首输出由 prefill 产生。再假设某组资源每秒能完成 6,144 个序列-token decode 步，按均值看尚有余量，后一分钟却每秒多到来 1,327.2 步。把它们简化成连续工作流，暂时忽略 prefill 依赖，60 秒积压 79,632 步，停止到达后还需约 12.96 秒排空。这是教学队列的工作预算，不是每条请求的延迟。[^workload]

本书随后把相同两份长请求送入真实的 Qwen3-8B／vLLM 0.23 实例。使用 RTX PRO 6000、24 GiB KV 池、最多 64 个活跃序列，关闭前缀缓存，强制生成指定长度；120 秒后继续等待全部请求完成。两组各完成 480 条，观察如下。[^arrival]

| 实际观察 | 均匀混合 | 前 9:1、后 1:9 |
| --- | ---: | ---: |
| 完整请求 p95 | 299.383 s | 299.420 s |
| TTFT p95 | 242.918 s | 258.871 s |
| 初次调度等待 p95 | 242.418 s | 258.404 s |
| 最后完成相对起点 | 419.846 s | 418.679 s |
| 抢占事件 | 62 | 24 |

完整请求 p95 和排空时间接近，首响应、等待轨迹与抢占数却不同。两组采样 KV 池占用都达到 100%，进一步说明这里已经存在明显压力。初次等待不含抢占后的额外等待，抢占数也不是被抢占的独立请求数。每组只顺序运行一次，因此这些差值是本次观察，尚不能估计稳定的性能差距。

另一份来自 ServeGen 公开窗口的回放要轻得多：原始时序与完整长度配对置换各完成 480 条，完整请求 p95 为 0.786／0.801 秒，均无抢占，采样 KV 占用峰值仅约 1.67%／2.02%。它证明了生成记录能够接入真实模型，也提醒我们时序差异是否显现，取决于服务所处的负载范围。两种回放既不恢复生产语义，也不能验证回答质量。[^serve-replay]

> **实验 3-2 · 核心：相同均值下的不同请求分布**
>
> 先重算四请求例子的开始、完成和 KV 时间线，再分析两分钟回放。固定模型与服务策略，每次只改变长度尾部、输入输出配对或到达时刻中的一项。比较 TTFT、完整延迟和状态峰值，并指出哪些变化来自负载、哪些结论仍依赖服务假设。

## 3.2 多轮交互与 Agent 任务

### 3.2.1 多轮 Chat 与前缀增长

多轮对话的下一次请求通常带着历史。第一轮输入是系统提示和用户问题；第二轮除了新问题，还可能包含上一轮回答；之后每轮继续累积。若只看用户新写了多少字，就会低估送入模型的输入长度。

不过，完整输入也不等于每轮都要重算。设第 $i$ 轮实际输入为 $I_i$，引擎报告命中 $K_i$，则未缓存输入为 $I_i-K_i$。第二章的 prefill 计算应使用实际恢复的前缀和未缓存部分。这里必须同时记录 token ID 与命中结果：文本看起来一样，不保证模板、工具列表、模型版本和缓存位置都允许复用。

本书代码 Agent 的开启 thinking 记录给出一个具体例子。四轮累计输入 5,297 个 token，其中命中 4,480 个，未命中 817 个。第二轮输入 1,443 个、命中 1,392 个，只需处理 51 个未缓存位置；但后续 decode 仍然要访问其历史状态。按相同输入做冷重算的 prefill 矩阵工作为 76.196 TFLOPs，使用所记录命中后为 11.976 TFLOPs。这个差额只衡量被省去的矩阵工作，不能同比缩放实测延迟。[^agent-calc]

历史本身也未必只增不减。某些模板不会把上一轮完整思考区再次带入，摘要会替换一段旧历史，工具定义变化可能使前部前缀失效。因此，应从实际输入序列统计复用，不能按“上一轮输入加上一轮输出”机械递推。

上下文策略还会改变未来负载。把状态持续追加在末尾，有利于保住旧前缀，却会让陈旧内容继续占据上下文；替换前部状态可以缩短历史，但其后的缓存可能需要重建。这一章先记录改变发生的位置、重建长度与复用间隔，第八章再比较保留、淘汰和重算。[^context]

### 3.2.2 Reasoning、验证与成功任务成本

增加推理时计算有几种方式。串行思考延长同一条生成链；并行采样同时探索多个候选；按难度分配则把更多预算给较难的任务。它们都可能改善结果，也都增加了不同的工作：串行方式扩大历史并延长依赖，并行方式增加候选和验证，动态分配还需要判断何时继续、何时停止。

因此，先给一个能验证的任务和一致的质量门槛，再比较消耗。不能让一个策略输出格式正确的最终答案，另一个只给出未完成的思考，然后按生成速度排序。即使最终正确率相同，也应计入验证与失败候选的代价。

本书的实验 3-3 恰好提供了一个失败例子。四题、每题两轮观测，串行、并行与按题目规模分配三种策略合计产生 44 个候选。在总输出上限 1,024 时，全部候选截断，没有最终答案；将上限增到 4,096 后，44 个候选仍未结束思考。增加预算确实付出了工作，却没有跨过预先规定的质量门槛。[^reasoning]

再关闭 thinking 做诊断，全部候选都自然结束，但仍无法通过“整段输出为严格 JSON”的接口检查。后验提取末尾唯一 JSON 后，三策略分别只有 1/8、2/8、1/8 个任务数值正确。这帮助解释了格式失败与答案错误，却不能回头修改主评分。该次运行还与另一个 GPU 服务的启动重叠，耗时不能用来建立受控的策略速度排名。[^reasoning-off]

*图 3-2：上部使用两分钟教学负载的客户组成与阶段需求；下部保留真实重放的不同指标，以及 reasoning 实验的失败构成。没有合格产出时，图中不绘制虚构的成功成本曲线。*

单 token 变便宜也不能替代这项检查。用一个简单假设说明：新系统 token 单价降到原来的 1/10，每任务用量却增加到 20 倍，成功率由 50% 提高到 80%。只计模型费用，并假定重复尝试的分布稳定，每个成功任务的费用比为 $2\times\frac{0.5}{0.8}=1.25$。价格下降、质量提高和成功任务费用上升可以同时发生。真实 Agent 的重试带着历史和状态，应直接汇总全部尝试的费用，不必强套独立重试模型。[^cost]

> **实验 3-3 · 延伸：Reasoning 预算与正确结果成本**
>
> 读取三批候选记录，分别统计截断、格式合规、数值正确与最终任务通过。保留原评分，再单列后验诊断。若继续比较串行、并行和动态预算，应先得到满足同一质量门槛的结果；未成功的记录仍计入消耗，成功成本保持未定义。

### 3.2.3 Agentic：模型、工具与检索的循环

代码 Agent 的一轮执行可以分成四段：模型决定下一步，工具执行，工具结果返回，模型把结果接入下一次输入。编译日志、测试错误、文件内容都在这个循环中成为新数据。工具不仅增加等待，还会改变下一轮的输入长度和分支。

本书使用一个固定任务：修复区间合并函数，使嵌套区间和端点相接的区间正确合并，同时不修改输入及其嵌套列表。模型可以读取指定文件、改写它、运行固定测试并结束任务，控制器不替模型修改代码。关闭 thinking 时，模型在 12 轮内读文件一次、改写五次、运行测试六次，仍未完成；开启后，四轮分别是输出截断、写文件、运行测试和结束。首轮无效生成也花了时间，必须留在任务记录中。[^agent]

检索增强问答也可以放进这张图。检索器决定返回哪些文档，文档成为语言模型的输入。为了达到同样的回答质量，一个检索方案可能只需少量高相关内容，另一个可能需要更多文档。后者不仅增加检索输出字节，还增加 prefill、KV 和后续历史读取。这里先把“检索结果怎样进入模型”接好，第八章再用固定质量任务比较候选，避免把少返回文档直接当成更优方案。[^retrieval]

## 3.3 多模态与实时交互

### 3.3.1 视觉 E→P→D 与 EC／KV

图片进入语言模型之前，还要经过预处理、视觉编码和投影。用 E 表示视觉编码，P 表示语言 prefill，D 表示后续 decode，一次视觉问答便有 E→P→D 这条基本依赖。图片大小影响 E，编码后视觉位置数影响语言部分；这两项工作应分别计算。

以固定的 Qwen3-VL-4B 为例，预处理后的 $640\times640$ 单图按 $16\times16$ patch 划分，得到 $40\times40=1600$ 个 patch，再按 $2\times2$ 空间合并，形成 400 个视觉位置。最终语言 embedding 宽 2,560，BF16 的 $[400,2560]$ 张量占 2,048,000 bytes。

但编码结果不止这一份。模型还取三个中间视觉层的 DeepStack 特征，固定实现将它们与最终输出一起交付，完整张量为 $[400,10240]$，占 8,192,000 bytes，即 7.8125 MiB。它仍对应 400 个语言位置，不能因为有四组特征就把序列长度乘四。视觉阶段本身的已计矩阵工作约 1.310 TFLOPs，尚不含 CPU 图片解码、resize 和后续语言计算。[^vision]

编码结果称为 EC，语言主干产生的状态是 KV。该配置的语言 KV 每位置占 144 KiB，400 个视觉位置对应 56.25 MiB。于是同一张教学截图可以同时有三个大小：原始压缩文件 0.8 MB、完整 BF16 EC 7.8125 MiB、视觉位置的逻辑 KV 56.25 MiB。它们处在不同阶段，不能互相替代。[^epd]

| 对象 | 本例大小 | 决定它能否复用的条件 |
| --- | ---: | --- |
| 压缩截图 | 0.8 MB，教学输入 | 同一文件内容 |
| 完整编码结果 EC | 7.8125 MiB | 图片、预处理、编码器与输出格式一致 |
| 视觉位置的语言 KV | 56.25 MiB | 还依赖先前上下文、顺序、位置与模型状态 |

同一图片回答不同问题时，EC 可能复用；语言 KV 则还要检查问题放在图片前还是后、此前历史是否改变。四张相同规格图片的 EC 为 31.25 MiB，视觉位置 KV 为 225 MiB；再加 400 个文本位置，输入逻辑 KV 为 281.25 MiB。特殊 token、输出增长、分页碎片和工作区另计。

这些数量已经足以支持后面的系统问题。第八章安排同卡编码与语言执行，第九章决定阶段之间怎样交接，第十二章再问原图、EC 和 KV 应经过哪条链路。此时不必先选部署位置，只需确保每条边搬的是什么、下游需要什么。

### 3.3.2 音频与图像生成的工作单位

文本输出一个 token 通常对应一次自回归推进，语音却还有帧内循环。Qwen3-Omni 的生成路径包含语义推理、Talker、码本预测与波形解码。在本书固定代码的逐帧计数中，code predictor 先处理两个位置，再执行十四次单位置调用，产生十五个残差码，却实际处理十六个位置。输出码数与模型处理位置数并不相等。[^media]

Fish Audio S2 Pro 提供另一种组织。slow 路径沿音频时间推进，fast 路径在每帧内部补齐其余码本，最后由 codec 解成波形。固定路径每帧先做一次 fast 预热，再做九次预测；第一次 logits 虽然不用，计算仍然发生。于是，语言 token/s、声学帧/s、PCM sample/s 和每秒生成多少秒声音，分别描述不同的工作。只给一个“生成速度”会掩盖内部重复。

图像生成又换了一种循环。以本书固定 Qwen-Image-2512 路径为例，$1024\times1024$ 图像形成 4,096 个 latent 位置，执行 50 个去噪步，true CFG 路径每步有两支 DiT 前向，总共是 100 次。去噪矩阵工作约 $7.830\times10^{15}$ FLOPs；文本编码器与 VAE 还有各自的工作。这里反复更新一组 latent，不能沿用“每生成一个文本 token 就追加一份 KV”的模型。[^image]

FLUX.2 klein 4B 的固定蒸馏路径只有四次前向，已计去噪矩阵工作约 $1.393\times10^{14}$ FLOPs。两者差异说明步数、模型和生成路线会显著改变需求，但尚不能据此给出同质量速度排名。视频还需按模型自己的帧对齐、时空压缩与分阶段去噪计数；H3 和 Wan 的规则分别保留在配套计算中。[^media]

先数实际调用，再比较资源，是这些模型共同需要的步骤。内部循环数决定累计工作，阶段依赖决定哪些时间可以重叠，输出质量决定比较是否成立。

### 3.3.3 连续感知、首段响应与打断

实时任务除了完成内容，还要在内容仍有用时完成。截图 Agent 若只在动作结束后观察，可能错过两次动作之间出现又消失的弹窗。作者参与的 AOI 研究把观测与动作分开考虑：持续产生的图像、音频和事件，经筛选后成为可供后续模型消费的记录。这样可以提高事件覆盖，但增加关键帧也可能挤占上下文，论文摘要报告了部分模型效果退化的情况。因此，更高观测频率还需配合筛选、保存和消费预算。[^aoi]

语音的时间约束更直接。用户停止说话后，系统要采集或确认输入，经过识别／编码、推理、语音生成和播放。首块在客户端到达，只说明数据已到；扬声器开始出声还取决于解码、缓冲和设备时钟。开始播放之后，供给又必须跟上消费。

本书保留了两份历史语音记录，共 163 个音频块。由第一次 `user_speech_stopped` 到下一块 `agent_audio` 的到达差分别为 399.919 ms 和 370.459 ms。选定窗口内相邻到达间隔中位数约为 93.889 ms 和 93.806 ms，但这些值混合了模型输出、发送和传输的节奏，不能单独归因于网络。记录缺少设备首播、取消确认与静音事件，真实首播和打断响应仍然未知。[^audio-real]

为了看清缓冲的作用，另做一份明确的教学时序。输入每 20 ms 形成一块，24 kHz、单声道、每样本 2 bytes，每块载荷为：

$$
24{,}000\times0.020\times1\times2=960\ \mathrm{bytes}.
$$

每块采集结束后，模型处理 12 ms、发送 1 ms，通常再传播 5 ms。第一块在 38 ms 到达，等待 40 ms 抖动缓冲后，于从采集起点算起的 78 ms 开始播放。第三块的传播延迟被设为 50 ms，直到 123 ms 才到，错过 118 ms 的播放计划，造成 5 ms 新增停顿。后续块虽已到达，也要按声音顺序等待。

将缓冲改为 60 ms，这次停顿消失，首播却推迟到 98 ms。增加缓冲可以吸收本次抖动，代价是更晚开始；若平均供给长期慢于播放，有限缓冲终究会耗尽。[^audio]

![图 3-4 实时交互的端到端时序](ch03/figure-3-4-realtime.svg)

*图 3-4：上部连接视觉和语音的阶段；中部用教学时长展示到达、播放和迟到；下部把两份历史记录的首块接收时间与未知的播放／取消项分开。教学缓冲对照不作为两份真实语音的性能解释。*

打断也应分成几件事：应用决定取消、设备停止发声、后端停止生成、缓存与缓冲释放。教学变体在 123 ms 发出打断，控制延迟 5 ms，设备每 10 ms 生效一次，因而 130 ms 静音，响应为 7 ms。这个计算只把既定播放投影为静音，没有取消模型工作。真实系统必须分别记录这些事件，才能判断省下了哪些资源。[^audio-interrupt]

RAW 图片精修的截止则是完整成片可用，不要求像语音那样持续供给。它也不能以视觉理解的 EC 替代原始图像信息。任务目标确定之后，才知道应优化第一段、连续间隔还是最终完成时间。

> **实验 3-5 · 延伸：实时语音的响应预算**

> 先按八块教学输入复算 40／60 ms 缓冲的首播与停顿，再加入 123 ms 打断。随后读取历史到达记录，逐项指出哪些时间能够观察、哪些仍然缺失。改变模型、网络与缓冲的收益比较，需要同一固定音频及对应阶段的实际记录。

## 3.4 训练的计算与状态需求

### 3.4.1 前向、反向与更新状态

推理通常固定参数，训练则要根据损失修改参数。从第二章的一层线性变换开始：$X$ 的形状为 $[m,k]$，$W$ 为 $[k,n]$，输出 $Y=XW$。前向矩阵乘约需 $2mkn$ FLOPs。给定损失对 $Y$ 的梯度，反向还要计算两项：

$$
\frac{\partial L}{\partial X}=\frac{\partial L}{\partial Y}W^{\mathsf T},\qquad\frac{\partial L}{\partial W}=X^{\mathsf T}\frac{\partial L}{\partial Y}.
$$

把这三项并排看，就能理解训练为什么比一次前向多出两份矩阵工作。这里把一次乘加计为两个 FLOPs。

| 操作 | 要解决的问题 | 左、右输入的形状 | 输出形状 | 矩阵 FLOPs |
|---|---|---|---|---|
| 前向 $Y=XW$ | 根据输入求输出 | $[m,k]$ 与 $[k,n]$ | $[m,n]$ | $2mkn$ |
| 输入梯度 $\mathrm dX=\mathrm dY W^{\mathsf T}$ | 将误差传回前一层 | $[m,n]$ 与 $[n,k]$ | $[m,k]$ | $2mkn$ |
| 权重梯度 $\mathrm dW=X^{\mathsf T}\mathrm dY$ | 求这层权重的调整方向 | $[k,m]$ 与 $[m,n]$ | $[k,n]$ | $2mkn$ |

两次矩阵乘各约 $2mkn$ FLOPs，因此这一层的前向、输入梯度和权重梯度合计约 $6mkn$。把各 token 实际执行的可训练参数矩阵相加，就得到 $6ND$ 的常见近似。这里 $D$ 表示训练 token 数，与前文阶段符号 decode 的 D 按语境区分。[^training]

常数 6 有计算来源，但 $N$ 需要选对。嵌入查表不是每 token 对全部 embedding 做矩阵乘；共享矩阵若被多次使用，要计多次调用；冻结参数、专家选择和辅助预测也会改变工作。注意力 QK 与 PV 的序列交互又不由权重参数量决定。因此，总参数代入 $6ND$ 适合粗估，完整预算还需分项。

反向需要前向留下的信息。计算 $\mathrm dW$ 要使用 $X$，非线性反向要保存其必要中间量，参数梯度在反向中产生，优化器状态则跨更新保留。它们的寿命不同：某层激活在该层反向结束后可以释放，优化器动量通常一直留到下一次更新。把所有中间张量大小直接相加，会高估一些复用空间，又可能漏掉执行时的双份缓冲。

以 Qwen3-8B 的 8,190,735,360 个参数为例，声明采用 BF16 权重、FP32 梯度、独立 FP32 master 权重以及 Adam 的两个 FP32 moment。无分片时每参数需要 $2+4+4+4+4=18$ bytes，共 147.433 GB，约 137.308 GiB。这个数还没包含激活和工作区，也不代表所有框架的默认格式。取消独立 master 副本或改变梯度格式，要重新按实际方案核算。[^train-matrix]

一个微批与一次参数更新也要区分。显存放不下完整训练批时，可以分多个微批累计梯度，最后再更新一次参数。只要目标、有效标签和归一化保持一致，微批数增加并不意味着相同数据被训练了更多轮；它首先改变的是执行顺序与激活寿命。第十章将据此讨论分片和流水。

一次训练迭代还需要取得输入。数据读取、解码、分词或批次整理可能在 CPU 上完成，准备好的张量再传入设备。如果下一批与当前批独立，可以在当前批计算时准备和传输下一批；是否真能重叠，还取决于缓冲、依赖和可用带宽。频繁把设备上的 loss 等结果取回 CPU，也可能引入等待。因此训练步时不只由前向、反向和更新的 FLOPs 决定。第五章解释传输与同步，第十章再讨论完整训练输入流程。

### 3.4.2 预训练、中期训练与 SFT

预训练和中期训练常沿用相同的自回归预测与梯度更新过程，变化主要发生在数据、序列长度、学习率和能力目标。“中期训练”并没有统一分界，读报告时应看实际阶段。

Qwen3 报告给出一条具体路径：通用阶段在 4,096 长度上使用超过 30T token；随后增加 STEM、代码、推理与合成数据比例，再训练约 5T，长度仍为 4,096；长上下文阶段采用数千亿 token，将长度扩到 32,768。该阶段语料中，75% 长度在 16,384–32,768，25% 在 4,096–16,384。第二阶段虽然叫 reasoning stage，仍是这里讨论的预训练阶段，不应与后训练 RL 混为一谈。[^qwen]

系统需求随长度改变。假设两组独立文档都含 8,192 个 token：一组为 $4096+4096$，另一组为 $7168+1024$。参数投影的行数相同，因果注意力的有效位置对却分别为 16,781,312 和 26,218,496。在 Qwen3-8B 一层上，QK／PV 前向工作约从 0.275 增到 0.430 TFLOPs，增加约 56%。这只是序列交互部分的变化，不能推成整层或步时增加 56%。文档打包若保留独立边界，应按各自的因果遮罩计数。[^training]

SFT 增加了输入与有效标签的区别。一条样本可能包含系统提示、用户问题、工具内容和回答，而损失只计回答位置。即使某些位置不计损失，它们仍参与上下文计算。是否只对有监督位置执行词表头，是具体实现选择；只设置 loss mask 不会自动剪掉主干矩阵。

全参数 SFT 与部分参数训练也需要各自的状态预算。训练的参数较少，可以减少梯度和优化器状态，但为了把梯度传到相应位置，冻结模块仍可能需要计算输入梯度。应沿实际反向路径数工作，不能按可训练参数占比同比缩减全程。

### 3.4.3 从 $6ND$ 到分项训练预算

现在完整算一组固定输入：Qwen3-8B，$B=1,\ T=8192$，全参数训练，所有位置执行词表头，没有重计算。逐层累计投影、FFN、QK／PV 与输出头，矩阵工作如下。[^train-matrix]

| 已计工作 | TFLOPs |

| 前向矩阵 | 143.789 |

| 前向加反向 | 431.368 |

## 3.5 RL：生成、反馈与更新

### 3.5.1 Rollout、奖励与环境验证

前面的推理从外部请求开始，预训练从已有文本开始。RL 则把两条路径接起来：当前策略先生成候选，再由反馈决定怎样更新参数，更新后的策略继续产生下一批数据。生成过程通常称为 rollout。

DeepSeek-R1 提供了从推理任务和可验证奖励出发的训练路线。对代码、数学等容易检查的任务，反馈可以来自规则或测试；对需要实际操作的任务，则要运行工具与环境。奖励若由另一个模型生成，还会产生额外推理。一次“训练迭代”因此可能包含多个模型、CPU 测试、沙箱等待和梯度更新。[^r1]

V4 报告中的路线还要分清两步：先通过 SFT 和 RL 训练领域专家，再以多教师 on-policy distillation 将能力合入统一模型。OPD 使用学生自己的轨迹，由教师分布提供学习信号；报告并不是说最终统一阶段继续采用原来的混合 RL。教师前向与规则验证是不同工作，不能统称为一次便宜评分。[^v4]

从负载角度看，这些路线共同要求记录：谁产生轨迹、哪些模型读取它、是否需要工具环境、哪些 token 参与学习、何时更新权重。并行和共置可以随后改变，工作与依赖应先明确。

### 3.5.2 有效样本、策略更新与权重交接

假设八个 prompt，每题生成四个候选，共 32 条；筛选后接受 16 条。拒收候选没有进入策略更新，但已经消耗生成和评分。若只统计接受样本，会低估采样与反馈的资源。

“接受”也不一定等于“正确”。某种训练方法可能保留失败轨迹作为负反馈，某种过滤规则可能排除截断或无效奖励，组内相同奖励又可能不给出有效优势。接受条件应属于明确的训练配方，不预设所有 RL 都丢弃错误答案。

本书的一次最小 verl 实跑恰好说明了后一点。Qwen2.5-0.5B-Instruct 在算术任务中，每步四题、每题两个回答，主运行的回答全部正确，组内优势却全为零，两步策略梯度范数也为零。FP32 参数发生了符合 AdamW weight decay 的变化，BF16 权重未变。这证明更新调用执行了，不证明策略学到了东西。另一个预先规定的固定符号奖励控制产生了非零梯度和权重交接，最终验证却只有 2/4 正确。它验证流程，没有证明质量提高。[^verl]

样本组织同样属于语义。该固定配方的一次更新含八条长度为 2 或 3 的回答，共 20 个有效回答 token。八个单回答微批使用同一个分母 20，累计梯度后更新一次。若每个微批先独立求均值，再平均八份，长短回答的权重就改变了。训练 token、回答数和参数更新次数不是可互换的计量单位。[^verl-loss]

更新后还要把策略权重送给生成端。若生成端继续使用旧版本，下一批数据对应的策略就不同。同步循环可以等权重就绪后再生成；异步方案允许部分阶段重叠，却要处理样本版本与滞后。第三章先保留这条依赖，第十章再讨论交接、抢占、恢复和资源配比。

### 3.5.3 同一有效样本目标下的阶段需求

用 Qwen3-8B 计算一份教学批次，避免直接猜测大模型系统的实际部署。固定 8 个 prompt、每题 4 个候选，$P=1024,\ G=256$，接受 16 条；所有候选执行一次同配置 reference 前向，接受样本执行一次策略更新，没有教师评分。各样本等长，不提前停止，不共享前缀。[^rl]

生成时每条先做一次 prefill，再做 255 次 decode。训练与评分时，轨迹已经已知，可以按 teacher-forced 前向处理：输入长度 $P+G-1=1279$，256 个输出标签位于相应位置。16 条接受样本每轮更新的输入位置共 20,464，监督输出共 4,096。它们不能都填进同一列“训练 token”。

| Rollout prefill | 32 | 465.143 |
| Rollout decode，255 步／条 | 32 | 129.056 |
| Reference 评分，一次前向 | 32 | 634.944 |
| 教师评分，设为零次 | 0 | 0 |
| 策略更新，一次遍历 | 16 | 952.416 |

## 3.6 从负载需求到训练与服务预算

### 3.6.1 Scaling Law：拟合、验证与适用范围

算清一次更新之后，下一个问题是：固定总计算预算，应训练更大的模型，还是让较小模型看更多数据？Scaling Law 用受控实验中的统计关系回答这类问题。一个常见形式是：

$$
L(N,D)=E+\frac{A}{N^{\alpha}}+\frac{B}{D^{\beta}}.
$$

$L$ 是验证损失，$N$ 是参数规模，$D$ 是训练 token 数。$E$ 表示模型中的渐近项，另外两项描述规模和数据不足时的损失。它是一种可拟合模型，系数依赖数据、架构、训练配方和统计方法。

若暂按 $C=6ND$ 固定训练计算，将 $D=\frac{C}{6N}$ 代入并对 $N$ 求极值，可得：

$$
N_{\mathrm{opt}}=\left(\frac{\alpha A}{\beta B}\right)^{1/(\alpha+\beta)}\left(\frac{C}{6}\right)^{\beta/(\alpha+\beta)}.
$$

只有相应系数为正、拟合形式与取值范围适用时，这个连续最优点才有意义。实际模型的宽度、层数、词表和并行粒度是离散选择，还要检查训练与部署条件。

Kaplan 等人的早期研究给出约 $N\propto C^{0.73},\ D\propto C^{0.27}$ 的分配关系；Chinchilla 研究用不同实验和拟合，得到模型规模与数据量应随预算更接近等比例增长的结果。它们说明假设与实验设计会改变预算判断，不能抽出一个固定 token／参数比应用于所有语料和训练配方。[^scaling]

验证外推至少要留出没有参与拟合的点。本书从 datablations 的作者 notebook 与匹配训练日志中整理了八个 C4 观测，事先将 $N\ge2\times10^9$ 的两个点留出，其余六点拟合。固定有限指数网格得到：

$$
\begin{aligned}L={}&1.21124+1.25125\left(\frac{N}{10^9}\right)^{-0.10}\\&+0.52343\left(\frac{D}{10^{10}}\right)^{-0.45}.\end{aligned}
$$

两个留出模型的观测损失分别为 2.574117 和 2.336741，预测为 2.582723 和 2.362710，留出 RMSE 约 0.019345 nats/token。图 3-7 保留拟合与留出身份，不根据留出误差重新选择主模型。[^fit]

八个点远不足以建立通用定律。参数与训练预算来自公开估计，验证样本预算不同，误差方差与独立性未知；排除预算冲突的来源点、改变参数估计和扩展指数网格，都有单独记录。留出点预测接近，只支持这次有限检验，不证明可以可靠外推到任意长训练或所有任务。

验证损失到业务能力还隔着一步。Llama 3 报告先由训练预算预测损失，再建立损失与任务表现的关系。这样做的原因很实际：部署方关心代码、检索或工具任务能否完成，并不直接购买较低的语言模型损失。相同损失也不能自动证明相同任务质量。[^llama3]

本书另做了六次小模型 CPU 训练：三个实际规模，每个两个 seed，固定数据、优化器和 524,288 个 next-byte 目标。六次留出损失都比初始化低，但最大模型并非每个 seed 都最好：seed 309 时，最大模型为 2.548 nats/byte，中等模型为 2.480。这个局部结果说明有限训练中还存在初始化与优化差异；它既不能替代 C4 拟合，也不能把 nats/byte 与另一 tokenizer 的 nats/token 直接比较。[^local-train]

长期服务又会改变训练最优点。假设两个候选达到同一质量目标，较小模型训练更久、前期费用更高，却在每次调用上更便宜；请求足够多时，多投入训练可能收回成本。Beyond Chinchilla-Optimal 将推理需求纳入这一分析，其 47 个模型覆盖 150M–6B，但 10,000 token／参数的极端比例只在 150M 模型测试，较大模型至多 1,000。观察到的继续改善不能不加限制地外推到任意规模。[^beyond]

*图 3-7：左为八个公开 C4 观测的拟合与固定留出误差；右将同一拟合的目标损失 2.9 代入生命周期代理。成本用抽象单位，虚线候选超出拟合 N/D 范围，交叉点不代表实际部署建议。*

### 3.6.2 从 Llama 到 Qwen 的训练投入

产品历史可以帮助理解预算选择，但不同团队的数据、配方和评测不同，不能把这些产品点当作受控 Scaling Law 实验。先观察一条较清楚的变化：相近的 7–8B 参数规模，训练 token 数持续增加。[^history]

| --- | ---: | ---: | ---: |
| Llama 1，6.7B | 1T | 149 | $4.02\times10^{22}$ FLOPs |
| Llama 2，约 7B | 2T | 286 | $8.40\times10^{22}$ FLOPs |
| Llama 3.1，约 8B | 约 15T | 约 1,875 | 约 $7.20\times10^{23}$ FLOPs |
| Qwen2.5，约 7B，family 披露 | 约 18T | 约 2,571 | 约 $7.56\times10^{23}$ FLOPs |
| Qwen3，约 8B，family 披露 | 约 36T | 约 4,500 | 约 $1.728\times10^{24}$ FLOPs |

这里使用报告规模标签做历史粗算，精确参数量与第二章配置账不同。Qwen 的 family 披露也不能替代每个模型逐阶段的完整计数。这个表支持“相近模型规模可以选择更多训练投入”，尚不能把能力变化全部归因于数据量。Llama 1 已经考虑长期推理成本，不能把这种考虑写成后来才出现。

更长训练、数据筛选、蒸馏和后训练都可能提高小模型的能力密度。小模型若达到所需质量，可能减少每次权重读取，甚至从多卡部署变成单卡；但“8B 接近旧 70B”必须带着评测范围。例如固定 Llama 3 模型卡中的 base 表，Llama 3 8B 与 Llama 2 70B 在 MMLU 上为 66.6／69.7，TriviaQA-Wiki 为 78.5／87.5，两项差距并不相同。不能将部分评测接近写成所有能力等价。[^cost]

大模型与 MoE 则要并列总参数和激活参数。DeepSeek-V3 报告为总参数 671B、每 token 激活约 37B、预训练 14.8T；V4-Flash 为 284B／约 13B、32T，V4-Pro 为 1.6T／约 49B、33T。总权重影响容量，激活参数只提供计算代理。V4 主干专家的三个投影可单独计算：

$$
C_{\mathrm{expert/token}}=18Lhf(k_{\mathrm{routed}}+k_{\mathrm{shared}})=18Lhf(6+1).
$$

Flash 的主干专家约 45.4495 GFLOPs/token，按 32T 累计约 $1.45438\times10^{24}$ FLOPs；Pro 约 169.2465 GFLOPs/token，按 33T 累计约 $5.58513\times10^{24}$ FLOPs。这只含专家矩阵，注意力、路由、MTP、优化器和重计算仍未加入。报告的损失权重也不是执行比例，例如 MTP 权重为 0.3，不表示只执行 30% 的辅助计算。[^training]

### 3.6.3 质量约束下的生命周期预算与交付

到这里，可以把模型的一生接起来。前期投入包括数据、训练、教师生成与评测，服务期间持续支付模型、工具、环境和运行成本。设候选 $m$ 的前期费用为 $C_0(m)$，未来有 $Q$ 个任务，第 $j$ 类任务占比为 $w_j$、每任务平均费用为 $c_j(m)$，则简化总费用为：

$$
C_{\mathrm{life}}(m)=C_0(m)+Q\sum_jw_jc_j(m).
$$

比较之前，各候选都要满足相同质量、时限与完成条件。若任务成功率不同，$c_j$ 中还需包含失败和重试；价格变化、模型寿命、维护与贴现等假设也应随预算说明。

若新模型额外训练 $\Delta C$，却使每个合格任务节省 $\Delta c>0$，简单的收回投入条件为 $Q\ge\frac{\Delta C}{\Delta c}$。例如额外投入 100 万美元、每次节省 0.002 美元，需要 5 亿次任务。这只是教学算式，是否真有这么多需求、模型能服务多久、质量是否保持，才决定该投入是否合理。

本章交给后文的输入可以收成三份表。它们共用描述方式，但保留各自模型和证据。

| 负载 | 必须保留的字段 | 后续使用 |
| --- | --- | --- |
| Chat／Agent | 任务检查、模型与版本、每轮输入／命中／输出、到达、工具依赖、分支与复用间隔 | 第 8 章安排批处理与状态；第 9 章交接与路由；第 11 章管理工具环境 |
| 视觉／实时 | 原图字节、E/P/D、EC/KV、帧或块到达、首段／持续供给目标、打断与过期工作 | 第 8、9 章安排编码和交接；第 12 章加入链路与执行位置 |
| 训练／RL | 数据与质量、长度和标签、微批／更新、候选／接受、反馈与模型调用、权重版本、完成期限 | 第 4–7 章检查供给与协作；第 10 章安排学习；第 11 章配置环境与资源池 |

对两分钟文本负载，均值给出的是总需求，时段组成暴露了阶段容量的缺口；对代码 Agent，缓存节省了重算，任务是否完成仍由独立检查决定；对 RL，接受样本相同也可以付出不同的候选成本。每次比较都应保留这些区别，再把需要补测的量写在旁边。

第四章开始加入芯片资源。届时可以拿着明确的矩阵工作、状态大小和依赖，分别检查计算、容量与供数是否匹配；不能再让一个平均 token 数或一个峰值算力，替代整条任务的需求。
