# 十二章的具体修改方向

本文对应[全书修订计划](README.md)。节号与显示图号按 2026-09-10 当前正文引用；图稿文件名中有旧号，实际路径以 [inventory.json](inventory.json) 为准。以下是全文阅读后的编辑建议，尚未实施。建议阅读顺序表示教学层次，暂不强制对应新的章节编号。

## 第 1 章：先让读者能分析一个请求

**现状与保留。** 当前 8 幅图。全景、量纲、70B 教学算例及真实 batch 对照已经构成入门基础。容量、计算量与读取量的区别应当保留为全书第一项能力。

**主要问题。** 1.1 同时介绍软件层次、请求路径和物理网络，读者尚未认识对象就接触 CPU／GPU／NPU、HBM、PCIe、DMA、RDMA 等名称。图 1-4 将历史延迟量级与当前设备资源放在一起；图 1-5 的容量和访问又涉及不同精度条件。入门章容易变成缩略版的全书。

**建议顺序。** 用户提交一次请求 → 模型与历史分别保存在哪里 → 输入如何变成输出 → 装得下与算得快分别由什么决定 → 一个有明确假设的 70B 算例 → 改变 batch 后瓶颈怎样变化 → 回到全书路线。

**图文处理。**

- 全景图只保留层次和后续章节位置；另用一条简短路径跟踪请求。硬件细节到第四章展开，当前只定义马上需要的组件。
- 把历史延迟量级与 H100 资源说明分开。比较容量和速度时在近旁写出精度，不能让 140 GB 与 70 GB 看起来是同一对象同一条件下的两种计数。
- 理论与实测分别呈现，先看权重复用的机制，再读 batch 曲线；不要求读者此时掌握完整 Roofline。
- TPU、SmartNIC、UB 等动机作为已学原则的应用，每个只引入一个新问题，详细设计留到相应章节。

**验收问题。** 70 GB 权重已在显存中，为什么下一步仍需读取？同样能装下模型的两台设备为什么可能速度不同？读者应能用容量、字节和时间回答。

## 第 2 章：从一层模型逐步展开变体

**现状与保留。** 当前 15 幅图，内容密度最高。固定 Qwen 基线、矩阵形状推导、生成计数、KV 与递推状态区别、专家总量与选中量区别都很有价值。多模型参数与计算资料保留。

**主要问题。** 2.1.2 的多模型总表先引入后文才解释的机制；2.6.1 又集中出现大段逐矩阵表。读者要一边认识结构一边跨模型对齐符号。部分图同时呈现机制、增长规律和最终汇总。

**建议顺序。** 一个 token／输入行 → 一层中的 attention、FFN 与残差 → 一次 prefill 和随后 decode → KV 保存与使用 → 在同一底图上改变头共享、历史表示或专家路径 → 代表模型对照 → 完整请求容量与计算。

**图文处理。**

- 将多模型完整比较后移到相关机制之后；前面只给 Qwen 主例的必要形状。逐矩阵全表保留在可直接跳转的配套页，正文选代表矩阵，展示如何从形状累计到总量。
- 在注意力公式前补小规模 Q／K／V 和查询—历史配对图；把因果三角形、旧历史矩形与后文第三、八、十章的表示对齐。
- 当前图 2-4 中历史逐步累积与 batch 读取转折分开；图 2-6 先解释 KV 头共享和 MLA 表示变化，再给容量结果。
- 压缩／窗口／索引按“当前块尚未完成—完成压缩—下一步访问”展开，避免一张图既说明算法又统计全部状态。
- 图 2-12 先画残差的两条路径，再展开复杂层；图 2-15 拆为调用链、沿调用累计工作、同文本不同分词器的比较，分别放到对应文字之后。
- GQA、MLA、KDA、mHC 等名称在使用处交代改变了什么。较复杂变体提供基本结论与深入路径，不能让掌握所有变体成为阅读第三章的前提。

**验收问题。** 输入 128 个位置、输出 4 个 token，执行几次后续 decode，最后保存多少位置？头共享减少的是什么，未减少的是什么？能否用一个新模型的形状表完成同类计数？

## 第 3 章：把静态工作量变成时间过程

**现状与保留。** 当前 12 幅图。持续请求、Agent、多模态、训练、RL 和生命周期已经覆盖负载来源；同均值不同突发、任务质量与计算速度的区别值得保留。

**主要问题。** 负载类型跨度大，真实轨迹、教学队列和复杂模型计算有时紧邻出现。读者容易从一种任务跳到另一种任务，却没有建立共同的观察方法。

**建议顺序。** 请求什么时候到达 → 每个请求有哪些阶段 → 各阶段产生哪些计算和状态 → 状态保存到何时 → 任务怎样才算完成。分别用在线生成、交互任务和训练反馈三类时间过程展开。

**图文处理。**

- 图 3-2 将到达轨迹、理想队列和真实运行结果逐步展开。先解释服务率是给定模型条件，再比较实测，不把教学处理率视为设备的恒定真值。
- Agent 用同一条轨迹对齐模型、工具、等待及历史驻留。失败验证和完整日志保留精确入口，主线只留下决定“任务是否完成”的事实和改变资源量的事件。
- 多模态分为输入表示、模型处理、到达与播放、取消四个问题；图 3-7 中阶段分工、音频教学时序和实测不挤在一个面板体系内。
- 训练先补一个线性层前后向依赖小图，再给矩阵工作量；第十章负责执行和存储的完整安排。
- RL 先画生成、验证、学习与权重反馈，再画保留样本数变化引起的工作量。区分奖励、参考策略、教师和验证器。
- Scaling Law 的主线保留“数据拟合—预测—留出点检验—预算选择”；较长微积分与历史配置查阅表分层呈现。成本曲线与拟合检验分图。

**验收问题。** 平均到达率相同为何排队不同？工具等待时哪些资源释放、哪些仍保留？丢弃比例提高且要求同样多有效样本时，生成工作为何增长？

## 第 4 章：建立设备内部的物理图像

**现状与保留。** 当前 14 幅图。同一个 Q 投影贯穿资源、存储、流水与性能分析，定量组织已很完整。尤其应保留 4.7 中用 DRAM／L2 计数检验缓存解释的过程。

**主要问题。** 硬件通路的直观程度尚不足以支撑部分细致推导；与第五章在局部存储和双缓冲上有内容重叠。多资源吞吐与单块完成时间容易被同一个 max 直觉混在一起。

**建议顺序。** 一次投影走过哪些单元 → 矩阵／向量单元处理什么 → 数据在各层存储间如何移动 → 谁发起搬运、谁等待 → 资源与有限缓冲怎样限制执行 → 预测与实测 → 设备选择。

**图文处理。**

- 增补或改造一幅稳定的设备剖面图；后续局部放大继续使用同一存储层次与边界。
- 矩阵执行先用小规模阵列表示数据如何复用，再展开形状、补齐和精度，减少只用功能框介绍计算单元。
- 4.2 的矩阵／指数／存储资源平衡，分别画稳态处理间隔和单块依赖，明确它们的度量差别。
- 图 4-9 的多槽流水先跟踪一个槽，再比较两槽／三槽／四槽；最终保留总体时间结果。4.4.3 的矩阵—向量交接在表格前补数据经过的路径。
- 4.3 的已知 Qwen 容量只作简短回顾，把篇幅交给存储所有权和访问层次；第五章再详细讲循环、分块、融合及数值约束。
- 专用架构按局部性、执行组织和固定成本介绍代表设计，规格演进表放扩展材料。

**验收问题。** 增加一个缓冲槽为何有时有用、有时无用？DRAM 读取减少为何总时间未必下降？读者应能指出是哪条路径或哪个资源仍在限制完成。

## 第 5 章：把已验证的方法扩展到完整章节

**现状与保留。** 当前 23 幅图，其中 5.2–5.3 的 13 幅已完成试改。保留数值、推理顺序、容量与带宽反例、双缓冲正确性和在线 Softmax 的具体例子。

**主要问题。** 试改以外部分尚未统一到相同尺寸；编译器变换、图重放、动态形状等内容需要让读者看见程序或地址究竟如何变化。5.1、5.4–5.6 不能仅换主题色。

**建议顺序。** 一次任务如何提交并返回 → 局部复用 → 相邻算子的中间结果 → 编译器表达与检查这些变换 → 运行时减少准备与等待 → 完整请求收益。

**图文处理。**

- 5.1 在完整时间线之前，分别认识主机与设备缓冲、提交和完成事件，保持后面双缓冲图的对象连续性。
- 5.4.2 在伪代码缩进与图中循环层级之间建立对应；用小图单独解释累加器跨归约循环保存、SiLU 在归约之后执行。
- 5.4.3 的非法提前激活与量化尺度反例保留在主线，不能因精简而只剩“编译器检查合法性”。
- 图 5-18 的四种实测轨迹先由“主机提交数／设备 kernel 数”的小示意导入，再读真实时间线。图 5-19 前补固定输入地址与复制路径，解释图重放为何会多一次复制。
- 动态形状先画真实行数如何进入形状桶，再比较准备与累计执行成本；Persistent Kernel 先画块的生产和就绪事件，再看时间收益。
- 5.6 保留配对请求差值和热点占比，强调调用形状／次数到请求结果的连接。术语跟进作为全章要求执行。

**验收问题。** 图重放为何减少 launch 却不减少设备 kernel？一种局部优化快 2.6 倍，为什么完整请求只省约 1 ms？

## 第 6 章：先分数据，再推通信，最后选规模

**现状与保留。** 当前 21 幅图。八卡 Qwen 主例从单卡到 TP 再到会话调度已贯通；专家放置、批内复用和物理路径提供了有力反例。

**主要问题。** 小矩阵切法、完整 FFN、头切分和二维切分连续出现；逻辑通信和物理拓扑需要不同底图。章节较长，系统实例不宜打断主例。

**建议顺序。** 相同八卡的不同实例组织 → 两卡小矩阵切分 → FFN 及 attention 部分结果 → 集合通信的起止状态 → 逐轮实现 → 实际互联 → 容量、延迟、吞吐与故障下的部署选择。MoE 作为不同数据分工的一条支线。

**图文处理。**

- 图 6-3 之前补两元素／两卡的按列拼接与按行求和，再展开 SwiGLU。全程固定卡的位置和分片颜色。
- 图 6-9 保留逐轮累加的思想，先跟踪块 0 的 1→11→111→1111，再显示其他块的对称执行；AllGather 另一步展开，防止以宽大文字框代替真正的持有关系。
- 图 6-6 的 TP2×EP4 先画哪些输入和 KV 被复制，再画行／列归约。容量结果放在读者已理解复制的地方。
- 图 6-14 将一条消息的物理路径与全部消息累计的链路载荷分开；图 6-15 先从小环面的首尾连接解释两个切面，再给规模增长比较。
- NVIDIA、TPU、UB 先各解释一个设计问题，完整产品组织放扩展比较。远端内存保留所有权与访问频次例子，不提前展开第七章的整个传输协议。
- 章末会话时间线保留；故障时沿同一时间线指出谁停住，再计算有效完成与费用。

**验收问题。** 每卡输出形状相同为何仍要相加？同样八卡，为什么两卡实例的组合可以比一个八卡实例更早完成四个会话？

## 第 7 章：分清路径、协议事件与应用可用性

**现状与保留。** 当前 21 幅图。两服务器梯度归约、窗口、状态共享、顺序、反馈和完整训练步已经形成三个模型的连续应用。

**主要问题。** 分片流量图、控制路径和资源生命周期常在同一章快速切换。图 7-7 的四种访问方式靠术语框并列，不易看清控制者与实际数据路径。与第六章有理想流水和在途量的重复。

**建议顺序。** 固定两服务器物理底图 → 哪些字节跨边界 → 一个请求怎样提交与完成 → 请求槽何时释放 → 正确发布与必要顺序 → 多个发送者怎样形成队列 → 回到训练步。

**图文处理。**

- 图 7-3 分为连续环／交错环的边界变化、分层归约状态、流量和时间对照，保留同一张量与 rank 编号。
- 图 7-7 用相同设备位置分别画载荷和控制责任；先比较 CPU 提交与设备发起，再介绍各接口。箭头必须指向明确的内存或队列。
- 图 7-9 先展示少量代表槽位“提交—在途—完成—回收”的一轮，再扩展到 128／313 的速率结果。
- 7.4 保留源缓冲与目的缓冲的不同释放点，给发布、消费者使用和覆盖建立连续状态图。共享传输状态的组织图与容量柱图分开。
- 7.5 先画入队和出队，再读队列曲线；流控、拥塞反馈、丢包恢复分步出现。固定 20 μs 降速是教学输入，不能画成已经实现某控制器的结果。
- 7.2 的 PP 简短回顾第六章，增加本章网络边界上的交接；7.6 保留最终关键路径图，明确数据就绪与网络执行是不同事件。

**验收问题。** 相同总发送量为何跨服务器时间不同？发送完成后为什么仍不能覆盖目的缓冲？减少 ACK 或放宽交付顺序究竟改变了哪项等待？

## 第 8 章：让读者看见调度和 KV 管理实际做了什么

**现状与保留。** 当前 15 幅图。32 GiB 单设备、16 条长请求、3 秒期限是很好的贯穿设计；先容量、再时间、再质量与成本的顺序应保留。正文标题“推理优化”与文件名“单实例推理”的命名应在全书定稿时统一。

**主要问题。** 分页、前缀共享、写时复制和取消等关键操作的文字多于状态图；读者可能看到节省量却没有看见映射如何改变。实际调度图过密时，单轮行为不够突出。

**建议顺序。** 一条请求的时钟和状态 → 多请求如何进入批次 → 长 prefill 怎样影响输出 → KV 如何按块分配和共享 → 压缩／卸载的额外代价 → 推测的保留与回退 → 综合配置。

**图文处理。**

- 图 8-3 先展示“短请求完成后空出一个槽”的前后两次迭代，再比较完整四请求时间线，固定请求编号和到达标记。
- 图 8-5 将预留、分页、共享拆为连续步骤。新增小规模块表，指向固定位置的物理页，避免让相同颜色被误解为物理复制。
- 8.3.2 增加共享尾块写时复制、引用释放和等待已提交 kernel 完成的状态序列。已归档四分支实验没有验证真实写时复制，教学图与实验观察分别标注。
- 图 8-6 的前缀树与 12 轮长度统计分开；混合递推状态补恢复点示意，帮助理解“文本匹配长度不等于可直接恢复长度”。
- 卸载先借用第五章槽位组件，只增加权重与主存边界，不再完整重推双缓冲；保留生成末端状态容量与仅输入状态容量的区别。
- 推测先贪心验证，再用两个符号的概率质量图解释随机接受与修正；后续再给平均输出数与成本，避免直接从序列框跳到概率公式。
- 图 8-14 保留容量—时间可行域；通用 Amdahl 曲线可缩成当前任务阶段分解或回顾，减少跨章重复。

**验收问题。** 公共前缀只存一份，为什么取消一条请求不能立即释放它？推测验证了一整块，为什么后半块必须丢弃？容量足够的压缩方案为何仍会超时？

## 第 9 章：从服务能力走向状态交接和部署

**现状与保留。** 当前 17 幅图。A／B 八 worker 的 PD 配比主例，以及 CPU／GPU 专家位置支例，分别回答阶段与算子分工。缓存路由与启动积压的设计题有明确判断边界。

**主要问题。** 开头图 9-1 在定义展开之前使用 PD／AF；KV 交接、双端驻留、目录事件等新问题缺少足够中间图。图 9-8 的等载荷实验与实际 PD／AF 工作范围容易混读。9.6 提前引用位于 9.7 的图 9-17。

**建议顺序。** 完整副本基线 → 资源秒与处理能力 → P／D 分工 → KV 的交接过程 → 配比和网络约束 → 专家计算位置与副本 → 缓存路由 → 启动、迁移与恢复 → 完整部署。

**图文处理。**

- 先用小图定义共置与分离，再给组织总览；每个 worker 明示为独立执行单元，不默认等于一张 GPU。
- 9.2.2 新增源端保留、目的分配、传输、发布、释放四步；同一条时间线上显示两份 KV 同时存在的区间。
- 图 9-3 热图前先画一次 4A→P、4B→D 的具体配置，算出两池与网络的能力，再扩展到所有整数分配。
- 第六章的专家覆盖与复用作简短提醒，第九章新增 CPU／GPU 完整路径、副本容量和回本。图 9-8 分清等载荷的消息数控制实验与真实完整请求的 PD／AF 通信，后者单独列工作范围。

## 第 10 章：围绕一次正确更新和可恢复进展组织

## 第 11 章：区分任务进度、资源占用与外部效果

**现状与保留。** 当前 19 幅图。三轮代码修复平台贯穿模型等待、环境驻留、创建与费用，非常适合用面积和时间解释资源。有限重试树及条件概率应保留。

**主要问题。** 环境、进程、容器、microVM、模板与快照是不同对象，单靠定义段容易混淆。资源调度、RL、模型采购之间跨度较大。时间线、存储面积、费用图需要统一度量提示。

**建议顺序。** 一项任务经过哪些角色 → 模型等待时仍占哪些资源 → 哪些状态必须保留 → 环境怎样准备、暂停或重建 → 共享池怎样满足成组和突发需求 → 模型与费用选择 → 失败后的完整核算。

## 全书串联的最终检查

十二章完成后，抽取一条读者路径连续检查：第二章认识 KV → 第四章知道访问哪层存储 → 第五章理解分块中哪些值保留 → 第八章理解页与前缀共享 → 第九章理解状态交接和恢复 → 第十章理解权重变化后状态的兼容条件 → 第十一、十二章理解模型状态以外的任务进度。

再抽取另一条路径：第一章分清工作与时间 → 第三章加入到达 → 第六、七章加入分工与通信 → 第八、九章得到服务能力与排队 → 第十章得到长期完成时间 → 第十一、十二章得到合格任务的完成与费用。

这两条路径上的名词应在需要时有简短定义，同一对象应有相近画法，每次重现都应增加一个新的判断条件。全书的系统认知由这些连接逐渐形成。
