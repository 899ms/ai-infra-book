# Native／schedule／Agent三策略完整请求对照

本目录固定第四次Agent尝试已选且通过留出的512/16候选，另复制原schedule256/4与原5-9替换路径。`selection-provenance.json`钉住选择证据和代码；不修改历史候选文件，不再调参。

协议：三个独立Qwen3-8B BF16 vLLM引擎，每个引擎执行11个随机三元组，共99次正式请求。三策略使用同一7239token输入、强制32输出、temperature0、禁APC、eager、串行并发1；每个策略先审计36层prefill与decode调用，再做两次独立预热。随机顺序seed509，实际顺序随每个请求保存。替换分派、输出分配和准备的真实费用包含在端到端时钟，不把Graph基准直接代入。

`run_three.py --output results`要求新目录和起始GPU无进程，执行中采样外部进程，顺序运行三次引擎并清理。只用作者分配的GPU，CPU背景未隔离。`analyze.py`检查99个请求、实际替换模块、所有token事件和输出配对、源SHA、进程活动与清理；本次全部完成，Mac独立核验通过，见results/summary.json；三个引擎exit0，结束GPU无进程。

模式名schedule表示原256/4，agent表示本轮512/16，native表示固定vLLM实现。相同输出仅覆盖一条已知输入，不作为模型总体质量证明，也不推断饱和吞吐。

## 实测结果与部署决定

99个正式请求完成；两候选相对native各33/33对输出token完全一致。下表为同引擎配对的完整请求中位节省，单位ms，负号表示候选更慢。

|独立引擎|schedule256/4|Agent512/16|
|---|---:|---:|
|0|−13.497794|−29.984366|
|1|−17.847601|−33.040217|
|2|−10.996308|+6.647363|

schedule三轮都没有正的中位收益；Agent仅一轮为正，另两轮为负，没有稳定的正收益证据。各对原时钟和token保留于requests-*/，不因观察到回退而删除样本。引擎间CPU背景与时钟变化可能影响耗时，结论限定于这次固定路径。

**部署保留native，两个候选不升级为默认路径。** 由于稳态节省没有重复确认，预算时间/节省无法给出有实验支持的有限正向摊销点；`deployment-decision.json`明确写null及原因，不能用第三轮Agent正值挑选一个有利摊销次数。此负结果完成了“是否回到完整请求后变快”的检验，不要求人为得到加速。
