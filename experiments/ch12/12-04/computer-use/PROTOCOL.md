# Screenshot-driven browser agent

Three fresh local Chrome sessions, fixed task and initial page, maximum 16 actions each. Qwen3-VL-8B-Instruct BF16 on the RTX PRO GPU receives a screenshot, task/action contract, and prior actions only. No DOM, selectors, hidden order state, or expected coordinates are given to the model. Normalized coordinates are scaled to a 1280×960 viewport; actual browser keyboard/mouse APIs execute actions. The local order is simulated and has no external side effect.

One image warmup with a one-token cap precedes formal trials and is excluded from task timings. Formal inference is greedy with a 160-token cap, prefix caching disabled. Every screenshot, prompt, response, token trace and client action timestamp is retained. The page's hidden state is read only to stop and independently verify exact task success. Invalid actions, early done, and action limit are failures and are retained. Three repetitions of one fixed fixture do not measure a broad Computer Use benchmark.

Model service timestamps share the server monotonic clock; browser timestamps share the Mac monotonic clock. Do not subtract timestamps across machines. Local Mac-to-server requests traverse an SSH tunnel; these are not the later controlled TCP/QUIC experiment. Browser setup and one-time model load are excluded from formal task duration. Acoustic output is unrelated and unmeasured.

## Separately recorded constrained batch

The original unconstrained batch failed all three first actions because JSON omitted the y property name (`{"action":"click","x":333,404}`). Keep those failures in agent-results/server-results. The second batch uses the same model/task/sampling settings with vLLM StructuredOutputsParams JSON schema. The schema permits only action/x/y/text/key properties, requires action, and enumerates supported actions and keys. The browser's stricter per-action validator remains unchanged and can still reject missing or extraneous fields. This is an explicit inference configuration intervention, not post-hoc action repair. Store it in structured-agent-results/structured-server-results and do not pool success rates with the original batch.

## Controlled network record replay

Use all eight rounds of the first constrained trial, chosen by trial index. Upload the actual JSON inference requests (base64 PNG, instruction/history, request ID and token cap) and return each actual action JSON. Wait the corresponding measured GPU service duration after complete upload. No fresh GPU inference or browser action occurs inside this network replay; source browser action and screenshot times are separately archived and excluded from transport round/trace duration.

One Docker container with network none, NET_ADMIN, 2 CPUs and 2 GiB RAM applies netem only to its own loopback: 40 ms per traversal, 20 Mbit/s, 0.1% random loss. Earlier calibration for this image/profile is archived in ../controlled-network. HTTP/1.1 uses TLS1.3; HTTP/3 uses aioquic1.3.0. Common 120s request deadline, handshake timeout20s. Three shuffled repetitions of protocol × connection reuse; each formal cell sequentially transfers all eight different rounds. Two one-round warmups give 98 exchanges (96 formal). Reuse-on has one fresh and seven reused requests per trace. Reuse-off opens a distinct connection each round and closes these at group cleanup; cleanup is excluded from trace duration. No concurrency in this workload, no resumption or 0-RTT. Server and client share a container event loop; record replay is not a physical WAN benchmark.

Verify every upload/response hash, parsed action, request ordering, service wait, connection identity/TLS/ALPN, HTTP/3 qlog response, netem settings and drained queue. Publish all three trace times per cell. Fixed source model service is common, so differences reflect this specific transport implementation/setup, not a model quality comparison or general protocol ranking. Window tuning, interrupted recovery and final cross-workload synthesis remain outside this component.
