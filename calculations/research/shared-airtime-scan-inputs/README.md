# C69 有限 ACK 阈值 × 声明媒体字节负载输入

本目录生成九个可执行 schema 输入，**没有运行网络或看候选结果来修截止时间**。运行 `python3 calculations/research/shared-airtime-scan-inputs/build.py` 可重建 scenarios、预写算术和来源锁；只调用消息构造器与公共应用 schema validator，不调用 Network/calculate。

九格为每个音频消息 320/640/960 B × transport ACK 阈值 1/2/4。全部采用相同 count_or_timer、max_delay=10 ms、相同 20 ms 生产间隔和固定播放槽。没有把阈值 1 换成另一 legacy ACK 实现。最多八个媒体消息，避免无界生成；每格上行 300 KB 图片、下行 50 KB 图片响应是完整 30 MB/5 MB 负载各缩小 100 倍的**新教学负载**，不修改或代替旧完整大例。

## 参数身份和因果

- source profile 原样选取 `shared-airtime-inputs/profiles.json.source_backed_reference_selection`：54 Mbps DATA、6 Mbps MAC ACK、legacy OFDM 20 MHz/5 GHz、三地址 non-QoS、无加密、无聚合。原件由已有 sources.lock 固定为 ns-3.44；这是官方实现支持的选择，不是现场测量或 IEEE 原文逐条认证。
- WAN 仍为上行 20 Mbps、下行 100 Mbps、各程 50 ms，client↔AP 共享空口另外追加；不以 WAN 速率冒充 PHY。
- 图片上传 ready=0；只有上传在 server 完整交付后，server 的 0.3 秒 compute task 才可开始；任务完成后才产生 50 KB 响应。0.3 秒沿用已有图片教学服务假设，非模型测量。
- 八个 server 音频消息独立在 0/20/40/60/80/100/120/140 ms 本地产生；代表生成端输出已就绪的既定轨迹，不伪造其内部 TTS 算子时间，也不依赖尚未到达的远端输入。
- 每块固定 20 ms 音频时长。client 槽起点固定 100/120/140/160/180/200/220/240 ms，最后槽终点 260 ms；100 ms 初始播放缓冲是教学选择。9 格完全相同，不因预期成功与否修改。
- 八块、20 ms/块沿用既有媒体研究的有限音频轨迹规模；960 B 与既有 TTS 的 24 kHz、mono、PCM16、20 ms 字节量相容。**320/640 B 本轮仅是声明载荷扫描**，不指定 codec，不声称这些字节数保留同样采样信息或音质；本例总体不可称等质量压缩实验。它们对应 128/256/384 kbps 的业务载荷率，未包含网络头和反馈。
- 音频采用原子 DATAGRAM，每块均 ≤1168 B，无端到端重发；图片采用 STREAM。音频优先级 100、图片 0，各格固定同一发送优先级；空口跨端仲裁仍为全局 FIFO 声明模型。MAC/端到端反馈继续由真实事件生成，不输入预先计算的 ACK 到达时间。
- 初始 cwnd=12000 B，reference NewReno；initial_rtt=100 ms 为教学初始估计，不种造已测 RTT；无独立 controller pacer。无故障选择、无 MAC 重试，max_attempts=1；消费禁用、额度与内存给足，避免额外 MAX 成为这九格的变化轴。horizon=3 秒是固定观察范围，未预先承诺所有业务完成。
- **pad_in_flight=false**：32 B 声明 QUIC 布局预算加实际业务尾片，才能使载荷扫描体现字节与符号差异。如果统一 pad1200，三种小音频块都会占相同 radio DATA 服务，不能仍声称研究了其码率开销。此选择只用于 reference NewReno，不把可变包长无解释套入 BBR 的 nominal packet 映射。

## 实现前守恒与最低 DATA 服务

每格上行图片 300000 B 分成 257 包（256×1168+992）；下行图片 50000 B 分成 43 包（42×1168+944）。加八包音频，每格原始业务 DATA 共 308 包。尚不把 ACK、PTO 或任何后续包计为预先知道的事件。

| 单音频块 | 音频总 B | 全业务总 B | 下行业务 B | 媒体载荷率 | 单音频成功交换 µs | 原始 DATA 成功服务合计 µs |
|---:|---:|---:|---:|---:|---:|---:|
| 320 | 2560 | 352560 | 52560 | 128000 bps | 178 | 91968 |
| 640 | 5120 | 355120 | 55120 | 256000 bps | 226 | 92352 |
| 960 | 7680 | 357680 | 57680 | 384000 bps | 274 | 92736 |

实际 QUIC 字节为 payload+32，IP/UDP 加28、LLC/MAC/FCS 加36，因此 DATA PSDU=payload+96。单次成功服务是 `20+4×ceil((22+8×PSDU)/216)+34+16+44` µs。满包服务302 µs，上行尾片278 µs、下行尾片270 µs，图片总服务 `298×302+278+270=90544 µs`。

该“最低”量只在**所有 offered 原始消息至少成功发送一次**的条件下成立，且仅计原始 DATA 自身的 MAC 确认与声明接入间隔，不含 transport ACK、空闲、竞争等待、WAN、失败/重传、compute 或播放缓冲；不能当总完成时间下界的紧界，更不能用于部分 horizon 推断已经占用的服务。

`hand-oracles.json` 另外提供静态阈值-only ACK 包账：按 up=257、down=51，阈值1/2/4算 `ceil(257/n)+ceil(51/n)=308/155/78` 条，每条成功 radio ACK-carrier 服务134 µs。这是明示的静态比较器，**不是实际 ACK 数预测，也不是其下界**：timer、源端排队时覆盖合并、retention、乱序和实际反馈决定真实 ACK。实际 ACK 数和播放成功字段保留 null，下一事件运行应输出而非倒填输入。

所有每格手算都在构造时独立进行；没有调用 airtime helper 获取预期。`inputs.lock.json` 固定 profile/来源锁、schema helper/validator/构造器与生成输出哈希。本包完成的是有限扫描输入和预期，未声称已完成 C69 曲线或质量结论。

实际 ACK1/ACK2 数274/144低于静态 threshold-only比较器308/155，说明不能把静态 ceil 值冒称网络实际 ACK 数；来源队列在实际发送时合并覆盖范围，实际反馈必须运行事件。ACK4恰为78亦不能反推其他格都应相等。减少 ACK 的同时本例图片完成从约1.0627秒延迟至1.0733秒，不能只据空口占用下降声称所有业务更快。

输出明确保留 offered 原始 DATA 条件下界、实际 DATA attempt 服务和 horizon 内总占用三个字段。未来带取消/过期的输入可能少发业务、低于 offered 条件下界；重试也可能增加服务，不得据大小差异自动判守恒错误。本轮结果尚待独立审查，不将构造作者的执行报告称为独立验证。
