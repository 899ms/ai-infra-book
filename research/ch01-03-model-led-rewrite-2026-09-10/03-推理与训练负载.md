# 第 3 章 推理与训练负载

假设一个服务平均每秒收到四个请求，每个请求输入 4,608 个 token、输出 1,152 个 token。第二章已经教我们按长度计算模型工作量。现在把平均工作量乘以每秒请求数，是否就能决定需要多少资源？

两种服务可以具有完全相同的平均数：一种始终均匀接收请求，另一种前一分钟集中处理长文档，后一分钟集中生成长回答。前者持续需要相近的资源配比，后者的工作重心则在输入处理与生成之间移动。Agent 又在模型与工具之间往返，GPU 暂停生成时，历史状态继续等待复用。训练也会因序列长度、有效标签和更新次数形成不同的计算与状态寿命。

本章在第二章的计算图中加入时间因素。先分析请求的到达，再介绍多轮对话、工具调用和实时媒体，随后讨论训练中的反向传播与 RL 循环。最后，将各阶段的资源需求汇总，估算训练投入和长期服务费用。

## 3.1 从一次执行到持续负载

### 3.1.1 Prefill 与 Decode

第二章已经给出单次执行的资源需求：以 $S$ 表示恢复的历史、$P$ 表示新输入、$G$ 表示返回数，普通生成在 prefill 后还有 $n_d=G-1$ 次 decode。本章继续使用这条调用约定，将重点放在这些工作何时到达、怎样相互等待。[^model]

![图 3-1 同一模型的 Prefill 与 Decode](ch03/figure-3-1-stages.svg)

*图 3-1：复用第二章的调用约定，$S=6144,P=2048,G=4$。三次后续 decode 将已处理位置从 8192 增至 8195；横轴表示调用次序。将这条链放到每个请求的到达时刻，才能形成负载时间线。*

两个阶段使用同一套权重，却提出不同的资源需求。以一组权重矩阵为例，prefill 的输入包含 $BP$ 行，单步 decode 只有 $B$ 行。输入位置较多时，一次权重读取可以服务较多乘加；低并发 decode 则可能为很少几个 token 读取整组权重。这是“prefill 常偏计算密集、decode 常偏带宽密集”的来源。

批量与历史会改变这种配比。增加 $B$，一次权重读取服务更多输入行，计算随之增加；各请求的历史则独立累加。第二章的 Qwen3-8B 算例中，8K 历史在 batch 达到 13 时已超过共享权重数据量。因此，从低并发转向高并发时，权重复用逐渐提高，注意力计算和历史访问也逐渐占据更大份额。

> **实验 3-1 · 延伸：Prefill 与 Decode 的资源变化**
>
> 使用第二章相同模型的长度、batch 与前缀命中表，把输入较多和生成较多的两段工作分别汇总。保持总 token 数，再改变输入与输出的比例，检查计算、历史读取和状态增长。结果应分别列工作量与理论耗时下界；没有测量时，不填完整请求延迟。

### 3.1.2 任务目标与评价指标

模型请求与用户任务通常不是一一对应的。回答一个问题可能只需一次生成，修复一个函数却可能需要读文件、改代码、运行测试、根据错误再修改。评估系统时，先写出什么算完成，再决定统计什么。

对流式文本请求，设请求到达时刻为 $t_a$，首个输出时刻为 $t_1$，最后输出时刻为 $t_G$。首 token 时间 TTFT 是 $t_1-t_a$，完整请求延迟是 $t_G-t_a$。若每个输出 token 都有时间戳，平均 TPOT 可写成 $\frac{t_G-t_1}{G-1}$，仅适用于 $G>1$。相邻 token 的间隔还应单独观察：同样的平均 TPOT，可能是一条平稳输出，也可能是几次长停顿后成批返回。

首个 token 到达客户端之前，请求要依次经过排队、输入准备、设备计算和结果返回等阶段。输入原来在主机还是设备，决定数据传输发生在哪里；计算完成后，结果还要经过主机处理和连接发送。记录同一请求在各阶段的开始和结束时间，就能看出 TTFT 主要花在哪些环节。第五章将展开设备提交、传输与完成的具体时序。

客户端有时按块接收多个 token，块间隔不能直接当作逐 token 间隔。reasoning 模型又增加了一个观察点：首个内部 token 出现时，用户未必已看到答案。因此，内部生成、用户可见输出和任务完成分别对应不同的时间点。语音的首次播放还要再经过解码与设备缓冲，稍后讨论。

| 要回答的问题 | 需要的指标或记录 |
| --- | --- |
| 多久开始回应？ | TTFT；reasoning 另记首个有用输出 |
| 输出是否连续？ | 逐 token／逐块间隔及其分布 |
| 多久把事情做完？ | 完整请求时间、完整任务时间 |
| 每秒完成多少合格任务？ | 在质量与时限要求下的有效吞吐 |
| 得到一个成功结果花多少？ | 全部尝试的模型、工具和环境费用／成功任务数 |
| 等待期间还占着什么？ | 状态所属的请求与模型版本、大小、驻留位置和寿命 |

p95 描述选定指标的尾部。本章采用最近秩法：把 $n$ 个观测从小到大排列，取第 $\lceil0.95n\rceil$ 个。四条请求的 p95 是最大值，480 条请求的 p95 是第 456 个。请求完成、排队与首响应分别排序，就能看出长等待发生在哪一段；全程 p95 则直接对每条请求的全程时间排序得到。

工具等待期间，状态仍具有寿命。设 CPU 工具执行 10 秒，模型保留 $M$ bytes 的 KV 等待下一轮，驻留量对时间的积分就是 $10M$ byte·s。等待越久，这份容量越久不能交给其他请求。这一指标把不发生模型计算的区间也纳入资源需求，第八章将据此比较继续保留、换出与重算。

成功任务成本把所有尝试的费用相加，再除以成功任务数。这样，失败生成、工具测试和环境运行都进入分子，分母对应用户得到的合格结果。一个批次零成功时，记录其总消耗与失败原因；成功任务成本由取得成功结果的样本估计。[^cost]

### 3.1.3 请求分布

TTFT 和输出间隔描述单个请求的体验。多个请求陆续到达时，这些指标还取决于它们是否争用同一时段的处理能力。因此，只知道平均长度和平均请求率还不够，还要看长短请求怎样组合、何时到达。

负载描述应保留到达时间、输入与输出长度的联合分布。长请求既增加自身服务时间，也可能延长状态驻留；短请求提前完成，则可能让后续请求较早开始。因此，平均工作相同不能保证等待、完成时间和状态峰值都相同。先用章首的两分钟负载把这个区别算清，再观察真实系统。

生产请求还会随客户组成改变。ServeGen 的研究覆盖阿里云 Model Studio 的 12 个模型、约 35.4 亿请求。收集横跨四个月，各模型在表中的分析窗口是一周或一个月。研究观察到，同一客户的请求形状相对稳定，而不同客户的速率变化会改变整体长度分布。于是，“来自哪个客户”“在什么时候到达”“输入与输出怎样配对”成为负载描述的一部分。论文中的一个规划案例，真实负载需要 24 个实例，ServeGen 估计为 25，仅采用简化负载的 NAIVE 方法估计为 12；这个结果绑定当时的 Qwen2.5-14B、A100、vLLM 配置和时限要求。[^servegen]

**例题 3-1：平均处理能力足够，为什么仍会积压？** 判断每秒可完成 6144 个后续 decode 步的资源，能否持续承接章首负载。

**解：** 回到章首每秒四个请求的例子。定义 A 为输入 8,192、输出 256，B 为输入 1,024、输出 2,048。每份记录持续两分钟，A、B 各 240 条。一份始终均匀混合；另一份前一分钟 $A:B=9:1$，后一分钟变成 1:9。两份均值相同，但每秒新输入和后续 decode 的需求变成了三种情况。

| 时间窗 | 新输入 token/s | 后续 decode 步/s |
| --- | ---: | ---: |
| 均匀混合 | 18,432 | 4,604 |
| 时段变化，前一分钟 | 29,900.8 | 1,736.8 |
| 时段变化，后一分钟 | 6,963.2 | 7,471.2 |

以一个时间窗内的工作为单位，积压可以递推为：

$$
Q_{k+1}=\max(0,Q_k+A_k-\mu_k\Delta t).
$$

其中 $Q_k$ 是窗口开始时的待处理工作，$A_k$ 是窗口内新到达的工作，$\mu_k\Delta t$ 是可完成量。这里用流体模型描述 decode 队列，假设工作在窗口内均匀到达，处理速度固定。到达速度低于处理速度时，积压逐渐减少，直至队列排空；到达速度超过处理速度时，未完成的工作留到下一窗口。prefill 的处理能力另行计算。

每秒四个请求的首个输出由 prefill 产生，所以 4608 个输出中有 4604 步属于后续 decode。令 decode 队列初始为空、服务能力为每秒 6144 步，先把请求的生成工作均匀汇入各窗口。前一分钟的处理能力足够，后一分钟每秒多到来 $7471.2-6144=1327.2$ 步，60 秒便留下 79,632 步；停止到达后，再用 $79632/6144$，得到约 12.96 秒排空时间。前一分钟未使用的能力无法保存到后一分钟，这正是全局均值掩盖积压的原因。[^workload]

**队列与显存容量的共同作用。** 在 Qwen3-8B／vLLM 0.23 上运行这两种到达序列，可以观察到上述差异怎样影响用户等待。设备为 RTX PRO 6000，KV 池为 24 GiB，同时最多执行 64 条序列；关闭前缀缓存，每条请求生成指定数量的 token。两组负载都在 120 秒内到达 480 条请求，全部完成后的结果如下。[^arrival]

| 实际观察 | 均匀混合 | 前 9:1、后 1:9 |
| --- | ---: | ---: |
| 完整请求 p95 | 约 299.4 s | 约 299.4 s |
| TTFT p95 | 242.9 s | 258.9 s |
| 初次调度等待 p95 | 242.4 s | 258.4 s |
| 最后完成相对起点 | 419.8 s | 418.7 s |
| 抢占事件 | 62 | 24 |

两次回放的完整请求 p95 与最后完成时间接近，TTFT 和初次调度等待却相差约 16 秒。采样 KV 池占用都达到 100%，请求在进入执行前经历了很长等待。输入与输出的时段组合改变了何时释放状态、何时接纳新请求，所以整批完成接近时，用户开始收到响应的时间仍可不同。KV 空间不足时，抢占又会使部分请求暂停，并在之后重新进入调度。

负载压力较低时，队列呈现另一种状态。ServeGen 公开窗口的两次回放各完成 480 条，完整请求 p95 为 0.786／0.801 秒，均无抢占，采样 KV 峰值约为 1.67%／2.02%。[^serve-replay] 将它与前面的高压力回放对照，可以看到容量余量的作用：状态占用较低时，请求较容易直接进入执行；状态池填满时，新请求必须等待已有请求释放空间。

![图 3-2 请求组成与阶段积压](ch03/figure-3-2-workload-budget.svg)

*图 3-2：A、B 比较相同总量下的客户组成和阶段需求；C 为同一实例的两次实际回放；D 根据例题 3-1 的固定服务率计算后一分钟积压。D 中的队列按每秒 6144 步处理积压，排空需要 12.96 秒；C 则展示单 GPU 实际执行请求的时间。*

## 3.2 多轮交互与 Agent 任务

### 3.2.1 多轮 Chat 与前缀增长

多轮对话的下一次请求通常带着历史。第一轮通常输入系统提示和用户问题；第二轮除了新问题，还可能包含上一轮回答；之后每轮继续累积。若只看用户新写了多少字，就会低估送入模型的输入长度。

不过，完整输入也不等于每轮都要重算。设第 $i$ 轮实际输入为 $I_i$，引擎报告命中 $K_i$，则未缓存输入为 $I_i-K_i$。第二章的 prefill 计算应使用实际恢复的前缀和未缓存部分。缓存复用要求模型和前缀的 token 序列一致。提示模板或工具定义变化会改变序列，使变化位置之后的前缀需要重新计算。

以一次包含四轮模型调用的代码修复任务为例。四轮累计输入 5,297 个 token，其中命中 4,480 个，未命中 817 个。第二轮输入 1,443 个、命中 1,392 个，只需处理 51 个未缓存位置；但后续 decode 仍然要访问其历史状态。如果每轮都重新计算全部输入，prefill 的矩阵运算共需 76.196 TFLOPs；复用已命中的前缀后，共需 11.976 TFLOPs。缓存省去的是旧位置的投影与前馈重算，新的查询仍要使用这些位置的历史。因此，缓存命中同时带来“少算旧输入”和“继续保留旧状态”两项结果。[^agent-calc]

修改上下文会改变可复用的前缀长度。末尾追加新内容时，原有前缀保持不变；摘要替换一段旧历史时，替换位置之后的表示要从新的前缀重新计算；工具定义或模板变化则可能更早改变输入。这些操作决定下一轮有多少位置命中、多少位置重新进入 prefill。

上下文策略还会改变未来负载。把状态持续追加在末尾，有利于保住旧前缀，却会让陈旧内容继续占据上下文；替换前部状态可以缩短历史，但其后的缓存可能需要重建。第八章将根据重建计算量、状态大小与复用间隔，比较保留、淘汰和重算的代价。[^context]

### 3.2.2 Reasoning、验证与成功任务成本

前缀缓存减少的是已有输入的重复计算。另一类方法则主动增加生成计算，希望提高答案的正确率。增加推理时的计算量，主要有三种方式：延长一条回答中的思考过程，同时生成多份回答并从中选择，或者根据题目难度分配生成次数和长度。延长思考会增加串行生成时间与历史状态；生成多份回答会增加计算和验证次数；按难度分配则需要决定每道题何时停止。

比较这些方法时，先规定怎样的答案算正确，再统计获得正确答案花费的时间和费用。长思考将计算集中在一条回答上，多次采样则把计算分给不同回答，由验证器选择可以采用的结果。总成本要包括生成、验证以及未被采用的回答。

**陷阱实例：生成更快，任务仍然没有完成。** 生成速度只有与任务正确率一起考察，才能反映系统是否有用。一次数学题实验中，对四道题分别生成多份回答，将输出上限从 1024 提高到 4096 个 token，两轮尝试仍未得到通过评分的最终答案。生成已经消耗资源，任务却没有完成；增加输出长度也没有自动带来有效解答。[^reasoning]

答案检查应区分接口格式和内容正确性。格式正确的回答可能算错，数值正确的回答也可能缺少任务要求的字段。把两类错误分开，才能判断应调整生成方式、输出约束还是解题过程。[^reasoning-off]

单 token 变便宜也不能替代这项检查。用一个简单假设说明：新系统 token 单价降到原来的 1/10，每任务用量却增加到 20 倍，成功率由 50% 提高到 80%。只计模型费用，并假定重复尝试的分布稳定，每个成功任务的费用比为 $2\times\frac{0.5}{0.8}=1.25$。价格下降、质量提高和成功任务费用上升可以同时发生。对带历史的 Agent，可以沿实际轨迹累加各次尝试，再以通过检查的任务数作分母。[^cost]

>
> 读取三批回答记录，分别统计截断、格式合规、数值正确与最终任务通过。保留原评分，再单列事后分析。若继续比较串行、并行和动态预算，应先得到满足同一质量要求的结果；未成功的记录仍计入消耗，成功成本保持未定义。

### 3.2.3 Agentic：模型、工具与检索的循环

验证不仅可以在最后判断答案，也可以在任务进行中提供反馈。代码 Agent 会把测试结果放回上下文，据此决定下一次修改。一轮执行可以分成四段：模型决定下一步，工具执行，工具结果返回，模型把结果接入下一次输入。编译日志、测试错误、文件内容都在这个循环中成为新数据。工具不仅增加等待，还会改变下一轮的输入长度和分支。

考虑一个具体任务：修复区间合并函数，使嵌套区间和端点相接的区间正确合并，同时不修改输入及其嵌套列表。模型可以读取指定文件、改写它、运行固定测试并结束任务，控制器不替模型修改代码。关闭 thinking 时，模型在 12 轮内读文件一次、改写五次、运行测试六次，仍未完成；开启后，四轮分别是输出截断、写文件、运行测试和结束。首轮截断产生的等待同样计入任务总时间。[^agent]

检索增强问答也包含类似的处理过程：检索器找到文档，再将文档交给语言模型生成答案。在达到同样回答质量的前提下，检索内容越少，后续 prefill、KV 存储和历史读取的开销就越小。因此，检索器返回的内容会直接影响模型负载。第八章将结合具体任务比较不同检索方案。[^retrieval]

工具循环确定了任务的依赖关系，接下来沿实际轨迹计算时间和状态寿命。先比较同一代码任务开启与关闭思考模式的两组记录。

**例题 3-2：加速首轮能节省多少任务时间？** 用第一章的 Amdahl 分析，假设后续行为与质量不变。

工具并行也需要沿依赖分析。若两个工具互不依赖，同时启动后等待两者结果，理想关键路径由二者最长者决定；若第二个工具要用第一个工具的输出，它们就必须串行。两种情况下，模型恢复前可能都要保留前缀。并行分支还能共享相同历史，但各自生成的尾部独立增长。共享成立时，逻辑状态可写成“一份公共前缀加各分支尾部”；没有实际共享时，容量仍要按副本计算。

这条轨迹的工具调用很短，模型段主导全程。若工具改为 10 秒编译，模型暂停的同时，下一轮所需历史仍占据容量；若多个任务同时等待，驻留量按任务累加。工具时长因此通过状态寿命影响可承接的并发，第八、九章将在这条时间线上安排缓存与交接。

## 3.3 多模态与实时交互

Agent 的工具结果通常以文本进入下一轮输入。若输入换成图片或连续语音，模型前面还要增加编码过程，输出端也可能需要持续播放。我们先看数据在阶段之间怎样改变形状，再看各阶段必须在何时完成。

### 3.3.1 视觉 E→P→D 与 EC／KV

图片进入语言模型之前，还要经过预处理、视觉编码和投影。用 E 表示视觉编码，P 表示语言 prefill，D 表示后续 decode，一次视觉问答便有 E→P→D 这条基本依赖。图片大小影响 E，编码后视觉位置数影响语言部分；这两项工作应分别计算。

以 Qwen3-VL-4B 为例，预处理后的 $640\times640$ 单图按 $16\times16$ patch 划分，得到 $40\times40=1600$ 个 patch，再按 $2\times2$ 空间合并，形成 400 个视觉位置。最终语言 embedding 宽 2,560，BF16 的 $[400,2560]$ 张量占 2,048,000 bytes。

但编码结果不止这一份。模型还取三个中间视觉层的 DeepStack 特征，将它们与最终层特征拼接，完整张量为 $[400,10240]$，占 8,192,000 bytes，即 7.8125 MiB。四组特征对应同一组 400 个位置：特征宽度变为四倍，语言序列仍增加 400 个位置。视觉编码的矩阵运算量约为 1.310 TFLOPs；图片解码与缩放发生在编码之前，语言计算则在编码之后。[^vision]

![图 3-5 图像位置合并与特征宽度的变化](ch03/figure-3-vision-shapes.svg)

*图 3-5：左图展开 $2	imes2$ 空间合并：位置数从 1600 减至 400。右图把四组特征沿宽度方向拼接，得到 $[400,10240]$ 的 EC；位置数仍为 400。语言模型再为这些位置保存各层 KV，因此 EC 的字节数与 KV 的字节数不同。*

图 3-5 中，视觉编码改变了位置数和特征宽度；进入语言模型后，还会产生另一种表示。编码结果称为 EC，语言主干产生的状态是 KV。该配置的语言 KV 每位置占 144 KiB，400 个视觉位置对应 56.25 MiB。于是同一张教学截图可以同时有三个大小：原始压缩文件 0.8 MB、完整 BF16 EC 7.8125 MiB、视觉位置的逻辑 KV 56.25 MiB。原图经过视觉编码形成 EC，EC 进入语言主干后形成各层 KV，表示随处理阶段逐步展开。[^epd]

| 对象 | 本例大小 | 决定它能否复用的条件 |
| --- | ---: | --- |
| 压缩截图 | 0.8 MB，教学输入 | 同一文件内容 |
| 完整编码结果 EC | 7.8125 MiB | 图片、预处理、编码器与输出格式一致 |
| 视觉位置的语言 KV | 56.25 MiB | 还依赖先前上下文、顺序、位置与模型状态 |

同一图片回答不同问题时，EC 可能复用；语言 KV 则还要检查问题放在图片前还是后、此前历史是否改变。四张相同规格图片的 EC 为 31.25 MiB，视觉位置 KV 为 225 MiB；再加 400 个文本位置，输入逻辑 KV 为 281.25 MiB。特殊 token、输出增长、分页碎片和工作区另计。

三个大小对应三个交接位置。发送原图，接收端还要执行视觉编码；发送 EC，接收端从语言 prefill 开始；发送 KV，则交接已经完成的语言历史。第八章安排同卡执行，第九章比较阶段交接，第十二章把相同数据流放到端、边、云链路上。

### 3.3.2 音频与图像生成的工作单位

视觉问答仍通过语言模型逐 token 生成文本。若输出本身是声音或图像，就需要重新确定一次计算更新什么、循环多少次，不能直接把文本的生成步数套用过去。

音频输出还有帧内循环。以 Fish Audio S2 Pro 为例，slow 路径沿音频时间推进，fast 路径在每帧内补齐码本，再由 codec 解成波形。每帧先用一次 fast 前向建立状态，再用九次预测补齐码本，因此一帧包含十次 fast 前向。语言 token/s、声学帧/s 与每秒生成多少秒声音因而是不同指标。[^source-1][^media]

图像生成又换了一种循环。以 Qwen-Image-2512 为例，$1024\times1024$ 图像形成 4,096 个 latent 位置，执行 50 个去噪步，true CFG 路径每步有两支 DiT 前向，总共是 100 次。去噪矩阵运算量约 $7.830\times10^{15}$ FLOPs；文本编码器与 VAE 还有各自的工作。latent 的位置集合在去噪期间保持固定，各步持续更新其内容，累计工作随去噪步数增加。[^image]

文本生成不断追加位置，图像去噪则反复更新同一组 latent。增加图像分辨率扩大每次前向的位置数，增加去噪步数增加重复次数，启用引导分支增加每步调用数。视频再加入帧数与时空压缩，资源预算依然从“单次尺寸乘实际调用”展开。

先数实际调用，再比较资源，是这些模型共同需要的步骤。内部循环数决定累计工作，阶段依赖决定哪些时间可以重叠，输出质量决定比较是否成立。

### 3.3.3 连续感知、首段响应与打断

算出声学码、图像位置和内部迭代数，只能得到工作总量。实时交互还要求这些工作按时完成：用户能否连续听到声音，取决于下一块音频是否在缓冲耗尽前到达。

时间要求同时作用于输入和输出。先看输入端：截图 Agent 如果只在动作结束后观察屏幕，就可能漏掉中途出现又消失的弹窗。AOI 研究将屏幕观测与动作执行分开：持续收集图像、音频和事件，再筛选出供模型使用的记录。增加观测频率可以发现更多短暂事件，但保存更多关键帧也会占用上下文；过多关键帧还可能挤占重要信息，使任务效果下降。[^aoi] 因此，持续观测还要配合筛选，决定哪些内容值得保留并交给模型处理。

语音的时间约束更直接。用户停止说话后，系统要采集或确认输入，经过识别／编码、推理、语音生成和播放。首块在客户端到达，只说明数据已到；扬声器开始出声还取决于解码、缓冲和设备时钟。开始播放后，后续音频还必须及时到达，才能避免中断。

音频块到达应用之后，还要经过解码、排队和播放。两次语音交互测量中，用户停止说话到首块音频到达的时间分别约为 400 ms、370 ms，后续音频块的到达间隔中位数均约为 94 ms。[^audio-real] 到达时间说明数据何时可用，播放时钟则决定数据何时被消费。下面用一条时间线说明两者之间的缓冲如何避免声音中断。

为了看清缓冲的作用，另做一份明确的教学时序。输入每 20 ms 形成一块，24 kHz、单声道、每样本 2 bytes，每块数据量为：

$$
24{,}000\times0.020\times1\times2=960\ \mathrm{bytes}.
$$

每块采集结束后，模型处理 12 ms、发送 1 ms，通常再传播 5 ms。第一块在 38 ms 到达，等待 40 ms 抖动缓冲后，于从采集起点算起的 78 ms 开始播放。第三块的传播延迟被设为 50 ms，直到 123 ms 才到，错过 118 ms 的播放计划，造成 5 ms 新增停顿。后续块虽已到达，也要按声音顺序等待。

将缓冲改为 60 ms，这次停顿消失，首播却推迟到 98 ms。增加缓冲可以吸收本次抖动，代价是更晚开始；若音频的平均到达速度长期低于播放速度，有限缓冲终究会耗尽。[^audio]

![图 3-6 实时交互的端到端时序](ch03/figure-3-4-realtime.svg)

*图 3-6：上部展示视觉编码、语言生成与语音播放之间的阶段依赖；中部用音频块的到达和消费过程说明缓冲怎样吸收时间波动。下一块在缓冲耗尽前到达，声音可以连续播放；到达过晚，就会出现空隙。下部列出两次语音交互测量中的首块接收时间。*

打断沿控制链依次生效：应用发出取消，播放设备静音，后端停止生成，缓冲与状态释放。教学时序在 123 ms 发出打断，控制延迟 5 ms，设备每 10 ms 生效一次，于是 130 ms 静音，用户感知响应为 7 ms。后端停止生成决定后续计算何时结束，缓冲释放决定容量何时可供其他任务使用，三者分别对应声音、计算与存储的停止时刻。[^audio-interrupt]

RAW 图片精修关注的是何时能得到完整成片，无需像语音那样连续输出。精修还需要保留原始图像信息，视觉理解使用的 EC 无法替代原图。由此可见，任务不同，时间要求也不同：有的要尽快开始，有的要持续流畅，有的要尽早全部完成。

## 3.4 训练的计算与状态需求

### 3.4.1 前向、反向与更新状态

推理通常固定参数，训练则要根据损失修改参数。从第二章的一层线性变换开始：$X$ 的形状为 $[m,k]$，$W$ 为 $[k,n]$，输出 $Y=XW$。前向矩阵乘约需 $2mkn$ FLOPs。给定损失对 $Y$ 的梯度，反向还要计算两项：

$$
\frac{\partial L}{\partial X}=\frac{\partial L}{\partial Y}W^{\mathsf T},\qquad\frac{\partial L}{\partial W}=X^{\mathsf T}\frac{\partial L}{\partial Y}.
$$

前向计算输出，反向分别计算输入梯度和权重梯度。三次矩阵乘法的运算量相同，因此这一线性层的训练矩阵运算量约为前向的三倍。下表将一次乘加计为两个 FLOPs。

| 操作 | 要解决的问题 | 左、右输入的形状 | 输出形状 | 矩阵 FLOPs |
|---|---|---|---|---|
| 前向 $Y=XW$ | 根据输入求输出 | $[m,k]$ 与 $[k,n]$ | $[m,n]$ | $2mkn$ |
| 输入梯度 $\mathrm dX=\mathrm dY W^{\mathsf T}$ | 将误差传回前一层 | $[m,n]$ 与 $[n,k]$ | $[m,k]$ | $2mkn$ |
| 权重梯度 $\mathrm dW=X^{\mathsf T}\mathrm dY$ | 求这层权重的调整方向 | $[k,m]$ 与 $[m,n]$ | $[k,n]$ | $2mkn$ |

两次矩阵乘各约 $2mkn$ FLOPs，因此这一层的前向、输入梯度和权重梯度合计约 $6mkn$。把各 token 实际执行的可训练参数矩阵相加，就得到 $6ND$ 的常见近似。这里 $D$ 表示训练 token 数；生成的额外调用次数统一记为 $n_d$，阶段图中的 D 仅是 decode 的名称。[^training]

常数 6 来自同一线性层的前向与两个梯度矩阵乘。对稠密主干，各 token 使用同一组参数矩阵，逐层相加就得到 $6ND$ 的主体。MoE 按选中专家累计，嵌入按查行处理，注意力 QK／PV 则按位置对累计；这三种操作分别由调用集合、查表与序列长度决定工作。后面用 Qwen3-8B 将粗估展开为逐项预算。

反向需要前向留下的信息。计算 $\mathrm dW$ 要使用 $X$，非线性反向要保存其必要中间量，参数梯度在反向中产生，优化器状态则跨更新保留。它们的寿命不同：某层激活在该层反向结束后可以释放，优化器动量通常一直留到下一次更新。前向产生的激活要等待相应反向才能释放，因此反向传播把中间数据的寿命从相邻算子之间延长到了前后两次遍历之间。

**例题 3-3：训练状态为什么超过推理权重数倍？**

**解：** 以 Qwen3-8B 的 8,190,735,360 个参数为例，保存 BF16 权重、FP32 梯度、一份独立的 FP32 主权重（master weight），以及 Adam 的两个 FP32 矩估计。不做分片时，每参数需要 $2+4+4+4+4=18$ bytes，共 147.433 GB，约 137.308 GiB。BF16 权重用于前向和反向计算，梯度用于计算更新量，FP32 主权重用于高精度更新，Adam 的两个矩估计则累计梯度及其平方的统计量。这些数据合计占用的空间，是推理 BF16 权重的九倍。[^train-matrix]

一个微批与一次参数更新也要区分。显存放不下完整训练批时，可以分多个微批累计梯度，最后再更新一次参数。只要目标、有效标签和归一化保持一致，微批数增加并不意味着相同数据被训练了更多轮；它首先改变的是执行顺序与激活寿命。第十章将据此讨论分片和流水。

![图 3-7 推理与各训练阶段的计算和状态](ch03/figure-3-5-training.svg)

*图 3-7：前向—反向—更新的依赖。8K 训练对全部位置执行词表头，矩阵柱累计前向与两个梯度；参数状态按 BF16 权重、FP32 梯度、master 权重与 Adam 两个 moment 分解。激活沿前向保存，直到对应反向完成后释放。*

训练过程中还要不断准备下一批输入。CPU 读取、解码、分词并整理批次，再把张量送到设备。双缓冲可以让当前批计算时准备下一批：一个缓冲供计算读取，另一个接收新数据，交替使用。计算耗尽已准备数据时会等待输入，取回设备结果时又会等待相应计算完成。第五章将结合前向、反向和参数更新的执行顺序，分析数据准备与计算如何重叠。

### 3.4.2 预训练、中期训练与 SFT

前向、反向和参数更新构成了一次训练步骤。预训练、中期训练与 SFT 都会使用这一过程，但数据组织和监督位置不同。预训练通常从广泛的文本中学习，中期训练再围绕后续能力目标调整数据、序列长度和学习率；具体阶段应结合模型报告中的训练安排理解。

Qwen3 报告给出一条具体路径：通用阶段在 4,096 长度上使用超过 30T token；随后增加 STEM、代码、推理与合成数据比例，再训练约 5T，长度仍为 4,096；长上下文阶段采用数千亿 token，将长度扩到 32,768。该阶段语料中，75% 长度在 16,384–32,768，25% 在 4,096–16,384。第二阶段虽然叫 reasoning stage，仍是这里讨论的预训练阶段，不应与后训练 RL 混为一谈。[^qwen]

系统需求随长度改变。假设两组独立文档都含 8,192 个 token：一组为 $4096+4096$，另一组为 $7168+1024$。参数投影的行数相同，因果注意力的有效位置对却分别为 16,781,312 和 26,218,496。在 Qwen3-8B 一层上，QK／PV 前向工作约从 0.275 增到 0.430 TFLOPs，增加约 56%。较长文档中的位置可以看到更多前文，所以在总行数不变时，历史交互增加；投影与 FFN 仍处理同样的 8192 行。整层增加量由这笔新增交互占原有工作的比例决定。[^training]

SFT 中，模型读取的位置与参与损失计算的位置往往不同。一条样本可以包含系统提示、用户问题、工具结果和回答，但训练只对回答部分计算损失。其余位置仍要经过主干网络，为回答提供上下文。实现还可以只对受监督位置计算词表投影；如果只是屏蔽这些位置的损失，之前的矩阵乘法仍会照常执行。

部分参数训练减少需要保存梯度与优化器状态的参数集合。冻结模块的权重保持不变，但梯度仍需穿过它们传到较早的可训练模块，因此相应输入梯度继续执行。沿反向图逐层判断是否求输入梯度、是否求权重梯度，就能把训练状态与计算分别算清。

### 3.4.3 从 $6ND$ 到分项训练预算

确定训练数据和有效 token 数之后，就可以累计总运算量。先用线性层“训练约为前向三倍”的关系作粗算，再把注意力、词表头和状态更新逐项补回，便能看清粗算与完整模型之间的差距。

以一次完整训练前向和反向为例：Qwen3-8B，$B=1,\ T=8192$，全参数训练，所有位置执行词表头，没有重计算。逐层累计投影、FFN、QK／PV 与输出头，矩阵运算量如下。[^train-matrix]

| 已计工作 | TFLOPs |
| --- | ---: |
| 前向矩阵 | 143.789 |
| 反向矩阵 | 287.579 |
| 前向加反向 | 431.368 |
| 其中因果注意力 QK／PV 前反向 | 59.381 |
| 总参数代入 $6ND$ | 402.591 |

矩阵总量比 $6ND$ 高约 7.15%。差额由两类修正共同形成：序列位置之间的 QK／PV 增加工作，嵌入查行和归一化等参数则从“每 token 完整矩阵乘”的粗估中移出。将实际矩阵逐项相加，得到 431.368 TFLOPs；其中历史交互的前反向为 59.381 TFLOPs。

将有效标签数减到 4096，如果仍对全部位置计算词表投影，矩阵运算量就不变。如果先取出有监督位置的隐藏向量，再只对它们执行词表投影，总量则降到 416.074 TFLOPs。主干网络仍处理全部输入，省下的是无监督位置的词表投影；反向时再把梯度放回对应位置。[^mask]

归一化、激活、损失与优化器也需要计算和读写。以参数更新为例，即使序列很短，仍要读写权重、梯度和优化器状态；序列越短，这部分成本在总量中的占比往往越高。因此，训练预算既要考虑随 token 数增长的矩阵计算，也要考虑按参数量发生的更新开销。[^nonmatrix]

模型新增的前向操作，也会增加对应的反向计算。历史压缩需要对投影、池化和状态更新求梯度，mHC 需要向各残差通路传播梯度，MoE 则要对实际选中的专家求梯度。[^v4-training] 第二章的计算图因而也能帮助我们判断：训练时要保存哪些中间结果，反向又要执行哪些运算。

## 3.5 RL：生成、反馈与更新

### 3.5.1 Rollout、奖励与环境验证

前面的推理从外部请求开始，预训练从已有文本开始。RL 则把两条路径接起来：当前策略先生成回答，再由反馈决定怎样更新参数，更新后的策略继续产生下一批数据。生成过程通常称为 rollout。

DeepSeek-R1 提供了从推理任务和可验证奖励出发的训练路线。对代码、数学等容易检查的任务，反馈可以来自规则或测试；对需要实际操作的任务，则要运行工具与环境。奖励若由另一个模型生成，还会产生额外推理。一次“训练迭代”因此可能包含多个模型、CPU 测试、沙箱等待和梯度更新。[^r1]

V4 先通过 SFT 和 RL 训练领域专家，再以多教师 on-policy distillation 将能力合入统一模型。OPD 由学生生成轨迹，教师在这些位置提供分布，学生据此学习。教师前向因此成为生成与更新之间的一项模型工作；规则验证则以测试或程序执行提供反馈，需要另一组计算资源。[^v4]

从负载角度看，这些路线共同要求记录：谁产生轨迹、哪些模型读取它、是否需要工具环境、哪些 token 参与学习、何时更新权重。并行和共置可以随后改变，工作与依赖应先明确。

### 3.5.2 有效样本、策略更新与权重交接

生成回答和计算奖励之后，还要决定哪些样本用于学习。这里的关键是区分已经生成的样本与最终进入更新的样本：前者决定生成开销，后者决定训练批次，两者的数量未必相同。

假设有八道题，每题生成四份回答，共得到 32 条样本，筛选后保留 16 条用于训练。其余回答虽然没有用于策略更新，生成和评分的开销却已经发生。因此，估算整个训练循环时，还要计入被筛掉的样本。

是否保留一条样本，由训练方法及筛选规则决定。有的方法把失败回答作为负反馈，有的方法排除截断或奖励无效的回答。采用组内相对优势时，还要比较同一道题多份回答的奖励。因此，保留样本数决定更新时处理多少数据，奖励和损失函数则决定这些数据产生怎样的梯度。

**陷阱实例：完成一次更新不等于取得学习进展。** 在使用组内相对奖励的策略更新中，如果同组回答得到相同奖励，减去组内平均奖励后，每条回答的优势都为零，相应的策略梯度也为零。回答全部正确就可能出现这种情况。模型完成了生成、评分和更新流程，却没有从这一组回答中获得区分优劣的信号。只有奖励差异提供了非零优势，策略损失才会推动参数沿相应方向调整。[^verl]

损失的求平均方式也会影响训练。若目标是对整批有效 token 求平均，累计各微批梯度时就要使用整批的有效 token 总数作为分母。若先分别计算每个微批的均值，再对这些均值求平均，较短微批中的 token 就可能获得更大权重。第十章将用具体训练方法解释这种差别。[^verl-loss]

更新后还要把策略权重送给生成端。若生成端继续使用旧版本，下一批数据对应的策略就不同。同步循环可以等权重就绪后再生成；异步方案允许部分阶段重叠，却要处理样本版本与滞后。第三章先保留这条依赖，第十章再讨论交接、抢占、恢复和资源配比。

### 3.5.3 同一有效样本目标下的阶段需求

这种区分可以用一个固定目标来量化：每轮都要保留 16 条样本用于更新。如果回答更难通过筛选，就必须先生成更多回答。下面保持更新批次不变，只增加为得到这批样本所需的生成和评分。

**例题 3-4：固定有效样本目标，样本保留比例降低需要多少额外工作？**

**解：** 以 Qwen3-8B 为例，设有八道题，每题生成四份回答，$P=1024,\ G=256$，共保留 16 条样本用于一次策略更新。参考模型（reference model）与策略模型结构相同，分别保存权重；参考模型对全部 32 份回答各执行一次前向，本例不调用教师模型。各样本长度相同，生成时不提前停止，也不共享前缀。[^rl]

生成时每条先做一次 prefill，再做 255 次 decode。训练与评分时，轨迹已经已知，可以按 teacher-forced 前向处理：输入长度 $P+G-1=1279$，256 个输出标签位于相应位置。16 条保留样本每轮更新的输入位置共 20,464，监督输出共 4,096。输入位置决定上下文计算，监督位置决定损失作用于哪些输出，二者分别进入训练预算。

| --- | ---: | ---: |
| Rollout prefill | 32 | 465.143 |

| 合计 | 保留 16 条 | 2,181.559 |

如果样本保留比例从 1/2 降到 1/4，但仍要求得到 16 条保留样本，教学对照改为生成 64 条。生成与参考模型计算翻倍，更新量不变，总矩阵运算量增到 3,410.701 TFLOPs，约增加 56.3%。每个保留样本承担的矩阵运算量从 136.347 增到 213.169 TFLOPs。增加的 1229.142 TFLOPs 全部来自额外回答的生成与参考模型计算；进入更新的 16 条样本保持不变。[^rl-low]

## 3.6 从负载需求到训练与服务预算

### 3.6.1 Scaling Law：拟合、验证与适用范围

算清一次更新之后，下一个问题是：固定总计算预算，应训练更大的模型，还是让较小模型看更多数据？Scaling Law 用受控实验中的统计关系回答这类问题。一个常见形式是：

$$
L(N,D)=E+\frac{A}{N^{\alpha}}+\frac{B}{D^{\beta}}.
$$

$L$ 是验证损失，$N$ 是参数规模，$D$ 是训练 token 数。$E$ 表示模型中的渐近项，另外两项描述规模和数据不足时的损失。它是一种可拟合模型，系数依赖数据、架构、训练方法与设置和统计方法。

若暂按 $C=6ND$ 固定训练计算，将 $D=\frac{C}{6N}$ 代入并对 $N$ 求极值，可得：

$$
N_{\mathrm{opt}}=\left(\frac{\alpha A}{\beta B}\right)^{1/(\alpha+\beta)}\left(\frac{C}{6}\right)^{\beta/(\alpha+\beta)}.
$$

在 $A,B,\alpha,\beta$ 均为正的拟合模型中，增加参数量会减小 $A/N^\alpha$，降低模型规模不足造成的损失；但总计算量固定时，可用于训练的数据量随之减少，$B/D^\beta$ 又会增大。令导数为零，就是寻找两种影响相抵的位置。由此得到的 $N_{\mathrm{opt}}$ 是连续取值的结果，实际设计时可在它附近选择合适的层数和宽度。

Kaplan 等人的早期研究给出约 $N\propto C^{0.73},\ D\propto C^{0.27}$ 的分配关系；Chinchilla 研究用不同实验和拟合，得到模型规模与数据量应随预算更接近等比例增长的结果。前一种分配更快增加模型参数，后一种把更多新增预算分给训练数据；曲线及其拟合指数因此直接改变参数与数据的选择。[^scaling]

**例题 3-5：怎样检验一条 Scaling Law？** 从公开训练记录中固定六个较小模型的观测用于拟合，另将两个较大模型的观测留出。先选定拟合方法，再比较留出预测与观察值。

**解：** 以 datablations 在 C4 数据上的八个模型为例，用六个较小模型拟合曲线，将 $N\ge2	imes10^9$ 的两个模型留作检验。两个大模型的实际损失分别约为 2.574、2.337，拟合曲线预测为 2.583、2.363。预测略高于实际值，均方根误差约为 0.0193 nats/token。图 3-9 用不同标记区分拟合点与检验点。[^fit]

留出检验之所以必要，是因为拟合只保证曲线尽量贴近用于求系数的数据。将较大模型排除在拟合之外，再比较预测与实际损失，才能检查这条关系能否预测新规模。这里的两个误差分别约为 $0.009$ 和 $0.026$；将它们平方、取平均再开方，便得到均方根误差。

预测验证损失之后，还要判断模型能否完成实际任务。Llama 3 报告先根据训练计算量预测损失，再建立损失与任务表现的关系。[^llama3] 这样，代码、检索和工具使用等任务的质量要求，才能进一步转化为训练规模与计算量的选择。

训练本身也存在波动。同样的数据与模型规模，改变随机初始化就可能得到不同的学习曲线；较大模型在训练尚未充分时，也未必优于较小模型。使用多个随机种子重复训练，可以区分规模变化带来的趋势与单次训练的偶然波动。[^local-train]

长期服务会把每次调用的费用累积到训练预算之上。较小模型可以通过更长训练达到目标质量，前期多付费用，之后每次调用读取更少权重、执行更少工作。Beyond Chinchilla-Optimal 将这种推理需求纳入分析，47 个模型覆盖 150M–6B；其中 150M 模型测试到 10,000 token／参数，较大模型测试到 1,000。[^beyond] 训练预算与服务次数共同决定较小模型的额外训练何时收回成本。

### 3.6.2 从 Llama 到 Qwen 的训练投入

前面的拟合说明了模型规模与训练数据之间可以怎样取舍。下面回到公开模型，观察开发者实际选择了怎样的训练投入：先比较每个参数对应的训练 token 数，再将算法运算量与具体硬件上的训练时间区分开。

从各报告披露的阶段和规模，可以看到一个趋势：相近的 7–8B 参数规模，训练 token 数持续增加。[^history]

| 模型与报告范围 | 训练 token | $D/N$ 粗略估算 | $6ND$ 粗略估算 |
| --- | ---: | ---: | ---: |
| Llama 1，6.7B | 1T | 149 | $4.02\times10^{22}$ FLOPs |
| Llama 2，约 7B | 2T | 286 | $8.40\times10^{22}$ FLOPs |
| Llama 3.1，约 8B | 约 15T | 约 1,875 | 约 $7.20\times10^{23}$ FLOPs |
| Qwen2.5，约 7B，模型系列披露 | 约 18T | 约 2,571 | 约 $7.56\times10^{23}$ FLOPs |
| Qwen3，约 8B，模型系列披露 | 约 36T | 约 4,500 | 约 $1.728\times10^{24}$ FLOPs |

表中根据报告给出的参数规模估算 $D/N$ 和 $6ND$，Qwen 的训练量采用模型系列披露的数据。同为约 7–8B 参数，训练数据从约 1T 增至数十 T token，说明模型大小不变时，仍可以增加前期训练投入。训练费用主要发生在上线之前，推理中的权重读取和计算费用则在每次服务时重复发生。

更长训练、数据筛选、蒸馏和后训练，把更多前期工作用于提高给定规模模型的任务能力。Llama 3 模型卡的基础模型评测中，Llama 3 8B 与 Llama 2 70B 在 MMLU 上分别为 66.6／69.7，TriviaQA-Wiki 为 78.5／87.5。[^cost] 两项差距不同，说明部署方要按自己的任务选择质量要求；通过门槛的小模型，才有机会把较小权重带来的容量与读取收益转成服务收益。

大模型与 MoE 则要并列总参数和激活参数。DeepSeek-V3 报告为总参数 671B、每 token 激活约 37B、预训练 14.8T；V4-Flash 为 284B／约 13B、32T，V4-Pro 为 1.6T／约 49B、33T。总权重影响容量，激活参数只提供计算量的粗略估计。V4 主干专家的三个投影可单独计算：

$$
C_{\mathrm{expert/token}}=18Lhf(k_{\mathrm{routed}}+k_{\mathrm{shared}})=18Lhf(6+1).
$$

Flash 的主干专家约 45.4495 GFLOPs/token，按 32T 累计约 $1.45438\times10^{24}$ FLOPs；Pro 约 169.2465 GFLOPs/token，按 33T 累计约 $5.58513\times10^{24}$ FLOPs。这只含专家矩阵，注意力、路由、MTP、优化器和重计算仍未加入。报告的损失权重也不是执行比例，例如 MTP 权重为 0.3，不表示只执行 30% 的辅助计算。[^training]

> **实验 3-9 · 延伸：Llama 与 Qwen 的训练投入**
>
> 逐行核对参数、训练 token 和阶段范围，重算 $D/N$ 与 $6ND$。对 MoE 单列总参数、按激活参数估算的计算量和专家分项计算，解释为什么这些列不能相互替代。Qwen3.5 的完整 token／GPU 小时组合缺失时保持空白，不沿用 Qwen3 的 36T。

GPU 小时还可以换算为日历时间。Llama 1 65B 的训练消耗 1,022,362 A100 GPU 小时。若持续使用 2,048 张卡，所需时间为 $1{,}022{,}362/2{,}048pprox499.2$ 小时，即约 20.80 天。除数是同时使用的设备数，因此设备数量变化会直接改变日历时间。

DeepSeek-V3 报告预训练 2.664M H800 GPU 小时，上下文扩展 119K、后训练 5K，合计 2.788M。14.8T 只配预训练阶段；在持续 2,048 卡的假设下，预训练约为 54.20 天。把三个阶段的小时全除以预训练 token，会混合统计范围。[^history]

用 GPU 小时换算日历时间，要除以同期使用的卡数。对 Llama 3.1 405B，取公开的 30.84M H100 GPU 小时，并假设这项工作全部使用最大规模 16,384 卡，计算为 $30.84\times10^6/(16384\times24)\approx78.43$ 天。阶段使用的卡数更少时，相同 GPU 小时需要更长日历时间；训练资源的分配时序因此决定训练完成时间。

### 3.6.3 质量约束下的生命周期成本与负载汇总

到这里，可以把模型的一生接起来。前期投入包括数据、训练、教师生成与评测，服务期间持续支付模型、工具、环境和运行成本。设模型 $m$ 的前期费用为 $C_0(m)$，未来有 $Q$ 个任务，第 $j$ 类任务占比为 $w_j$、每任务平均费用为 $c_j(m)$，则简化总费用为：

$$
C_{\mathrm{life}}(m)=C_0(m)+Q\sum_jw_jc_j(m).
$$

比较之前，各模型都要满足相同质量、时限与完成条件。若任务成功率不同，$c_j$ 中还需包含失败和重试；价格变化、模型寿命、维护与贴现等假设也应随预算说明。

若新模型额外训练 $\Delta C$，却使每个合格任务节省 $\Delta c>0$，简单的收回投入条件为 $Q\ge\frac{\Delta C}{\Delta c}$。例如额外投入 100 万美元、每次节省 0.002 美元，需要 5 亿次任务。前 5 亿次调用逐步偿还额外训练费用，此后的调用继续累积净节省。于是，预期需求量把一次性的训练选择与长期部署联系起来。

后续章节将使用本章整理出的三类负载信息。下表列出各类负载需要记录的内容，以及这些信息将用于哪些系统设计问题。

| 负载 | 必须保留的字段 | 后续使用 |
| --- | --- | --- |
| Chat／Agent | 任务检查、模型与版本、每轮输入／命中／输出、到达、工具依赖、分支与复用间隔 | 第 8 章安排批处理与状态；第 9 章交接与路由；第 11 章管理工具环境 |
| 视觉／实时 | 原图字节、E/P/D、EC/KV、帧或块到达、首次响应时间／连续播放要求、打断与过期工作 | 第 8、9 章安排编码和交接；第 12 章加入链路与执行位置 |
| 训练／RL | 数据与质量、长度和标签、微批／更新、生成样本数／保留样本数、奖励计算与模型调用、权重版本、完成期限 | 第 4–7 章分析算力、存储与通信需求；第 10 章安排学习；第 11 章配置环境与资源池 |

这三类例子都说明，描述负载需要记录具体的执行过程。两分钟请求中，各时段的输入输出比例决定积压何时出现；代码 Agent 中，工具依赖决定等待时间和状态保存多久；RL 中，筛选前后的样本数决定生成与更新各处理多少数据。掌握这些信息，才能为各阶段安排资源。

第四章将结合芯片的算力、存储容量与带宽，分析这些负载如何在设备上执行。本章算出的矩阵尺寸、状态大小和访问次数，将用于判断计算需要多久、数据能否放下，以及读写能否及时完成。各阶段的依赖关系则决定哪些工作可以重叠，哪些必须等待。

## 谬误与陷阱

**均值相同就是同一负载。** 请求长度的尾部、输入输出的配对和到达顺序决定短窗需求。例题 3-1 中，处理能力足以应付平均到达量，后一分钟却仍会积压。

**token 更便宜，完成任务也更便宜。** 额外思考、未通过检查的回答、工具与环境都应进入分子，合格任务数进入分母。零成功的批次只能报告消耗与失败，不能估计成功成本。

**训练了相同数量的 token，系统工作就相同。** 序列分布改变注意力位置对，标签与词表头策略改变输出工作，更新次数改变优化器成本；RL 还包含未被采用的回答的生成与反馈。

## 本章小结

持续服务的负载既取决于每次请求要做多少工作，也取决于请求何时到达、各步如何等待。平均速率可以粗略估算所需资源，短时间内的积压和状态保存时间则解释了平均值遗漏的压力。多轮任务还包含工具等待与失败尝试，实时任务要保证数据及时到达，训练则增加反向、参数更新和权重同步。

预算比较始终保持质量与完成目标一致。Scaling Law 为训练分配提供可检验的统计模型，长期服务需求又可能改变前期投入的选择。核心练习 3-2、3-4、3-7 分别把这些方法用于持续请求、交互任务和 RL 循环。
