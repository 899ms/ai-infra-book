# 第 5 章 算子与运行时

一个矩阵乘的输入、权重和输出合计只有 128 MiB，执行时却可能搬动超过 3 GiB 的数据。将输出块的边长扩大一倍，访问量接近减半，但片上活动空间从 24 KiB 增到 80 KiB。数据搬得少了，能够同时运行的工作组也可能变少。究竟哪种实现更快，要从这两项变化一起判断。

第四章给出了硬件的计算能力、存储层次与数据通路。本章把这些资源交给一个具体程序。数学表达式只规定结果，程序还要决定循环顺序、分块大小、数据布局、临时结果放在哪里，以及主机何时向设备提交工作。这些选择会改变实际搬移量，也会改变数据就绪与缓冲复用的时刻。

我们从 Qwen3-8B 的一段 FFN 开始，逐步扩大观察范围：先看输入怎样送入设备、计算怎样发起、结果何时可用，再优化一个矩阵乘，把相邻算子连起来；随后解释编译器怎样组织这些变换，运行时怎样减少准备和提交工作，最后检查完整请求是否受益。注意力作为第二条代表链，用来说明带归约的运算为什么需要更仔细地处理分块与中间状态。

以 Qwen3-8B 为例：隐藏宽度 $H=4096$，FFN 中间宽度 $F=12288$，32 个 query head、8 个 KV head，head dimension 为 128。先取 $M=1024$ 行输入，输入与权重为 BF16，矩阵累加使用 FP32。这里的 M 表示一次算子调用处理的 token 行数，可以来自一条序列，也可以来自多个请求。单请求逐 token decode 时，M 通常只有 1。[^model]

FFN 的主要运算是 $G=XW_g$、$U=XW_u$、$Z=\operatorname{SiLU}(G)\odot U$，随后计算 $ZW_d$。gate 与 up 可以分别调用，也可以拼成一次较宽的矩阵乘。两种写法都要产生 G、U 两份结果，各占 24 MiB。

| FFN 中的对象 | 形状 | BF16 大小 | 接下来的用途 |
| --- | --- | ---: | --- |
| 输入 X | $[1024,4096]$ | 8 MiB | gate 与 up 投影共享 |
| 每支投影权重 | $[4096,12288]$ | 96 MiB | 在多行输入之间复用 |
| G、U 各一份 | $[1024,12288]$ | 各 24 MiB | 激活与逐元素乘法 |
| Z | $[1024,12288]$ | 24 MiB | down 投影输入 |
| down 输出 | $[1024,4096]$ | 8 MiB | 后续残差与模型层 |

如果 down 投影使用量化输入，还要把 24 MiB 的 BF16 激活转换为更窄的表示，并产生所需尺度。下面先分析 BF16 激活，再加入这一步量化。

第二条链是 QKV 投影、QK Norm、RoPE 和注意力。对于同样的 1024 个输入位置，Q 的 BF16 载荷为 8 MiB，K、V 各为 2 MiB；QK Norm 与 RoPE 保持各自输出形状，但改变内容。注意力读取的历史 K/V 长度由请求状态决定，不能只看当前输入行数。

| 注意力链的阶段        | 输入与中间结果                        | 主要交接问题             |
| -------------- | ------------------------------ | ------------------ |
| QKV 投影         | Q：$[M,32,128]$；K/V：$[M,8,128]$ | 投影输出布局与后续访问是否匹配    |
| QK Norm 与 RoPE | Q/K 的归一化和位置变换                  | 哪些结果能就地或在 tile 内交接 |
| 注意力            | 当前 Q 与有效历史 K/V                 | 分数是否物化，局部状态怎样合并    |
| 输出交接           | 每个 query head 的输出              | 重排、输出投影与残差的边界      |

“算子”在这些表里表示数学工作。“kernel”是设备上实际执行的程序。“主机提交”是 CPU 发起执行的动作。三者不一定一一对应：一个矩阵乘可能启动多个 kernel；多个算子可能融合成一个 kernel；一次 CUDA Graph 提交又可能让设备执行许多个 kernel。下面先解释普通执行，图重放在 5.5 节展开。

## 5.1 一次设备执行：提交、搬运与同步

先看一个最简单的程序：CPU 准备输入，把输入交给 GPU 计算，再取回结果。数学上可能只有一句 $Y=XW$，实际运行却涉及两个处理器、不同位置的内存，以及它们之间的等待。本节先把这个过程讲清楚，后面再讨论怎样减少其中的工作和等待。

### 5.1.1 从框架调用到 kernel launch

在 PyTorch 等框架中写下矩阵乘法后，CPU 上的代码通常需要检查张量形状和数据类型、选择实现、准备参数，再通过运行时和驱动向 GPU 提交任务。向设备提交一次内核执行，通常称为 **kernel launch（内核启动）**。运行时负责执行期间的任务提交、内存和同步等工作；编译器如何生成内核，留到 5.4 节展开。

算子、kernel 和 launch 是三个观察角度。算子描述要算什么；kernel 是设备执行的程序；launch 是发起这次执行的动作。一个矩阵乘可能由多个 kernel 完成，多个逐元素算子也可能融合成一个 kernel。数模型图上的节点，不能直接得到启动次数。

以 CUDA 为例，一次 kernel 执行会组织一组线程，线程组成线程块（thread block），这些线程块合称一个 grid。程序可把不同的输出矩阵块交给不同线程块，再由块内线程协作。线程块会被安排到有可用资源的 SM 上，不必同时开始。这里的“块”还要按上下文区分：矩阵分块是数据划分，线程块是执行组织，两者怎样对应由程序决定。

**launch 调用返回，只表示主机这一步调用结束，不表示 GPU 已完成计算。** GPU 可能已经开始，也可能还在等待前面的工作。CPU 可以继续准备下一项任务；需要读取设备结果时，才必须确认相关工作完成。异步执行正是让 CPU 与 GPU 能够各自向前推进的基础。[^execution]

启动本身也需要时间。大矩阵的设备计算可能足以覆盖 CPU 准备下一次调用的时间；很小的算子执行得快，GPU 则可能算完后仍等不到下一个任务。这时只优化设备内的乘加，整体收益可能很小。后面的融合会同时影响 kernel 数和数据读写，CUDA Graph 则主要减少重复组织与提交任务的工作。

### 5.1.2 数据在哪里：H2D、D2H 与 D2D

Host 指发起工作的主机，Device 指执行工作的设备。对有独立显存的 GPU，常见复制方向如下。

| 名称 | 数据从哪里到哪里 | 例子 |
| --- | --- | --- |
| H2D（Host to Device） | 主机内存 → 设备内存 | 把训练输入或待计算的张量传入 GPU |
| D2H（Device to Host） | 设备内存 → 主机内存 | 把生成的 token ID 或计算结果取回 CPU |
| D2D（Device to Device） | 设备内存 → 设备内存 | 在同一 GPU 上把数据复制到另一份缓冲 |

多 GPU 之间的复制也可能属于 D2D，但路径取决于设备连接和软件支持，第六章再展开。本章先看单设备。GPU 内核读取显存中的权重属于设备访存，不是又做了一次 H2D；同样，把结果写回显存也不等于已经把结果传回 CPU。

下面这条链适合说明独立输入、输出都在主机上的简单程序：

> CPU 准备输入 → H2D → GPU 执行 kernel → D2H → CPU 使用结果。

完整模型并不在每个算子前后都走一遍这条链。显存足够时，权重通常在模型加载后留在 GPU，层间激活直接交给下一个设备内核，KV 也可以跨 decode 步保留。在 GPU 上完成采样后，输出侧可能只需回传少量 token ID；下一步使用的 token 还可以留在 GPU。是否每步都要等待 CPU，取决于调度、停止判断和其他依赖。因此要先问“这次究竟传什么”，再计算字节数。

一个 $[8192,4096]$ 的 BF16 张量占 $8192\times4096\times2=64$ MiB。假设主机到设备的有效单向带宽为 24 GiB/s，仅传输就需要约 2.6 ms。把这份输入分成两半，字节数仍是 64 MiB，传输总工作也没有减少；收益只能来自让前一半先开始计算，与后一半传输重叠。小到几个字节的结果回传则往往受发起与等待时间限制，不能按字节数同比缩短。[^buffer]

主机内存的类型也影响复制。普通内存可以被操作系统换出；**锁页内存（pinned memory）**在使用期间保持页面驻留，便于设备直接搬运。“锁页”不是给张量加互斥锁，也不会阻止应用主动改写它。普通内存参与传输时，运行时可能先复制到内部的锁页缓冲，再发起设备搬运。

假如每批都先把 64 MiB 普通内存复制到新建的锁页缓冲，再发往 GPU，就在 H2D 之外多做了一次 64 MiB 的主机复制。复用已有锁页缓冲可以省去反复分配和锁页，让 CPU 直接准备下一批输入。异步调用返回后，这块输入仍须保持不变，直到复制结束。[^execution]

### 5.1.3 stream、event 与完成顺序

GPU 可以接收多项尚未完成的工作。CUDA 用 **stream（流）**表示一串按顺序执行的任务，其中既可以有 kernel，也可以有内存复制。同一 stream 中先提交 H2D，再提交读取该输入的 kernel，可以保持所需的先后关系。CPU 不必在每两项之间都停下来等待。

不同 stream 之间则不能仅靠 CPU 的提交先后来保证数据依赖。假设复制在 stream A 上，计算在 stream B 上，需要在 A 的复制之后记录一个 **event（事件）**，再让 B 等待这个事件，随后执行计算。这里等待的是 B 中的后续设备工作，CPU 仍可继续运行。event 表示流推进到指定位置；创建一个 event 对象本身，不表示任何数据已经就绪。默认 stream 还有随配置变化的同步规则，分析例子时应明确使用哪种流。[^execution]

CPU 要使用异步 D2H 的结果时，也必须等待相应复制完成。可以等待结果对应的事件或 stream；等待整个设备通常会把无关任务也纳入等待范围。调试时全设备同步容易理解，若每个小算子后都这样做，就会阻止 CPU 提前提交后续工作。

缓冲何时可以复用，要看谁还在使用它。

| 缓冲 | 什么时候才可安全改写或读取 |
| --- | --- |
| 异步 H2D 使用的主机源缓冲 | 复制读取结束后，CPU 才可改写 |
| GPU 输入缓冲 | 所有使用它的设备工作结束后，才可覆盖 |
| 异步 D2H 使用的设备源缓冲 | 复制读取结束后，设备才可覆盖 |
| D2H 的主机目标缓冲 | 复制完成后，CPU 才可读取结果 |

异步提交与同时执行是两件事。即使使用两个 stream，同一份输入仍要先复制再计算；不同批次的复制和计算有机会重叠，但还要有可用的复制引擎、足够缓冲和带宽。多建几个 stream 不能提高链路本身的带宽，也不能取消数据依赖。5.3 节会用双缓冲把这些条件具体算出来。

### 5.1.4 怎样读时间线和测量时间

先用一组教学时间把各阶段分开：输入已在主机准备好，相关主机调用合计占用 CPU 3 μs；H2D 用 8 μs，kernel 用 20 μs，D2H 用 4 μs。为便于手算，另假定第一项设备工作在 3 μs 时开始，设备上的三项工作依次执行，中间没有额外间隙。

| 执行者 | 时间区间 | 正在做什么 |
| --- | --- | --- |
| CPU | 0–3 μs | 依次提交复制、kernel 和结果回传 |
| 复制引擎 | 3–11 μs | H2D，传入输入 |
| GPU 计算单元 | 11–31 μs | 执行 kernel |
| 复制引擎 | 31–35 μs | D2H，传回结果 |
| CPU | 35 μs 之后 | 确认回传完成，使用结果 |

这次调用中，CPU 提交占用 3 μs，kernel 执行占用 20 μs，从开始提交到结果可用则是 35 μs。CPU 在提交后还可以做其他工作；如果马上需要结果，就必须等待。真实运行中，GPU 也可能在 CPU 提交完所有任务之前就开始执行，所以这张表是一种明确给定的时序，不是所有程序都按四项时间简单相加。

用 CPU 时钟只包住异步 kernel 调用，通常测到的是提交经过的时间。若要测“从发起到结果完成”，应在开始前排除不属于本次测量的未完成工作，在结束计时前等待本次结果。CUDA event 则可在设备时间线上标出起止位置，测量其间经过的时间；若中间包含复制、等待或其他任务，所得时间也会包含它们，不能都称为纯 kernel 时间。

性能分析工具可以同时显示 CPU API 调用、GPU kernel、内存复制及它们的关联。读图时，先找输入何时就绪、计算何时开始、结果何时可用，再观察空隙。一次 API 调用到 kernel 开始之间的间隔可能包含排队或依赖等待，不能全部叫作 launch 开销。多个 stream 有重叠时，各 kernel 时长之和也不等于程序的墙钟时间。

如果首次调用花 100 ms 编译，随后每次执行 1 ms，运行一次需要 101 ms，运行 100 次则共需 200 ms，平均每次 2 ms。继续复用，平均时间才逐渐接近 1 ms。首次执行与长期重复执行回答不同的问题；输入已在设备上的 kernel 时间，又只覆盖了用户等待的一部分。

> **随文练习：读一次执行。** 按上表分别计算提交时间、kernel 时间和结果可用时间。若 kernel 缩短到 5 μs，其他阶段和顺序不变，结果何时可用？若下一批输入与本批无关，哪一段 H2D 有机会与本批计算重叠，需要额外保留哪份输入？前一问结果为 20 μs；后一问还需给定缓冲与硬件条件，不能只凭“异步”二字计算收益。

有了这张时间线，后续优化便有了明确对象：分块减少或重新组织设备访存，融合改变内核边界和中间结果，流水调整不同批次或数据块的开始时间，运行时则减少重复准备和提交。下面先从一个矩阵乘内部的数据访问开始。

## 5.2 单算子：分块、布局与实际访存

### 5.2.1 矩阵形状与重复读取

先只看一支 FFN 投影：$C=AW$，其中 A 为 $[1024,4096]$，W 为 $[4096,12288]$。一次乘加计两个 FLOPs，总工作量为：

$$
2MKN=2\times1024\times4096\times12288\approx103\ \text{GFLOPs}.
$$

如果 A 与 W 各读取一次，C 写回一次，BF16 数据需要经过接口的总量为：

$$
2(MK+KN+MN)\ \text{bytes}=(8+96+24)\ \text{MiB}=128\ \text{MiB}.
$$

MiB 按 $2^{20}$ bytes 换算。128 MiB 中，权重占 96 MiB，是输入的 12 倍。若能把一次权重读取用于全部 1024 行输入，复用就很充分；若每处理一小组行就重新读取权重，访问量很快会超过这个数。[^tiles]

考虑最直接的循环：

```python
for i in range(M):
    for j in range(N):
        acc = 0.0
        for k in range(K):
            acc += A[i, k] * W[k, j]
        C[i, j] = acc
```

计算相邻的两个输出 C[i,j] 与 C[i,j+1] 时，程序再次遍历同一行 A。计算下一行输出时，又会使用相同权重 W。循环中出现了很多相同地址，能否避免从较远存储重新取数，取决于缓存、访问顺序与工作集大小。

如果 W 按行连续存储，内层 k 循环访问 W[k,j] 时跨越整行，地址之间相隔 N 个元素。换成 i、k、j 的顺序，内层就连续读取 W[k,:]，同时把 A[i,k] 复用于多个输出。数学乘加次数相同，实际缓存行为可能明显不同。不过，简单交换循环也可能把原来只写一次的 C 变成反复读改写；最终还要看编译器将哪些值保留在寄存器里。

例如两组线程块都需要同一份权重，源码中会出现两次读取。若第二次由 L2 提供，显存只需供数一次，L2 却仍需服务两次请求。于是同一个程序可以同时受到 L2 和显存带宽约束。下面先数工作缓冲向下一层请求的数据，再观察这些请求中有多少真正到达显存。

### 5.2.2 容量约束下的分块复用

分块把一次过大的计算拆成能在局部存储中完成的片段。每次保留一个 $m\times n$ 的输出块，沿 K 维按 k 个元素推进；当前 A 块为 $m\times k$，W 块为 $k\times n$。两个输入块中的元素可参与多次乘加，输出累加器在整个 K 归约结束前保持存活。

假设输入是 BF16、累加器是 FP32，不采用双缓冲，三块数据需要的活动容量为：

$$
S_{\mathrm{active}}=2mk+2kn+4mn\quad\text{bytes}.
$$

这一写法比统一用一个元素宽度更接近实际问题：累加器通常比输入宽。若再为下一轮 A/W 预留一组搬运槽，输入块容量还要增加一次；地址、对齐、流水暂存等资源也需要另列。

把归约块宽固定为 $k=32$。再假设输入块不在不同输出块之间复用、输出只在归约结束后写回一次，工作缓冲与下一层之间的访问量为：

$$
V=2MK\frac{N}{n}+2KN\frac{M}{m}+2MN.
$$

A 被多少组列块使用，就读多少遍；W 被多少组行块使用，就读多少遍。在当前整除形状下，可以得到三个候选：

| 输出块 | 活动容量 | 工作缓冲与下一层的访问量 | 算术强度 |
| --- | ---: | ---: | ---: |
| $32\times32$ | 8 KiB | 6168 MiB | 15.9 FLOP/byte |
| $64\times64$ | 24 KiB | 3096 MiB | 31.7 FLOP/byte |
| $128\times128$ | 80 KiB | 1560 MiB | 63.0 FLOP/byte |

取 64×64 输出块，N 方向有 $12288/64=192$ 个块，8 MiB 的输入 A 因而被扫描 192 次，共 1536 MiB。M 方向有 $1024/64=16$ 个块，96 MiB 的权重被扫描 16 次，又是 1536 MiB。再加 24 MiB 输出，合计 3096 MiB。

改成 128×128 后，输入与权重的扫描次数分别降到 96 次和 8 次，访问量变为 $768+768+24=1560$ MiB。矩阵乘的约 103 GFLOPs 没变，访问量却接近减半；代价是活动空间从 24 KiB 增到 80 KiB，扩大约 3.3 倍。

假设某一级可用存储只有 96 KiB，并暂不考虑其他资源，24 KiB 的块可以同时放四份，80 KiB 的块只能放一份。更大的块提高了块内复用，却可能减少并行工作。下一步应测量的，正是访问减少能否抵消并发下降。

80 KiB 的方案仍搬动 1560 MiB，约为 128 MiB 的 12 倍，说明扩大一个 tile 尚未用尽所有复用机会。若再利用其他层级保存权重，或改变输出块的遍历次序，重读还可能减少。Orojenesis 等研究正是把存储容量与执行映射一起考虑，寻找不同容量下更合适的复用方式。[^tiles]

这一原则适用于不同设备，具体工作分配则不同。NVIDIA GPU 通常将输出 tile 分配给线程块，由 warp 协作加载并调用矩阵指令；昇腾要同时安排 Cube、Vector 及它们之间的局部缓冲和搬运；Apple GPU 则以 threadgroup、SIMD-group 与后端支持的存储和同步机制组织计算。相同 tile 在不同后端上未必具有相同资源占用。尾部不整齐时，还要增加掩码或补齐：有效元素字节与实际执行的完整 tile 工作量应分别计算。

### 5.2.3 布局与归约的并行代价

容量足够，也可能因为访问集中而无法持续供数。取一个 32×32 的 FP32 暂存块，假设有 32 个 bank，每个 bank 每轮只能服务一个 32-bit 字，bank 号等于字地址对 32 取模。32 个 lane 同时读一行时，请求落到 32 个 bank；同时读一列时，如果行跨度为 32 个字，就会集中到同一个 bank 的不同地址，需要 32 轮。

每行末尾多放一个 padding 字，行跨度变成 33，列访问就分散到不同 bank。容量从 4096 bytes 增为 4224 bytes，只多约 3.1%，同一列请求却从 32 轮缩到 1 轮。两种布局都读取 32 个有效字，变化在于这些字能否同时被提供。整段程序的收益取决于这种列访问占了多少时间。

归约带来另一种并行问题。RMSNorm 对一行 x 计算平方和，用其均值和一个稳定项得到缩放因子，再将因子应用到整行。对于 $[M,4096]$ 输入，一组处理一行时，M 决定同时可安排多少组，而 4096 决定组内工作量。decode 只有一行时，即使每行计算已经紧凑，也可能没有足够的组使用整台设备。

将每行拆成八组，每组只处理 512 个元素，第一阶段的工作组数便从 1024 增到 8192。但每组只有局部平方和：$1024\times8$ 个 FP32 partial 需要 32 KiB，合并后每行一个 FP32 缩放因子再占 4 KiB。随后各组重新读入原始数据，才能用最终因子完成归一化。

这份 BF16 输入本身占 8 MiB，因此重读就增加了 8 MiB；加上 partial 和缩放因子的交接，额外访问约为 8.1 MiB。原先按求和、归一化各读一遍输入，再写一次输出计，共 $8+8+8=24$ MiB；拆分后增至约 32.1 MiB，启动也从一次变成三次。八倍的第一阶段工作组数，换来了约三分之一的额外访问和两次启动。行数少时可能值得，原来已经有足够并行度时就未必。[^reduction]

宽行还可能让单组实现用完寄存器，把临时量写入较慢存储。拆分后每组保留的 FP32 行片段从 16 KiB 缩到 2 KiB，因而也可能避免溢出。若测得加速，需要据生成代码判断收益来自更多并行，还是更少临时写回。CPU 上同样如此：M2 Max 的循环对照中，仅改成连续访问就能快约 5–9 倍，继续细分块却可能更慢。分块是否有益，取决于它改变了原来哪一项限制。[^exp1]

> **实验 5-1 · 延伸：矩阵分块与访存计数**
>
> 先用小矩阵比较 i-j-k 与 i-k-j 循环，再加入两种块大小。分别报告数学工作量、源码数组访问与实测时间，解释连续访问为什么可能比“更少源码字节”重要。归约选做保持行宽改变行数，再增加行宽，比较一组一行和拆分方案的辅助缓冲、启动与误差。配套记录可用于无 GPU 的分析路径。

## 5.3 算子链：融合、缓冲与流水

### 5.3.1 中间张量与融合边界

回到 FFN。计算 $Z=\operatorname{SiLU}(G)\odot U$，最直接的做法是先生成 $T=\operatorname{SiLU}(G)$，再计算 $Z=T\odot U$。G、U、T、Z 在主例中各占 24 MiB。

分开执行时，SiLU 读取 G、写出 T，乘法读取 T 与 U、写出 Z，主张量接口总访问为 120 MiB。融合后，一个程序读取 G 与 U，在局部计算 SiLU 和乘法，最终写出 Z，只需 72 MiB。消除 T 的一次写回和一次读取，节省 48 MiB。

从 120 MiB 降到 72 MiB，读写减少 40%。如果这段工作完全受同一接口带宽限制，且有效带宽不变，时间可缩短到原来的 60%，即加速约 1.7 倍。这给出了第一个性能预期；资源占用和实际缓存行为会决定能接近它多少。

继续加入固定尺度的 1-byte cast：Z 的 24 MiB 读入和 12 MiB 写出使独立执行增加 36 MiB，合计 156 MiB。三步完全融合时，只需读 G、U 各 24 MiB，写量化结果 12 MiB，共 60 MiB，省下 96 MiB。

省下 96 MiB 访问并不意味着峰值容量也减少 96 MiB。假设每步先分配输出、再释放已经用完的输入，独立执行在 SiLU 阶段同时保留 G、U、T，共 72 MiB；完全融合同时保留 G、U 和 12 MiB 最终输出，共 60 MiB。峰值只少 12 MiB，而读写少了 96 MiB，原因是同一份中间量既占空间，又会被写出和读回。动态量化还需计算尺度，后面再讨论它如何改变融合边界。[^fusion]

融合收益可以写成一个便于检查的条件：减少的中间交接与启动成本，应超过新增重读、资源占用和同步成本。后一半同样重要。把两个矩阵乘与中间激活全部塞进一个程序，可能要求更小 tile 或更多局部状态，使宽权重反复读取。一个最快的独立 GEMM 与一个最快的逐元素算子，也未必构成最快的融合组合。

在 RTX PRO 6000 的激活链对照中，融合使耗时从约 14.2 μs 降到 7.7 μs，约快 1.8 倍。这与减少一次 24 MiB 中间量写回和重读的方向一致。要把收益继续扩大到整个 FFN，还需要看前后的矩阵乘占了多少时间，以及融合有没有改变它们的块大小。[^exp2]

> **实验 5-2 · 核心：融合的流量与资源占用**
>
> 对 G、U 各 24 MiB 的激活链，先复算独立执行的 120 MiB 与融合后的 72 MiB。再画出分配、最后消费和释放时刻，求所选分配策略的峰值容量。改变 tile 大小或加入一个重排缓冲，判断省下的读写是否仍值得。最后阅读配套实测，区分中间张量容量、接口流量、实际显存计数与时间。

### 5.3.2 布局交接、缓冲寿命与双缓冲

相邻两个算子可能喜欢不同的数据布局。生产者沿行生成最方便，消费者却希望按列或特定块顺序读取。如果先物化完整的 24 MiB 输出，再生成一份重排结果，至少要增加 24 MiB 读和 24 MiB 写。可以比较三种方案：接受共同布局、独立重排、由生产者直接生成消费方布局。最后一种也可能增加地址计算或降低写入效率，需要把生产与消费一起计时。

即使布局相同，缓冲也不能过早复用。设搬运器将块 0 放入槽 A，计算单元开始读取它；与此同时，可以把块 1 搬入槽 B。当计算切换到 B 后，A 才能用于后续块。槽 A 的最后一个读取者尚未完成时，提前覆盖会造成数据竞争。双缓冲的关键是把“下一块搬入”与“当前块计算”重叠，同时保持槽的使用顺序。

如果每块搬运耗时 $t_m$、计算耗时 $t_c$，串行执行 n 块需要 $n(t_m+t_c)$。在资源互不争用、同步开销忽略且缓冲足够时，两阶段流水需要：

$$
t_m+(n-1)\max(t_m,t_c)+t_c.
$$

首块填充与末块排空仍在。若搬运和计算共享受限带宽，这个理想式还要修正。NVIDIA 的异步复制与 barrier、昇腾的搬运和事件机制、Metal 的命令依赖与线程组同步分别提供实现手段，具体完成语义与作用域以所用后端为准。

例如每块搬运 2 μs、计算 3 μs，四块串行执行要 $4\times(2+3)=20$ μs。使用两个输入槽后，0–2 μs 搬入块 0，2–5 μs 计算块 0；块 1 的搬运可放在 2–4 μs，与计算重叠。按此推进，四块在 14 μs 时完成，时间减少 30%。

![图 5-2 双缓冲怎样缩短四块数据的完成时间](ch05/figure-5-2-fusion-buffer.svg)

*图 5-2：四块数据由串行执行的 20 μs 缩短到双缓冲的 14 μs。假设每块搬运 2 μs、计算 3 μs，两种资源可并行且不争用带宽，忽略同步开销。颜色区分两个输入槽；同一槽在计算消费完成后才能再次装入数据。*

两个槽已将完成时间降到 $2+4\times3=14$ μs：首块搬运后，计算资源连续忙了 12 μs。即使继续增加输入槽，也无法在计算速度不变时突破这一下限。相反，若槽太少而且访问顺序不匹配，等待就会重新出现。三个排队的 16 KiB 块需要 48 KiB，再加 32 KiB 重排空间，总共 80 KiB，超过 64 KiB 预算 16 KiB。至少要让一个块的生产推迟，或者改变布局，才能避免覆盖尚未消费的数据。[^buffer]

5.1 节的 H2D 也可以采用双缓冲：GPU 计算当前批时，把下一批输入传到另一份设备缓冲。复制流在传输后记录事件，计算流等待该事件再使用新输入；计算结束也要留下完成通知，防止复制流过早覆盖旧输入。主机源缓冲与设备输入缓冲的复用时刻不同，应分别管理。第十章的训练输入和卸载会继续使用这些规则。

### 5.3.3 FlashAttention：分块与在线 Softmax

普通注意力可以写成 $S=QK^\mathsf{T}/\sqrt d$、$P=\operatorname{softmax}(S)$、$O=PV$。问题在于 S 与 P 的尺寸都随长度平方增长。

取一个 query head，长度 $L=8192$、$d=128$，先考虑不加掩码的完整注意力。Q、K、V、O 各占 2 MiB；若 S、P 各完整保存为 FP32，每份占 256 MiB，是单份 Q 的 128 倍。两份中间矩阵各写一次、读一次，就产生 1 GiB 访问，而四份输入输出各经过一次只有 8 MiB。这里最值得消除的是平方增长的中间结果。[^attention]

分块能避免物化完整 S，但 Softmax 的分母依赖整行分数。看过前一块时，还不知道后一块是否有更大的值，能否提前丢弃旧分数？可以，只要保留足以修正旧结果的状态。

对每个 query 行，维护已见最大分数 m、按 m 缩放的指数和 l，以及尚未除以分母的输出向量 U。遇到新块分数 s 和对应 V 后，令：

$$
m'=\max(m,\max(s)),\qquad r=\exp(m-m'),\qquad p=\exp(s-m'),
$$

$$
l'=rl+\sum_j p_j,\qquad U'=rU+\sum_jp_jV_j.
$$

最后输出 $O=U/l$。新最大值增大时，旧指数基准改变，所以旧分母与旧输出都乘以不超过 1 的 r。第一块可以直接初始化状态；带掩码时，要正确处理没有有效元素的块，避免对全为负无穷的分数做无效相减。

一个两元素例子足以检查缩放方向。分数为 $[0,\ln2]$，值为 $[1,3]$。第一块得到 $m=0,l=1,U=1$；第二块令 $m'=\ln2,r=1/2$，更新为 $l'=1.5,U'=3.5$，输出 $7/3$。如果旧结果反而乘以 2，答案就错了。

在线状态让前一块分数不再需要保留。训练反向阶段仍需要相关信息，但可以保存较小的统计量，并在反向时重新计算局部分数和概率，以额外计算换取避免巨大的中间矩阵驻留。这不改变注意力的数学定义，浮点运算顺序不同则仍可能产生数值差异。

现在重新选择 tile。设有一个 128 KiB 的抽象快速缓冲，驻留 a 行 Q、FP32 输出累加器与三个逐行统计向量；K/V 顺序使用一个共享槽，分数与概率也复用一个槽。容量需求为：

$$
2ad+2bd+4ab+4ad+12a\le131072.
$$

把 d=128 代入，在给定的 128 KiB 快速缓冲中，为每种 b 选择能容纳的最大 a，可得：

| K/V 块行数 b | Q 块行数 a | K/V 扫描次数 | 指定接口访问 | 块对更新次数 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 166 | 50 | 204 MiB | 409600 |
| 64 | 110 | 75 | 304 MiB | 9600 |
| 128 | 76 | 108 | 436 MiB | 6912 |

把 K/V 块从 64 行缩到 1 行，Q 块可以从 110 行增到 166 行，整份 K/V 的扫描次数从 75 次降到 50 次。访问量从 304 MiB 降到 204 MiB，少约三分之一；块对更新却从 9600 次增至 409600 次，约为原来的 43 倍。

因此，选择 1 行块是否有利，取决于节省的 100 MiB 访问能否抵消新增的循环、指数更新与输出缩放。如果再为 K/V 增加预取槽，还要从同一份 128 KiB 预算中拿出空间，Q 块会缩小。更少 IO、较少更新和更多重叠，正在竞争同一份局部容量。

FlashAttention-2 继续调整工作划分与并行安排，减少非矩阵操作和工作组间交接；FlashAttention-3 进一步利用支持的硬件异步路径，让搬运、矩阵计算与 Softmax 工作交错推进。减少中间 IO 后，下一项限制可能转成非矩阵计算、寄存器、同步或流水供给，优化并不会在“少写一次”处结束。[^fa]

这一思路在实际内核中能带来很大变化。8192-token 单头注意力的 RTX 对照中，数学后端约需 2.6 ms，Flash 后端约需 80 μs，约快 33 倍；新增分配峰值从约 850 MiB 降到 22 MiB。避免完整分数与概率矩阵，使容量与时间一起下降。接下来要判断的是：减少 IO 后，Softmax、矩阵计算和流水中的哪一项开始限制执行。[^exp3]

> **实验 5-3 · 延伸：分块 Softmax 与注意力 IO**
>
> 先复算两元素在线 Softmax，再用小张量比较一次算完与分块更新。随后逐项复算 128 KiB 的工作集，改变 b 和预取槽数，记录 K/V 重扫、输出缩放与容量。使用 GPU 记录时同时报告后端、掩码、精度与缓存条件；CPU 时间只用于验证程序行为。

## 5.4 编译器：表达、变换与选择

### 5.4.1 AKG：为什么需要跨算子选择

前面每一步都能手工完成：换循环、定块大小、搬入局部存储，再把下一步计算放到合适的位置。但模型包含很多形状和算子组合，硬件又有多级存储与不同计算单元。单个内核调好之后，中间张量仍可能在算子边界反复写回，组合维护很快成为新的工作。

我参与的 AKG 工作把这类选择交给编译器：从张量表达式出发，经多面体表示组织循环、分块和分层融合，同时安排片上存储与数据搬运，再生成硬件代码并调优。下面仍沿 FFN 的矩阵乘接激活来理解这条编译路径。[^akg]

三个相邻算子有两处边界，各自可以保留或消除，已经有四种划分。链长增到十个算子，就有 $2^9=512$ 种。一般地，k 个算子有 $2^{k-1}$ 种相邻边界划分，还未加入块大小和布局。手工写出某一种并不难，为不断变化的形状和硬件维护这些组合才是困难所在。编译器需要从依赖和容量约束中排除不可行组合，再比较剩余选择。

kernel 数也不能代替执行时间。Korch 的一个历史子图中，三个 kernel 分别用 38.7、24.2、28.2 μs，合计约 91 μs；重新拆分和组合后，四个 kernel 分别用 7.6、18.4、7.5、35.7 μs，合计约 69 μs。启动数增加三分之一，总时间反而缩短约四分之一。边界应当顺应计算与访存特点，单纯最小化 kernel 数会错过这样的方案。[^korch]

![图 5-3 融合边界怎样改变中间读写](ch05/figure-5-3-boundaries.svg)

*图 5-3：同一条 SiLU—乘法—cast 链，每少物化一个 24 MiB 中间量，就少一次写回和一次读取，即 48 MiB。G、U 各为 $[1024,12288]$ BF16，最终输出为 1 byte/元素，尺度已给定；保留中间舍入，不含动态尺度归约和投影。*

### 5.4.2 Polyhedral Compilation：用循环变换表达优化

理解多面体编译，可以先从循环程序开始。我们暂时不讨论变换矩阵，直接看每一步计算怎样移动。

设 $Y=\operatorname{SiLU}(AW)$。原始程序有两段：第一段完成整个矩阵乘，第二段遍历完整 C 并计算激活。

```python
for i in range(M):
    for j in range(N):
        acc = 0.0
        for k in range(K):
            acc += A[i, k] * W[k, j]
        C[i, j] = acc

for i in range(M):
    for j in range(N):
        Y[i, j] = silu(C[i, j])
```

先保持运算内容不变，把 i、j 分别拆成“第几个块”和“块内第几个元素”。Halide／TVM 风格的 schedule 将这个动作称为 split；同时拆两个维度，就形成常见的 tile。比如将 1024 行拆成 16 个 64 行块，逻辑关系是 $i=64i_o+i_i$。不能整除时，最后一个块需要边界检查。

原来按一行接一行访问，现在希望一个输出 tile 连续完成。于是把循环排成外层块坐标、内层块内坐标，这就是 reorder。算法没有要求不同输出元素之间必须按原行序完成；只要不破坏各输出自身的归约和数据依赖，就可以调整它们的遍历次序。

接着把缓存放进合适的循环层级。输出 tile 的累加器在块开始时创建，在全部 k 工作结束后释放。每次取一个 A tile 和 W tile，在局部复用。下面是概念伪代码，`load_tile`、`matmul_accumulate` 表示成块搬运和计算，并非某一版本可直接执行的 API。

```python
for io in range(ceil_div(M, BM)):
    for jo in range(ceil_div(N, BN)):
        acc = zeros_fp32(BM, BN)
        for ko in range(ceil_div(K, BK)):
            a = load_tile(A, io, ko, BM, BK)  # 含尾部掩码
            w = load_tile(W, ko, jo, BK, BN)
            matmul_accumulate(acc, a, w)
        c = round_to_bf16(acc)               # 若原路径在此舍入
        store_tile(Y, io, jo, silu(c))
```

取 BM=BN=64，当前输出块只有 4096 个元素，FP32 累加器占 16 KiB。完整 C 则有 $1024\times12288$ 个 BF16 元素，占 24 MiB。让激活紧跟当前 tile 完成，交接对象就从完整的 24 MiB 矩阵缩为局部的 4096 个结果，省去 48 MiB 完整矩阵读写。

代码仍保留 `round_to_bf16`：原程序先将 acc 舍入为 BF16 再做激活，融合后也应保持这个顺序。消除存储位置，并不自动允许消除那次舍入。

Halide 将算法与调度分开，`compute_at` 可以指定在消费者的哪个循环层级计算生产者。TVM 也能把生产者拉近消费位置，或让消费者紧跟一片生产结果。放在最外层，可能生成整个中间矩阵；放在 tile 层，就只生成当前需要的一片，但也可能让其他 tile 重复计算。计算位置因而同时决定中间容量与重算次数。[^schedule]

| 调度动作 | 读循环时怎样理解 | 需要检查什么 |
| --- | --- | --- |
| split／tile | 一长段循环拆成外层块和块内循环 | 尾部、块容量和冗余工作 |
| reorder | 改变循环嵌套顺序 | 读写依赖与访问局部性 |
| 计算位置 | 在需要某片结果的位置生成或消费它 | 重算次数、覆盖范围与依赖 |
| 局部缓存 | 把一片输入或中间量放入较近存储 | 容量、生命周期、同步与布局 |
| 循环 fuse | 将多个迭代维合成一个遍历维度 | 索引恢复、并行分配与依赖 |
| 算子融合 | 将多个数学阶段放进共同执行边界 | 中间量是否可消除、数值是否改变 |

循环 fuse 与算子融合不是同一个动作。把二维输出坐标摊平成一维工作编号，并不会自动把 SiLU 与 GEMM 合在一起；反过来，算子融合也可能保留多层循环。

现在再看 **Polyhedral Compilation，多面体编译**。它为规则循环中的每次计算建立可分析的表示：循环变量在哪些范围取值，每一步读写哪些数组元素，哪些步骤因读写同一元素而必须保持先后。规则边界与访问关系可以用线性约束表示，这也是“多面体”这一名称的来源。对程序员而言，关键结果是编译器能够系统地推导依赖和执行顺序，而不只对源码做局部替换。

在矩阵乘例子里，编译器看见 C[i,j] 的累加沿 k 推进；激活必须等所需 C 完成；不同 i、j 输出又提供并行空间。它可以用这些关系组织合法的重排、分块和融合，并推导搬运与缓冲所需的区域。图 5-4 沿五个步骤展示完整矩阵怎样变成 tile 内的交接。

![图 5-4 从循环变换理解多面体编译](ch05/figure-5-4-polyhedral.svg)

*图 5-4：五个步骤从完整中间矩阵走向 tile 内交接。矩阵尺寸为 M=1024、K=4096、N=12288，输出块为 64×64、归约块为 32；A/W 使用 BF16，累加器使用 FP32。每个输出块完成全部 128 个归约块后才能激活，融合仍保留原路径的中间舍入。*

AKG 的技术工作超出了给几个 schedule 原语选参数。论文将张量表达降低到多面体 IR，使用调度器组织循环；把融合启发式与分块结合，在不同层级安排局部交接；进一步扩展表示来支持复杂 tile 与架构相关变换。存储管理据此确定需要搬入的区域和片上缓冲，代码生成阶段补上不适合直接放入多面体模型的处理，最后由调优选择具体参数。对论文目标 NPU，卷积向适配矩阵单元的计算形式转换也是其中一项专门工作。[^akg]

Halide／TVM 的 schedule 使这些选择可以被显式表达，AKG 的多面体表示与调度则把依赖、分块和存储区域联结起来。64×64 输出块需要的 16 KiB 累加器，应当活到最后一个 k 块完成；8 KiB 的当前 A/W 输入块则可以在下一次迭代前替换。编译器只有看见这两种不同的寿命，才能同时安排复用与搬运。

我早期做 FPGA 系统时，也曾希望靠接口库简化编程。但 HLS 生成的执行路径达不到所需流水，后来必须继续分析可用原语与读写依赖，通过代码变换改变执行方式。接口能表达计算，生成的循环和数据通路才决定它怎样使用硬件。[^author]

映射到 CUDA、Triton、Ascend C 或 Metal 时，这些动作仍然存在，只是显式控制范围不同。CUDA 可以直接组织线程、共享内存与同步；Triton 以成块张量程序表达较多工作分配；Ascend C 要面对 Cube／Vector 与局部搬运；Metal 通过线程组和平台支持的 SIMD-group 原语实现计算。高层代码少写几行，不意味着底层少做几次工作，判断仍要落到生成代码与实际执行。

### 5.4.3 变换合法性与数值正确性

一个输出尚未完成归约时，能否先做激活？取两个部分和 1 与 −1，先相加得到 0，SiLU(0)=0；分别做 SiLU 再相加约为 0.4621。结果明显不同。这是运算依赖和代数性质的问题，不是计时噪声，也无法通过调整 tile 大小修复。

在线 Softmax 能按块合并，是因为保留了 m、l、U 这些足够的状态，并在最大值变化时修正旧累加结果。只保留每块已经归一化的输出，再把它们相加，就丢失了不同块的权重比例。RedFuser 等研究进一步探索由归约关系推导可合并的局部状态；能合并哪些状态，必须从运算本身证明。[^numerics]

浮点又带来另一层约束。加法在实数中可结合，在有限精度中一般不能任意换顺序。RMSNorm 拆分行归约后，局部和的组合方式改变，可能在误差容限内仍得到不同位模式。相同输入重复运行一致，不代表改变 batch、调度或后端后也逐位一致。

量化融合尤其容易隐去语义变化。若尺度由整行最大绝对值决定，在读取完整行之前，前缀尺度还不是最终尺度。用它提前量化，再试图补偿结果，可能因舍入不可逆而失去等价性。

**例：尺度变化无法恢复已丢失的精度。** 一行 256 项分成两个 128 项块，每块首项分别为 1 和 10，其余为零；点积权重只有第一项为 1。采用最大有限值 448 的 E4M3FN 格式，按整行最大值 10 量化时，第一项缩放为 44.8，再舍入为可表示的 44，反量化结果为 $44\times10/448=55/56$。按前缀处理时，第一块只见到最大值 1，第一项可量化为 448，反量化贡献为 1。后面见到最大值 10 后，即使正确调整旧累加器尺度，也不能把此前未发生的舍入补回来，两条路径最终分别为 $55/56$ 和 1。把包含 10 的块提前，这个反例的差异又会消失：执行顺序已经改变了数值语义。

两种输出相差 $1/56$，约 1.8%。这是舍入顺序造成的系统差异，即使后续计算没有计时或调度变化也会存在。能否接受这项变换，要由模型允许的误差决定；只证明实数公式可重排还不够。[^numerics]

即使保留相同数值规则，融合也可能增加访问。考虑一个 $[4096,4096]$ 的 FP16 输入 A，大小为 32 MiB，量化为 FP8 后为 16 MiB；它乘以 $[4096,1536]$ 的 FP8 权重，输出 12 MiB。若输出列按 128 分块，共有 12 个列块，每个列块都要读一次 A，并假设它们不共享输入缓存。

先独立量化，读 A 的 32 MiB，写量化值的 16 MiB，随后 12 个列块共读 $12\times16=192$ MiB，这部分合计 240 MiB。把量化融入矩阵乘，先读 32 MiB 求整行尺度，再让每个列块读原来的宽输入，共 $32+12\times32=416$ MiB。

输出行也按 128 分块，4096 行形成 32 个行块。每个行块读取一遍 6 MiB 权重，加上 12 MiB 输出写回，两条路径共有的访问为 $32\times6+12=204$ MiB。因此总量分别是 $240+204=444$ MiB 和 $416+204=620$ MiB。融合省去一份 16 MiB 量化结果的写出，却让 12 个消费者反复读取更宽的输入，最终多读约 40%。如果把 1536 个输出列合成一个块，两条路径的这项差额才消失；但更大输出块又需要更多局部空间。于是，下一步需要比较块容量和缓存复用，而不只是检查中间张量是否消失。[^numerics]

框架还可能自动改变边界。例如 SiLU、乘法与量化在源码中分开表达，编译器仍可将它们合成一个 kernel。关闭 vLLM 的某个专门融合 pass 后，Inductor 也可能继续融合同一段表达。因而比较两个方案时，必须先看它们最终执行了什么；否则所谓“融合前后”，可能实际运行的是同一种组合。[^exp4]

### 5.4.4 成本估计、自动调优与实测反馈

变换是否合法解决“能否执行”，成本模型解决“值得先试哪个”。一个模型可以根据字节、块数、矩阵指令利用率与资源预算筛选候选，但缓存命中、寄存器溢出和并发争用通常还需要实际反馈。

同一转置程序的一组 RTX 输入上，16×16 块约需 7.9 μs，32×32 块约需 2.9 μs，快约 2.7 倍；继续扩大块却没有改善。块的每个维度增大一倍，元素数扩大四倍，线程协作、共享内存和指令组织都会变化。成本模型可以据此减少搜索范围，但最终仍要看生成代码是否实现了预期复用。[^exp5]

> **实验 5-5 · 延伸：编译变换与硬件代码**
>
> 对照 5.4.2 的循环动作，阅读同一程序的生成表示。改变步长或块大小，找出局部缓存、向量化、同步与边界处理的变化，再与配套时间对应。循环示例用于解释机制，实验中的转置程序用于检查实际后端行为。

自动调优可以在固定模板内搜索块大小，也可以改变调度结构。TVM 的 Ansor／MetaSchedule 已经使用真实硬件测量，不应把传统编译器描述成没有反馈。让 Agent 修改 schedule 或实现，扩大的是候选空间，同时也提高了编译、正确性检查和性能验证成本。

搜索先保留满足数值要求的候选，再测量它们的时间。但即使一个候选在平均分上更好，也可能不适合实际调用。设两个形状 A、B 的原耗时都是 10 μs，候选分别为 5 μs 和 20 μs。两个加速比是 2 与 0.5，算术平均为 1.25；两个形状各调用一次，总时间却从 20 μs 增到 25 μs。

![图 5-5 形状频数怎样改变优化收益](ch05/figure-5-5-feedback.svg)

*图 5-5：候选是否更快取决于形状 A 的调用占比。假设 A、B 原来各需 10 μs，候选分别需 5、20 μs，所有调用串行，不计额外分派和准备成本。A 占比超过 $2/3$ 才有总时间收益；标记点对应两种正文工作负载。*

如果 A 出现 100 次、B 只出现一次，原时间为 1010 μs，候选为 $100\times5+20=520$ μs，约快 1.9 倍。令 A 的调用占比为 p，候选平均时间就是 $5p+20(1-p)=20-15p$ μs；要小于原来的 10 μs，必须满足 $p>2/3$。图 5-5 的交点说明，优化方案的选择随负载组成改变，而不是由两个微基准加速比的平均数决定。

准备与搜索还会消耗时间。假设调优花费 10 分钟，部署后每次调用省 5 μs，需要 $600/(5\times10^{-6})=1.2\times10^8$ 次调用才能收回这段时间。每秒调用一万次时，约需 3.3 小时；每秒只有一百次，则约需 14 天。搜索找到更快实现只是第一步，还要看它是否会被足够频繁地使用。

搜索也可能没有收益。实验 5-6 的两轮共 12 次 Agent 调用没有找到新优化，多次提交实际上重复了已有代码。此时调优成本已经发生，稳态节省却为零，便不存在有限的回本次数。后文使用已有 schedule 候选检验完整请求，不依赖这两轮搜索获得新实现。[^exp6]

## 5.5 运行时：提交、重放与动态形状

### 5.5.1 主机提交与设备执行

5.1 节已经区分了主机提交、设备执行和结果完成。现在回到反复执行模型的情形：CPU 除了发起 kernel，还可能准备批次、检查形状、选择实现和更新元数据。如果设备算得很快，这些准备就可能跟不上。这里要判断哪些工作可以少做，哪些等待可以与其他工作重叠。

如果一个小算子只需几微秒，Python 调用、分派或主机调度就可能暴露在关键路径上。CPU 准备下一项工作的过程有时能与 GPU 当前计算重叠；只有没有被覆盖的部分才增加完成时间。因此，要把两条时间线放在一起，不能把每次 API 调用时长简单相加，也不能把 GPU 空隙都归因于 Python。

**例：减少主机工作与隐藏主机等待。** 设有 100 段执行，每段配置与设备计算均为 20 μs。严格串行时需要 4000 μs；如果下一段配置不依赖上一段结果，并且有足够缓冲，双阶段流水需要 $20+100\times20=2020$ μs。仅把设备计算缩短到 5 μs，流水时间变为 $100\times20+5=2005$ μs，改进不足 1%；配置也缩短到 5 μs，才降到 505 μs。设备变快之后，主机配置成为限制。[^host]

多步调度与异步输出分别针对这两个方向：前者让一些调度决定复用多步，后者将上一轮结果处理与下一轮设备计算重叠。普通自回归仍依赖上一步 token；有语法约束、可变接受长度或状态更新时，还要等相关结果就绪。预先安排工作不等于提前知道结果。

vLLM 早期版本通过进程划分与异步执行缓解主机侧开销，是这种问题的工程例子；一次版本更新同时改变多项机制时，整体收益不能自动拆成各项贡献。Ollama 的 Metal、CUDA、MLX 等后端也提供另一种对照：相同应用入口，可能落到不同的内核、内存管理和命令提交路径。跨平台对照需先固定模型、精度与任务，不能把不同量化的性能差异全部归给后端。[^runtime]

### 5.5.2 CUDA Graph 的捕获与重放

对于反复执行的相似工作，可以先记录设备任务和依赖，再重复提交这份执行图。CUDA Graph 减少的是重复组织与提交工作，并不自动删除每个 kernel 内的读写。

以实验 5-8 的 FFN 为例，三次普通执行有 18 次主机 kernel launch、18 个设备 kernel。图重放之后，主机改为 3 次 graph launch，设备仍执行 18 个 kernel。再融合激活链，设备才减少到 15 个。这个例子把“提交更少”与“设备工作改变”区分得很清楚。[^exp8]

捕获的图还带有执行条件。典型重放路径使用固定地址的缓冲；每次把新数据写入这些缓冲后，再按依赖启动执行。创建一个同形状的新张量对象，不会让图自动改为读取新地址。部分节点参数可以通过支持的更新机制调整，但这不等于任意动态程序都可以直接重放。

若上游直接写入图使用的固定缓冲，交接可以较简单；若输入来自另一份对象，常需额外复制。教学模型中，eager 的设备计算为 20 μs，暴露提交等待为 20 μs；图路径的重放与元数据准备共 5 μs。若 BF16 输入为 $[256,4096]$，复制载荷为 2 MiB，按源读加目标写计算接口字节为 4 MiB。在假定 2 TB/s 有效复制流量带宽下，增加约 2.1 μs，图路径共约 27.1 μs，仍低于 eager 的 40 μs。[^graph]

保持设备计算和主机等待不变，只把边界输入扩大到 2048 行，载荷增至 16 MiB，额外读写为 32 MiB，复制约需 16.8 μs，图路径变成约 41.8 μs，反而慢于 40 μs 的 eager。

图重放原本省了 $20-5=15$ μs 的提交与准备时间，因此额外复制必须少于 15 μs。按 2 TB/s 计，它最多容纳 30 MB 读写，即约 14.3 MiB 输入载荷。2 MiB 输入在这个门槛以内，16 MiB 则超过门槛。若生产者直接写入图的固定缓冲，额外复制消失，两种输入都能保住这项提交收益。这个比较隔离了边界复制成本，真实形状改变还会影响设备计算。

因此可以采用分段图：捕获重复性好、提交间隙明显的段，其他段保留 eager。vLLM 图分派、SGLang 分段捕获、FlashInfer plan/run 都围绕不同边界组织准备和执行，不能只凭“支持 CUDA Graph”判断所有形状都受益。

准备工作也不一定每层重做。如果 36 层使用同一种兼容计划，每层重建一次就做了 36 次相似准备；共享一份计划则只需一次。在 FlashInfer 的两组对照中，执行时间分别从约 2.0、2.4 ms 降到 0.72、0.75 ms，均约快 3 倍，kernel 数保持不变。收益来自减少重复规划。请求形状或元数据改变后，仍需更新相应内容。[^plan]

### 5.5.3 动态形状、分桶与特化摊销

LLM 的 token 行数、历史长度和专家负载都可能变化。一份通用程序可以处理多种形状，但会承担动态索引、掩码或较保守的调度。逐形状编译可以选择更合适的代码，却增加准备成本与工件数量。分桶位于两者之间：把实际形状补齐到少数代表规格，代价是冗余工作和更大的缓冲。

为公平比较，需要把实例寿命放进计算。令准备时间为 P，一组固定形状频数的执行时间为 T，该组重复 r 次，总预算是：

$$
T_{\mathrm{total}}=P+rT.
$$

考虑十次 FFN 调用组成的一组：8 次为 256 行，1 次为 1536 行，1 次为 2048 行，共 $8\times256+1536+2048=5632$ 行。分桶采用 512 和 2048 两个桶，实际执行 $8\times512+2048+2048=8192$ 行，多算约 45%。

假设通用、分桶、特化路径的有效矩阵处理率分别为 100、200、250 TFLOP/s，每行 FFN 有 $6HF$ 次浮点运算。通用路径处理真实的 5632 行，每组约需 17.0 ms；分桶虽然多算 45%，但处理率翻倍，每组仍只需约 12.4 ms；特化不补齐，每组约需 6.8 ms。再假设三种方案的一次性准备分别为 100、400、900 ms，就得到下表。[^specialization]

| 策略 | 一次性准备 | 每组十次调用 | 额外工作 |
| --- | ---: | ---: | --- |
| 通用 | 100 ms | 17.0 ms | 不补齐 |
| 分桶 | 400 ms | 12.4 ms | 小形状与 1536 行补齐 |
| 逐形状特化 | 900 ms | 6.8 ms | 准备三个工件 |

![图 5-6 准备成本与重复执行的交点](ch05/figure-5-6-specialization.svg)

*图 5-6：更快的稳态执行需要更多重复次数才能抵消准备成本。每组含 8 次 256 行、1 次 1536 行、1 次 2048 行 FFN；分桶补至 512／2048 行。有效处理率假设为 100／200／250 TFLOP/s，准备成本为 100／400／900 ms。曲线使用未舍入数值计算，不是编译器实测。*

分桶比通用多花 300 ms 准备，每组约省 $17.0-12.4=4.6$ ms，因此需要重复约 65 组才值得。特化比分桶多花 500 ms，每组再省约 5.6 ms，需要约 90 组。用未舍入数值求整数边界，1–64 组通用最省，65–89 组分桶最省，90 组起特化最省。

若实例只执行 70 组，三种方案总时间约为 1.29、1.27、1.38 s。分桶虽然比特化多做计算，完成时间却更短，因为省下的准备超过多花的执行时间。若三种程序都已缓存，准备成本归零，特化从第一组起就更快。形状分布决定每组成本，复用次数和缓存状态决定能否收回准备投入。

第八章将进一步加入真实的请求到达过程。相同的形状集合，如果很快集中复用，与隔很久才再次出现，可能产生不同缓存保留和重新准备成本。这里先得到一个可供后续使用的判断：稳态速度必须和实际复用次数一起比较。

### 5.5.4 Persistent Kernel 与细粒度调度〔进阶〕

普通 kernel 边界常以整个算子完成为交接点。但消费者有时只需要生产者已经完成的一部分 tile，等待所有 tile 会延迟后续工作。Persistent Kernel 让一个较长驻留的设备程序领取细粒度任务，并通过设备内队列或事件管理依赖，使 tile 就绪后可以更早进入下一阶段。

设有八个投影 tile，每块生产约需 32.2 μs，激活消费约需 39.3 μs。若等全部投影完成再开始激活，再计入两次各 5 μs 的主机启动，总时间约为 $2\times5+8\times(32.2+39.3)=582$ μs。若矩阵与向量资源能独立工作，第一块生产后就可开始消费，后续生产便能被较慢的消费阶段覆盖。

Mirage Persistent Kernel／MPK 用设备内任务与事件表达这类提前交接。八块数据需要 16 个生产／消费任务；假设每个任务花 0.5 μs 分派、0.2 μs 发布完成事件，每块生产和消费分别变为 32.9 μs 和 40.0 μs。只需一次主机启动，完成时间约为 $5+32.9+8\times40.0=358$ μs，约快 1.6 倍。16 个任务合计增加 11.2 μs 管理工作，但两类任务在不同资源上可以重叠，不应将它们全部加到关键路径上。这里假设缓冲充足；真正要测量的是任务管理、缓冲限制与资源争用会吃掉多少重叠收益。[^persistent]

四种机制可以放在同一张表里比较：

| 机制 | 主要改变 | 必须支付或检查的代价 |
| --- | --- | --- |
| 算子融合 | 中间交接与设备执行边界 | 局部容量、重读、数值语义 |
| CUDA Graph | 重复准备与主机提交 | 捕获、固定缓冲、形状兼容与复制 |
| Persistent Kernel | 设备内任务调度与驻留 | 分派、通知、同步与资源长期占用 |
| 流水重叠 | 工作的开始时间与依赖粒度 | 缓冲、填充排空与资源争用 |

它们可以组合，收益却不能相乘。把大 batch 切成微批有助于提前交接，也可能增加启动次数和小矩阵损失，并重复读取权重。第六章将进一步判断 tile 或分片何时可交给另一张卡；这里先保留数据就绪、资源需求与缓冲寿命。

## 5.6 从局部优化到完整请求

### 5.6.1 确认优化进入实际执行路径

Qwen3-8B 有 36 层。给定 7239 个输入 token，生成 32 个输出 token，先做一次 prefill 产生首输出，再做 31 次 decode。如果每层每步调用一次 SwiGLU，这条请求共有 $36\times32=1152$ 次激活：prefill 36 次，decode 1116 次。

虽然 decode 调用次数是 prefill 的 31 倍，每次却只有一行输入；prefill 每次有 7239 行。按行数计，prefill 处理 $36\times7239=260604$ 行，decode 合计只有 1116 行。单看调用次数会把优化重点放在 decode，单看元素数又会忽略小算子的启动与低利用率。

我们在同一引擎中将 36 层激活切换为一个已有 schedule 候选。实际轨迹确认 1152 次调用都进入相应路径，11 对请求的输出 token 一致。接下来比较它改变了哪一阶段，以及该阶段在整条请求中占多少时间。[^exp9]

### 5.6.2 热点占比、依赖与关键路径

如果请求有 20% 的串行时间花在一个热点上，把热点加快两倍，理想总时间变为 $0.8+0.2/2=0.9$，加速约为 1.11 倍。这是经典的占比分析，但它要求该比例是请求中可按串行相加的时间，且其他工作不变。

有并发分支时，还要检查关键路径。教学例子包含 10 μs 准备、60 μs 热点、与热点并行的 40 μs 分支，以及 10 μs 收尾。原请求需要 $10+\max(60,40)+10=80$ μs。热点加快四倍后，变成 $10+\max(15,40)+10=60$ μs。沿旧热点路径相加得到的 35 μs 不再是请求完成时间，因为另一分支成为限制。

若新热点实现让并行分支因资源争用延长到 90 μs，请求反而需要 $10+90+10=110$ μs，比原来的 80 μs 慢约 38%。于是，局部候选即使快了四倍，也可能让整条请求退化。对存在重叠的热点，下一步应测量它与其他工作共同运行时的时间。[^dag]

例如两个各 10 μs 的 kernel 完全重叠，时长之和为 20 μs，完成时间却只有 10 μs；把其中一个缩到 5 μs，整体仍需 10 μs。要估计请求收益，必须沿依赖找出真正延迟完成的工作，而不是只将 profiler 中的各行时间相加。

### 5.6.3 固定请求的前后对照与设计决定

在上面的请求中，原生 prefill 的 36 次 SwiGLU 合计约需 11.2 ms，候选仍约为 11.2 ms。31 步 decode 的 1116 次激活则从约 2.4 ms 降到 0.92 ms，约快 2.6 倍。候选主要改善小矩阵的 decode 路径，对较大的 prefill 几乎没有帮助。[^exp9]

| 激活计算阶段 | 原生 | 候选 | 对整条请求的意义 |
| --- | ---: | ---: | --- |
| Prefill，36 次 | 约 11.2 ms | 约 11.2 ms | 首输出前的主要激活工作未变 |
| Decode，1116 次 | 约 2.4 ms | 约 0.92 ms | 合计只节省约 1.5 ms |

原生全部激活约占 13.6 ms，而该次采集区间约为 851 ms，比例只有 1.6%。即使把激活时间全部消除，且其余工作不变，也最多省约 13.6 ms；现在只缩短其中的 decode 部分，自然只留下约 1 ms 级的改善空间。小算子的 2.6 倍加速，进入完整请求后被其他工作稀释了。

独立的 11 对客户端计时与这个量级相符。输入、输出长度和并发保持不变，两条路径的首 token 时间均约 436 ms，完整请求中位数约为 817 ms 和 815 ms；更适合观察这项小变化的是每轮的配对差值。

![图 5-8 完整请求的逐轮配对差值](ch05/figure-5-8-request.svg)

*图 5-8：每点为同轮原生请求时间减去候选请求时间，正值表示候选更快。Qwen3-8B，7239-token 输入、强制 32-token 输出，并发 1、BF16、eager，关闭前缀缓存；11 对交错计时，轮内先后随机。虚线为配对差值中位数约 1.3 ms，实测期间存在其他驻留服务。上表的阶段时间来自另一次独立 profile。*

11 对中有 9 对总时间缩短，2 对变慢；配对节省的中位数约为 1.3 ms，只占约 817 ms 请求的 0.16%。这组结果支持“候选改善了 decode 激活”，但尚不足以确定跨运行、不同形状或并发负载下也有稳定的请求收益。

这个结果还指出下一步更有价值的问题。若目标是改善当前长输入请求，应寻找 prefill 中占比更大的工作；若目标是验证该候选，应改变输入输出长度，让 decode 占比提高，再观察节省是否随调用次数增长。同时保持相同执行模式，因为 eager 中暴露的主机等待可能在 Graph 下已被压缩，同一局部优化在两种模式中未必带来相同的请求收益。这样，下一次实验由本次数字提出，而不是重复追求更高的孤立内核加速比。

> **实验 5-9 · 核心：内核优化与请求加速**
>
> 使用配套候选、绑定记录和 11 对请求数据，先核对替换确实生效，再计算配对差值。分别解释 prefill、decode 热点、完整请求与输出一致性。将 profile 中约 1.6% 的占比写成带假设的上限，说明为什么不能直接用 Graph 微基准加速比预测请求收益。自行实跑时另选输出目录，保留退化轮次与不支持形状的回退。

## 本章的设计决定

回到本章的 FFN，几项选择都可以从同一组数字解释。64×64 块需要 24 KiB 局部空间、搬动 3096 MiB；128×128 块需要 80 KiB、搬动 1560 MiB。SiLU 与乘法融合让激活链的访问从 120 MiB 降到 72 MiB。图重放把三次 FFN 的主机提交从 18 次降到 3 次，设备却仍执行 18 个 kernel。这些变化分别作用于复用、算子交接和主机提交，因而可以互补，也可能改变彼此的收益条件。

选择还会随输入翻转。边界复制从 2 MiB 增到 16 MiB，原来有益的图重放可能变慢；实例只执行 70 组调用，分桶比稳态更快的特化更省时；decode 激活快约 2.6 倍，遇到 prefill 主导的请求，整体只剩约 1 ms 级变化。每次都应从省下多少工作、增加多少工作，走到究竟谁还在等待。

下一章把这些交接扩大到多张设备。一个 tile 何时生成、还有谁要读取它、它必须保留多久，将决定通信何时开始和需要多少缓冲。局部存储中的读写与生命周期，将成为设备之间分工的起点。
