# 第 2 章 模型架构

第一章把一次模型执行分解为容量、计算与数据读取，并借助硬件的关键数字估算时间下界。这样的估算可以迅速排除一些方案，却还留下一个问题：所代入的计算量和数据量从哪里来？“一个 8B 模型”只说明参数数量的大致范围，没有说明每个 token 使用哪些参数、历史保存在什么地方，也没有说明不同工作之间的先后关系。

打开模型的计算图，才能回答这些问题。注意力将当前表示与历史位置联系起来，前馈网络用学习得到的权重变换每个位置的特征，残差路径连接网络深度上的表示。生成过程又把同一张图反复执行：权重通常保持不变，历史状态不断增加或者更新，一部分中间结果可以复用，另一部分必须重新计算。这些结构和执行方式共同决定模型需要多少计算与存储资源。

本章先以 Qwen3-8B 为例，计算一次前向和完整生成所需的资源，再介绍不同的历史表示、专家结构和跨层连接，最后比较完整模型。掌握这些方法后，读者就能从模型配置和请求长度算出要保存哪些数据、读取多少字节、执行多少运算，并指出各步之间的依赖。表中的每个数字，都可以追溯到具体的矩阵、状态或调用。

文中的数字采用本书仓库内固定配置、计算结果和实验记录。矩阵乘加计为 2 FLOPs，GB 表示十进制字节，GiB 表示 $2^{30}$ bytes；常规权重与 KV 算例使用 BF16，每元素 2 bytes，递推状态另列精度。特殊函数与非矩阵算术不混入矩阵 FLOPs。不同模型的参考执行路径有差异，文中会在相应比较处说明。完整来源与复现入口列于章末。

## 2.1 计算图与前向执行

理解模型资源需求，首先要把计算节点和数据依赖分开。一个节点执行矩阵乘法或其他变换，一条边表示后续节点需要前面的结果。节点的工作量决定需要多少处理能力，边上的张量决定数据量，边的方向则决定哪些工作能够同时推进。三者共同描述模型，单看参数量无法替代其中任何一项。

本章的计算图先描述数学运算和数据依赖。实际执行时，框架会把这些运算交给设备程序；一个运算可能拆成多个程序，多个运算也可能合在一起执行。图上的一条张量边只说明后续需要这份数据，不表示它一定要在 CPU 与 GPU 之间复制。第四章说明数据放在哪里，第五章再解释程序怎样提交、数据怎样传入传出。

### 2.1.1 序列依赖与因果计算图

考虑一个只有四个 token、三层网络的例子。把序列位置画在横轴，把网络深度画在纵轴。在普通 RNN 中，一个位置的隐藏状态由当前输入和前一位置状态共同决定，可写为 $h_t=f(x_t,h_{t-1})$。因此，同一层的第 t 个位置必须等待第 $t-1$ 个位置。历史被压入固定宽度的状态，序列变长不会使这个状态无限增长，但模型必须用有限表示保留后续任务需要的信息。

因果 Transformer 的依赖形式不同。第 l 层计算某个位置时，通过注意力读取上一层中该位置及其之前各位置的表示。只要输入 token 已知，并且上一层的相应表示已经完成，同一层不同位置的计算就不需要再等待本层前一个位置的输出。三角形因果掩码限制信息来源，却不要求所有已知位置逐个执行。网络深度方向的依赖仍然存在：下一层使用这一层的结果。

从图上看，RNN 的状态沿序列位置逐个传递，Transformer 的已知输入则逐层推进。两者保存历史的方法也随之不同：RNN 把历史压进当前状态，注意力保留各位置的 K、V，让后来的查询重新选择相关内容。RNN 通过更新固定大小的状态保留历史，注意力则让每个新查询直接访问此前保存的表示。后面的状态分析都从这个区别展开。

原始 Transformer 包含编码器和解码器，现代因果语言模型常用 decoder-only 主干，本章采用这一结构。处理已知输入时，同层位置可以并行；生成时，第一个输出确定后才能成为下一次输入。因此，输入处理沿网络深度推进，生成还增加了跨调用的串行依赖。[序列依赖计算记录](../calculations/results/sequence-dependencies-book.md)通过前缀重算与状态复用对照呈现了这条执行链。

这些宏观差异最终都要落实到矩阵尺寸。下面先沿 Qwen3-8B 展开一次前向，建立逐层计算的方法，再用相同方法分析另外三个模型。

Qwen3-8B 的主干有 36 层，隐藏维度 $d$ 为 4096，FFN 中间维度 $f$ 为 12288；注意力有 32 个 Q 头、8 个 KV 头，每头维度为 128。词表大小为 151936，词嵌入和输出头不共享权重。本书对照固定配置与 checkpoint 索引得到的总参数数目为 8,190,735,360，而不是恰好 $8\times10^9$。[固定配置与逐算子结果](../calculations/results/qwen3-8b-prefill-8192.md)保留了这一核对过程。

一次前向执行从 token ID 开始。词嵌入为每个 ID 查出一个 4096 维向量，向量依次经过 36 层注意力与 FFN，最后经过归一化和词表投影产生 logits。词嵌入按 ID 选择行，一个 token 取出一条向量，整个词表则作为常驻数据供不同 token 查询。词表输出头则将隐藏向量与词表矩阵相乘；只生成下一个 token 时，通常只需要最后一个输入位置的 logits。

设同时处理 B 条等长请求，每条本次输入 P 个已知 token。投影和 FFN 可以把它们的输入表示为 $X\in\mathbb{R}^{BP\times4096}$，即 $m=BP$ 行。每条请求只补入一个 token 时，$m=B$。第一种情形容易形成行数较大的矩阵，第二种在小 batch 下接近矩阵与向量的乘法。权重相同，输入形状却明显不同。

本章固定两个主要场景：$B=1$、无已有历史、$P=8192$ 的输入处理；以及 $B=1$、已有 8192 个历史位置时，再处理一个 token。为了避免混淆，S 表示本次调用前已有历史，P 表示本次已知输入，网络隐藏维度统一记为 d。最终输出数量 G 将在 2.2 定义。

**例题 2-1：从矩阵形状计算一层的参数量和运算量。** 给定表 2-A 的 Qwen3-8B 配置，求一层主要投影的参数量，以及处理 $m$ 行输入的运算量。

**解：** 本章统一采用右乘记号。若 $X\in\mathbb{R}^{m\times k}$，$W\in\mathbb{R}^{k\times n}$，则

$$
Y=XW\in\mathbb{R}^{m\times n},\qquad N_W=kn,\qquad F_{\mathrm{GEMM}}=2mkn.
$$

例如，两行三维输入乘以一个 $3\times4$ 的权重矩阵，得到两行四维输出。输出共有八个元素，每个元素计算三个乘加，因此矩阵运算量为 $2\times2\times3\times4=48$ FLOPs。输入行数增大时，计算随之增加，权重矩阵本身却没有变大。后面的模型表都按这条规则计算参数量和运算量。

| 符号 | 含义与使用范围 |
| --- | --- |
| $B,P,S$ | 请求数、本次每请求输入位置数、已有历史长度 |
| $m=BP$ | 投影处理的总行数；普通 decode 时 $P=1$，故 $m=B$ |
| $d,f$ | 主干隐藏宽度、前馈网络中间宽度 |
| $n_Q,n_{\mathrm{KV}},d_h$ | 查询头数、KV 头数、每头维度 |
| $N_{\mathrm{pair}}$ | 每层跨全部请求的有效因果位置对数，不含头数 |
| $t_e$ | 专家 $e$ 收到的行数；无丢弃路由时 $\sum_e t_e=mk_{\mathrm{top}}$ |
| $m_{\mathrm{out}}$ | 真正执行词表头的行数；只预测每请求末位置时为 $B$ |

### 2.1.3 注意力计算与位置表示

采用数学右乘记号，输入 X 经过三个线性投影得到 Q、K、V。Q 的总宽度为 $32\times 128=4096$，K 和 V 的总宽度各为 $8\times 128=1024$。因此，$W_q$ 为 $[4096,4096]$，$W_k$ 和 $W_v$ 各为 $[4096,1024]$。代码中的线性层常以 $(d_{\mathrm{out}},d_{\mathrm{in}})$ 保存权重；换成数学右乘记号后，输入宽度在前、输出宽度在后，便可逐项对照下面的表格。

上述投影产生了 Q、K、V，但尚未让当前位置与历史交换信息。接下来将 Q 拆成 32 个头，把 K、V 拆成 8 个头。每组四个 Q 头共用一个 KV 头。对一个 Q 头，查询向量与允许访问位置的 K 做点积，缩放后加因果掩码，再做 Softmax，得到不同历史位置的权重。随后用这些权重对 V 加权求和。各 Q 头的结果拼接后，经 $[4096,4096]$ 的输出投影 $W_o$ 返回隐藏空间。

用矩阵记号表示这一过程，就是 $A=\operatorname{Softmax}(QK^{\mathsf T}/\sqrt{d_h}+M)$，$O=AV$。这里 M 表示掩码。Qwen3 还对 Q、K 做 QK Norm，并使用 RoPE 编码位置信息。QK Norm 作用于各头特征，RoPE 对对应特征对做位置相关旋转，使查询与键的相互作用携带位置信息；两者都位于注意力评分之前。经过归一化和位置处理后，Q、K 才用于计算注意力分数。

输入 P 个新位置、已有 S 个历史位置时，每条请求的第 i 个新位置可以访问 S+i 个位置。因此，有效因果位置对数为：

$$
N_{\mathrm{pair}}=B\left(PS+\frac{P(P+1)}{2}\right)
$$

每个位置对上，一个 Q 头的 QK 点积约需 2$d_h$ FLOPs，随后 AV 的贡献又约需 2$d_h$ FLOPs。合计所有 Q 头，QK 与 AV 的有效矩阵运算量为：

$$
F_{\mathrm{attn}}=4n_Qd_hN_{\mathrm{pair}}=16384N_{\mathrm{pair}}
$$

在没有已有历史的 prefill 中，序列长度加倍时，投影的输入行数变为两倍，全历史注意力的位置对数则约为原来的四倍，因为新加入的位置也要与此前的历史交互。计算这些位置对有两种常见路径：完整矩形乘法先产生所有分数再屏蔽上三角，因果分块则跳过上三角。分块还可以把评分、归一化和 V 汇总接在一起，让分数在片上被使用后释放。第五章将沿这条数据流解释如何减少中间结果的显存读写。

### 2.1.4 前馈网络与前向计算量

注意力负责跨位置的信息交互，FFN 则对每个位置的特征执行非线性变换。Qwen3-8B 使用 SwiGLU：输入分别经过 gate 与 up 两条升维投影，其中 gate 分支应用 SiLU，再与 up 分支逐元素相乘，最后通过 down 投影降回隐藏维度：

$$
\operatorname{FFN}(X)=\left[\operatorname{SiLU}(XW_{\mathrm{gate}})\odot(XW_{\mathrm{up}})\right]W_{\mathrm{down}}
$$

gate 与 up 矩阵各为 $[4096,12288]$，down 为 $[12288,4096]$。三个矩阵合计 $3df$、约 1.51 亿个参数，以 BF16 保存为 288 MiB；处理 m 行输入需要约 $6mdf$ 矩阵 FLOPs。SiLU、逐元素乘、残差加法和 RMSNorm 另列。FFN 逐位置工作，每行使用相同的三份权重；升维后再降维的过程既产生矩阵计算，也形成较宽的中间激活。

注意力的 QKV 与输出投影合计约 4194 万个参数。将它与 FFN 的约 1.51 亿相加，FFN 占这些主要投影参数的约 78%，因此短上下文的计算中，三个 FFN 矩阵占据很大份额。随着输入变长，FFN 随位置数线性增长，全历史注意力则随 $P(P+1)/2$ 增长。两种增长率使计算重心随上下文长度移动。

## 2.2 自回归生成与资源核算

单次前向给出了计算模块的组成，完整生成还需要确定调用次数和状态寿命。同一份权重可能在一个请求中被使用数百次，KV 则一边读取一边增长。最终保存的字节数与累计访问的字节数因此可以相差几个数量级。

### 2.2.1 Prefill、Decode 与状态复用

模型收到一段已知输入后，可以同时计算多个位置的表示。这一阶段称为 prefill。由最后位置的 logits 选择首个输出 token 后，下一次调用把这个 token 作为新输入，得到再下一个输出；这种逐步扩展的阶段称为 decode。两者使用同一个模型，但前者有多个已知输入位置，后者在普通串行生成中每条请求只增加一个位置。

如果每生成一个 token 都把整个前缀重新送入模型，旧位置的投影与 FFN 会重复执行。因果模型中，旧位置不能看到后来加入的 token；在权重、位置与相关计算条件不变时，旧位置产生的 K、V 可以保留。后续查询读取这些历史 K、V，并补入当前位置的新 K、V，就避免了旧位置的大量重算。

缓存把“重新计算旧位置的表示”变成“保存并访问旧位置的状态”。未来位置会产生自己的 Q，用它对旧位置的 K 评分，再以分数汇总 V，所以长期保存的是 K 和 V。旧查询已经完成了自己的任务，下一步使用新的查询。第八章再将这套同请求复用扩展到跨请求共享。

Qwen3-8B 的 BF16 KV 每个历史 token 占：

$$
\begin{aligned}c_{\mathrm{KV}}&=2L n_{\mathrm{KV}}d_h b_{\mathrm{KV}}\\&=2\times36\times8\times128\times2\ \mathrm{bytes}\\&=144\ \mathrm{KiB}.\end{aligned}
$$

第一个 2 表示 K 和 V，$b_{\mathrm{KV}}$ 表示每个 KV 元素的字节数。8192 个历史位置合计 1.125 GiB，每增加一个位置，再新增 144 KiB。每次全历史 decode 用新的 Q 访问旧 K、V，并把当前位置加入历史，因此保存量逐步增加，同一份旧历史又被多次使用。[缓存累计计算](../calculations/results/cache-sequence-qwen3-8b-b1.md)按调用次数明确列出了这些量。

### 2.2.2 驻留容量与逻辑访问

KV 说明了缓存如何用存储换取少做计算。要判断这种交换对系统意味着什么，还需要把 KV 与权重、临时数据放在一起比较。为此，我们把数据分成权重、历史状态和临时数据三类。区分的依据是用途与寿命，而不只是它们都占用显存。

| 数据类别 | 保存与复用 | 本章主要核算项 |
| --- | --- | --- |
| 权重 | 通常在多次调用间保持不变 | 常驻字节、被访问的权重集合、批内复用 |
| 历史状态 | 随请求保留，持续追加或更新 | 有效容量、每步读取、写入及更新计算 |
| 临时数据 | 随算子和阶段产生、消亡 | 张量尺寸、接口数据量、同时存活范围 |

Qwen3-8B 全部 BF16 权重约占 16.38 GB，即 15.26 GiB。模型加载后，这份数据供多个请求反复使用。一次前向中，嵌入按 token ID 查行，层内投影与 FFN 使用对应矩阵，末端词表头计算输出分数。访问哪些权重，因而由计算图中的具体操作决定。

对于 $[m,d]\times[d,f]$，每一行都使用同一个权重矩阵。将权重块读入片上存储后，可以依次用于多行输入，让一次读取支撑更多乘加。处理行数 $m$ 增加，计算量随之增加，整份矩阵的容量保持不变。第五章将进一步解释片上容量与分块怎样决定一份权重能够复用多少次。

临时数据占用多少内存，取决于哪些张量同时存在。前一层释放缓冲后，后一层可以复用同一块空间；算子融合还可以让部分中间值只保存在寄存器或片上存储中。因此，计算读写量时要数清每次访问，计算内存峰值时则要找出同时存活的张量。第五章将结合具体程序分析。

容量和访问量反映不同问题。保存一份状态只占一份空间，但反复使用它会产生多次读取。计算这些读取产生多少设备流量，还要知道数据来自寄存器、片上缓存还是 HBM。分析应按这个顺序进行：先算数据大小，再数访问次数，最后确定每次访问经过哪一级存储。

**例题 2-2：增加 batch 后，历史读取量何时超过权重读取量？** Qwen3-8B 每批将所需共享权重读取一遍，数据量约为 15.14 GB，嵌入按请求查行另计。每请求的 8K BF16 历史为 1.125 GiB，假定各请求独立、旧历史各读一次。

**解：** 求 $B\times1.125\ \mathrm{GiB}\ge15.14\ \mathrm{GB}$，换成相同单位后，最小整数 batch 为 13。历史缩短到 2K 时，阈值升为 51。共享权重数据量保持不变，每个新增请求却带来自己的一份历史。于是，8K 历史在 13 个请求时就超过共享权重，2K 历史则要到 51 个请求。较长历史更早使独立状态成为主要数据量，解释了批内权重复用为何会逐渐让位于历史访问。来源与精确整数见[跨章核对](../research/2026-infra-survey/qa/qwen-cross-chapter-review.md)。

沿第一章的数据路径看，加载把权重从存储送到 GPU 显存，执行再把所需权重送到计算单元。KV 和层间激活也可在设备内部保存与使用。相同的逻辑访问因此可以留在片上、经过 HBM，或跨设备传输；第四章将给这些路径分别配置容量与带宽。

### 2.2.3 完整生成的计算与状态累积

上一节比较了一步执行中的读取量。一个完整回答会重复执行许多步，同一份历史也随之被读取许多次。现在固定一个普通串行生成请求：$B=1$，已恢复前缀为 S，本次输入 $P\ge1$ 个 token，最终返回 $G\ge1$ 个 token。令 $H=S+P$。prefill 处理新输入并产生首输出，随后执行 $n_d=G-1$ 次 decode。最后返回的 token 尚未重新送入模型，所以请求结束时并不自动为它保存 KV。

![图 2-4 历史读取的阶梯与批内权重复用](ch02/figure-2-history.svg)

*图 2-4：左图用 $H=4$、四次 decode 展开累计读取：原来的四个位置每步都读，后来生成的位置从下一步起参与读取。已填色方块共 $4+5+6+7=22$ 个，最终保存的位置却只有 8 个。右图采用 Qwen3-8B 的实际状态宽度，每步将共享权重和各请求的旧历史各读取一遍；8K、2K 历史的读取量分别在 batch 为 13、51 时超过共享权重。*

左图中的每一行都比上一行多一个已填色方块：先前追加的位置现在也成为历史。第 j 次 decode（j 从 0 开始）执行前，历史长度为 $H+j$。于是，若每次 decode 将此前的历史各读取一遍，累计读取量为：

$$
R_{\mathrm{old}}=c_{\mathrm{KV}}\sum_{j=0}^{n_d-1}(H+j)=c_{\mathrm{KV}}\left[n_dH+\frac{n_d(n_d-1)}{2}\right]
$$

decode 追加状态为 $c_{\mathrm{KV}}n_d$；若保留整个上下文，最终有效 KV 为 $c_{\mathrm{KV}}(H+n_d)$。本次请求的全部新增 KV 还应包含 prefill 写入的 $c_{\mathrm{KV}}P$。已有前缀的恢复与传输单独核算。求和中的每一项都对应一次 decode 开始时已有的历史：早出现的位置参与更多后续查询，晚出现的位置参与较少查询。

**例题 2-3：一份历史为什么会被读取一千多 GiB？** 求一个请求结束时的状态与生成期间累计旧历史数据量。

**解：** 取 $S=0$、$P=8192$、$G=1025$，则 $n_d=1024$，累计访问 8,912,384 个历史位置。每个位置占 144 KiB，因此累计读取约 1224 GiB。生成期间只新增 144 MiB KV，结束时共保存约 1.27 GiB。累计读取量是最终保存量的近千倍，因为较早生成的历史被后续查询反复使用。

累计计算也必须沿同样的调用序列完成。投影和 FFN 的单 token 工作相对固定，注意力项随 $H+j$ 增长，输出头按实际调用位置计量。如果把 G 直接当作 decode 次数，就会多算一次模型前向、一次状态追加和相应历史读取。$G=1$ 是很有用的边界检查：只有 prefill 产生首输出，后续 decode 为零。

图 2-4 左侧沿生成步数累加读取，右侧沿请求数累加读取。多条独立请求的状态容量与历史访问分别相加，批内权重则共同使用。长度不同时，逐请求代入各自的 $H$ 与 $n_d$：长输出让已有历史被更多次读取，输入越长，第一次 decode 需要访问的历史就越多。对实际对话，可先从每轮输入、缓存命中与返回数重建这条调用链，[已保存的 Chat 长度核算](../calculations/results/sealed-chat-known-prefill.md)给出了具体代入过程。

## 2.3 历史状态表示与访问机制

全历史 KV 的容量随序列长度增长，累计读取又随生成次数增加。架构可以从不同位置改变这笔需求：减少每个历史位置的表示宽度，压缩或选择历史条目，或者把历史更新进固定大小的状态。这些选择影响的对象不同，也会产生不同的新增工作。比较时必须同时观察保存、选择、读取和更新。

### 2.3.1 多头注意力与 KV 共享

多头注意力允许不同查询子空间建立各自的历史关联。在标准 MHA 中，每个 Q 头对应自己的 K、V 头；MQA 让所有 Q 头共用一组 K、V；GQA 则把 Q 头分组，每组共享一组 K、V。共享后，每个历史位置需要保存的 K、V 组数减少，历史位置的数量保持不变。

先看一个只有四个查询头的单层例子。MHA 为四个查询头各存一份 K、V；GQA 可以让前两个查询头共享第一份 K、V，后两个共享第二份；MQA 则让四个查询头共用一份。若历史长度和头宽相同，需要保存的 KV 份数依次为四、二、一。因此，GQA 在这个例子中把历史保存量减半。四个查询头仍可给同一段历史打出四组不同的分数，这正是“共享历史表示”与“合并查询”之间的区别。

![图 2-5 查询头与共享历史的对应关系](ch02/figure-2-3-sharing.svg)

*图 2-5：四个查询头的教学例子。连线表示每个查询使用哪一组历史 K、V；三种结构都保留四个查询。图中组数用于解释共享关系，不是三个真实发布模型的配置。*

回到 Qwen3-8B：它让每四个查询头共用一组 KV，总计 32 个查询头、8 个 KV 头。如果给每个查询头单独保存 KV，容量会是当前配置的四倍；如果全部查询共享一组，则会是当前配置的八分之一。实际 GQA 配置保存 8192 个位置需要约 1.13 GiB。下面的容量图固定历史长度与头宽，只改变 KV 组数，因此柱高之比直接呈现共享比例。

共享 K、V 改变了被查询的数据，32 个 Q 头仍分别计算分数和加权输出。因此，KV 投影和保存量按组数减少，QK／AV 交互仍按查询头数累计。一次读入的 K、V 还可服务同组多个查询头，从而在实际计算中复用同一份数据。

### 2.3.2 潜变量压缩与 MLA 执行路径

GQA、MQA 通过减少 KV 组数节省空间，MLA 则通过降低历史表示的维度节省空间。可以先把输入投影为低维潜变量 c，再通过上投影得到用于注意力的 K、V。模型在训练中学习这些低维表示与上投影，生成时将历史以 c 的形式保存。

更关键的是，执行时不一定要把全部历史潜变量显式展开。设 $K=cU_k$，则查询与键的点积可写为 $qK^{\mathsf T}=(qU_k^{\mathsf T})c^{\mathsf T}$。把键的上投影吸收到查询侧，便可直接对潜变量评分。V 的线性上投影也可在适当的矩阵结合次序下移到加权汇总之后。前一种次序为每个历史位置恢复 K，后一种次序只变换当前查询，再与潜变量交互。随着历史变长，这项重排把随历史重复的上投影移到了当前查询一侧。

本章采用 Kimi K3 的 Gated MLA 作实例。紧凑路径保存 512 维潜变量和参与 QK 的 64 维额外分支；NoPE 设置保留该分支的计算维度，省去旋转位置编码。24 个 MLA 层、8192 历史、BF16 下，保存量为 $24\times8192\times(512+64)\times2$，即 216 MiB。

仓库固定的 Hugging Face 参考代码采用展开缓存：先恢复各头的 K、V，再将它们保存，同一长度约占 11.25 GiB。两条路径的差额来自保存位置——紧凑路径在上投影之前缓存，展开路径在上投影之后缓存。前者每步变换查询并访问潜变量，后者直接访问已展开的历史。[两条 MLA 执行路径的计算](../calculations/results/k3-mla-expanded-b1-t8192-s0.md)沿各自矩阵分别累计。

MLA 每条历史变窄，条目数量仍随 $S$ 增长，所以历史容量和评分工作继续随长度增长。K3 的其他层采用另一种办法：把历史更新进固定大小的递推矩阵。先理解这两种表示，再将它们相加，就能得到整模型的状态曲线。

### 2.3.3 局部窗口、历史压缩与稀疏索引

减少历史表示宽度之后，还可以改变保留哪些历史、每次访问哪些历史。局部窗口只关注最近的一段位置；压缩机制把若干位置合成较少的条目；稀疏选择先确定相关条目，再把它们送入主注意力。窗口决定保留的近期范围，压缩决定长期条目的数量，索引决定当前查询读取哪些条目。索引器先扫描用于选择的表示，再把选中的主状态交给注意力，两段访问分别产生工作。

DeepSeek-V4-Flash 的固定配置有 43 个主干层、4096 隐藏维度、64 个注意力头，每头维度 512。Q 先从 4096 维投影到 1024 维，再得到 $64\times 512$ 维查询；共享 KV 从 4096 维投影到 512 维；输出采用分 8 组的低秩投影。投影宽度并不必然等于隐藏维度，沿“hidden×hidden”估算所有矩阵会漏掉真实形状。

其主干包含 2 个纯窗口层、21 个 CSA 层和 20 个 HCA 层，窗口长度为 128。CSA 按压缩比 4 保存历史，并维护索引；HCA 按压缩比 128 保存更粗的历史。用 BF16 参考表示，CSA 每个完成的压缩条目含 512 维主状态，另有 128 维索引条目。已有 S 个位置时，完成条目数按 $\lfloor S/4\rfloor$ 计算；尚未完成的压缩块还需独立缓冲。

一次 CSA 查询的主注意力最多读取窗口加 512 个压缩条目，但索引打分仍扫描压缩索引历史。在 $S=8192$ 时，一个 CSA 层保留 2048 个压缩条目：主历史约 2 MiB、索引约 0.5 MiB，窗口约 0.125 MiB；主注意力选择的压缩条目最多约 0.5 MiB，索引扫描却仍需处理那 2048 个索引条目。HCA 则有 64 个完成条目，主历史约 0.0625 MiB，并访问窗口加这组粗粒度历史。

将 43 层相加，8192 历史下的窗口、压缩历史和索引约为 59.125 MiB；另有约 11.641 MiB 的 FP32 压缩器缓冲，合计约 70.8 MiB。最后查询的主注意力与索引数据量约 27.6 MiB。[状态分解](../calculations/results/state-deepseek-v4-flash-n8192-b1-native.md)将这些分项列开，因此能看出选择条目数、保存量和每步读取量并不相等。

![图 2-7 V4 的窗口、压缩与索引](ch02/figure-2-5-sparse.svg)

*图 2-7：上部区分保存的窗口、压缩条目与索引；下部按 8192 历史列出整模型参考状态构成；最后查询的主注意力数据量约 17.1 MiB，索引扫描约 10.5 MiB，合计约 27.6 MiB。未完成压缩块的缓冲单列，索引扫描不包含在主注意力选中条目数中。*

新 token 到达时，压缩器先计算其投影并更新未完成块；块凑齐后，再生成一个长期条目。每 token 更新与块完成写入具有不同节奏：在 128 的边界，细粒度与粗粒度压缩层可同时完成条目，形成集中写入。恢复旧前缀后，这些缓冲也决定后缀怎样续算。[缓存后缀续算记录](../calculations/results/v4-prefix-flash-6144-2048.md)采用逐 token 的参考实现的增量计算过程，沿实际调用累计压缩与输出工作。

### 2.3.4 线性注意力与有限状态递推

另一种路线是把历史汇总到固定大小的矩阵中。以线性聚合 $S_t=S_{t-1}+k_tv_t^{\mathsf T}$、$o_t=q_t^{\mathsf T}S_t$ 为例，每个新位置写入一个键值外积，当前查询直接读取累积矩阵。逐位置的历史列表由一份关联矩阵替代，查询的工作由矩阵维度决定。Softmax 注意力则先对各位置评分再归一化，保留逐位置选择；两种机制在这一点上形成不同的信息组织。

![图 2-8 逐位置历史与固定状态矩阵](ch02/figure-2-recurrence.svg)

*图 2-8：左侧为逐位置保存的历史，查询分别使用各位置的 K、V；右侧用简单的外积累加说明有限状态递推。每个新位置修改同一份矩阵，矩阵尺寸保持不变，读写却在每步发生。KDA 在这一递推思路中进一步加入门控、衰减和误差修正。*

KDA 使用更丰富的门控与 delta 更新。状态更新不仅写入新信息，还根据当前键对既有状态的预测形成修正，并通过衰减控制旧信息保留。直观上，它更新的是一张固定大小的关联矩阵，而不是不断追加一张逐 token 列表。旧信息以汇总后的关联保留，当前键控制修正的位置，衰减门控制旧贡献继续存在的程度。

K3 每个 KDA 层有 96 个头，每头递推矩阵为 $128\times128$。按 FP32 保存，单层为 6 MiB，69 层为 414 MiB。一次 decode 读取旧矩阵、融合新信息并写回，理想一读一写就是 828 MiB。这个量不随历史长度增长：短历史时它是一笔显著的固定开销，长历史时则避免了逐位置扫描持续扩大。

prefill 与 decode 的实现方式也不同。decode 使用单步递推；一段已知输入可以通过块式算法并行计算，再在块之间传递状态。块内中间量和块间状态会占用临时空间，因此最终递推状态的大小不足以预测 prefill 峰值。第五章按缓冲寿命分析这一问题；[块式状态与缓冲记录](../calculations/results/k3-kda-chunk-t8192-c64.md)给出具体分配与数值核验。

### 2.3.5 混合注意力的状态构成

实际模型常把有限状态层与全局注意力层混合使用。这样既利用递推结构的历史压缩，也保留部分直接访问全局历史的能力。但整模型状态不再服从单一的“固定”或“线性增长”规则，而是多种分量之和。

K3 共 93 层，其中 69 个 KDA 层、24 个 MLA 层；24 个 MLA 层中包含末尾的一层。8192 历史、紧凑 BF16 MLA、FP32 递推状态及给定 BF16 短卷积槽位下，三项分别为 216 MiB、414 MiB 与 19.4 MiB，合计约 649.4 MiB。若使用参考展开缓存，MLA 一项就变为 11.25 GiB，整体随之改变。[混合状态计算](../calculations/results/state-kimi-k3-n8192-b1-compact.md)为两条路径保留独立结果。

Qwen3.6-35B-A3B 同样需要按层型计算。其 30 个线性注意力层加 10 个完整注意力层，使每请求每历史 token 的全局 KV 为 20 KiB，另有固定 FP32 递推状态 60 MiB 和 BF16 卷积槽 1.875 MiB。8192 历史时，三项合计 221.9 MiB。这些状态来自注意力分支；接下来的 MoE 分支在同一主干上改变权重选择，两类机制共同组成完整模型。

![图 2-9 混合注意力与专家计算的组合](ch02/figure-2-6-hybrid.svg)

*图 2-9：Qwen3.6-35B-A3B 的层组成。每层按配置执行线性注意力或完整注意力，随后都执行路由与共享专家。分支表示不同层型，线性注意力并不意味着没有 MoE。全模型按 30 个线性层、10 个完整注意力层分别累加，再加入 40 层 MoE。*

![图 2-10 状态容量、访问与输入工作](ch02/figure-2-7-state-growth.svg)

*图 2-10：$B=1$；A、B 为历史长度上的结构推算，C 固定 8192 个新输入并只执行末位置词表头。容量、已计状态访问和 prefill 矩阵运算量分面呈现。K3 容量曲线使用紧凑 MLA；状态访问将全局历史读取与递推矩阵理想读写相加，未包含所有卷积与操作数。prefill 面板按各自参考实现累计整模型工作，与前两项共同呈现保存、访问和计算之间的关系。*

这几条状态曲线的形状来自不同表示。Qwen3-8B 每增加一个位置，所有 GQA 层都追加 K、V；K3 只有 MLA 部分追加历史，KDA 部分保持固定矩阵；V4 则在压缩块完成时增加条目。对长历史，增长速度决定新增容量；对短历史，递推矩阵等固定部分决定起始占用。

混合结构的容量可以概括为 $M_{\mathrm{state}}(S)=M_{\mathrm{fixed}}+cS$：递推与卷积形成固定项，仍保存逐位置历史的层形成线性项。这个式子适用于这里的 K3 紧凑路径和 Qwen3.6 状态；V4 的压缩条目还要保留取整与块边界。相同容量预算下，短历史可能由固定项主导，长历史则逐渐由增长项主导。

这些状态在执行中承担不同的信息访问：全局 KV 允许查询直接选择旧位置，递推矩阵通过更新保留历史关系，压缩索引则在较少条目中寻找相关内容。2.6.3 将把资源比较接到具体检索任务；相应数值和输出记录见[完整模型实验](../experiments/ch02/02-05/full-model-run/README.md)。

## 2.4 条件计算与专家权重复用

前面几节通过共享、压缩和递推减少历史状态。对另一个主要数据来源——模型权重——也可以问同样的问题：每个 token 是否必须使用模型中的全部参数？下面从 FFN 出发分析这一问题。

稠密 FFN 对每个 token 使用同一组矩阵；MoE 把容量分散给多个专家，由路由器为每个 token 选择少数专家。它使“模型保存多少参数”与“一个 token 激活多少参数”分离，也让 batch 内不同 token 的选择影响实际权重访问集合。

### 2.4.1 稠密前馈网络与专家路由

一个典型 MoE 分支先从输入计算路由分数，选择 top-k 专家，再把 token 送入选中专家，最后按路由权重合并输出。有共享专家时，还会有一条所有 token 都参与的分支。专家本身通常仍由 gate、up、down 三个矩阵构成，因此可以按 2.1.4 的 SwiGLU 计算逐个展开。

Qwen3.6-35B-A3B 的固定文本配置包含 40 层，隐藏维度 2048；每层 256 个路由专家，每 token 选 8 个，专家中间维度为 512，另有共享专家。一个路由专家包含 $3\times 2048\times 512=3,145,728$ 个参数，以 BF16 保存为 6 MiB。每层全部路由专家占 1.5 GiB，一个 token 选中的八个专家占 48 MiB。

设专家 e 实际收到 $t_e$ 个 token，其 gate/up 是 $[t_e,2048]\times [2048,512]$，down 是 $[t_e,512]\times [512,2048]$，主要矩阵运算量为 $6t_e\times 2048\times 512$。将各专家的运算量相加，就得到全部路由专家的矩阵运算量。路由器先决定各个 $t_e$，选中专家执行三次投影，随后收集并加权合并结果；共享分支对全部输入行执行。

完整模型保存全部专家，当前 token 沿被选中的专家执行。A3B 描述激活规模，基础文本参数则为 34,660,610,688，统一 BF16 权重约 69.321 GB。注意力、路由、共享专家和输出头与路由专家一起构成一次前向，[Qwen3.6 逐矩阵结果](../calculations/results/qwen36-prefill-8192.md)按各模块累计。

### 2.4.2 激活计算与批内权重访问

**例题 2-4：相同专家计算量，权重读取为何相差 32 倍？** 对 Qwen3.6 的同一层，比较均匀分派和集中分派。

**解：** 即使激活参数相同，batch 内的权重读取也可能不同。假设 $B=64$，每个 token 选择 8 个专家，总共有 512 次 token–expert 分派。若均匀分到 256 个专家，每个专家平均接收 2 个 token，当前批次会访问全部路由专家；若所有 token 都集中到同 8 个专家，则每个专家接收 64 个 token，当前批次只访问 8 份专家权重。

这两种情况的专家矩阵有效 FLOPs 相同，因为 $t_e$ 的总和都是 512。按每个不同专家理想读取一次权重计算，每层访问量却从 1.5 GiB 降到 48 MiB，相差 32 倍。40 层合计的路由专家权重容量为 60 GiB，集中情形的批内选中集合合计为 1.875 GiB；容量仍是原来那 60 GiB，除非系统另行改变放置或卸载策略。

| $B=64$ 的路由情形 | 每层访问的不同专家 | 每专家 token 数 | 每层路由专家理想读取 |
| --- | ---: | ---: | ---: |
| 均匀分配 | 256 | 2 | 1.5 GiB |
| 集中于同 8 个专家 | 8 | 64 | 48 MiB |

![图 2-11 同样的专家运算量与不同的权重读取量](ch02/figure-2-expert-reuse.svg)

*图 2-11：两侧均为 64 个 token，每个 token 选择 8 个专家，共形成 512 行专家输入。左侧将这些行分散到 256 份权重上，右侧集中到 8 份权重上；矩形示意输入矩阵，左侧省略了重复的小矩阵。每份专家权重为 6 MiB，分别读取 256 份与 8 份，便得到 32 倍的差距。*

读取差额来自每份权重服务的输入行数：均匀分派时每专家只有两行，集中分派时每专家有 64 行。同一份权重支持的计算增加 32 倍，理想权重访问量便减少 32 倍。与此同时，原来要执行许多输入为两行的矩阵乘法，现在只需执行少数输入为 64 行的矩阵乘法；权重复用和计算效率因此都会受到影响。[均匀路由](../calculations/results/qwen36-decode-b64.md)与[集中路由](../calculations/results/qwen36-decode-b64-concentrated.md)保留了这两个分派的逐专家结果。

Qwen3.6 在已有 8192 历史的 $B=1$ decode 中约需 7.33 GFLOPs，小于 Qwen3-8B 的约 20.0 GFLOPs。这个整模型差额由几项结构共同形成：2048 维主干缩小投影，30 个线性层使用递推状态，MoE 每次只执行选中的专家及共享分支。总参数增长来自专家集合，当前工作则由实际经过的计算路径决定。

### 2.4.3 共享专家与潜空间计算

上述差距由专家接收的输入行数决定。接下来还要考虑专家本身的尺寸：共享专家处理全部输入，潜空间专家则先缩小输入维度。两者都会改变一个专家需要多少权重、执行多少运算。

DeepSeek-V4-Flash 每层有 256 个路由专家，每 token 选 6 个，另有 1 个共享专家；路由专家中间维度为 2048。单专家的 gate/up 为 $[t_e,4096]\times [4096,2048]$，down 为反向尺寸，参数为 25,165,824。前三层采用哈希路由，后续采用评分路由，计算记录按对应分支展开选择过程。

共享专家为所有 token 提供共同变换，路由专家提供按 token 选择的变换。V4 每层选六个路由专家，再执行一个共享专家，因此当前 token 使用七组专家矩阵，驻留时则保存 256 组路由专家和共享分支。注意力、连接与输出模块再加入各自工作，形成整模型预算。

K3 的路由专家有 896 个，每 token 选 16 个，并在 3584 维潜空间中执行宽度 3072 的专家变换。主干输入进入潜空间、专家输出离开潜空间，都有额外投影；共享专家仍使用主干空间，首层 dense 与其他层的专家结构也要区分。路由概率在哪个维度施加、输出如何合并，同样会影响操作数与标量工作。[V4／K3 专家矩阵记录](../calculations/results/experts-kimi-k3-b64-balanced.md)逐层保存这些差异。

如果专家分布在不同设备上，就要把输入 token 发送到对应设备，专家完成计算后再合并结果。通信量因此取决于专家放在哪里、输入由哪张设备持有。第六章讨论多卡划分，第九章介绍 CPU／GPU 放置及 AF 分离。本节先确定每个专家处理的 token 数、矩阵尺寸和权重读取量。

> **实验 2-6 ★★〔延伸〕：专家矩阵与负载**
>
> 从 Qwen3.6 的 256 选 8 算例出发，对均匀与集中路由分别建立 $t_e$ 表。核对两者专家 FLOPs 相同，而批内不同专家权重集合相差 32 倍。再换成 V4 的 256 选 6 加共享专家，最后尝试 K3 的潜空间专家。
>
> 对每次修改都列出新增计算、被复用权重和路由／合并工作。矩阵有效 FLOPs 与 tile 补齐工作分别记录。若下一步要选择多卡方案，还需要补专家放置和 token 所属的请求及其序列位置，单独的分派次数直方图不足以确定全部通信。

## 2.5 网络形状与计算组织

历史状态与专家选择改变了主要数据集合，网络的深度、宽度和连接方式则进一步决定这些工作以什么形状、什么顺序执行。相近的参数预算不保证相同的执行图，甚至相近的矩阵 FLOPs 也可能伴随不同的缓冲寿命和串行步骤。

### 2.5.1 深度、宽度与专家粒度

在参数总量大致不变的条件下，可以用更窄的层换取更多层，也可以用更少的层换取更大的宽度。增加深度会增加逐层等待，并为每个保存历史的层增加一份 KV 或递推状态；增加宽度则扩大单个矩阵和中间张量，改变分块方式与片上存储需求。因此，深窄模型与浅宽模型即使参数量接近，执行过程也不同。

专家数量与宽度之间也有类似关系。Qwen3-235B 的真实基线有 128 个宽度 1536 的专家，每 token 选 8 个。教学变体改为 64 个宽度 3072 的专家，每 token 选 4 个，专家总参数预算和激活专家矩阵运算量可以保持相同。可是 router 的输出维度改变，每专家接收的 token 数和 GEMM 形状也改变，因此完整模型并非严格等参。

在 16-token 算例中，三种专家粒度的专家矩阵运算量保持相同，基线与 64 专家变体均约为 454 GFLOPs。专家数减半、单专家宽度加倍时，相同数量的权重被分成更少的大矩阵；专家数加倍、宽度减半时，则成为更多的小矩阵。router 要为每个专家计算路由分数，因此其参数也随专家数变化。[专家粒度计算](../calculations/results/qwen235-granularity-baseline.md)将路由与专家矩阵分别累计，呈现同一专家参数总量如何形成不同的执行形状。

形状也决定多卡分工的最小单位。128 个专家可分成八组，每组 16 个；四个 KV 头按完整头分工时只能形成四份，八卡执行就需要复制部分 KV 或调整分组。第五章从矩阵分块分析执行效率，第六章将进一步把这些矩阵和状态分配到设备。

### 2.5.2 残差连接与跨层状态

普通残差路径将子层输入与变换结果相加，使信息能够沿网络深度传递。它的参数量可能远小于 FFN，数据流作用却不能忽略。模型采用更复杂的连接时，需要保存的跨层表示、混合工作和临时缓冲都可能改变。

V4-Flash 的 mHC 保存 4 路残差状态，先将它们混合为 4096 维子层输入，执行注意力或 FFN，再把结果写回残差通路。因此，主体矩阵保持 4096 维输入，新增工作集中在进入和离开子层的混合与汇合。四路状态扩大了跨层表示，混合操作负责连接它们与原有子层。

固定 8192-token 算例中，mHC 混合投影约为 555 GFLOPs，普通算术约为 149 GFLOPs，特殊函数独立记录。混合系数经 Sinkhorn 迭代归一化，再用于残差通路的组合；这些迭代处理同一组局部中间量。末端 hc_head 汇合新输入的主干表示，随后词表头处理选定输出位置。[mHC 分项计算](../calculations/results/hc-deepseek-v4-flash-b1-t8192.md)按这条顺序展开。

K3 的 AttnRes 对网络中较浅层产生的块表示加权求和，形成当前层的输入。后面的层还要使用这些块表示，所以它们需要在本次前向中继续保存；前向结束后即可释放。历史 KV 则要保留到后续生成步骤。两者的寿命不同：AttnRes 增加一次前向中的临时存储，KV 随请求跨多次调用保留。[逐层调度记录](../calculations/results/k3-attn-res-b1-t8192.md)列出了块表示的生成与释放过程。

### 2.5.3 多 token 预测与辅助计算

普通自回归主干对当前上下文产生下一个位置的预测。MTP 在训练目标或辅助结构中加入对更多位置的预测，可以为学习和推理提供额外路径。分析时必须区分三件事：训练时优化了哪些预测目标，发布的模型实际包含哪些模块，服务后端又启用了哪些模块。

用于推测解码时，MTP 根据当前主干特征预先生成后续 token，再交给目标模型验证。如果多个 token 通过验证，一轮就能产生多个有效输出；否则从最后一个通过验证的位置继续生成。因此，加速效果取决于草稿生成、目标模型验证各需多久，以及每轮有多少 token 被接受。第八章将计算这三者的关系。

本书固定的 V4 单次 MTP 算例由调用方提供主干特征与 token ID，只执行相应辅助块，没有再次执行主干。$B=1$、$T=1$ 时，矩阵运算量为 1.80 GFLOPs，其中共享词表头为 1.06 GFLOPs。辅助块自有逻辑参数、checkpoint 数据量和共享嵌入／输出头分别计量，避免把共享权重重复加入常驻容量。[单次 MTP 计算](../calculations/results/v4-mtp-first-call.md)给出这一个辅助调用的组成，可作为后续草稿—验证循环的输入。

辅助预测提醒我们，一次 forward、一次采样和一个有效输出可能是不同的单位。第三章将把编码、生成、迭代及实时输出组织成完整负载；第八章再计算草稿与验证的服务收支。

### 2.6.2 参数规模、数值精度与容量约束

分项计算给出了模型权重和每条请求状态的大小。现在把它们放进同一张显存容量表，就可以判断一台设备能同时保留多少条请求，以及量化权重能腾出多少空间。

对一张设备，先扣权重，再扣工作区和其他固定预留，剩余空间才能放请求状态。对普通等长、独立 KV 的简化情形，可写为：

$$
B_{\max}=\left\lfloor\frac{M_{\mathrm{device}}-M_{\mathrm{weight}}-M_{\mathrm{workspace}}}{M_{\mathrm{state/request}}}\right\rfloor
$$

分子是扣除固定驻留之后可用于请求的空间，分母是每条请求的状态。每增加一条请求，都要为它分配相应的状态空间；剩余空间放不下完整的一份状态时，就无法再增加请求，因此结果要向下取整。递推与卷积状态同样属于每请求数据，与 KV 一起计入分母。

Qwen3-8B 的 BF16 权重约 16.381 GB。设备可用显存为 24 GB（十进制），固定工作区预留 2 GiB，每请求保留 8192-token BF16 KV，则计算上可放 4 条请求，加入第 5 条会超出预算。第一章“约 8B 权重约 16 GB”的估算，在这里被补成具体参数、状态与余量的计算。

70B 则使用固定的 DeepSeek-R1-Distill-Llama-70B，真实参数为 70,553,706,496。其 BF16 权重为 141.107 GB，每条 8192-token BF16 KV 为 2.5 GiB。在本例采用的分组量化方案中，保留嵌入、输出头和归一化等较高精度部分，并计入 scale 与打包尾部后，8-bit 方案约为 73.726 GB，4-bit 方案约为 39.500 GB。

4-bit 方案的 39.500 GB 来自低位宽矩阵、高精度保留项、scale 与打包的共同贡献，比将全部参数一律按半字节计算更大。显存容量为 80 GB（十进制）、固定预留 2 GiB 时，8-bit 方案可放 1 条 8K 请求，4-bit 方案可放 14 条。历史从 8K 增至 32K 时，每请求 KV 增至四倍，4-bit 方案可同时容纳的请求数降到 3 条。压缩权重腾出的空间可以保存更多请求的历史，但每条历史越长，能同时容纳的请求就越少。[8K 容量表](../calculations/results/llama70-capacity-8k.md)与[32K 对照](../calculations/results/llama70-capacity-32k.md)采用同一格式完成这一比较。

*图 2-14：左侧按十进制 GB 分解一个请求的权重、状态和 2 GiB 固定预留，并计算剩余显存可同时容纳多少条请求；右侧固定 70B 模型的 4-bit 量化格式、80 GB 容量与预留，比较每条请求的历史长度为 8K 和 32K 时，可同时容纳的请求数。每条请求的历史越长，相同剩余空间容纳的请求数越少。*

同样方法也能分析更大的部署。235B 的 BF16 权重约 470 GB，超过八张 24 GB 卡合计的 192 GB，而八张 80 GB 卡合计为 640 GB。后者为状态、工作区与复制留下约 170 GB 总余量；第六章将按具体分工把这笔总量分配到每张设备，得到逐卡预算。

容量先给出可放置的实例规模，长度与并发再决定实例要服务的工作。更低位宽释放空间，较短历史允许更多请求同时驻留，批内复用则改变这些请求的执行成本。部署选择因此沿容量、访问与计算逐步展开，第三章将进一步加入请求的到达与时限。

> **实验 2-7 ★〔核心〕：模型规模与硬件的适配范围**
>
> 设可用显存为 24 GB（十进制），其中为工作区预留 2 GiB。使用 Qwen3-8B BF16，分别计算每条请求的历史长度为 4K、16K 时，显存最多能同时容纳多少条请求。再逐步增加工作区预留量，找出可容纳请求数首次减少时的预留量，并解释剩余空间为什么放不下原来的请求数。
>
> 对 70B 模型的 4-bit 量化方案，将容量改为 48 GB，比较 8K 与 32K 历史。对给定八卡部署方案，检查最忙设备；多卡切分的推导在第六章完成。

### 2.6.3 请求条件与模型比较

显存容量决定能同时容纳多少请求，完整调用链则决定每条请求要做多少计算。下面固定输入和输出长度，沿 prefill 与 decode 累加，再用同一文本检查任务结果，把资源消耗与模型用途联系起来。

比较完整模型时，可以从两种输入出发。固定 $S,P,G,B$，得到相同调用长度下的资源需求，便于观察结构差异；固定文本和任务，则先经各模型的分词器得到输入长度，再检查输出。这两种对照分别回答“同样多的位置怎样计算”和“同一个任务需要怎样执行”。

先做资源对照。取 $S=0$、$P=128$、$G=4$、$B=1$，即一次输入前向加三次 decode，最终保留 131 个已处理位置。本书已有四模型结果如下。[统一请求计算](../calculations/results/request-four-models-book.md)分别累积前向、历史增长、读取与写入。

| 模型 | 完整请求矩阵运算量（TFLOPs） | 本次计算采用的实现方式 |
| --- | ---: | --- |
| Qwen3-8B | 1.83 | 有效因果矩阵运算量，最后位置输出头 |
| V4-Flash | 3.40 | 主干有效注意力／专家工作，参考索引计算 |
| V4-Pro | 12.72 | 独立 Pro 配置，按自己的层型和选择上限计算 |
| Kimi K3 | 27.13 | 展开 MLA 与块式 KDA 算法 |

这张整请求表采用已保存的参考实现，其中 K3 使用展开 MLA：历史先恢复为各头的 K、V，再执行交互。前面的紧凑 MLA 则把上投影移到查询和汇总一侧。完整请求沿同一条选定路径累计 prefill 与三次 decode，历史从 128 增到 131；这一路径的矩阵形状与状态表示共同决定各项运算量。

从一次调用扩展到完整请求之后，输入和输出的作用更加清楚。增加 $P$，主要增加一次输入处理及后续每步的历史底数；增加 $G$，则反复执行投影、专家与输出头，并多次读取历史。长输入、短输出与短输入、长输出由此形成不同的资源组成，第三章将把这一区别放入持续到达的负载。

> **实验 2-8 ★〔延伸〕：从请求长度计算模型需求**
>
> 使用[已保存的 Chat／Agent 记录](../experiments/ch02/02-08/README.md)中的已知长度，按 2.2 的规则计算输入与后续调用。四条原始 capture 共报告 753 个输入 token、489 个缓存 token 和 79 个返回 ID；这些汇总本身不能确定所有模型调用和恢复路径。
>
> 先计算可证字段对应的工作，再写出普通串行生成的条件假设。逐条请求处理首输出与 $G-1$ 次 decode，不把返回总数直接当作观测的 decode 次数。请求分布、工具等待与复用间隔将在第三章分析。

现有同消息实验把 Qwen3-8B 与 V4 Flash 放在八道短语检索题上，两者均 8/8 精确答对并正常停止。同一文本经过分词后，短文输入分别为 Qwen 的 523 或 524 token、V4 的 501 token；较长一档分别为 2121 或 2122、2036。固定文本保留了任务，资源核算则使用各自实际 token 长度。

这组实验的部署分别为 Qwen 的 BF16／vLLM，以及 V4 的 MXFP4 专家 fallback、FP8 KV／SGLang，后者还使用 110 GiB CPU offload 与兼容适配。[配对检索记录](../experiments/ch02/02-09/paired-retrieval/README.md)保存了输入、原始响应与评分。对于这八道题，两个部署均完成任务；将其长度代回各自模型表，就能同时得到任务结果和对应资源需求。

本章从计算图出发，逐步算出了完整请求的资源需求。注意力决定如何保存和访问历史，MoE 决定每次选择哪些权重，网络深度与连接方式决定计算顺序和临时存储。下一章将加入请求长度分布、到达时间、工具调用、训练与 RL，分析这些计算如何随时间累积成系统负载。

## 谬误与陷阱

**参数更多，每 token 计算就一定更多。** 总参数决定完整模型的容量；MoE 的选中专家、注意力层型和调用形状决定当前工作。对照表 2-A 与资源表，分别解释这两种大小。

**KV 缩小四倍，注意力计算就缩小四倍。** GQA 共享历史表示，查询头仍分别评分；MLA 改变历史宽度，也改变上投影的执行位置。先找被改变的矩阵与状态，再计算其余工作。

**状态不随历史增长，状态访问就可以忽略。** 固定递推矩阵仍需更新；prefill 还可能产生临时块状态。容量、累计访问与峰值工作区分别回答不同问题。

**同 token 数就是公平的模型能力比较。** 输入和输出的 token 数适合比较资源结构；同文本任务还需固定评分、质量与执行条件，并允许不同分词器产生不同长度。

## 本章小结

从模型配置到资源需求，需要先展开各层型，再按实际调用累计。矩阵尺寸给出参数与计算，状态表示给出保存与访问，专家集合决定条件计算和复用，连接方式决定跨层依赖与缓冲寿命。四个完整模型表使用同一核算方法，但保留各自的结构与执行路径。

读完本章，应能从新配置列出一次前向、一次 decode 和完整生成的需求，并解释长度或 batch 改变时哪些项增长。第三章将继续加入到达与工具依赖，使这些需求成为随时间变化的负载。
