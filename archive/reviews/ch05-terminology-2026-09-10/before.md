# 第 5 章 算子与运行时

同样约 103 GFLOPs 的矩阵乘，输入、权重和输出合计 128 MiB，一种分块方式却要从下一层存储搬入、写出约 3 GiB 数据。扩大输出块可以把这部分访问减半，但每个块占用的局部空间从 24 KiB 增至 80 KiB，留给其他块的空间随之减少。程序的选择同时改变了数据复用和并行执行的机会。

第四章解释了设备能提供多少计算、存储与数据传输能力。本章考察程序怎样使用这些能力。我们沿一段前馈网络（FFN）逐步扩大观察范围：先看一次计算怎样提交并完成，再改变矩阵乘的循环与分块，把相邻算子的中间结果留在局部，随后用编译器组织这些选择，最后检查运行时和完整请求中的收益。

贯穿本章的主例取自 Qwen3-8B：隐藏宽度 $H=4096$，FFN 中间宽度 $F=12288$。先取 $M=1024$ 行输入 X，计算一支投影 $C=XW$；X、W 和 C 使用 BF16，每个元素占 2 bytes，矩阵乘使用 FP32 累加。M 是一次调用处理的 token 行数。它可以是 prefill 的一段输入，也可以是一批请求汇集的 token；单请求逐 token decode 时，M 为 1。[^model]

| 对象 | 形状 | 大小 | 在计算中的作用 |
| --- | --- | ---: | --- |
| 输入 X | $[1024,4096]$ | 8 MiB | 每行产生一行投影结果 |
| 权重 W | $[4096,12288]$ | 96 MiB | 在 1024 行输入之间共享 |
| 投影 C | $[1024,12288]$ | 24 MiB | 随后进行激活等处理 |

本章始终围绕三个问题推进：哪些工作被重复执行，哪些数据可以复用，完成时间由谁决定。访问量、缓冲容量和 kernel 数分别描述程序的一部分；把它们放回执行顺序，才能推导时间。

## 5.1 一次设备执行：提交、搬运与同步

先考虑输入和输出都在 CPU 内存中的矩阵乘。CPU 准备输入，将它送入 GPU，发起计算，再取回结果。这一过程需要两个处理器协作。理解它们何时各自向前推进、何时等待对方，是后续融合、流水和图重放的基础。

### 5.1.1 从框架调用到 kernel launch

在 PyTorch 中写下矩阵乘法，首先执行的是 CPU 上的框架代码：读取张量形状和数据类型，选择实现，准备地址和参数，再通过运行时与驱动向 GPU 提交任务。向设备发起一次内核执行称为 **kernel launch（内核启动）**。运行时负责执行期间的提交、内存和同步；编译器则事先或在首次调用时生成设备代码。

这里有三个层次。**算子**描述数学工作，例如矩阵乘和激活；**kernel** 是设备上执行的程序；**launch** 是 CPU 发起这次执行的动作。一个矩阵乘可以通过多个 kernel 完成，几个逐元素算子也可以装进同一个 kernel。这种对应关系使优化有两个入口：改变设备怎样计算，或者改变主机怎样组织计算。

一次 CUDA kernel 执行会启动一组线程。线程组成线程块（thread block），多个线程块组成 grid。矩阵乘通常把不同的输出 tile 交给不同线程块，块内线程协作读取输入并累加结果。设备将线程块安排到有可用资源的 SM 上。较早完成的块释放资源，后续块便可开始；因此，整个 grid 可以分多批驻留在设备上。

kernel launch 采用异步提交。调用返回时，CPU 已完成这次提交，GPU 则按队列和依赖推进计算。CPU 可以立即准备下一项任务。只有在 CPU 需要设备结果，或准备覆盖仍被设备使用的数据时，两侧才需要建立完成关系。[^execution]

这种分工形成一条简单流水：CPU 生产设备任务，GPU 消费设备任务。大矩阵计算持续较久，CPU 有时间准备下一次调用；小算子很快结束，GPU 更容易耗尽已提交的任务而进入等待。减少这种等待和缩短 kernel 内部时间，是两种不同的优化。

### 5.1.2 数据在哪里：H2D、D2H 与 D2D

Host 指主机，Device 指设备。对具有独立显存的 GPU，常见复制方向有三种：

| 名称 | 复制方向 | 典型对象 |
| --- | --- | --- |
| H2D（Host to Device） | 主机内存 → 设备内存 | 当前批次的输入张量 |
| D2H（Device to Host） | 设备内存 → 主机内存 | CPU 要使用的计算结果 |
| D2D（Device to Device） | 设备内存 → 设备内存 | 固定输入缓冲或重排结果 |

对于刚才的矩阵乘，执行链为：

> CPU 准备输入 → H2D → GPU 计算 → D2H → CPU 使用结果。

模型运行时，大量数据会跨调用保留。权重加载后留在显存，层间激活由下一设备内核直接读取，KV 跨 decode 步继续使用。在 GPU 上完成采样后，CPU 接收的可以只是少量 token ID。因而，模型每层的设备访存和跨 CPU／GPU 的复制具有不同频率：权重可以只传入一次，却在设备上读取很多次。

**例 5-1：传输一批输入。** 一个 $[8192,4096]$ 的 BF16 张量占 $8192\times4096\times2=64$ MiB。取 H2D 有效单向带宽为 24 GiB/s，传输时间为：

$$
T_{\mathrm{H2D}}=\frac{64\ \mathrm{MiB}}{24\ \mathrm{GiB/s}}\approx2.6\ \mathrm{ms}.
$$

将输入分成两份 32 MiB 张量，每份约需 1.3 ms，传输总工作保持不变。分割的价值在于第一份可以更早到达：GPU 开始计算前半批时，复制引擎继续传送后半批。5.3 节将据此求出整批完成时间。[^buffer]

主机内存的组织也影响这条路径。普通内存的页面由操作系统管理；**锁页内存（pinned memory）**在使用期间保持驻留，便于设备直接搬运。普通内存传输常经过内部锁页缓冲：CPU 先复制一遍，再由设备读取。若每批都把 64 MiB 数据复制进新建的锁页缓冲，就在 H2D 之前多做了一次主机复制。让 CPU 直接在可复用的锁页缓冲中准备输入，可以省去这次中转和反复分配。[^execution]

### 5.1.3 stream、event 与完成顺序

异步执行把“已提交”和“已完成”分开，也就需要一种方法表达任务之间的先后。CUDA 的 **stream（流）**是一串按顺序执行的设备任务。把 H2D 和读取该输入的 kernel 放在同一 stream 中，计算就排在复制之后；CPU 可以连续提交两项工作。

若复制和计算放在不同 stream 中，就用 **event（事件）**传递完成关系。复制流在 H2D 后记录事件，计算流等待事件，再使用这份输入。等待发生在计算流的设备任务序列中，CPU 仍可继续提交其他工作。

同样的机制管理缓冲复用。设槽 A 中存放当前输入，复制完成后，主机源缓冲便可准备下一批；GPU 端的槽 A 还要等计算读取结束才能覆盖。主机源和设备目标保存的是同一批数据，它们结束使用的时刻却不同。

| 缓冲 | 最后使用者 | 随后的动作 |
| --- | --- | --- |
| H2D 的主机源缓冲 | 复制引擎读取 | CPU 写入下一批输入 |
| GPU 输入缓冲 | 消费该输入的 kernel | 复制引擎写入下一批输入 |
| D2H 的设备源缓冲 | 复制引擎读取 | GPU 写入新结果 |
| D2H 的主机目标缓冲 | 复制引擎写入 | CPU 读取当前结果 |

这张表给出了事件应放在哪里：放在最后一次使用之后，交给下一位使用者等待。CPU 需要 D2H 结果时，可以等待对应事件；其他无关的设备任务继续运行。5.3 节的双缓冲正是把两套这样的使用顺序交错起来。

### 5.1.4 从提交时间到结果可用时间

**例 5-2：同一次执行的三个时间。** 输入已在主机准备好。CPU 在 0–3 μs 内提交全部任务，第一项设备工作从 3 μs 开始；H2D、kernel、D2H 分别用 8、20、4 μs，设备按依赖连续执行。

| 执行者 | 时间区间 | 工作 |
| --- | --- | --- |
| CPU | 0–3 μs | 提交复制、计算与结果回传 |
| 复制引擎 | 3–11 μs | H2D |
| GPU 计算单元 | 11–31 μs | kernel |
| 复制引擎 | 31–35 μs | D2H |
| CPU | 35 μs 起 | 使用结果 |

CPU 提交占用 3 μs，kernel 执行占用 20 μs，结果在 35 μs 可用。若把 kernel 从 20 μs 缩到 5 μs，结果在 $3+8+5+4=20$ μs 可用。内核快了四倍，整次执行则从 35 μs 降至 20 μs，约快 1.8 倍；剩余 15 μs 由提交和复制构成。

计时工具对应着不同位置的时钟。CPU 时钟包住异步调用，读到提交经过的时间；在结束前等待结果，读到从发起到完成的时间。CUDA event 在设备任务序列中标出起止位置，读到设备推进这段序列所用的时间。profiler 将主机调用、设备计算和复制画在同一时间线上，使提交之后的排队、依赖等待和执行可以逐段辨认。

首次调用还可能生成代码或建立工作区。假设首次编译用 100 ms，随后每次执行 1 ms，调用一次共 101 ms，调用 100 次共 200 ms，平均每次 2 ms。编译费用随复用次数摊薄，设备执行则每次发生。到了 5.5 节，我们将用同一方法判断分桶和特化需要重复多少次才值得。

至此，优化对象已经具体化。复制和计算各有工作量，依赖决定它们从何时开始，准备工作则按不同频率发生。下面先固定一次矩阵乘，追踪设备内部的数据访问。

## 5.2 单算子：分块、布局与实际访存

矩阵乘中，同一个输入元素参与多个输出的计算。同一个权重元素又被多行输入使用。利用这些重复关系，就能让一次较远的读取服务更多乘加；实现这种复用，需要安排循环、局部存储和同时运行的工作。

### 5.2.1 矩阵形状与重复读取

沿用章首投影 $C=AW$，其中 $M=1024,K=4096,N=12288$。一次乘加计两个 FLOPs，矩阵乘的工作量为：

$$
F_{\mathrm{gemm}}=2MKN=2\times1024\times4096\times12288\approx103\ \mathrm{GFLOPs}.
$$

A 与 W 各读一次，C 写一次，BF16 数据合计为：

$$
V_{\mathrm{once}}=2(MK+KN+MN)=(8+96+24)\ \mathrm{MiB}=128\ \mathrm{MiB}.
$$

其中 MiB 为 $2^{20}$ bytes。128 MiB 描述每份数据各经过一次的情形。观察最直接的程序，就能找到重复访问的来源：

```python
for i in range(M):
    for j in range(N):
        acc = 0.0
        for k in range(K):
            acc += A[i, k] * W[k, j]
        C[i, j] = acc
```

计算 C[i,j] 与 C[i,j+1] 时，程序两次遍历 A 的第 i 行。转到下一行输出，又会遍历同一份 W。若这些数据在两次使用之间仍留在缓存，第二次读取由缓存提供；若已被其他数据替换，就要向更远的存储请求。

循环顺序首先决定相邻访问的地址。W 按行连续存储时，内层 k 循环从 W[k,j] 走到 W[k+1,j]，跨过 N 个元素。把循环次序换成 i、k、j，内层就依次读取 W[k,j]、W[k,j+1]，同时将 A[i,k] 用于多个输出。这样一次连续传输取得的数据能立即参与计算。

交换循环也改变了结果的保存方式：原程序把一个 C[i,j] 累加完才写回，新顺序要同时更新一段输出。若这段输出留在寄存器或局部缓存，更新是便宜的；若每次都读写较远存储，就增加了结果交接。因此，循环顺序和工作集大小必须一起设计。分块提供了一种让这段活动数据保持可控的方法。

本节把“工作缓冲与下一层存储之间的访问”作为计数对象。设备若还有 L2，多个工作组的重复请求可以由同一份 L2 数据服务，显存传输由缓存未命中的请求产生。沿层级逐级追踪同一批请求，便能把程序复用与硬件缓存的作用分开。[^tiles]

### 5.2.2 容量约束下的分块复用

**例 5-3：用更大输出块换取复用。** 每次保留一个 $m\times n$ 输出块，沿 K 维按 k 个元素推进。当前 A 块为 $m\times k$，W 块为 $k\times n$，两块输入读入后共同更新输出。输入为 BF16，输出累加器为 FP32，使用一组输入缓冲，则活动容量为：

$$
S=2mk+2kn+4mn\quad\mathrm{bytes}.
$$

这个式子的前三项分别对应 A、W 和累加器。A 中一个元素服务当前 n 列输出，W 中一个元素服务当前 m 行输出；m、n 越大，一次输入读取参与的乘加越多。与此同时，累加器面积按 mn 增长。

固定 $k=32$。各输出块独立读取输入，沿 K 完成全部累加后才写回结果。N 方向有 N/n 个列块，每个都要遍历 A；M 方向有 M/m 个行块，每个都要遍历 W。因此访问量为：

$$
V=2MK\frac{N}{n}+2KN\frac{M}{m}+2MN.
$$

取 64×64 输出块，192 个列块各读一遍 8 MiB 的 A，共 1536 MiB；16 个行块各读一遍 96 MiB 的 W，又是 1536 MiB。再写出 24 MiB 结果，总量为 3096 MiB。它的活动容量为 $4+4+16=24$ KiB。

把输出块改成 128×128，列块减少到 96 个，行块减少到 8 个，两份输入的读取均减半，总量变为 $768+768+24=1560$ MiB。两个输入块各占 8 KiB，累加器占 64 KiB，活动容量增至 80 KiB。

| 输出块 | 活动容量 | 工作缓冲与下一层之间的访问 | 算术强度 |
| --- | ---: | ---: | ---: |
| 32×32 | 8 KiB | 6168 MiB | 15.9 FLOP/byte |
| 64×64 | 24 KiB | 3096 MiB | 31.7 FLOP/byte |
| 128×128 | 80 KiB | 1560 MiB | 63.0 FLOP/byte |

![图 5-1 局部容量与矩阵重读](ch05/figure-5-1-tiles.svg)

*图 5-1：扩大输出块，用更多活动容量减少输入重读。矩阵为 $[1024,4096]\times[4096,12288]$，归约块宽 32，输入 BF16、累加 FP32，单组输入缓冲，各输出块独立读入输入。纵轴为工作缓冲与下一层之间的访问量，虚线为三份矩阵各经过一次的 128 MiB。*

这笔交换何时能缩短时间？先考察两种实现都受该接口带宽限制的情形。令它们的有效带宽分别为 $B_{64}$ 和 $B_{128}$，则：

$$
\frac{T_{128}}{T_{64}}=\frac{1560}{3096}\frac{B_{64}}{B_{128}}.
$$

大块访问量约为小块的一半，因而只要它仍保持小块约一半以上的有效带宽，就有访存时间优势。若两者带宽相同，时间接近减半；若大块因并行度下降只能获得原来四成带宽，时间比约为 $0.504/0.4=1.26$，反而慢约 26%。

局部容量正是影响并行度的一个来源。设某级存储共有 96 KiB 可供这些工作集使用，24 KiB 可以放四份，80 KiB 只能放一份。多份驻留工作可以交错发起访存，让一些工作等待数据时，另一些继续计算。大块增强了每次读取的复用，小块增加了可交错推进的工作；有效带宽体现了这两种作用的合成结果。

因此，块大小选择可以从明确的门槛开始：先由容量排除放不下的块，再由访问量求出值得保留的候选，最后比较候选获得的处理率。5.4 节将把这一过程交给编译器。

### 5.2.3 布局与归约的并行代价

分块控制“读多少”，布局控制“这些读取能否同时得到服务”。考虑一个 32×32 的 FP32 暂存块，有 32 个 bank，每个 bank 每轮提供一个 32-bit 字，bank 号为字地址对 32 取模。32 个 lane 读一行时落在 32 个 bank；读一列时，行跨度为 32 个字，所有地址落到同一 bank，需要 32 轮。

在每行末尾补一个字，行跨度变为 33。同一列相邻行的 bank 号便依次加一，32 次请求分散到 32 个 bank，一轮即可完成。空间由 4096 bytes 增为 4224 bytes，只多约 3.1%。这次改变保留了有效数据和请求数，却让存储可以并行服务请求。

归约则同时影响工作分配和交接。以 RMSNorm 为例，一行的缩放因子来自整行平方和，随后每个元素乘以这个因子和对应的学习权重 gamma。对 $[1024,4096]$ BF16 输入，一组处理一行，可以独立安排 1024 组；对单 token decode，同一种分配只产生一组，设备的大量执行资源会空闲。

把每行分成八个 512 元素片段，可以增加第一阶段的并行任务。完整归约随之变成三个阶段：每个片段产生局部平方和，合并八个局部和得到行缩放因子，再用该因子归一化输入。前两阶段只需传递很少的数，但最后一阶段要重新读取原始数据。

仍取 1024 行。第一阶段从 1024 组增到 8192 组；8192 个 FP32 局部和占 32 KiB，1024 个 FP32 缩放因子占 4 KiB。一组一行的程序在局部保留输入，读入 8 MiB 输入，每行再读取一份 BF16 gamma，累计 8 MiB，最后写出 8 MiB 结果，访问为 $8+8+8=24$ MiB。拆分后，最终应用阶段重读 8 MiB 输入；局部和、缩放因子的写出与读取再增加约 0.1 MiB，总量为 32.1 MiB，kernel 启动从一次变成三次。[^reduction]

拆分还缩小了每组活动状态。完整 FP32 行片段占 16 KiB，八分之一只占 2 KiB。原来需要寄存器溢出到较远存储的工作，可以因此留在寄存器中。并行任务数增加与每组状态缩小，是拆分归约获得收益的两个具体来源；新增读取和阶段交接则是它支付的费用。

矩阵分块、bank padding 和归约拆分都在重新安排同一批数学工作。它们分别改变跨输出的复用、请求的同时服务能力，以及归约内部的并行任务。实际程序的时间变化，可以沿这三种机制逐项解释。配套实验中的连续访问与宽行归约对照提供了对应的执行记录。[^exp1]

## 5.3 算子链：融合、缓冲与流水

单算子内部已经利用局部存储复用输入。相邻算子之间也有同样的机会：生产者生成的数据，消费者往往立即使用。如果能在数据仍靠近计算单元时完成消费，就可以减少一次远距离交接。关键在于消费者需要多少数据，以及这些数据何时完整。

### 5.3.1 中间张量与融合边界

现在把主例扩展到 FFN 的两支投影。令 $G=XW_g$、$U=XW_u$，激活链计算 $Z=\operatorname{SiLU}(G)\odot U$，再将 Z 交给 down 投影。G、U、Z 的形状均为 $[1024,12288]$，BF16 大小各为 24 MiB。

SiLU 和乘法都是逐元素运算。Z[i,j] 只依赖 G[i,j] 与 U[i,j]，不同位置之间没有归约。这意味着，读入一对元素后，可以直接算出最终元素，而无需先生成全部 SiLU 结果。

**例 5-4：消除一次中间交接。** 分开执行时，先计算 $T=\operatorname{SiLU}(G)$，读取 G、写出 T，共 48 MiB；再计算 $Z=T\odot U$，读取 T、U，写出 Z，共 72 MiB。总访问为 120 MiB。将两步融合，每次读取 G、U 的一片，在局部完成 SiLU 和乘法，写出 Z，只需 72 MiB。

省下的 48 MiB 正是 T 的一次写回和一次读取。沿用上一节的带宽模型，取两种程序的有效带宽相同，时间比为 $72/120=0.6$，加速约 1.7 倍。实际激活链对照从约 14.2 μs 降到 7.7 μs，约快 1.8 倍。两种分析都将收益指向同一处：省去完整 T 的交接。[^exp2]

再给这条链加入使用固定尺度的 1-byte 量化转换。独立转换需读取 24 MiB 的 Z，写出 12 MiB 量化结果，增加 36 MiB。三步完全分开的总量为 156 MiB；融合前两步为 108 MiB；三步全部融合为 $24+24+12=60$ MiB。图 5-2 用同一份必要输入输出作为底座，分别加上两个中间量的读写。

![图 5-2 融合边界与中间读写](ch05/figure-5-2-boundaries.svg)

*图 5-2：每消除一个 24 MiB 中间量的物化边界，少一次写出和一次读入，共 48 MiB。G、U 为 BF16，最终输出占 1 byte/元素，量化尺度预先给定。各方案保留相同的运算与舍入顺序。*

中间张量的容量与访问量在这里具有不同含义。设每步先分配输出，完成后释放已用完的输入。独立执行 SiLU 时，G、U、T 同时存活，峰值为 72 MiB；三步融合时，G、U 与最终输出同时存活，峰值为 60 MiB。读写减少 96 MiB，峰值却只减少 12 MiB，因为读写会反复经过同一份空间。[^fusion]

逐元素链特别适合这种局部交接：一个位置的输入齐备，就能完成这个位置的输出。后面遇到归约时，消费者需要的结果要等一组元素共同产生，融合位置也随之改变。

### 5.3.2 布局交接、缓冲寿命与双缓冲

相邻算子有时使用不同布局。生产者沿行写出方便，消费者却希望按另一种块顺序读取。若另建一份 24 MiB 重排结果，就需要读原结果、写新结果，共 48 MiB。把重排并入生产者，可以消除这次完整搬移，但生产者要按消费方地址写出。比较两种方式时，将“原生产者＋重排”的时间与“改变写出布局的生产者”的时间放在一起，即可得到布局选择的实际代价。

缓冲还决定两阶段能否同时推进。设搬运器把块 0 放入槽 A，计算单元随后读取 A。在 A 被读取期间，搬运器将块 1 放入槽 B；计算转向 B 后，A 便可装入块 2。这样，两个槽将同一资源的连续使用错开，使搬运和计算交叠。

**例 5-5：四块数据的双缓冲。** 每块搬运 2 μs，计算 3 μs。搬运器和计算单元独立工作，事件开销记为零。串行执行四块需要 $4\times(2+3)=20$ μs。

采用两个槽后，0–2 μs 搬入块 0，2–5 μs 计算块 0；块 1 在 2–4 μs 搬入，5 μs 时已经就绪。此后每隔 3 μs 完成一块。块 2 在 5 μs 才开始写槽 A，因为此前计算仍在读块 0；块 3 同理在 8 μs 开始写槽 B。第四块于 14 μs 完成，时间减少 30%。

![图 5-3 同样四块数据的串行与双缓冲执行](ch05/figure-5-3-fusion-buffer.svg)

*图 5-3：两个输入槽交替复用，把搬运放进计算期间。每块搬运 2 μs、计算 3 μs，资源独立，忽略同步开销；同一颜色表示同一槽，计算读取结束后才能再次写入。*

将四块推广到 n 块。首块要先搬运，随后流水每隔两个阶段中较长的时间推出一块，末块还需完成计算。因此：

$$
T_{\mathrm{pipe}}=t_m+(n-1)\max(t_m,t_c)+t_c.
$$

其中 $t_m$ 为每块搬运时间，$t_c$ 为每块计算时间。在刚才的例子中，首块搬运后，计算单元连续忙了 12 μs，总时间已是 $2+4\times3=14$ μs。增加第三个槽可以提前搬运，却无法让计算单元每 3 μs 完成一块的速度再提高。此时要继续缩短时间，应减少每块计算，而不是继续增加输入缓冲。

当两阶段访问顺序不同，缓冲需要保存更多待消费的数据。三个排队的 16 KiB 块占 48 KiB，再加 32 KiB 重排空间，共需 80 KiB。若预算只有 64 KiB，生产者在第三块到来前必须等待消费者释放一个槽。这种由有限容量向上游传递的等待称为背压。选择共同布局能够减少排队，扩大缓冲则能容纳更多已经生产但尚未消费的数据。[^buffer]

5.1 节的主机输入也可以按此组织。复制流传入下一批，计算流处理当前批；“复制完成”事件把新输入交给计算，“计算完成”事件把旧槽交还复制。双缓冲的实现由两条完成关系构成，时间收益则来自两种资源同时工作。

### 5.3.3 FlashAttention：分块与在线 Softmax

逐元素链只需交接一对输入。注意力的输出却依赖整行分数，是检验分块方法的下一步。标准注意力先计算 $S=QK^\mathsf{T}/\sqrt d$，再计算 $P=\operatorname{softmax}(S)$，最后计算 $O=PV$。

取一个头，序列长度 $L=8192$，头维度 $d=128$，对全部位置计算注意力。Q、K、V、O 使用 BF16，各占 2 MiB；完整 S、P 使用 FP32，各占 256 MiB。四份输入输出各经过一次共 8 MiB，而 S、P 各写一次、读一次就产生 1 GiB 访问。平方增长的中间矩阵主导了这部分搬移。[^attention]

直接套用逐元素融合会遇到一个障碍：Softmax 的分母是整行指数和。只读到前一块时，既不知道最终分母，也不知道后面是否会出现更大的分数。要提前丢弃旧分数，就必须把旧分数对最终答案的影响压缩成可继续更新的状态。

先从一行的数学形式看这份状态。令已读分数的最大值为 m，将所有指数写成 $\exp(s_j-m)$。减去共同最大值既控制指数的数值范围，又在分子、分母中相互抵消。保留指数和 $\ell=\sum_j\exp(s_j-m)$，以及加权值向量 $u=\sum_j\exp(s_j-m)V_j$，最终输出就是 $u/\ell$。

读入新块后，最大值更新为 $m'$。旧指数从以 m 为基准改为以 $m'$ 为基准，每一项都乘以相同的 $r=\exp(m-m')$。因此，无需找回旧分数，只需同时缩放旧分母和旧加权值，再加上新块：

$$
m'=\max(m,\max(s)),\qquad r=\exp(m-m'),\qquad p_j=\exp(s_j-m'),
$$

$$
\ell'=r\ell+\sum_jp_j,\qquad u'=ru+\sum_jp_jV_j.
$$

**例 5-6：用两个块完成一行 Softmax。** 分数为 $[0,\ln2]$，对应值为 $[1,3]$，每块只含一个元素。第一块得到 $m=0,\ell=1,u=1$。第二块使最大值增至 $\ln2$，旧贡献乘以 $r=1/2$；新元素的指数为 1，于是 $\ell'=1/2+1=1.5$，$u'=1/2+3=3.5$，结果为 $7/3$。一次处理整行时，两个权重正比于 1 和 2，结果同样为 $(1+2\times3)/3=7/3$。

这就解释了 FlashAttention 如何省掉完整 S、P：每处理一块，只保留 m、$\ell$ 和 u，块内分数完成贡献后即可释放。保留的是足以继续计算答案的状态，而不是全部历史中间结果。

状态更小以后，仍需选择块形状。设快速缓冲为 128 KiB，一次保留 a 行 Q 与 FP32 输出累加器，分数块大小为 a×b。K 与 V 按阶段复用同一个 b×d 输入槽，分数和概率复用一个 a×b 槽，另为逐行统计和更新暂存分配三个 FP32 向量。活动容量为：

$$
S=\underbrace{2ad}_{Q}+\underbrace{2bd}_{K/V\text{ 槽}}+\underbrace{4ab}_{\text{分数/概率}}+\underbrace{4ad}_{\text{输出累加器}}+\underbrace{12a}_{\text{逐行状态}}\le131072.
$$

K/V 块越小，它自身和分数块占用越少，就能放下更多 Q 行。更多 Q 行共享一次 K/V 扫描，整份 K/V 被重读的次数随之减少。取 b=64，能放下 a=110 行 Q，需要 $\lceil8192/110\rceil=75$ 次完整扫描。每次读 4 MiB 的 K/V，另有一次 Q 读取和 O 写回，共 $75\times4+4=304$ MiB。

将 b 缩为 1，能放下 a=166，扫描次数降为 50，访问降至 $50\times4+4=204$ MiB。但每次扫描从 128 个 K/V 块变成 8192 个块，在线状态必须更频繁地更新。

| K/V 块行数 b | 可保留的 Q 行数 a | K/V 完整扫描次数 | 缓冲与下一层之间的访问 | 块对更新次数 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 166 | 50 | 204 MiB | 409600 |
| 64 | 110 | 75 | 304 MiB | 9600 |
| 128 | 76 | 108 | 436 MiB | 6912 |

从 64 行块缩到 1 行块，少读 100 MiB，却把块对更新从 9600 次增至 409600 次，约为原来的 43 倍。每次更新都要执行循环控制、最大值比较、指数与输出缩放；一行 K/V 也让矩阵工作变得狭窄。减少扫描和减少状态更新由此竞争同一份容量。块选择要为较宽的矩阵计算和成批状态更新留下空间。

FlashAttention-2 进一步组织线程间工作划分，减少中间交换和非矩阵操作；FlashAttention-3 利用异步执行，将搬运、矩阵乘和 Softmax 交错起来。这条演进沿着本节的因果关系推进：先消除巨大中间矩阵，再提高剩余计算与搬运的执行效率。[^fa]

8192-token 单头对照中，数学后端约需 2.6 ms，Flash 后端约需 80 μs，约快 33 倍；新增分配峰值从约 850 MiB 降至 22 MiB。[^exp3] 这个案例把分块与融合联系起来：分块使活动数据放入快速存储，在线状态使归约可以逐块继续，融合让块内中间结果在被消费后立即消失。

## 5.4 编译器：表达、变换与选择

前两节通过手工分析选择了循环、块大小、缓冲和算子边界。模型运行却会遇到不断变化的行数与算子组合，每种设备也有不同的存储层级和执行资源。编译器的任务，是把这些选择表达成可变换的程序，利用依赖排除错误执行，再从合法方案中寻找较低的成本。

### 5.4.1 从一个实现到一组候选

仍看 SiLU—乘法—量化链。两处相邻边界各有“保留”和“融合”两种选择，共有四种划分：三步独立、融合前两步、融合后两步、三步融合。链长变为十个算子，就有 $2^9=512$ 种相邻边界划分。每一种划分还可以选择块大小、局部布局和流水深度。

这些选择相互影响。合并两步可以消除中间写回，也会增加同一时刻需要保存的值；活动状态扩大，又会改变能够采用的块大小。因而，编译器要同时表达计算内容、执行顺序和数据保存位置。只记录一个算子名，无法推导这些代价。

一个可行的选择过程分为三步。首先，把数学工作表示为循环和数组访问，得到候选变换的对象；其次，根据读写依赖和数值规则检查合法性；最后，结合容量和实测时间比较执行成本。下面先用可读的循环展示前两步，再看 AKG 怎样通过多面体编译组织整个过程。

### 5.4.2 用循环变换表达分块与融合

取 $Y=\operatorname{SiLU}(AW)$，沿用 $M=1024,K=4096,N=12288$，矩阵乘用 FP32 累加，结果舍入为 BF16 后再激活。最直接的程序先生成完整 C，再遍历 C 生成 Y：

```python
for i in range(M):
    for j in range(N):
        acc = 0.0
        for k in range(K):
            acc += A[i, k] * W[k, j]
        C[i, j] = round_to_bf16(acc)

for i in range(M):
    for j in range(N):
        Y[i, j] = silu(C[i, j])
```

第一项变换是 **split（拆分）**。把 i 拆成块号 $i_o$ 与块内坐标 $i_i$，令 $i=64i_o+i_i$。原来的 1024 行就成为 16 个块，每块 64 行。对 j 同样处理，得到 192 个列块。同时拆分两个输出维度，就形成 64×64 的 **tile（分块）**。

拆分只改变索引表达。要连续完成一个 tile，还需要 **reorder（重排）**：将输出块坐标放到外层，块内坐标放到内层。再把 K 按 32 拆成 128 个归约块。程序先选定一个输出 tile，逐块加载所需 A、W，累加到同一片输出状态中。

这时，每个输入块何时创建、何时释放就变得清楚。A、W 的当前块各占 4 KiB，在一次归约块计算后即可替换；4096 个 FP32 累加器占 16 KiB，要活过全部 128 次归约块计算。将缓存放在不同循环层，正是在表达这两种不同寿命。

最后调整激活的**计算位置**。一个输出 tile 完成全部 K 归约后，其 4096 个 C 值已经齐备，可以立即做 SiLU 并写出 Y；其他输出 tile 尚未完成也不影响这一片结果。完整 24 MiB 的 C 因而被缩成 tile 内的交接，消除了 48 MiB 写回与重读。

```python
for io in range(ceil_div(M, BM)):
    for jo in range(ceil_div(N, BN)):
        acc = zeros_fp32(BM, BN)
        for ko in range(ceil_div(K, BK)):
            a = load_tile(A, io, ko, BM, BK)
            w = load_tile(W, ko, jo, BK, BN)
            matmul_accumulate(acc, a, w)
        c = round_to_bf16(acc)
        store_tile(Y, io, jo, silu(c))
```

这里 `load_tile` 和 `matmul_accumulate` 分别表示成块读取和矩阵累加；尾块通过有效坐标掩码处理。伪代码中的缩进承担了重要含义：输入块在 ko 循环内更新，累加器在 ko 循环外保留，激活在 ko 循环结束后发生。

![图 5-4 循环层级决定缓存寿命与交接位置](ch05/figure-5-4-polyhedral.svg)

*图 5-4：从完整中间矩阵到 tile 内交接。输出分成 16×192 个 64×64 块，每块沿 K 完成 128 次归约块计算。A/W 使用 BF16，累加器使用 FP32；输入块随 ko 更新，累加器跨 ko 保留，激活在归约结束后执行。*

Halide 将“计算什么”和“如何调度”分开，程序员用 split、tile、reorder 等动作改变执行方式。`compute_at` 进一步指定生产者在消费者的哪个循环层级计算。TVM 也通过调度表达计算位置和缓存读写，将生产与消费移到所需的数据块附近。[^schedule]

计算位置同时决定复用和重算。把生产者放在最外层，会先生成完整结果，供所有消费者读取；放到一个消费者 tile 内，就只生成当前所需的一片。如果多个消费者 tile 需要同一片数据，放得过深会重复生产它。编译器由此需要在“保存后复用”和“靠近消费者重新生成”之间选择。

循环中的 `fuse` 还可以把多个迭代维合成一个维度。例如 16×192 个输出 tile 可以展平成 3072 个工作编号，再分配给设备工作组。这个动作改变遍历与工作分配；将 SiLU 紧接到矩阵乘 tile 后面，则改变算子之间的交接。两者可以在同一份调度中组合使用。

### 5.4.3 依赖与舍入怎样限制变换

刚才把激活移入输出 tile，却保留在 ko 循环之后，原因可以用两个数说明。设一个输出的两个部分和为 1 与 −1，完整和为 0，SiLU(0)=0。若在每个部分和之后先做 SiLU，再相加，结果为 $\operatorname{SiLU}(1)+\operatorname{SiLU}(-1)\approx0.4621$。移动激活越过归约边界，已经改变了运算。

编译器需要保留的依赖因此有两个层次：同一输出的部分和要按归约规则合并，消费者要等它需要的结果产生。不同输出之间提供并行空间；同一输出内部的归约和消费则规定了必须遵守的先后。

FlashAttention 能跨块继续，是因为它保存了可合并的 m、$\ell$、u，并在指数基准变化时同步修正旧贡献。若只保留每块已经归一化的输出，就丢失了各块分母的相对大小。比如两个块各自只有一个值 1 和 3，块内输出仍是 1 和 3；仅凭这两个输出，无法恢复它们在完整分数中究竟占 1:2 还是 2:1 的权重。归约分块需要保存足以重建全局关系的状态。

浮点舍入进一步限制了变换。原程序将 FP32 累加结果舍入为 BF16，再激活，融合程序便把 `round_to_bf16` 留在同一数学位置。中间值可以从寄存器直接传给激活，这次舍入仍然存在。数据保存位置与数值格式是两项独立选择。

**例 5-7：改变尺度的时机。** 一行 256 项分成两个 128 项块，两个块的首项分别为 1 和 10，其余为零。量化使用最大有限值为 448 的 E4M3FN，尺度由整行最大绝对值决定；随后做点积，权重仅第一项为 1。因此结果完全取决于第一项如何量化。

先读完整行，最大值为 10。第一项缩放为 $1\times448/10=44.8$，舍入到该格式可表示的 44，反量化结果为 $44\times10/448=55/56$。若读完第一块就量化，当时最大值为 1，第一项可表示为 448，反量化贡献恰好为 1。

后一块出现 10 后，可以改变后续计算尺度，却无法补回第一项本应经历的 44.8→44 舍入。两条路径相差 $1/56$，约 1.8%。因此，采用整行最终尺度的程序，要先完成最大值归约，再按该尺度量化；读取顺序决定了尺度何时齐备。[^numerics]

这些例子给编译器划出了清楚的边界。输出之间可以交换执行顺序，输入可以分块缓存，完整结果可以在局部直接消费；归约的合并方式和量化的舍入位置则属于运算定义，需要在变换中保留。

### 5.4.4 AKG：用多面体编译组织循环与存储

AKG 的核心技术是 **Polyhedral Compilation（多面体编译）**。它把规则循环表示为三类信息：有哪些迭代要执行，每次迭代读写哪些数组元素，以及哪些读写要求保持先后。循环边界和规则下标可以用线性约束描述，这就是“多面体”名称的来源。对本章的分析而言，它的作用是让编译器能够推导这些关系，而后系统地改变执行顺序。[^akg]

以矩阵乘为例，编译器可以确定不同 i、j 对应不同输出，沿 k 的更新则指向同一个累加结果。选定 64×64×32 的 tile 后，还可以由数组访问推导当前需要的 A、W 区域：A 为 64×32，W 为 32×64。由此，调度不只是决定循环先后，还给存储管理提供了搬入区域和存活区间。

AKG 从张量表达式生成多面体表示，将分块与分层融合结合起来：在一个层级安排完整算子之间的关系，在更内层安排 tile 的交接和局部缓存。存储管理根据这些区域分配片上空间、插入搬运，代码生成再将计算映射到硬件执行方式，调优阶段选择块形状等参数。前文手工完成的“拆循环—确定区域—保存累加器—完成后消费”，在这里成为相互联系的编译步骤。

这种联系也能暴露融合的反向代价。前面的逐元素链通过融合少读了中间值；若中间值更窄且被许多消费者复用，保留它反而可以减少读取。

**例 5-8：保存量化结果还是在消费者中重算。** 取 $[4096,4096]$ 的 FP16 输入 A，占 32 MiB，量化为 FP8 后占 16 MiB；FP8 权重为 $[4096,1536]$，占 6 MiB，FP16 输出占 12 MiB。输出按 128×128 分块，共有 32 个行块、12 个列块。各输出块独立读取所需数据，量化尺度来自整行最大值。

先独立量化，每个活动行用 8 KiB 局部空间保留原输入，求出该行尺度后直接量化。全部输入读 32 MiB，量化结果写 16 MiB。随后 12 个列块各读一遍窄输入，共 192 MiB，输入相关访问为 $32+16+192=240$ MiB。

把量化移入矩阵乘消费者后，先读取 32 MiB 原输入求出行尺度；12 个列块随后各读一次原来的 32 MiB 输入，并在本地量化。输入相关访问为 $32+12\times32=416$ MiB。省去的 16 MiB 写出，被 12 次更宽的输入读取超过。

两种方案都由 32 个行块各读取 6 MiB 权重，再写出 12 MiB 输出，共 $32\times6+12=204$ MiB。因此总量分别为 $240+204=444$ MiB 与 $416+204=620$ MiB，融合后多访问约 40%。

输出列块数直接决定这笔交换。每增加一个列块，保留量化结果的方案多读 16 MiB，融合方案多读 32 MiB。将 1536 个输出列放入同一块，可消除这种跨列块重复；相应输出累加器也从 128 列扩大为 1536 列，需要十二倍空间。这里的融合选择又回到了 5.2 节的容量与复用问题。[^numerics]

AKG 将融合与分块共同考虑，正是为了处理这样的相互作用。调度移动了生产位置，数组访问随之改变；新的访问区域决定读取与缓冲，缓冲大小又决定可执行的分块。沿这一闭环，编译器比较的是完整执行方案。

### 5.4.5 成本估计与实测选择

依赖和数值规则确定合法方案，容量排除放不下的方案，成本估计再决定优先测试哪些候选。5.2 节已给出一种估计：用访问量和有效带宽比较两个 tile。编译器还可以加入矩阵指令利用率、寄存器需求和启动成本，形成候选排序。

测量用于补足难以从静态程序直接求出的处理率。同一转置程序的 RTX 对照中，16×16 块约需 7.9 μs，32×32 块约需 2.9 μs，扩大后快约 2.7 倍。块的每个维度扩大一倍，内部元素数扩大四倍，存储布局和线程协作也一起改变。读取生成代码，再结合访存与时间记录，就能把候选的差异还原为具体执行行为。[^exp5]

TVM 的自动调优利用真实硬件反馈搜索调度；让 Agent 修改 schedule 或实现，则进一步扩大候选的表达空间。两者都需要经过生成、编译、数值检查和测量。模型源码的算子边界会被编译器继续融合，所以测量对象是最终生成并执行的程序。[^exp4] 搜索方法还要解决另一个问题：用什么负载评价候选。

**例 5-9：调用频数改变最佳实现。** 两个形状 A、B 原来各需 10 μs，候选分别需 5 μs、20 μs。A 快两倍，B 用时翻倍。若两个形状各调用一次，总时间从 20 μs 增至 25 μs，候选慢 25%；若 A 调用 100 次、B 调用一次，总时间从 1010 μs 降至 520 μs，候选约快 1.9 倍。

令 A 在调用中所占比例为 p。原程序每次平均 10 μs，候选为：

$$
\overline T_{\mathrm{candidate}}=5p+20(1-p)=20-15p\quad\mathrm{\mu s}.
$$

要使候选平均时间更短，需满足 $20-15p<10$，即 $p>2/3$。图 5-5 的交点把“适合哪种负载”变成了一个频数门槛。

![图 5-5 形状频数与候选的平均执行时间](ch05/figure-5-5-feedback.svg)

*图 5-5：形状 A 占比超过 2/3 时，候选的总执行时间更短。A、B 原耗时均为 10 μs，候选分别为 5、20 μs；调用串行，图中比较稳态执行。两个标记点对应各调用一次和 A 调用 100 次、B 调用一次。*

因此，调优可以按形状分别选择实现，也可以按实际频数选择一份综合成本较低的方案。搜索本身消耗的编译与测量时间，则属于准备成本。配套的 Agent 实验保留了候选生成、重复提交和测量记录；这些记录与下一节的复用次数一起，用来评价一次搜索是否值得。[^exp6]

## 5.5 运行时：提交、重放与动态形状

编译器选出设备程序后，运行时还要反复准备输入、选择程序、提交任务并管理缓冲。同一份内核代码，放在不同的提交与复用方式中，会形成不同的完成时间。本节把主机工作接回 5.1 节的执行时间线。

### 5.5.1 主机工作怎样进入流水

模型一次前向包含许多相继执行的阶段。CPU 为下一阶段检查形状、准备参数或元数据，GPU 执行当前阶段。如果下一阶段的准备可以提前，两侧便形成流水；若 CPU 一直等到 GPU 完成才开始准备，设备会在两个阶段之间停下来。

**例 5-10：设备加速之后，谁限制流水？** 设有 100 段工作，每段主机配置与设备计算都为 20 μs。下一段配置所需数据已知，缓冲足够，两类资源独立。严格串行需要 $100\times(20+20)=4000$ μs；采用流水后，首段先配置，随后每 20 μs 完成一段，总时间为 $20+100\times20=2020$ μs。

将设备计算缩短至 5 μs，主机仍每 20 μs 才准备好一段。流水变成 $100\times20+5=2005$ μs，只比原来少 15 μs。设备等待的比例扩大，因为任务供给速度没有提高。再把主机配置缩至 5 μs，两侧才能每 5 μs 推进一段，完成时间降为 $5+100\times5=505$ μs。[^host]

这个例子说明了主机优化的两个方向。一是减少准备工作，例如重复使用已经确定的形状和执行计划；二是把准备移到前一段设备执行期间，例如异步处理上一轮输出。它们分别减少流水中的工作量和阶段之间的空隙。

自回归生成给提前准备划出了具体的数据依赖：下一 token 的模型计算要使用上一轮选出的 token；批次组织、语法状态和停止判断则由运行时安排在相应完成点。运行时沿这些依赖寻找可提前执行的工作，将串行链上的等待压缩。vLLM 等引擎的异步执行与调度演进围绕这一问题展开。[^runtime]

### 5.5.2 CUDA Graph：复用提交与支付边界复制

反复执行相似的任务序列时，可以把设备任务及其依赖先记录成图，再重复提交。CUDA Graph 将多次组织 kernel 参数和依赖的工作转成一次图重放。设备仍按图中的节点完成计算，主机组织任务的频率则发生变化。

图 5-6 取三次 FFN 执行作对照。普通提交产生 18 次主机 kernel launch 和 18 个设备 kernel；图重放改为 3 次 graph launch，设备仍执行 18 个 kernel。将激活链融合后，设备 kernel 减至 15 个；再使用图重放，主机仍只需 3 次 graph launch。融合改变设备执行边界，图重放复用主机提交组织。[^exp8]

![图 5-6 主机提交与设备执行的对应关系](ch05/figure-5-6-runtime.svg)

*图 5-6：三次 FFN 的四种执行方式。上行为主机 launch API，下行为设备 kernel；各组横轴从对应 NVTX 范围起点计时，单位 μs。轨迹来自实验 5-8 的 Nsight 采集。*

重放还需要让新输入进入图使用的地址。典型实现为图保留固定缓冲，上游每次将新数据写到这里，图按已记录的地址读取。若上游输出位于另一份张量中，就在图执行前增加一次复制；若上游直接写固定缓冲，这次复制便可省去。

**例 5-11：边界复制何时超过提交收益？** 普通执行的设备计算为 20 μs，暴露在完成时间中的提交等待为 20 μs，共 40 μs。图路径的重放与元数据准备为 5 μs，设备计算保持 20 μs。图原本可以节省 15 μs。

取 BF16 边界输入为 $[256,4096]$，载荷 2 MiB。复制同时读取源和写入目标，接口访问为 4 MiB；按 2 TB/s 的有效读写流量带宽计，复制需约 2.1 μs，图路径共约 27.1 μs，比普通执行少约 12.9 μs。

保持计算与准备时间不变，把边界输入扩大至 2048 行，载荷增为 16 MiB。复制读写增为 32 MiB，用时约 16.8 μs，图路径共约 41.8 μs。这次复制已超过原本省下的 15 μs。

令输入载荷为 X，复制带宽为 B，图路径更快的条件为 $2X/B<15\ \mathrm{\mu s}$。代入 B=2 TB/s 得：

$$
X<\frac{15\times10^{-6}\times2\times10^{12}}{2}\ \mathrm{bytes}\approx14.3\ \mathrm{MiB}.
$$

2 MiB 在门槛内，16 MiB 在门槛外。让生产者直接写图缓冲，或者选择边界张量较小的图段，都能减少这笔交接费用。图的捕获范围因而是一次执行边界选择：段内复用越多，省下的提交越多；边界越昂贵，交接就消耗越多收益。[^graph]

准备计划也可以跨层复用。若 36 层需要相同的兼容计划，每层重建就做 36 次相似工作，共享后只做一次。FlashInfer 的两组对照将时间从约 2.0、2.4 ms 降至 0.72、0.75 ms，设备 kernel 数保持不变。这里消除的是重复规划，体现了 plan 与 run 分开的价值。[^plan]

### 5.5.3 动态形状、分桶与特化摊销

输入行数变化时，运行时可以选择三种方式。通用程序根据当前形状计算索引和边界；分桶将输入补齐到少数代表形状，复用这些形状的程序；逐形状特化则为常见形状生成专门实现。越充分地利用已知形状，越有机会简化设备工作，但也需要准备和保存更多工件。

**例 5-12：实例执行多久，特化才值得？** 取十次 FFN 为一组：8 次为 256 行，1 次为 1536 行，1 次为 2048 行，共 $8\times256+1536+2048=5632$ 行。采用 512、2048 两个桶时，实际处理 $8\times512+2048+2048=8192$ 行，多算约 45%。

完整 FFN 的三个投影每行共需 $6HF$ FLOPs。取通用、分桶、特化的有效矩阵处理率为 100、200、250 TFLOP/s，则每组时间分别约为 17.0、12.4、6.8 ms。分桶虽然多算 45%，处理率却翻倍，仍比通用实现更快。再设它们的准备时间分别为 100、400、900 ms，得到下表。[^specialization]

| 策略 | 一次性准备 P | 每组执行 T | 形状处理方式 |
| --- | ---: | ---: | --- |
| 通用 | 100 ms | 17.0 ms | 按实际 5632 行执行 |
| 分桶 | 400 ms | 12.4 ms | 补至两个桶，执行 8192 行 |
| 逐形状特化 | 900 ms | 6.8 ms | 三个形状分别生成程序 |

运行 r 组的总时间为 $T_{\mathrm{total}}=P+rT$。图 5-7 的截距代表准备，斜率代表每组执行；越快的稳态方案越平缓，但开始时付出的准备越多。

![图 5-7 准备成本与累计执行时间](ch05/figure-5-7-specialization.svg)

*图 5-7：同一组调用反复执行时，最省时的策略随复用次数变化。曲线采用例 5-12 的形状、处理率和准备时间，整数选择边界使用未舍入数值计算。*

分桶多花 300 ms 准备，每组比通用省约 4.6 ms，需要约 65 组抵消。特化又多花 500 ms，每组比分桶省约 5.6 ms，需要约 90 组。由完整数值求得，1–64 组通用最省，65–89 组分桶最省，90 组起特化最省。

如果实例只执行 70 组，总时间分别约为 1.29、1.27、1.38 s。分桶领先，是因为它已经收回相对通用的准备投入，而特化尚未收回相对分桶的额外投入。若三种程序均已缓存，本次准备成本为零，特化从第一组起领先。运行时的选择因而同时依赖形状频数与工件是否已经存在。

把这笔计算推广到自动调优。若搜索耗时 10 分钟，每次使用新实现省 5 μs，以累计节省时间抵消搜索时间，需要 $600/(5\times10^{-6})=1.2\times10^8$ 次调用。每秒一万次约需 3.3 小时，每秒一百次约需 14 天。准备越昂贵，越应优先投入到高频、长期复用的形状中。

第八章将把这种选择放到请求到达与动态批处理之中。形状在短时间内集中出现，既提高复用次数，也让相应工件更值得保留；长时间不再出现的形状则逐步让出缓存空间。

### 5.5.4 Persistent Kernel：将交接推进到 tile

CUDA Graph 复用主机提交，设备上的相邻 kernel 通常仍按图中的完成依赖交接。如果消费者只需要生产者的一片结果，就可以把依赖进一步细化到 tile：第一片就绪，消费者便开始，其他片继续生产。

Persistent Kernel 让较长驻留的设备程序领取任务，以设备内队列和事件管理依赖。它减少重复主机启动，并将全算子交接改成细粒度任务交接。Mirage Persistent Kernel／MPK 是采用这种设备任务组织的研究系统。[^persistent]

沿一支投影接激活，取 512 行输入，按 64 行分成八个 tile。设矩阵与向量资源独立、缓冲充足，每块生产约需 32.2 μs，消费约需 39.3 μs，主机启动每次 5 μs。等全部投影完成再开始激活，共需 $2\times5+8\times(32.2+39.3)\approx582$ μs。

改成八个生产任务和八个消费任务，每个任务支付 0.5 μs 分派、0.2 μs 完成通知。每块生产变为 32.9 μs，消费变为 40.0 μs。一次主机启动后，首块先生产，后续生产与较慢的消费重叠，完成时间为 $5+32.9+8\times40.0\approx358$ μs，约快 1.6 倍。

这条时间线与双缓冲具有同一个结构：首块填充，后续由较慢阶段决定间隔。任务管理增加了工作，但细化依赖使等待减少得更多。缓冲槽从生产开始保留到消费结束；槽耗尽时，生产任务就要等待回收。于是任务队列、就绪事件和缓冲回收共同决定设备流水怎样推进。

从本节回看三种组织方式：图重放复用提交，特化复用准备，persistent 细化交接。它们都利用重复性或提前就绪的数据减少等待，而最终节省多少时间，需要沿整条请求的依赖继续计算。

## 5.6 从局部优化到完整请求

前面已经解释了怎样减少字节、提高处理率和缩短等待。用户看到的却是完整请求何时结束。本节先建立局部收益进入请求的计算方法，再用同一个模型的实际请求作综合分析。

### 5.6.1 热点占比决定加速空间

设请求由串行阶段构成，其他阶段时间保持不变，热点占原时间的比例为 f，热点加速为 s。将原请求时间归一化为 1，新时间为 $(1-f)+f/s$，整体加速为：

$$
S_{\mathrm{request}}=\frac{1}{(1-f)+f/s}.
$$

若热点占 20%，加快两倍后总时间变为 $0.8+0.2/2=0.9$，约快 1.11 倍。继续把热点加快到十倍，总时间为 0.82；即使热点时间降到零，仍有 0.8 的其他工作，整体加速上限为 1.25 倍。

这个关系就是 Amdahl 定律。它解释了优化收益逐渐缩小的原因：热点越快，剩余时间越由其他阶段构成。设计顺序由此变得明确——先按请求中的可节省时间选择目标，再为这个目标寻找实现，而不是按孤立 kernel 的最高加速比排列优先级。

### 5.6.2 并行分支与关键路径切换

请求中有并行工作时，完成时间取决于依赖图中最长的一条路径。设准备 10 μs 后，同时启动热点 A 和分支 B，分别需 60、40 μs；收尾需 10 μs，并等待两条分支都完成。原请求时间为：

$$
T=10+\max(60,40)+10=80\ \mathrm{\mu s}.
$$

将 A 加快四倍至 15 μs，B 仍需 40 μs，新时间为 $10+\max(15,40)+10=60$ μs。A 省下 45 μs，请求却只省 20 μs，因为 B 接替 A 成为关键路径。

![图 5-8 局部加速引起关键路径切换](ch05/figure-5-8-critical-path.svg)

*图 5-8：收尾等待 A、B 两条分支。A 从 60 μs 缩短至 15 μs 后，较慢分支由 A 切换为 B，请求从 80 μs 降至 60 μs。准备和收尾各为 10 μs，两条分支使用独立资源。*

A 缩至 40 μs 时，恰好与 B 同时结束；继续只优化 A，完成时间便停在 60 μs。这个交点给出了局部优化的停止位置。若要继续缩短请求，应优化 B，或减少准备和收尾。

共享资源还会改变分支自身的时间。设 A 的新实现大量占用带宽，使并行 B 延长到 90 μs，请求就变成 $10+\max(15,90)+10=110$ μs。局部计算省下的时间被另一分支的争用延迟超过。比较实现时，将两条分支放回共同运行的时序，才能识别这种代价转移。[^dag]

### 5.6.3 综合案例：一次 Qwen3 请求的优化选择

现在把这一方法用于 Qwen3-8B。请求输入 7239 个 token，生成 32 个输出 token，并发为 1，采用 BF16 与 eager 执行。模型有 36 层，先做一次 prefill 产生首输出，再做 31 次 decode。每层每步执行一次 SwiGLU，共有 $36\times32=1152$ 次调用，其中 prefill 36 次，decode 1116 次。

两类调用承担不同工作。prefill 每次处理 7239 行，36 次合计 260604 行；decode 每次处理一行，1116 次合计 1116 行。decode 的调用数是 prefill 的 31 倍，处理的行数却小得多。这正是本章反复遇到的形状差异：大矩阵提供较多并行工作，小矩阵中启动、工作分配和低利用率占据更大比重。

在同一引擎中，将 36 层 SwiGLU 切换为一个已有 schedule 候选，执行轨迹中的 1152 次调用均进入候选路径。阶段计时如下。[^exp9]

| SwiGLU 阶段 | 调用形状与次数 | 原生时间 | 候选时间 |
| --- | --- | ---: | ---: |
| Prefill | 7239 行，36 次 | 约 11.2 ms | 约 11.2 ms |
| Decode | 1 行，1116 次 | 约 2.4 ms | 约 0.92 ms |

候选主要改善一行输入的 decode，约快 2.6 倍，合计节省约 1.5 ms。prefill 的激活耗时基本相同。轨迹中的这些激活与其他设备工作顺序执行。原生全部激活约为 13.6 ms，占约 851 ms 采集区间的 1.6%；保持其他工作不变，即使消除全部激活，也只有 13.6 ms 空间。现在只缩短其中的 decode 部分，请求改善应落在约 1 ms 的量级。

客户端的 11 对交错计时与这项预期相符。两条路径的首 token 时间均约 436 ms，完整请求中位数分别约为 817 ms、815 ms。对每轮计算“原生减去候选”，配对节省中位数约为 1.3 ms，占原请求约 0.16%。图 5-9 保留每轮差值，显示 9 对缩短、2 对变慢的分布。

![图 5-9 完整请求的逐轮配对时间差](ch05/figure-5-9-request.svg)

*图 5-9：同轮原生请求时间减去候选请求时间，正值表示候选更快。Qwen3-8B，7239-token 输入、强制 32-token 输出，并发 1，BF16、eager，关闭前缀缓存；11 对交错计时，轮内顺序随机，期间有其他驻留服务。虚线为配对节省中位数约 1.3 ms。阶段表来自独立 profile。*

这个结果给出两项具体设计决定。要改善当前长输入请求的首 token 时间，应转向 prefill 中占比更大的计算或等待，因为 decode 的改进发生在首输出之后。要研究这个候选的价值，则应增加 decode 所占比例：更长输出会重复使用一行激活路径，让单步节省有更多累积机会。

从单算子到请求，论证并没有更换方法。先确定每种形状做了多少次，再计算每次省多少时间，最后沿依赖判断节省能否进入完成时间。候选的局部加速、阶段占比与请求计时由此构成一条完整的解释。

## 本章小结

本章从一支矩阵投影出发，逐步把计算放回存储、算子链、编译器与请求之中。贯穿这些层次的是三种关系。

第一，**复用需要空间**。更大的输出 tile 让同一输入参与更多乘加，也占据更多累加器；保存量化结果让多个列块读取更窄的数据，也需要中间存储。容量的价值由它避免了多少重读或重算决定。

第二，**交接需要完整的结果或足够的状态**。逐元素链可以在一个位置的输入齐备后直接完成，归约则要保存部分和或在线统计。编译器根据依赖移动计算位置，运行时通过事件管理数据就绪与缓冲回收。融合和流水都以这份依赖关系为基础。

第三，**节省要经过执行顺序才能成为时间收益**。带宽决定一批字节搬多久，较慢阶段决定流水间隔，复用次数决定准备费用能否收回，关键路径决定局部改进能否缩短请求。优化的对象因此是程序实际执行的工作及其等待。

下一章将这些关系扩大到多张设备。一片结果何时就绪、谁需要读取、要保存多久，将决定通信何时开始以及两端需要多少缓冲。

## 常见误区

**用 kernel 数代替执行成本。** 图重放将三次 FFN 的主机提交从 18 次降到 3 次，设备仍执行 18 个 kernel；融合才把设备 kernel 减到 15 个。主机组织和设备工作应沿各自的时间线解释。

**把访问量最小作为唯一目标。** 注意力的 K/V 块从 64 行缩到 1 行，访问少 100 MiB，块对更新却增至约 43 倍。读取、状态更新与矩阵处理率共同构成执行成本。

**把更多缓冲等同于更高吞吐。** 搬运 2 μs、计算 3 μs 的四块流水，用两个槽已在 14 μs 完成。第三个槽只能让输入更早就绪，下一步应提高已经连续工作的计算阶段。

**把稳态最快等同于总时间最短。** 执行 70 组调用时，分桶约需 1.27 s，逐形状特化约需 1.38 s。特化每组更快，额外准备却尚未收回。

>

## 历史与进一步阅读

Halide 将算法与调度分离，使分块、重排和计算位置成为程序员可组合的动作；TVM 将张量计算、后端生成与自动调优联结起来；AKG 则将多面体调度、分层融合与片上存储安排结合，用于神经处理器代码生成。沿三者的原始材料阅读，可以进一步追踪表达方式怎样影响编译器能够自动完成的变换。[^schedule][^akg]

我早期的 FPGA／HLS 工作，也经历过从接口封装转向代码变换的过程：为了形成所需流水，必须识别原语和读写依赖，改变生成的数据通路。这个经历说明了研究问题如何从编程便利转向执行组织。[^author]

Korch 提供了另一个有启发的编排例子：一个历史子图从三个 kernel、合计约 91 μs，变为四个 kernel、合计约 69 μs。更合适的拆分与组合缩短了设备工作，足以抵消新增边界。[^korch] 这一方向与本章的融合反例一起，把优化目标从边界数量推进到执行成本。
