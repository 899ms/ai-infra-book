# token、矩阵形状与上下文含义复查

按 12 章搜索并逐段检查“行输入、输入行、每行、行数、位置、宽度、槽位”等表述，重点核对数量的对象和单位。逐项修改见 edits.json。

- 第二章从 token 的特征向量引入矩阵行，例题 2-1 就地解释 m，并给出单请求 prefill 与多请求 decode 的例子。m 统计本次处理的 token 位置，不是不同词元的种类数，也不含仅从缓存读取的旧上下文位置。
- 本次处理的 token 数为各请求本次输入长度之和。等长请求为 m=BP；普通单步 decode 才有 m=B。
- 共享专家的一般计算量由 2BN_s 改为 2mN_s。专家路由算例明确采用每请求一个 token 的 decode 条件。
- token 发给 k 个专家会产生 k 次分派。专家输入矩阵的有效行数按分派计；补零行只属于执行形状，不对应新 token。
- 第六章纠正“按输入行切分”：实际划分权重矩阵的行，对应同一个 token 的输入特征；权重矩阵的列对应输出特征。全部 token 仍保留。
- 第五章解释按模型层累计的 token 表示数量与请求本身的 token 数不同。
- 第十二章明确视觉位置是图像特征向量的索引，音频错过“槽位”直接写成错过预定播放时刻。
- 第七章的网络请求槽位已有记录空间的定义；第十一章已区分用户任务、模型调用和工具执行，保留这些符合上下文的表述。矩阵分块、存储布局、表格行列等本来就在描述矩阵或图表的地方，保留“行、列”，不机械替换成 token。

验证结果见 validation.json。对 m 与 B 的更正检查两种情况：P=1 时与原 decode 数值一致；P>1 时共享专家处理 BP 个 token。对权重行切分，以 [2,3] 乘 [[1,4],[2,5]] 验证部分和 [2,8]+[6,15]=[8,23]，切分的是特征，不是两个 token。
