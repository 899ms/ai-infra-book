# Actual model candidate generation and Docker validation replay

Use fixed Qwen3-8B revision, BF16, no thinking, six saved candidates in two sequential model batches (B then A), independent seeds, preserve all output token IDs, parse failures and measured candidate ready timestamps. B asks direct recursive Fibonacci; A asks sum-of-squares loop. Validation will use known mathematical references, including B long-tail input and a declared timeout. Do not silently repair generated code or discard failures.

Replay identical candidates and original relative ready times for each policy: two total validation slots, fixed one per batch; shared FIFO; shared A-batch-first, nonpreemptive. Execute candidate code only inside rtx-pro Docker containers, no network, resource/time limits, no host user-directory mounts. Record container creation, dispatch, compile, execution, feedback, termination and resource release separately. Hold slots until container exit/removal observed. Three shuffled policy repetitions. Preserve timeouts as censored execution times, not proof of semantically incorrect code. Batch eligibility/feedback is a training-readiness proxy; no claim of actual verl/DistRS optimizer execution or training quality. Compare resource occupancy and both batches' feedback waits rather than declaring one batch's faster feedback an overall throughput gain.
