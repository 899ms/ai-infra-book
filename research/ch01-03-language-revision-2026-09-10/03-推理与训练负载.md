# 第 3 章 推理与训练负载

假设一个服务平均每秒收到四个请求，每个请求输入 4,608 个 token、输出 1,152 个 token。第二章已经教我们按长度计算模型工作量。现在把平均工作量乘以每秒请求数，是否就能决定需要多少资源？

两种服务可以具有完全相同的平均数：一种始终均匀接收请求，另一种前一分钟集中处理长文档，后一分钟集中生成长回答。前者持续需要相近的资源配比，后者的工作重心则在输入处理与生成之间移动。Agent 又在模型与工具之间往返，GPU 暂停生成时，历史状态继续等待复用。训练也会因序列长度、有效标签和更新次数形成不同的计算与状态寿命。

这一章把第二章的计算图放进时间线。我们先观察请求如何到达，再沿多轮对话、工具调用和实时媒体展开依赖，随后补上反向传播与 RL 循环。最后，才讨论这些负载怎样转成训练和长期服务预算。

## 3.1 从一次执行到持续负载

### 3.1.1 Prefill 与 Decode

第二章已经给出单次执行的资源需求：以 $S$ 表示恢复的历史、$P$ 表示新输入、$G$ 表示返回数，普通生成在 prefill 后还有 $n_d=G-1$ 次 decode。本章继续使用这条调用约定，将重点放在这些工作何时到达、怎样相互等待。[^model]

![图 3-1 同一模型的 Prefill 与 Decode](ch03/figure-3-1-stages.svg)

*图 3-1：复用第二章的调用约定，$S=6144,P=2048,G=4$。三次后续 decode 将已处理位置从 8192 增至 8195；横轴表示调用次序。将这条链放到每个请求的到达时刻，才能形成负载时间线。*

两个阶段使用同一套权重，却提出不同的资源需求。以一组权重矩阵为例，prefill 的输入包含 $BP$ 行，单步 decode 只有 $B$ 行。输入位置较多时，一次权重读取可以服务较多乘加；低并发 decode 则可能为很少几个 token 读取整组权重。这是“prefill 常偏计算密集、decode 常偏带宽密集”的来源。

批量与历史会改变这种配比。增加 $B$，一次权重读取服务更多输入行，计算随之增加；各请求的历史则独立累加。第二章的 Qwen3-8B 算例中，8K 历史在 batch 达到 13 时已超过共享权重载荷。因此，从低并发转向高并发时，权重复用逐渐提高，注意力计算和历史访问也逐渐占据更大份额。

> **实验 3-1 · 延伸：Prefill 与 Decode 的资源变化**
>
> 使用第二章相同模型的长度、batch 与前缀命中表，把输入较多和生成较多的两段工作分别汇总。保持总 token 数，再改变输入与输出的比例，检查计算、历史读取和状态增长。结果应分别列工作量与资源时间下界；没有测量时，不填完整请求延迟。

### 3.1.2 任务目标与评价指标

模型请求与用户任务通常不是一一对应的。回答一个问题可能只需一次生成，修复一个函数却可能需要读文件、改代码、运行测试、根据错误再修改。评估系统时，先写出什么算完成，再决定统计什么。

对流式文本请求，设请求到达时刻为 $t_a$，首个输出时刻为 $t_1$，最后输出时刻为 $t_G$。首 token 时间 TTFT 是 $t_1-t_a$，完整请求延迟是 $t_G-t_a$。若每个输出 token 都有时间戳，平均 TPOT 可写成 $\frac{t_G-t_1}{G-1}$，仅适用于 $G>1$。相邻 token 的间隔还应单独观察：同样的平均 TPOT，可能是一条平稳输出，也可能是几次长停顿后成批交付。

首个 token 到达客户端之前，请求沿排队、输入准备、设备计算与结果交付推进。输入原来在主机还是设备，决定数据传输发生在哪里；计算完成后，结果还要经过主机处理和连接发送。沿同一请求记录开始与完成事件，就能把 TTFT 分解到实际等待位置。第五章将展开设备提交、传输与完成的具体时序。

客户端有时按块接收多个 token，块间隔不能直接当作逐 token 间隔。reasoning 模型又增加了一个观察点：首个内部 token 出现时，用户未必已看到答案。因此，内部生成、用户可见输出和任务完成各自有时间边界。语音的首次播放还要再经过解码与设备缓冲，稍后讨论。

| 要回答的问题 | 需要的指标或记录 |
| --- | --- |
| 多久开始回应？ | TTFT；reasoning 另记首个有用输出 |
| 输出是否连续？ | 逐 token／逐块间隔及其分布 |
| 多久把事情做完？ | 完整请求时间、完整任务时间 |
| 每秒交付多少合格结果？ | 在质量与时限要求下的有效吞吐 |
| 得到一个成功结果花多少？ | 全部尝试的模型、工具和环境费用／成功任务数 |
| 等待期间还占着什么？ | 状态身份、大小、驻留位置和寿命 |

p95 描述选定指标的尾部。本章采用最近秩法：把 $n$ 个观测从小到大排列，取第 $\lceil0.95n\rceil$ 个。四条请求的 p95 是最大值，480 条请求的 p95 是第 456 个。请求完成、排队与首响应分别排序，就能看出长等待发生在哪一段；全程 p95 则直接对每条请求的全程时间排序得到。

工具等待期间，状态仍具有寿命。设 CPU 工具执行 10 秒，模型保留 $M$ bytes 的 KV 等待下一轮，驻留量对时间的积分就是 $10M$ byte·s。等待越久，这份容量越久不能交给其他请求。这一指标把不发生模型计算的区间也纳入资源需求，第八章将据此比较继续保留、换出与重算。

成功任务成本把所有尝试的费用相加，再除以成功任务数。这样，失败生成、工具测试和环境运行都进入分子，分母对应用户得到的合格结果。一个批次零成功时，记录其总消耗与失败原因；成功任务成本由取得成功结果的样本估计。[^cost]

### 3.1.3 请求分布

负载描述应保留到达时间、输入与输出长度的联合分布。长请求既增加自身服务时间，也可能延长状态驻留；短请求提前完成，则可能让后续请求较早开始。因此，平均工作相同不能保证等待、完成时间和状态峰值都相同。先用章首的两分钟负载把这个区别算清，再观察真实系统。

生产请求还会随客户组成改变。ServeGen 的研究覆盖阿里云 Model Studio 的 12 个模型、约 35.4 亿请求。收集横跨四个月，各模型在表中的分析窗口是一周或一个月。研究观察到，同一客户的请求形状相对稳定，而不同客户的速率变化会改变整体长度分布。于是，“来自哪个客户”“在什么时候到达”“输入与输出怎样配对”成为负载描述的一部分。论文中的一个规划案例，真实负载需要 24 个实例，ServeGen 估计为 25，仅采用简化负载的 NAIVE 方法估计为 12；这个结果绑定当时的 Qwen2.5-14B、A100、vLLM 配置和时限要求。[^servegen]

**例题 3-1：平均供给充足，为什么仍会积压？** 判断每秒可完成 6144 个后续 decode 步的资源，能否持续承接章首负载。

**解：** 回到章首每秒四个请求的例子。定义 A 为输入 8,192、输出 256，B 为输入 1,024、输出 2,048。每份记录持续两分钟，A、B 各 240 条。一份始终均匀混合；另一份前一分钟 $A:B=9:1$，后一分钟变成 1:9。两份均值相同，但每秒新输入和后续 decode 的需求变成了三种情况。

| 时间窗 | 新输入 token/s | 后续 decode 步/s |
| --- | ---: | ---: |
| 均匀混合 | 18,432 | 4,604 |
| 时段变化，前一分钟 | 29,900.8 | 1,736.8 |
| 时段变化，后一分钟 | 6,963.2 | 7,471.2 |

以一个时间窗内的工作为单位，积压可以递推为：

$$
Q_{k+1}=\max(0,Q_k+A_k-\mu_k\Delta t).
$$

其中 $Q_k$ 是窗口开始时的待处理工作，$A_k$ 是窗口内新到达的工作，$\mu_k\Delta t$ 是可完成量。采用窗口内均匀到达、固定服务能力的流体模型，将 decode 工作汇入一个队列：需求低于供给时队列排空，需求超过供给时差额留下，成为下一窗口的初始积压。prefill 则按它自己的服务能力建立另一份预算。

每秒四个请求的首输出由 prefill 产生，所以 4608 个输出中有 4604 步属于后续 decode。令 decode 队列初始为空、服务能力为每秒 6144 步，先把请求的生成工作均匀汇入各窗口。前一分钟供给充足，后一分钟每秒多到来 $7471.2-6144=1327.2$ 步，60 秒便留下 79,632 步；停止到达后，再用 $79632/6144$，得到约 12.96 秒排空时间。前一分钟未使用的能力无法保存到后一分钟，这正是全局均值掩盖积压的原因。[^workload]

**真实系统对照。** 本书把相同两份长请求送入真实的 Qwen3-8B／vLLM 0.23 实例。使用 RTX PRO 6000、24 GiB KV 池、最多 64 个活跃序列，关闭前缀缓存，强制生成指定长度；120 秒后继续等待全部请求完成。两组各完成 480 条，观察如下。[^arrival]

| 实际观察 | 均匀混合 | 前 9:1、后 1:9 |
| --- | ---: | ---: |
| 完整请求 p95 | 约 299.4 s | 约 299.4 s |
| TTFT p95 | 242.9 s | 258.9 s |
| 初次调度等待 p95 | 242.4 s | 258.4 s |
| 最后完成相对起点 | 419.8 s | 418.7 s |
| 抢占事件 | 62 | 24 |

两次回放的完整请求 p95 与最后完成时间接近，TTFT 和初次调度等待却相差约 16 秒。采样 KV 池占用都达到 100%，请求在进入执行前经历了很长等待。输入与输出的时段组合改变了何时释放状态、何时接纳新请求，所以整批完成接近时，用户开始收到响应的时间仍可不同。表中抢占按事件计数，原始时间线保留了每次重新调度的过程。

负载压力较低时，队列呈现另一种状态。ServeGen 公开窗口的两次回放各完成 480 条，完整请求 p95 为 0.786／0.801 秒，均无抢占，采样 KV 峰值约为 1.67%／2.02%。[^serve-replay] 将它与前面的高压力回放对照，可以看到容量余量的作用：状态占用较低时，请求较容易直接进入执行；状态池填满时，新请求必须等待已有请求释放空间。

![图 3-2 请求组成与阶段积压](ch03/figure-3-2-workload-budget.svg)

*图 3-2：A、B 比较相同总量下的客户组成和阶段需求；C 为同一实例的两次实际回放；D 根据例题 3-1 的固定服务率计算后一分钟积压。D 的 12.96 秒排空属于教学工作队列，与 C 的单 GPU 实测时间有不同供给和执行条件。*

## 3.2 多轮交互与 Agent 任务

### 3.2.1 多轮 Chat 与前缀增长

多轮对话的下一次请求通常带着历史。第一轮输入是系统提示和用户问题；第二轮除了新问题，还可能包含上一轮回答；之后每轮继续累积。若只看用户新写了多少字，就会低估送入模型的输入长度。

不过，完整输入也不等于每轮都要重算。设第 $i$ 轮实际输入为 $I_i$，引擎报告命中 $K_i$，则未缓存输入为 $I_i-K_i$。第二章的 prefill 计算应使用实际恢复的前缀和未缓存部分。这里必须同时记录 token ID 与命中结果：文本看起来一样，不保证模板、工具列表、模型版本和缓存位置都允许复用。

本书代码 Agent 的开启 thinking 记录给出一个具体例子。四轮累计输入 5,297 个 token，其中命中 4,480 个，未命中 817 个。第二轮输入 1,443 个、命中 1,392 个，只需处理 51 个未缓存位置；但后续 decode 仍然要访问其历史状态。按相同输入做冷重算的 prefill 矩阵工作为 76.196 TFLOPs，使用所记录命中后为 11.976 TFLOPs。缓存省去的是旧位置的投影与前馈重算，新的查询仍要使用这些位置的历史。因此，缓存命中同时带来“少算旧输入”和“继续保留旧状态”两项结果。[^agent-calc]

上下文编辑改变复用边界。末尾追加新内容时，原有前缀保持不变；摘要替换一段旧历史时，替换位置之后的表示要从新的前缀重新计算；工具定义或模板变化则可能更早改变输入。这些操作决定下一轮有多少位置命中、多少位置重新进入 prefill。

上下文策略还会改变未来负载。把状态持续追加在末尾，有利于保住旧前缀，却会让陈旧内容继续占据上下文；替换前部状态可以缩短历史，但其后的缓存可能需要重建。这一章先记录改变发生的位置、重建长度与复用间隔，第八章再比较保留、淘汰和重算。[^context]

### 3.2.2 Reasoning、验证与成功任务成本

增加推理时计算有几种方式。串行思考延长同一条生成链；并行采样同时探索多个候选；按难度分配则把更多预算给较难的任务。它们都可能改善结果，也都增加了不同的工作：串行方式扩大历史并延长依赖，并行方式增加候选和验证，动态分配还需要判断何时继续、何时停止。

比较这些策略，先固定任务的完成标准，再计算为达到标准付出的总工作。串行思考把预算放在同一条历史上，并行采样把预算分给多条候选，验证器则负责判断哪条候选可以交付。成功结果是这几段工作共同产生的，成本也沿完整流程累计。

**陷阱实例：更快生成了失败候选。** 实验 3-3 比较顺序生成独立候选、并发生成独立候选，以及按题目规模决定候选数量。各候选从同一题目独立开始，顺序与并发改变的是候选执行时序。固定四题、两轮观测中，1024 和 4096 输出预算下的候选都未交付符合主评分的最终答案。失败仍消耗资源，但无法据此估计每个成功任务的成本。[^reasoning]

关闭 thinking 后的格式与答案诊断保留在[实验材料](../experiments/ch03/03-03/no-thinking/README.md)。诊断可以解释失败，主评分仍使用事先规定的接口与正确性要求。[^reasoning-off]

单 token 变便宜也不能替代这项检查。用一个简单假设说明：新系统 token 单价降到原来的 1/10，每任务用量却增加到 20 倍，成功率由 50% 提高到 80%。只计模型费用，并假定重复尝试的分布稳定，每个成功任务的费用比为 $2\times\frac{0.5}{0.8}=1.25$。价格下降、质量提高和成功任务费用上升可以同时发生。对带历史的 Agent，可以沿实际轨迹累加各次尝试，再以通过检查的任务数作分母。[^cost]

> **实验 3-3 · 延伸：Reasoning 预算与正确结果成本**
>
> 读取三批候选记录，分别统计截断、格式合规、数值正确与最终任务通过。保留原评分，再单列后验诊断。若继续比较串行、并行和动态预算，应先得到满足同一质量门槛的结果；未成功的记录仍计入消耗，成功成本保持未定义。

### 3.2.3 Agentic：模型、工具与检索的循环

代码 Agent 的一轮执行可以分成四段：模型决定下一步，工具执行，工具结果返回，模型把结果接入下一次输入。编译日志、测试错误、文件内容都在这个循环中成为新数据。工具不仅增加等待，还会改变下一轮的输入长度和分支。

本书使用一个固定任务：修复区间合并函数，使嵌套区间和端点相接的区间正确合并，同时不修改输入及其嵌套列表。模型可以读取指定文件、改写它、运行固定测试并结束任务，控制器不替模型修改代码。关闭 thinking 时，模型在 12 轮内读文件一次、改写五次、运行测试六次，仍未完成；开启后，四轮分别是输出截断、写文件、运行测试和结束。首轮无效生成也花了时间，必须留在任务记录中。[^agent]

检索增强问答也可以放进这张图。检索器决定返回哪些文档，文档成为语言模型的输入。为了达到同样的回答质量，一个检索方案可能只需少量高相关内容，另一个可能需要更多文档。后者不仅增加检索输出字节，还增加 prefill、KV 和后续历史读取。这里先把“检索结果怎样进入模型”接好，第八章再用固定质量任务比较候选，避免把少返回文档直接当成更优方案。[^retrieval]

### 3.2.4 分支、工具等待与状态驻留

先看同一代码任务的两种实际轨迹。

| 观察 | Thinking 关闭 | Thinking 开启 |
| --- | ---: | ---: |
| 模型调用轮数 | 12 | 4 |
| 总输出 token | 765 | 2,733 |
| 模型调用墙钟之和 | 13.156 s | 76.294 s |
| 工具墙钟之和 | 0.476 s | 0.078 s |
| 独立返回值与调用后输入不变检查 | 315/1013 | 1013/1013 |
| 额外返回子列表无别名检查 | 1/1013 | 710/1013 |

关闭 thinking 的轨迹缓存命中约 83.4%，仍未修好代码；开启后，模型时间增加，原任务的返回值与调用后输入不变检查全部通过。额外的无别名检查要求返回子列表与原输入相互独立，开启轨迹在其中 710 个用例通过，另 303 个仍共享了子列表。[^agent] 两组检查分别对应两种程序性质，解释了为什么任务完成标准必须具体到可执行的验证。

开启模式共输出 2733 个 token，其中 2553 个在 thinking 结束符之前，3 个为结束符，177 个在之后。思考占据绝大多数生成工作，工具调用则把生成的决定转为文件修改与测试。模型墙钟与工具墙钟沿轨迹依次相加，便形成用户经历的任务时间。

**例题 3-2：加速首轮能节省多少任务时间？** 用第一章的 Amdahl 分析，假设后续行为与质量不变。

**解：** 沿同一轨迹做一次条件替换：只把首轮 36.375 秒的模型段缩短一半，其余阶段、输出、工具行为和质量都不变，总时间便从 76.510 秒降到 58.323 秒。此时 $f=36.375/76.510$，$s=2$，总加速比约为 1.31；首轮加速两倍的收益受其原有时间占比限制。首轮占总时间约 47.5%，将这一段减半节省约 23.8% 的总时间；其余阶段继续形成约 40.1 秒的固定部分。优化收益由被缩短阶段的原有占比决定。[^agent-speedup]

工具并行也需要沿依赖分析。若两个工具互不依赖，同时启动后等待两者结果，理想关键路径由二者最长者决定；若第二个工具要用第一个工具的输出，它们就必须串行。两种情况下，模型恢复前可能都要保留前缀。并行分支还能共享相同历史，但各自生成的尾部独立增长。共享成立时，逻辑状态可写成“一份公共前缀加各分支尾部”；没有实际共享时，容量仍要按副本计算。

这条轨迹的工具调用很短，模型段主导全程。若工具改为 10 秒编译，模型暂停的同时，下一轮所需历史仍占据容量；若多个任务同时等待，驻留量按任务累加。工具时长因此通过状态寿命影响可承接的并发，第八、九章将在这条时间线上安排缓存与交接。

## 3.3 多模态与实时交互

### 3.3.1 视觉 E→P→D 与 EC／KV

图片进入语言模型之前，还要经过预处理、视觉编码和投影。用 E 表示视觉编码，P 表示语言 prefill，D 表示后续 decode，一次视觉问答便有 E→P→D 这条基本依赖。图片大小影响 E，编码后视觉位置数影响语言部分；这两项工作应分别计算。

以固定的 Qwen3-VL-4B 为例，预处理后的 $640\times640$ 单图按 $16\times16$ patch 划分，得到 $40\times40=1600$ 个 patch，再按 $2\times2$ 空间合并，形成 400 个视觉位置。最终语言 embedding 宽 2,560，BF16 的 $[400,2560]$ 张量占 2,048,000 bytes。

但编码结果不止这一份。模型还取三个中间视觉层的 DeepStack 特征，固定实现将它们与最终输出一起交付，完整张量为 $[400,10240]$，占 8,192,000 bytes，即 7.8125 MiB。四组特征对应同一组 400 个位置：特征宽度变为四倍，语言序列仍增加 400 个位置。视觉阶段本身的已计矩阵工作约 1.310 TFLOPs，尚不含 CPU 图片解码、resize 和后续语言计算。[^vision]

编码结果称为 EC，语言主干产生的状态是 KV。该配置的语言 KV 每位置占 144 KiB，400 个视觉位置对应 56.25 MiB。于是同一张教学截图可以同时有三个大小：原始压缩文件 0.8 MB、完整 BF16 EC 7.8125 MiB、视觉位置的逻辑 KV 56.25 MiB。原图经过视觉编码形成 EC，EC 进入语言主干后形成各层 KV，表示随处理阶段逐步展开。[^epd]

| 对象 | 本例大小 | 决定它能否复用的条件 |
| --- | ---: | --- |
| 压缩截图 | 0.8 MB，教学输入 | 同一文件内容 |
| 完整编码结果 EC | 7.8125 MiB | 图片、预处理、编码器与输出格式一致 |
| 视觉位置的语言 KV | 56.25 MiB | 还依赖先前上下文、顺序、位置与模型状态 |

同一图片回答不同问题时，EC 可能复用；语言 KV 则还要检查问题放在图片前还是后、此前历史是否改变。四张相同规格图片的 EC 为 31.25 MiB，视觉位置 KV 为 225 MiB；再加 400 个文本位置，输入逻辑 KV 为 281.25 MiB。特殊 token、输出增长、分页碎片和工作区另计。

三个大小对应三个交接位置。发送原图，接收端还要执行视觉编码；发送 EC，接收端从语言 prefill 开始；发送 KV，则交接已经完成的语言历史。第八章安排同卡执行，第九章比较阶段交接，第十二章把相同数据流放到端、边、云链路上。

### 3.3.2 音频与图像生成的工作单位

音频输出还有帧内循环。以 Fish Audio S2 Pro 为例，slow 路径沿音频时间推进，fast 路径在每帧内补齐码本，再由 codec 解成波形。固定路径每帧先做一次 fast 预热，再做九次预测，第一次未使用的 logits 也付出了计算。语言 token/s、声学帧/s 与每秒生成多少秒声音因而是不同指标。Qwen3-Omni 的 Talker、码本与波形阶段保留在[多模态计算资料](../case-studies/generative-multimodal-models.md)，同样按实际调用计数。[^media]

图像生成又换了一种循环。以本书固定 Qwen-Image-2512 路径为例，$1024\times1024$ 图像形成 4,096 个 latent 位置，执行 50 个去噪步，true CFG 路径每步有两支 DiT 前向，总共是 100 次。去噪矩阵工作约 $7.830\times10^{15}$ FLOPs；文本编码器与 VAE 还有各自的工作。latent 的位置集合在去噪期间保持固定，各步持续更新其内容，累计工作随去噪步数增加。[^image]

文本生成不断追加位置，图像去噪则反复更新同一组 latent。增加图像分辨率扩大每次前向的位置数，增加去噪步数增加重复次数，启用引导分支增加每步调用数。视频再加入帧数与时空压缩，资源预算依然从“单次尺寸乘实际调用”展开。

先数实际调用，再比较资源，是这些模型共同需要的步骤。内部循环数决定累计工作，阶段依赖决定哪些时间可以重叠，输出质量决定比较是否成立。

### 3.3.3 连续感知、首段响应与打断

实时任务除了完成内容，还要在内容仍有用时完成。截图 Agent 若只在动作结束后观察，可能错过两次动作之间出现又消失的弹窗。作者参与的 AOI 研究把观测与动作分开考虑：持续产生的图像、音频和事件，经筛选后成为可供后续模型消费的记录。这样可以提高事件覆盖，但增加关键帧也可能挤占上下文，论文摘要报告了部分模型效果退化的情况。因此，更高观测频率还需配合筛选、保存和消费预算。[^aoi]

语音的时间约束更直接。用户停止说话后，系统要采集或确认输入，经过识别／编码、推理、语音生成和播放。首块在客户端到达，只说明数据已到；扬声器开始出声还取决于解码、缓冲和设备时钟。开始播放之后，供给又必须跟上消费。

本书保留两份历史语音记录，共 163 个音频块。以客户端事件计时，从第一次 `user_speech_stopped` 到下一块 `agent_audio` 到达分别为 399.919 ms、370.459 ms，选定窗口内相邻到达间隔中位数约为 93.889 ms、93.806 ms。[^audio-real] 这些事件标出声音到达应用的节奏；播放端随后还要解码、排队并按设备时钟消费。下面用一条教学时间线，把到达与播放之间的缓冲展开。

为了看清缓冲的作用，另做一份明确的教学时序。输入每 20 ms 形成一块，24 kHz、单声道、每样本 2 bytes，每块载荷为：

$$
24{,}000\times0.020\times1\times2=960\ \mathrm{bytes}.
$$

每块采集结束后，模型处理 12 ms、发送 1 ms，通常再传播 5 ms。第一块在 38 ms 到达，等待 40 ms 抖动缓冲后，于从采集起点算起的 78 ms 开始播放。第三块的传播延迟被设为 50 ms，直到 123 ms 才到，错过 118 ms 的播放计划，造成 5 ms 新增停顿。后续块虽已到达，也要按声音顺序等待。

将缓冲改为 60 ms，这次停顿消失，首播却推迟到 98 ms。增加缓冲可以吸收本次抖动，代价是更晚开始；若平均供给长期慢于播放，有限缓冲终究会耗尽。[^audio]

![图 3-4 实时交互的端到端时序](ch03/figure-3-4-realtime.svg)

*图 3-4：上部连接视觉和语音的阶段；中部用教学时长展示到达、播放和迟到；下部把两份历史记录的首块接收时间与未知的播放／取消项分开。教学缓冲对照不作为两份真实语音的性能解释。*

打断沿控制链依次生效：应用发出取消，播放设备静音，后端停止生成，缓冲与状态释放。教学时序在 123 ms 发出打断，控制延迟 5 ms，设备每 10 ms 生效一次，于是 130 ms 静音，用户感知响应为 7 ms。后端停止生成决定后续计算何时结束，缓冲释放决定容量何时可供其他任务使用，三者分别对应声音、计算与存储的停止时刻。[^audio-interrupt]

RAW 图片精修的截止则是完整成片可用，不要求像语音那样持续供给。它也不能以视觉理解的 EC 替代原始图像信息。任务目标确定之后，才知道应优化第一段、连续间隔还是最终完成时间。

> **实验 3-5 · 延伸：实时语音的响应预算**
>
> 先按八块教学输入复算 40／60 ms 缓冲的首播与停顿，再加入 123 ms 打断。随后读取历史到达记录，逐项指出哪些时间能够观察、哪些仍然缺失。改变模型、网络与缓冲的收益比较，需要同一固定音频及对应阶段的实际记录。

## 3.4 训练的计算与状态需求

### 3.4.1 前向、反向与更新状态

推理通常固定参数，训练则要根据损失修改参数。从第二章的一层线性变换开始：$X$ 的形状为 $[m,k]$，$W$ 为 $[k,n]$，输出 $Y=XW$。前向矩阵乘约需 $2mkn$ FLOPs。给定损失对 $Y$ 的梯度，反向还要计算两项：

$$
\frac{\partial L}{\partial X}=\frac{\partial L}{\partial Y}W^{\mathsf T},\qquad\frac{\partial L}{\partial W}=X^{\mathsf T}\frac{\partial L}{\partial Y}.
$$

把这三项并排看，就能理解训练为什么比一次前向多出两份矩阵工作。这里把一次乘加计为两个 FLOPs。

| 操作 | 要解决的问题 | 左、右输入的形状 | 输出形状 | 矩阵 FLOPs |
|---|---|---|---|---|
| 前向 $Y=XW$ | 根据输入求输出 | $[m,k]$ 与 $[k,n]$ | $[m,n]$ | $2mkn$ |
| 输入梯度 $\mathrm dX=\mathrm dY W^{\mathsf T}$ | 将误差传回前一层 | $[m,n]$ 与 $[n,k]$ | $[m,k]$ | $2mkn$ |
| 权重梯度 $\mathrm dW=X^{\mathsf T}\mathrm dY$ | 求这层权重的调整方向 | $[k,m]$ 与 $[m,n]$ | $[k,n]$ | $2mkn$ |

两次矩阵乘各约 $2mkn$ FLOPs，因此这一层的前向、输入梯度和权重梯度合计约 $6mkn$。把各 token 实际执行的可训练参数矩阵相加，就得到 $6ND$ 的常见近似。这里 $D$ 表示训练 token 数；生成的额外调用次数统一记为 $n_d$，阶段图中的 D 仅是 decode 的名称。[^training]

常数 6 来自同一线性层的前向与两个梯度矩阵乘。对稠密主干，各 token 使用同一组参数矩阵，逐层相加就得到 $6ND$ 的主体。MoE 按选中专家累计，嵌入按查行处理，注意力 QK／PV 则按位置对累计；这三种操作分别由调用集合、查表与序列长度决定工作。后面用 Qwen3-8B 将粗估展开为逐项预算。

反向需要前向留下的信息。计算 $\mathrm dW$ 要使用 $X$，非线性反向要保存其必要中间量，参数梯度在反向中产生，优化器状态则跨更新保留。它们的寿命不同：某层激活在该层反向结束后可以释放，优化器动量通常一直留到下一次更新。前向产生的激活要等待相应反向才能释放，因此反向传播把中间数据的寿命从相邻算子之间延长到了前后两次遍历之间。

**例题 3-3：训练状态为什么超过推理权重数倍？**

**解：** 以 Qwen3-8B 的 8,190,735,360 个参数为例，采用 BF16 权重、FP32 梯度、独立 FP32 master 权重以及 Adam 的两个 FP32 moment，无分片。每参数需要 $2+4+4+4+4=18$ bytes，共 147.433 GB，约 137.308 GiB。BF16 权重用于前反向，梯度保存更新方向，master 权重承接高精度更新，两个 moment 累积梯度统计。正是这些跨更新保存的副本，使参数相关状态达到推理 BF16 权重的九倍。[^train-matrix]

一个微批与一次参数更新也要区分。显存放不下完整训练批时，可以分多个微批累计梯度，最后再更新一次参数。只要目标、有效标签和归一化保持一致，微批数增加并不意味着相同数据被训练了更多轮；它首先改变的是执行顺序与激活寿命。第十章将据此讨论分片和流水。

训练还需要持续供给下一批输入。CPU 读取、解码、分词并整理批次，再把张量送到设备。双缓冲可以让当前批计算时准备下一批：一个缓冲供计算读取，另一个接收新数据，交替使用。计算耗尽已准备数据时会等待输入，取回设备结果时又会等待相应计算完成。第五章将把这些交接接到前向—反向—更新的时间线上。

### 3.4.2 预训练、中期训练与 SFT

预训练和中期训练常沿用相同的自回归预测与梯度更新过程，变化主要发生在数据、序列长度、学习率和能力目标。“中期训练”并没有统一分界，读报告时应看实际阶段。

Qwen3 报告给出一条具体路径：通用阶段在 4,096 长度上使用超过 30T token；随后增加 STEM、代码、推理与合成数据比例，再训练约 5T，长度仍为 4,096；长上下文阶段采用数千亿 token，将长度扩到 32,768。该阶段语料中，75% 长度在 16,384–32,768，25% 在 4,096–16,384。第二阶段虽然叫 reasoning stage，仍是这里讨论的预训练阶段，不应与后训练 RL 混为一谈。[^qwen]

系统需求随长度改变。假设两组独立文档都含 8,192 个 token：一组为 $4096+4096$，另一组为 $7168+1024$。参数投影的行数相同，因果注意力的有效位置对却分别为 16,781,312 和 26,218,496。在 Qwen3-8B 一层上，QK／PV 前向工作约从 0.275 增到 0.430 TFLOPs，增加约 56%。较长文档中的位置可以看到更多前文，所以在总行数不变时，历史交互增加；投影与 FFN 仍处理同样的 8192 行。整层增加量由这笔新增交互占原有工作的比例决定。[^training]

SFT 增加了输入与有效标签的区别。一条样本可能包含系统提示、用户问题、工具内容和回答，而损失只计回答位置。即使某些位置不计损失，它们仍参与上下文计算。是否只对有监督位置执行词表头，是具体实现选择；只设置 loss mask 不会自动剪掉主干矩阵。

部分参数训练减少需要保存梯度与优化器状态的参数集合。冻结模块的权重保持不变，但梯度仍需穿过它们传到较早的可训练模块，因此相应输入梯度继续执行。沿反向图逐层判断是否求输入梯度、是否求权重梯度，就能把训练状态与计算分别算清。

### 3.4.3 从 $6ND$ 到分项训练预算

现在完整算一组固定输入：Qwen3-8B，$B=1,\ T=8192$，全参数训练，所有位置执行词表头，没有重计算。逐层累计投影、FFN、QK／PV 与输出头，矩阵工作如下。[^train-matrix]

| 已计工作 | TFLOPs |
| --- | ---: |
| 前向矩阵 | 143.789 |
| 反向矩阵 | 287.579 |
| 前向加反向 | 431.368 |
| 其中因果注意力 QK／PV 前反向 | 59.381 |
| 总参数代入 $6ND$ | 402.591 |

矩阵总量比 $6ND$ 高约 7.15%。差额由两类修正共同形成：序列位置之间的 QK／PV 增加工作，嵌入查行和归一化等参数则从“每 token 完整矩阵乘”的粗估中移出。将实际矩阵逐项相加，得到 431.368 TFLOPs；其中历史交互的前反向为 59.381 TFLOPs。

若有效标签减到 4,096，但仍使用 dense 词表头，矩阵工作不变；显式 gather 有监督位置、只对这些位置计算词表头后，工作降到 416.074 TFLOPs。压缩词表头省去无监督位置的词表投影，主干则继续处理完整上下文；选择位置与散回梯度连接了这两种形状。[^mask]

## 3.5 RL：生成、反馈与更新

### 3.5.1 Rollout、奖励与环境验证

前面的推理从外部请求开始，预训练从已有文本开始。RL 则把两条路径接起来：当前策略先生成候选，再由反馈决定怎样更新参数，更新后的策略继续产生下一批数据。生成过程通常称为 rollout。

DeepSeek-R1 提供了从推理任务和可验证奖励出发的训练路线。对代码、数学等容易检查的任务，反馈可以来自规则或测试；对需要实际操作的任务，则要运行工具与环境。奖励若由另一个模型生成，还会产生额外推理。一次“训练迭代”因此可能包含多个模型、CPU 测试、沙箱等待和梯度更新。[^r1]

V4 先通过 SFT 和 RL 训练领域专家，再以多教师 on-policy distillation 将能力合入统一模型。OPD 由学生生成轨迹，教师在这些位置提供分布，学生据此学习。教师前向因此成为生成与更新之间的一项模型工作；规则验证则以测试或程序执行提供反馈，形成另一条资源路径。[^v4]

从负载角度看，这些路线共同要求记录：谁产生轨迹、哪些模型读取它、是否需要工具环境、哪些 token 参与学习、何时更新权重。并行和共置可以随后改变，工作与依赖应先明确。

### 3.5.2 有效样本、策略更新与权重交接

假设八个 prompt，每题生成四个候选，共 32 条；筛选后接受 16 条。拒收候选没有进入策略更新，但已经消耗生成和评分。若只统计接受样本，会低估采样与反馈的资源。

训练配方决定接受哪些样本。有的配方保留失败轨迹作为负反馈，有的过滤截断或无有效奖励的回答；组内优势还需要比较同组候选的奖励差异。因此，接受样本数决定进入更新的数据量，奖励与损失规则决定这些数据产生怎样的梯度。

**陷阱实例：完成一次更新不等于取得学习进展。** 固定 verl 小模型实验中，同组回答全对、奖励相同，减去组内基准后优势为零，策略梯度也为零。改变控制奖励后得到非零梯度。[^verl] 这一对照揭示反馈的作用：生成样本提供了数据，候选之间的奖励差异才为该配方提供调整方向。

样本组织还决定学习目标。不同长度回答若按 token 平均，梯度累计应保留同一个全批有效 token 分母；先对每个微批求均值再平均，可能改变样本权重。第十章将沿固定配方展开这一过程。[^verl-loss]

更新后还要把策略权重送给生成端。若生成端继续使用旧版本，下一批数据对应的策略就不同。同步循环可以等权重就绪后再生成；异步方案允许部分阶段重叠，却要处理样本版本与滞后。第三章先保留这条依赖，第十章再讨论交接、抢占、恢复和资源配比。

### 3.5.3 同一有效样本目标下的阶段需求

**例题 3-4：固定有效样本目标，接受比例降低需要多少额外工作？**

**解：** 用 Qwen3-8B 计算一份教学批次，避免直接猜测大模型系统的实际部署。固定 8 个 prompt、每题 4 个候选，$P=1024,\ G=256$，接受 16 条；所有候选执行一次同配置 reference 前向，接受样本执行一次策略更新，没有教师评分。各样本等长，不提前停止，不共享前缀。[^rl]

生成时每条先做一次 prefill，再做 255 次 decode。训练与评分时，轨迹已经已知，可以按 teacher-forced 前向处理：输入长度 $P+G-1=1279$，256 个输出标签位于相应位置。16 条接受样本每轮更新的输入位置共 20,464，监督输出共 4,096。输入位置决定上下文计算，监督位置决定损失作用于哪些输出，二者分别进入训练预算。

| 阶段 | 处理样本 | 已计矩阵工作，TFLOPs |
| --- | ---: | ---: |
| Rollout prefill | 32 | 465.143 |
| Rollout decode，255 步／条 | 32 | 129.056 |
| Reference 评分，一次前向 | 32 | 634.944 |
| 教师评分，设为零次 | 0 | 0 |
| 策略更新，一次遍历 | 16 | 952.416 |
| 合计 | 接受 16 条 | 2,181.559 |

reference 对全部候选提供评分，策略更新只读取接受样本，所以两者处理的样本集合不同。一次已知轨迹的评分可以并行处理多个位置，rollout 则必须逐步产生未知输出。即使来自同一模型，这两阶段也形成不同的矩阵行数与调用节奏。优化器、损失算术和环境验证沿各自操作另行累计。

如果接受比例从 1/2 降到 1/4，但仍要求得到 16 条接受样本，教学对照改为生成 64 条。生成与 reference 评分翻倍，更新量不变，总矩阵工作增到 3,410.701 TFLOPs，约增加 56.3%。每个接受样本承担的矩阵工作从 136.347 增到 213.169 TFLOPs。增加的 1229.142 TFLOPs 全部来自额外候选的生成与 reference 评分；进入更新的 16 条样本保持不变。[^rl-low]

![图 3-6 RL／OPD 的工作与数据流](ch03/figure-3-6-rl.svg)

*图 3-6：上部按生成、反馈、筛选、更新和权重交接画依赖，教师支路单列；下部为 Qwen 教学批次。图示参考 V4 的工作组织，但数值不是 V4 实测。接受 16 条的目标不变，拒收候选仍计入生成与评分。*

一次完整 BF16 Qwen3-8B 权重快照为 16.381 GB。若给每个 rollout 副本各独立发送一次，载荷为副本数乘快照大小；优化器状态不需要因此一起发送。这只是最简单的传输模型，广播、增量更新、转换与设备布局会改变实际路径。

阶段配比由工作量与执行形状共同决定。rollout 的 decode 反复执行少量输入行，评分和训练读取已知轨迹形成较大矩阵，工具验证则使用 CPU 与环境资源。将每阶段工作换成对应资源时间，再沿生成—反馈—更新—权重交接连接，就得到一个完整周期。第四至第十章将逐步补上这些阶段的供给与调度。

## 3.6 从负载需求到训练与服务预算

### 3.6.1 Scaling Law：拟合、验证与适用范围

算清一次更新之后，下一个问题是：固定总计算预算，应训练更大的模型，还是让较小模型看更多数据？Scaling Law 用受控实验中的统计关系回答这类问题。一个常见形式是：

$$
L(N,D)=E+\frac{A}{N^{\alpha}}+\frac{B}{D^{\beta}}.
$$

$L$ 是验证损失，$N$ 是参数规模，$D$ 是训练 token 数。$E$ 表示模型中的渐近项，另外两项描述规模和数据不足时的损失。它是一种可拟合模型，系数依赖数据、架构、训练配方和统计方法。

若暂按 $C=6ND$ 固定训练计算，将 $D=\frac{C}{6N}$ 代入并对 $N$ 求极值，可得：

$$
N_{\mathrm{opt}}=\left(\frac{\alpha A}{\beta B}\right)^{1/(\alpha+\beta)}\left(\frac{C}{6}\right)^{\beta/(\alpha+\beta)}.
$$

在 $A,B,\alpha,\beta$ 为正的拟合模型中，增加参数会减少模型规模不足项，同时在固定计算预算下减少可训练的数据量、增大数据不足项。导数为零的位置平衡这两种变化，形成式中的连续最优点。实际选择宽度与层数时，再比较这一点附近的离散配置。

Kaplan 等人的早期研究给出约 $N\propto C^{0.73},\ D\propto C^{0.27}$ 的分配关系；Chinchilla 研究用不同实验和拟合，得到模型规模与数据量应随预算更接近等比例增长的结果。前一种分配更快增加模型参数，后一种把更多新增预算分给训练数据；曲线及其拟合指数因此直接改变参数与数据的选择。[^scaling]

**例题 3-5：怎样检验一条 Scaling Law？** 从公开训练记录中固定六个较小模型的观测用于拟合，另将两个较大模型的观测留出。先选定拟合方法，再比较留出预测与观察值。

**解：** 本书从 datablations 的作者 notebook 与匹配训练日志整理八个 C4 观测，以 $N\ge2\times10^9$ 的两个点作事先留出。固定指数网格拟合后，两个观测损失约为 2.574、2.337，预测为 2.583、2.363，留出 RMSE 约 0.0193 nats/token。图 3-7 保留拟合与留出身份，完整系数和敏感性见[八点拟合](../calculations/results/datablations-real-c4-eight-point-fit.md)。[^fit]

留出误差将拟合变成了可检查的预测：六个点确定曲线，两个更大模型检验外推。约 0.0193 nats/token 的 RMSE 汇总了本次两个预测与观测的差额；模型族、训练数据和拟合系数作为一组实验条件保存在配套记录中。

验证损失到业务能力还隔着一步。Llama 3 报告先由训练预算预测损失，再建立损失与任务表现的关系。这样做的原因很实际：部署方关心代码、检索或工具任务能否完成，并不直接购买较低的语言模型损失。从损失预测接到任务评测，才能将训练预算连接到部署所需的能力。[^llama3]

配套还提供固定数据、三个规模、两个 seed 的小模型训练，以 nats/byte 记录损失。最大模型在有限训练中并非每个 seed 都最好。[^local-train] 同一规模的不同初始化形成不同学习轨迹，因此用重复训练观察波动，是从单条曲线走向预算预测的一步。

长期服务会把每次调用的费用累积到训练预算之上。较小模型可以通过更长训练达到目标质量，前期多付费用，之后每次调用读取更少权重、执行更少工作。Beyond Chinchilla-Optimal 将这种推理需求纳入分析，47 个模型覆盖 150M–6B；其中 150M 模型测试到 10,000 token／参数，较大模型测试到 1,000。[^beyond] 训练预算与服务次数共同决定较小模型的额外训练何时收回成本。

更长训练、数据筛选、蒸馏和后训练，把更多前期工作用于提高给定规模模型的任务能力。固定 Llama 3 模型卡的 base 表中，Llama 3 8B 与 Llama 2 70B 在 MMLU 上分别为 66.6／69.7，TriviaQA-Wiki 为 78.5／87.5。[^cost] 两项差距不同，说明部署方要按自己的任务选择质量门槛；通过门槛的小模型，才有机会把较小权重带来的容量与读取收益转成服务收益。

大模型与 MoE 则要并列总参数和激活参数。DeepSeek-V3 报告为总参数 671B、每 token 激活约 37B、预训练 14.8T；V4-Flash 为 284B／约 13B、32T，V4-Pro 为 1.6T／约 49B、33T。总权重影响容量，激活参数只提供计算代理。V4 主干专家的三个投影可单独计算：

$$
C_{\mathrm{expert/token}}=18Lhf(k_{\mathrm{routed}}+k_{\mathrm{shared}})=18Lhf(6+1).
$$

Flash 的主干专家约 45.4495 GFLOPs/token，按 32T 累计约 $1.45438\times10^{24}$ FLOPs；Pro 约 169.2465 GFLOPs/token，按 33T 累计约 $5.58513\times10^{24}$ FLOPs。这只含专家矩阵，注意力、路由、MTP、优化器和重计算仍未加入。报告的损失权重也不是执行比例，例如 MTP 权重为 0.3，不表示只执行 30% 的辅助计算。[^training]

用 GPU 小时换算日历时间，要除以同期使用的卡数。对 Llama 3.1 405B，取公开的 30.84M H100 GPU 小时，并假设这项工作全部使用最大规模 16,384 卡，计算为 $30.84\times10^6/(16384\times24)\approx78.43$ 天。阶段使用的卡数更少时，相同 GPU 小时需要更长日历时间；训练资源的分配时序因此决定交付期限。

>

### 3.6.3 质量约束下的生命周期预算与交付

到这里，可以把模型的一生接起来。前期投入包括数据、训练、教师生成与评测，服务期间持续支付模型、工具、环境和运行成本。设候选 $m$ 的前期费用为 $C_0(m)$，未来有 $Q$ 个任务，第 $j$ 类任务占比为 $w_j$、每任务平均费用为 $c_j(m)$，则简化总费用为：

$$
C_{\mathrm{life}}(m)=C_0(m)+Q\sum_jw_jc_j(m).
$$

比较之前，各候选都要满足相同质量、时限与完成条件。若任务成功率不同，$c_j$ 中还需包含失败和重试；价格变化、模型寿命、维护与贴现等假设也应随预算说明。

若新模型额外训练 $\Delta C$，却使每个合格任务节省 $\Delta c>0$，简单的收回投入条件为 $Q\ge\frac{\Delta C}{\Delta c}$。例如额外投入 100 万美元、每次节省 0.002 美元，需要 5 亿次任务。前 5 亿次调用逐步偿还额外训练费用，此后的调用继续累积净节省。于是，预期需求量把一次性的训练选择与长期部署联系起来。

本章交给后文的输入可以收成三份表。它们共用描述方式，但保留各自模型和证据。

| 负载 | 必须保留的字段 | 后续使用 |
| --- | --- | --- |
| Chat／Agent | 任务检查、模型与版本、每轮输入／命中／输出、到达、工具依赖、分支与复用间隔 | 第 8 章安排批处理与状态；第 9 章交接与路由；第 11 章管理工具环境 |
| 视觉／实时 | 原图字节、E/P/D、EC/KV、帧或块到达、首段／持续供给目标、打断与过期工作 | 第 8、9 章安排编码和交接；第 12 章加入链路与执行位置 |
| 训练／RL | 数据与质量、长度和标签、微批／更新、候选／接受、反馈与模型调用、权重版本、完成期限 | 第 4–7 章检查供给与协作；第 10 章安排学习；第 11 章配置环境与资源池 |

三类例子沿同一条逻辑收束。两分钟负载把请求组成转成阶段积压；代码 Agent 把工具依赖转成等待和状态寿命；RL 把候选筛选转成生成与更新之间不同的数据量。平均 token 数被展开为实际调用、先后关系和在途状态，系统才能按这些需求安排资源。

第四章开始加入芯片资源。把本章得到的矩阵形状、状态大小、访问次数与阶段依赖放到设备上，便能回答计算单元是否忙得过来、存储是否放得下、数据能否及时送达。模型结构、负载时间线与硬件供给至此接成同一条分析路径。

## 谬误与陷阱

**均值相同就是同一负载。** 请求长度的尾部、输入输出的配对和到达顺序决定短窗需求。例题 3-1 的平均供给通过检查，后一分钟仍会积压。

**token 更便宜，完成任务也更便宜。** 额外思考、失败候选、工具与环境都应进入分子，合格任务数进入分母。零成功的批次只能报告消耗与失败，不能估计成功成本。

**训练了相同数量的 token，系统工作就相同。** 序列分布改变注意力位置对，标签与词表头策略改变输出工作，更新次数改变优化器成本；RL 还包含未接受候选的生成与反馈。

## 本章小结

持续负载由单次需求、到达与依赖共同形成。平均速率用于初筛，短窗积压和状态寿命揭示被平均掩盖的限制。多轮任务要保留工具等待与失败尝试，实时任务要区分到达和消费；训练则增加反向、更新与跨版本交接。

预算比较始终保持质量与完成目标一致。Scaling Law 为训练分配提供可检验的统计模型，长期服务需求又可能改变前期投入的选择。核心练习 3-2、3-4、3-7 分别把这些方法用于持续请求、交互任务和 RL 循环。
