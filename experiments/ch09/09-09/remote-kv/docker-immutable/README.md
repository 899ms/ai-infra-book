# Docker TCP KV恢复控制：通过，保留重复键差异

按作者要求使用rtx-pro Docker，无E2B凭据。此处是9-9存储后端功能控制；11-2的创建、暂停、快照与重建实验另见[Docker生命周期](../../../../ch11/11-02/docker-lifecycle/README.md)。

Qwen3-8B BF16、SGLang0.5.13.post1、1024固定输入与16强制输出；生产者3请求后退出，再由新引擎请求3次。独立Docker文件存储通过127.0.0.1 HTTP传递真实KV页，保留原生key和页布局。容器固定image ID见docker-inspect.json，1CPU／512MiB、无GPU、非privileged。GPU只用于模型；两引擎exit0，监督记录无GPU残留，实验容器已删除，绑定目录保留。

六请求文本和完整output_ids均一致，均16输出、零retraction。消费者64次get取回页文件，每页2,359,296bytes；HTTP响应payload合计151,015,360bytes，客户端get累计0.403383s。该计时含CPU／协议／文件缓存，既不是物理SSD带宽，也不是跨机器或WAN数据。首请求整体恢复未快于生产者冷请求，不由命中率推断加速；一个功能样本也不能报告代表性p95。

`analyze.py`在RTX主机逐页核验SHA、文件长度、客户端与服务端账本对应、运行源码SHA、命中来源、输出及清理，输出summary.json。读取64页，最终65个主文件；最终数量包含请求期间后续发布，不能当成初始输入页数。运行源文件保持与raw.json内SHA一致，analyze.py另修正说明中的旧“through SSH”措辞，实际传输为同机loopback。

## 已存在键策略与不一致

先前[docker-control](../docker-control/)以重复键必须字节相同为门槛，消费者已成功恢复后一次set被HTTP400拒绝，exit1。该失败独立保留。这里采用原生HiCacheFile的先写保留语义，已存在键不覆写；同时记录incoming／stored SHA并保存冲突副本。不是删除数值门槛，输出与传输完整性检查仍执行；但此语义不检查重写内容等价。

`analyze_collisions.py`用CPU解析BF16，核验了1个冲突页：2,359,296bytes、1,179,648元素，其中1,045,586bytes及971,941数值不同，最大绝对差4.5、相对L2差0.04058848。此key是生产者第65个set（零起点64），消费者有一次对该key的set；**不属于消费者64个get中的任意key**。因此本次取回输入页的SHA检查通过，但不能推广为所有后续KV逐位相同，也没有验证未来请求使用冲突页的行为。未凭汇总统计断言差异成因。

所有主页和冲突原件保留在RTX同目录docker-store/；Mac只同步日志、源码、分析与哈希，未取回约150MB页镜像。文件通过rename发布但未fsync，无掉电持久性结论。`run_control.py`可在新的空目录复现；已有docker-execution.json时拒绝覆盖。结果与跨Mac的四次失败独立，完整9-9路由／Chat／Agent远端比较及9-8容量矩阵仍未完成。
