# Planned image recovery comparison

This protocol is preparation only; no completed recovery result is implied.

Use the same immutable10,656,312-byte RAW and4,556,971-byte JPEG fixture as image-records, including its0.483963046s measured CPU-service replay. Fix Docker network-none/NET_ADMIN,2CPU/2GiB,loopback netem80ms RTT,20Mbit/s,0.1% random loss. Keep receive settings at defaults and transfer concurrency1. HTTP/1.1 TLS1.3 and HTTP/3 both use new connections after an injected interruption.

Compare three policies: uninterrupted complete transfer; connection failure followed by full RAW reupload/reprocessing replay; connection failure followed by byte-range continuation of an already materialized immutable output. The interrupted paths close the client connection after at least1MiB of JPEG has actually arrived. Retain the exact received prefix length and hash, including read-chunk overshoot. Do not pretend the connection itself resumes. Reconnect immediately with a new connection, with no configured backoff; connection setup and verification count in completion latency. Full restart discards the prefix and repeats complete upload/service/output. Continuation retains the prefix and requests the remaining range by immutable operation/output identity, validates range metadata and concatenates only matching output bytes. Verify the final complete JPEG and decoded RGB in every successful case.

Cache/storage retention is an explicit policy prerequisite: the server keeps the already-produced JPEG in memory for range continuation during its process lifetime. This does not prove recovery from server/process loss, resumable partial RAW uploads, durable image storage or resumption of incomplete GPU computation. Server-side extra bytes generated/queued after interruption must not be mistaken for client-delivered bytes. Save per-phase upload size, received prefix/suffix, connection identities, fault timestamps, service invocations, HTTP status/range metadata and qlogs. The source image is fixed; model service is a recorded wait, not new inference.

Use three shuffled repetitions of protocol × policy, with separate uninterrupted protocol warmups. Preserve all failures, complete timings and recovery overhead rather than selecting only successful attempts. Common120s request timeout and20s handshake timeout apply to all paths. Run after window-sizing releases its container so two benchmark containers do not compete for the same CPU or loopback shaping observation interval. The final report must distinguish measured byte/application recovery from physical WAN or acoustic behavior.
