## 原文阅读与采用

阅读全文：[Unified Bus 背后的思考](../../references/files/documents/ub-reflection.html)。采用的是设计问题、备选与权衡，具体协议保证沿用仓库已有规范核对入口；本轮没有宣称重新逐条验证全部 UB 规范。

| 原文部分 | 提炼的设计原则 | 大纲落点 |
| --- | --- | --- |
| 为什么要做 UB／总线与网络 | 统一应用表达和协作抽象，仍对实际物理距离、带宽和故障范围计价 | 7.1.3、7.6.4 |
| 主从架构与对等架构 | 数据由设备产生和消费时，考虑把反复发起操作的能力交给设备；管理与数据路径分别看 | 7.3.2 |
| 单边与双边语义／带立即数通知 | 数据搬运和通知承担不同责任，组合或融合两者以减少交互 | 7.3.1、7.4.1 |
| Load/Store 与 Read/Write／寻址／缓存一致性 | 指令、队列、缓存和异常处理之间分配责任，按依赖和访问粒度选择 | 7.3.3–7.3.4、7.4.1 |
| 强事务序与弱事务序／1Pipe | 统一排序的吸引力与故障处理的代价并存，先圈必要依赖，再确定顺序保证范围 | 7.4.2 |
| Jetty 与传输层解耦／HOL、公平性与隔离 | 应用关系和传输状态可以分开复用，共享程度由热点、寿命与隔离约束决定 | 7.4.3–7.4.4 |
| 拥塞控制／可靠传输 | 从信息、反馈时延和服务能力推导队列；分别选择丢失检测与重传范围 | 7.5.2–7.5.3 |
| 死锁避免／URPC | 让恢复和响应仍有前进路径；传引用的收益与访问量、表示及寿命一起计算 | 7.4.4、7.5.4 |

原文开头已说明早期设计与产品化版本可能不同。本章保留作者的动机与判断变化；原文有关事务序模式、缓存与原子性的概括不直接用作协议定义。必要依赖由程序正确性决定，AI 的概率性不能替代发布同步。原文中多路径、故障及状态资源的例子按已归档规范与实现分别核对，具体字段留在扩写资料。
