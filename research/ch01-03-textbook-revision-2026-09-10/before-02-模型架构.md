# 第 2 章 模型架构

第一章把一次模型执行分解为容量、计算与数据读取，并借助硬件的关键数字估算时间下界。这样的估算可以迅速排除一些方案，却还留下一个问题：所代入的计算量和数据量从哪里来？“一个 8B 模型”只说明参数数量的大致范围，没有说明每个 token 使用哪些参数、历史保存在什么地方，也没有说明不同工作之间的先后关系。

打开模型的计算图，才能回答这些问题。注意力将当前表示与历史位置联系起来，前馈网络用学习得到的权重变换每个位置的特征，残差路径连接网络深度上的表示。生成过程又把同一张图反复执行：权重通常保持不变，历史状态不断增加或者更新，一部分中间结果可以复用，另一部分必须重新计算。模型架构由此形成了对基础设施的需求。

本章先用 Qwen3-8B 完成单次前向与完整生成的资源核算，再分别改变历史状态、专家权重和网络组织，最后比较完整模型。重点是建立一种可复用的判断能力：给定配置和请求条件，能够指出需要保存什么、访问什么、执行多少工作，以及哪些工作必须等待。模型能力仍是这些选择需要满足的条件，资源分析本身不能证明某种架构具有更好的学习能力。

正文数字按解释所需保留精度，原始精确值、旧稿中的详细算例与配置核对保存在[修订前全文与核算细节](../research/ch02-teaching-revision-2026-09-09/before-manuscript.md)，对应结果文件仍可复算。

文中的数字采用本书仓库内固定配置、计算结果和实验记录。矩阵乘加计为 2 FLOPs，GB 表示十进制字节，GiB 表示 $2^{30}$ bytes；常规权重与 KV 算例使用 BF16，每元素 2 bytes，递推状态另列精度。特殊函数与非矩阵算术不混入矩阵 FLOPs。不同模型的参考执行路径有差异，文中会在相应比较处说明。完整来源与复现入口列于章末。

## 2.1 计算图与前向执行

理解模型资源需求，首先要把计算节点和数据依赖分开。一个节点执行矩阵乘法或其他变换，一条边表示后续节点需要前面的结果。节点的工作量决定需要多少处理能力，边上的张量决定数据量，边的方向则决定哪些工作能够同时推进。三者共同描述模型，单看参数量无法替代其中任何一项。

本章的计算图先描述数学运算和数据依赖。实际执行时，框架会把这些运算交给设备程序；一个运算可能拆成多个程序，多个运算也可能合在一起执行。图上的一条张量边只说明后续需要这份数据，不表示它一定要在 CPU 与 GPU 之间复制。第四章说明数据放在哪里，第五章再解释程序怎样提交、数据怎样传入传出。

### 2.1.1 序列依赖与因果计算图

考虑一个只有四个 token、三层网络的例子。把序列位置画在横轴，把网络深度画在纵轴。在普通 RNN 中，一个位置的隐藏状态由当前输入和前一位置状态共同决定，可写为 $h_t=f(x_t,h_{t-1})$。因此，同一层的第 t 个位置必须等待第 $t-1$ 个位置。历史被压入固定宽度的状态，序列变长不会使这个状态无限增长，但模型必须用有限表示保留后续任务需要的信息。

因果 Transformer 的依赖形式不同。第 l 层某个位置，通过注意力访问上一层不晚于该位置的表示。只要输入 token 已知，并且上一层的相应表示已经完成，同一层不同位置的计算就不需要再等待本层前一个位置的输出。三角形因果掩码限制信息来源，却不要求所有已知位置逐个执行。网络深度方向的依赖仍然存在：下一层使用这一层的结果。

这也是“将 RNN 旋转 90 度”的类比有帮助的地方：它把读者的注意力从时间方向串行移向网络深度上的处理。但类比到这里就需要停止。RNN 通常在时间上共享变换参数，Transformer 的不同层通常使用不同参数；注意力新增了内容相关的跨位置访问；历史也没有被压进同一个固定宽度向量。两张图的边集合并不相同，旋转坐标轴不能得到等价算法。

原始 Transformer 包含编码器和解码器。现代因果语言模型常用 decoder-only 主干，本章后续都以这一形式计算。这里的“序列并行”只表示已知位置之间的计算机会，不是多卡序列并行方案，也不意味着未知输出可以一次生成。第一个输出尚未确定时，作为下一次输入的 token 也尚未确定，生成过程仍有跨调用的因果依赖。[序列依赖计算记录](../calculations/results/sequence-dependencies-book.md)用同一模型分别做前缀重算和状态复用，以数值结果验证这一点。

### 2.1.2 模型配置与张量结构

接下来把教学图换成真实配置。Qwen3-8B 的主干有 36 层，隐藏维度 $d$ 为 4096，FFN 中间维度 $f$ 为 12288；注意力有 32 个 Q 头、8 个 KV 头，每头维度为 128。词表大小为 151936，词嵌入和输出头不共享权重。本书对照固定配置与 checkpoint 索引得到的总参数数目为 8,190,735,360，而不是恰好 $8\times10^9$。[固定配置与逐算子结果](../calculations/results/qwen3-8b-prefill-8192.md)保留了这一核对过程。

一次前向执行从 token ID 开始。词嵌入为每个 ID 查出一个 4096 维向量，向量依次经过 36 层注意力与 FFN，最后经过归一化和词表投影产生 logits。词嵌入是按 ID 选择行，不能因为嵌入矩阵常驻内存，就认为每次查询都会读取整个矩阵。词表输出头则将隐藏向量与词表矩阵相乘；只生成下一个 token 时，通常只需要最后一个输入位置的 logits。

设同时处理 B 条等长请求，每条本次输入 P 个已知 token。投影和 FFN 可以把它们的输入表示为 $X\in\mathbb{R}^{BP\times4096}$，即 $m=BP$ 行。每条请求只补入一个 token 时，$m=B$。第一种情形容易形成行数较大的矩阵，第二种在小 batch 下接近矩阵与向量的乘法。权重相同，输入形状却明显不同。

本章固定两个主要场景：$B=1$、无已有历史、$P=8192$ 的输入处理；以及 $B=1$、已有 8192 个历史位置时，再处理一个 token。为了避免混淆，S 表示本次调用前已有历史，P 表示本次已知输入，网络隐藏维度统一记为 d。最终输出数量 G 将在 2.2 定义。

| 配置项 | Qwen3-8B 固定值 | 对资源需求的直接影响 |
| --- | ---: | --- |
| 层数 $L$ | 36 | 重复的计算、逐层状态与深度依赖 |
| 隐藏维度 $d$ | 4096 | 子层输入输出与投影尺寸 |
| FFN 中间维度 $f$ | 12288 | 三个 FFN 矩阵的权重与计算 |
| Q／KV 头数 | 32／8 | 查询计算与历史保存宽度 |
| 头维度 $d_h$ | 128 | 每个头的点积与状态宽度 |
| 词表大小 $V$ | 151936 | 嵌入和输出头规模 |

**矩阵表的阅读方法。** 本章统一采用右乘记号。若 $X\in\mathbb{R}^{m\times k}$，$W\in\mathbb{R}^{k\times n}$，则

$$
Y=XW\in\mathbb{R}^{m\times n},\qquad N_W=kn,\qquad F_{\mathrm{GEMM}}=2mkn.
$$

例如，两行三维输入乘以一个 $3\times4$ 的权重矩阵，得到两行四维输出。输出共有八个元素，每个元素计算三个乘加，因此矩阵工作为 $2\times2\times3\times4=48$ FLOPs。输入行数增大时，计算随之增加，权重矩阵本身却没有变大。后面的模型表都沿用这条规则，读者不必记住展开后的十位整数。

| 符号 | 含义与使用范围 |
| --- | --- |
| $B,P,S$ | 请求数、本次每请求输入位置数、已有历史长度 |
| $m=BP$ | 投影处理的总行数；普通 decode 时 $P=1$，故 $m=B$ |
| $d,f$ | 主干隐藏宽度、前馈网络中间宽度 |
| $n_Q,n_{\mathrm{KV}},d_h$ | 查询头数、KV 头数、每头维度 |
| $N_{\mathrm{pair}}$ | 每层跨全部请求的有效因果位置对数，不含头数 |
| $t_e$ | 专家 $e$ 收到的行数；无丢弃路由时 $\sum_e t_e=mk_{\mathrm{top}}$ |
| $m_{\mathrm{out}}$ | 真正执行词表头的行数；只预测每请求末位置时为 $B$ |

矩阵表中的 FLOPs 按**单层、单次调用**列出，注明倍数的多路投影需乘该倍数；整模型再按对应层型数量累加。嵌入查询、归一化、激活、路由选择和状态更新另列，它们没有大 GEMM 也仍然需要执行。注意力交互一行统计有效位置对，参考实现中的掩码矩形计算或分块补齐需要另算。

### 2.1.3 注意力计算与位置表示

采用数学右乘记号，输入 X 经过三个线性投影得到 Q、K、V。Q 的总宽度为 $32\times 128=4096$，K 和 V 的总宽度各为 $8\times 128=1024$。因此，$W_q$ 为 $[4096,4096]$，$W_k$ 和 $W_v$ 各为 $[4096,1024]$。代码常把线性层权重以 $(d_{\mathrm{out}},d_{\mathrm{in}})$ 保存，读取源码时要先统一记号，不能把存储转置误判为另一种算子。

投影之后，将 Q 拆成 32 个头，把 K、V 拆成 8 个头。每组四个 Q 头共用一个 KV 头。对一个 Q 头，查询向量与允许访问位置的 K 做点积，缩放后加因果掩码，再做 Softmax，得到不同历史位置的权重。随后用这些权重对 V 加权求和。各 Q 头的结果拼接后，经 $[4096,4096]$ 的输出投影 $W_o$ 返回隐藏空间。

用矩阵记号表示这一过程，就是 $A=\operatorname{Softmax}(QK^{\mathsf T}/\sqrt{d_h}+M)$，$O=AV$。这里 M 表示掩码。Qwen3 还对 Q、K 做 QK Norm，并使用 RoPE 编码位置信息。QK Norm 作用于各头特征，RoPE 对对应特征对做位置相关旋转，使查询与键的相互作用携带位置信息；两者都位于注意力评分之前。它们有归一化、乘加与特殊函数相关工作，不能因为矩阵 FLOPs 表主要列 GEMM 就从执行图上删去。

输入 P 个新位置、已有 S 个历史位置时，每条请求的第 i 个新位置可以访问 S+i 个位置。因此，有效因果位置对数为：

$$
N_{\mathrm{pair}}=B\left(PS+\frac{P(P+1)}{2}\right)
$$

每个位置对上，一个 Q 头的 QK 点积约需 2$d_h$ FLOPs，随后 AV 的贡献又约需 2$d_h$ FLOPs。合计所有 Q 头，QK 与 AV 的有效矩阵工作为：

$$
F_{\mathrm{attn}}=4n_Qd_hN_{\mathrm{pair}}=16384N_{\mathrm{pair}}
$$

这条公式统计允许参与的因果位置对。如果参考实现先做完整矩形乘法，再屏蔽上三角，执行的矩阵工作会更多；如果内核跳过因果上三角，则更接近有效项。数学上的 P×P 注意力矩阵也不意味着它必须完整写回显存。融合内核可以分块更新归一化和输出，避免大中间矩阵的全量物化。其实现留到第五章，但从这里开始就应区分有效计算、具体算法工作和物理流量。

### 2.1.4 前馈网络与前向计算量

注意力负责跨位置的信息交互，FFN 则对每个位置的特征执行非线性变换。Qwen3-8B 使用 SwiGLU：输入分别经过 gate 与 up 两条升维投影，其中 gate 分支应用 SiLU，再与 up 分支逐元素相乘，最后通过 down 投影降回隐藏维度：

$$
\operatorname{FFN}(X)=\left[\operatorname{SiLU}(XW_{\mathrm{gate}})\odot(XW_{\mathrm{up}})\right]W_{\mathrm{down}}
$$

gate 与 up 矩阵各为 $[4096,12288]$，down 为 $[12288,4096]$。三个矩阵合计 $3df$、约 1.51 亿个参数，以 BF16 保存为 288 MiB；处理 m 行输入需要约 $6mdf$ 矩阵 FLOPs。SiLU、逐元素乘、残差加法和 RMSNorm 另列。FFN 没有直接跨位置访问，不表示它没有数据搬移：读取大权重矩阵以及传递升维激活，正是其重要代价。

注意力的 QKV 与输出投影合计约 4194 万个参数。由表 2-1 的矩阵尺寸相加可得，在不含历史交互的主要矩阵工作中，FFN 约占 78%。这说明即使讨论的是 Transformer，资源分析也不能只盯着注意力。输入变长时，这部分随 token 数线性增长；无已有前缀的全历史注意力交互则随 $P(P+1)/2$ 增长。长上下文会改变两部分所占比例，不能在所有长度上都把总计算简化成固定的“每 token 两倍参数量”。

这两个数的差异来自本次处理的 token 数、历史交互和输出头调用范围。不能拿一次 8192-token prefill 与一次单 token decode 的总 FLOPs 直接比较“单 token 效率”，更不能据此推导两种执行的实际时间比例。

## 2.2 自回归生成与资源核算

单次前向给出了计算模块的组成，完整生成还需要确定调用次数和状态寿命。同一份权重可能在一个请求中被使用数百次，KV 则一边读取一边增长。最终保存的字节数与累计访问的字节数因此可以相差几个数量级。

### 2.2.1 Prefill、Decode 与状态复用

模型收到一段已知输入后，可以同时计算多个位置的表示。这一阶段称为 prefill。由最后位置的 logits 选择首个输出 token 后，下一次调用把这个 token 作为新输入，得到再下一个输出；这种逐步扩展的阶段称为 decode。两者使用同一个模型，但前者有多个已知输入位置，后者在普通串行生成中每条请求只增加一个位置。

如果每生成一个 token 都把整个前缀重新送入模型，旧位置的投影与 FFN 会重复执行。因果模型中，旧位置不能看到后来加入的 token；在权重、位置与相关计算条件不变时，旧位置产生的 K、V 可以保留。后续查询读取这些历史 K、V，并补入当前位置的新 K、V，就避免了旧位置的大量重算。

对普通全历史注意力，缓存并没有消除历史读取。它把“重新计算旧位置的表示”变成“保存并访问旧位置的状态”。Q 通常无需为未来位置长期保存，因为后续位置会产生自己的查询；K 和 V 才是未来查询要访问的对象。缓存是否合法还要求前缀、权重与执行语义匹配，跨请求共享与失效管理将在第八章讨论。

Qwen3-8B 的 BF16 KV 每个历史 token 占：

$$
\begin{aligned}c_{\mathrm{KV}}&=2L n_{\mathrm{KV}}d_h b_{\mathrm{KV}}\\&=2\times36\times8\times128\times2\ \mathrm{bytes}\\&=144\ \mathrm{KiB}.\end{aligned}
$$

第一个 2 表示 K 和 V，$b_{\mathrm{KV}}$ 表示每个 KV 元素的字节数。8192 个历史位置合计 1.125 GiB，每增加一个位置，再新增 144 KiB。一次全历史 decode 会在逻辑上用到旧历史，当前 K、V 也参与当步注意力；但旧历史是否全部从 HBM 重读，要看缓存层次、内核和复用行为。[缓存累计计算](../calculations/results/cache-sequence-qwen3-8b-b1.md)按调用次数明确列出了这些量。

### 2.2.2 驻留容量与逻辑访问

为了让后续模型比较使用同一口径，我们把数据分成权重、历史状态和临时数据三类。区分的依据是用途与寿命，而不只是它们都占用显存。

| 数据类别 | 保存与复用 | 本章主要核算项 |
| --- | --- | --- |
| 权重 | 通常在多次调用间保持不变 | 常驻字节、被访问的权重集合、批内复用 |
| 历史状态 | 随请求保留，持续追加或更新 | 有效容量、每步读取、写入及更新计算 |
| 临时数据 | 随算子和阶段产生、消亡 | 张量尺寸、接口载荷、同时存活范围 |

Qwen3-8B 全部权重统一按 BF16 计算，约占 16.38 GB，即 15.26 GiB。这个数描述保存整个模型的容量。一次 forward 的权重访问并不机械等于这个数：词嵌入只查若干行，词表输出头通常参与矩阵乘；MoE 还会选择专家。计算表中的“每算子理想读取一次”也不是对物理 HBM 的测量。

对于 $[m,d]\times [d,f]$，m 行输入使用同一矩阵。在足够理想的复用条件下，权重读取可被多行共同承担。因此，prefill 的计算量随 m 增长，并不要求每个 token 都独立从 HBM 重读整份权重。反过来，如果矩阵分块后不能充分保留权重或激活，实际重读次数又可能高于简单的一次读取模型。硬件容量与数据布局决定了哪些复用能够实现。

临时数据还带来另一个区别：所有中间张量的大小之和不是内存峰值。前一个层的缓冲可能已经释放，后一个层的缓冲才开始使用；融合又可能使某些中间值只存在于寄存器或片上存储。计算接口载荷时可以逐边列出，计算容量峰值时则必须检查同时存活的集合。第五章将用具体执行路径补齐这张图。

由此得到三种不同的量：有效状态表示需要的容量，声明算法或算子接口所访问的数据，以及具体设备接口上的实际流量。它们之间需要明确的映射条件。后文说某种表示“更紧凑”，首先指第一种量；能否节省 HBM 读取或执行时间，还需检查后两种量和新增计算。

这里还要区分“加载权重”和“计算时读取权重”。显存足够时，权重可以在模型加载后留在 GPU；每次前向仍要由设备计算单元读取，但通常无需再次从主机内存传入。KV 和层间激活也可以一直留在设备上。因此，本章累计的逻辑访问字节不能直接当成主机与 GPU 之间的传输字节。

### 2.2.3 完整生成的计算与状态累积

现在固定一个普通串行生成请求：$B=1$，已恢复前缀为 S，本次输入 $P\ge1$ 个 token，最终返回 $G\ge1$ 个 token。令 $H=S+P$。prefill 处理新输入并产生首输出，随后执行 $D=G-1$ 次 decode。最后返回的 token 尚未重新送入模型，所以请求结束时并不自动为它保存 KV。

第 j 次 decode（j 从 0 开始）执行前，历史长度为 $H+j$。于是，累计旧历史读取的唯一载荷为：

$$
R_{\mathrm{old}}=c_{\mathrm{KV}}\sum_{j=0}^{D-1}(H+j)=c_{\mathrm{KV}}\left[DH+\frac{D(D-1)}{2}\right]
$$

decode 追加状态为 $c_{\mathrm{KV}}D$；若保留整个上下文，最终有效 KV 为 $c_{\mathrm{KV}}(H+D)$。本次请求的全部新增 KV 还应包含 prefill 写入的 $c_{\mathrm{KV}}P$。已有前缀的恢复与传输单独核算。这些公式中的读取只统计旧历史，不把当前 token 在同一调用内的操作数访问混进去，也不包含页尾空位与分配元数据。

取 $S=0$、$P=8192$、$G=1025$，则 $D=1024$，累计访问的旧历史位置数为 8,912,384。乘以 144 KiB，旧历史读取载荷约为 1224 GiB，而最终 KV 只有 1.27 GiB，decode 新增 KV 为 144 MiB。两者相差很大，是因为同一段历史被后续查询反复使用；它不表示需要同时分配一千多 GiB 内存。

累计计算也必须沿同样的调用序列完成。投影和 FFN 的单 token 工作相对固定，注意力项随 $H+j$ 增长，输出头按实际调用位置计量。如果把 G 直接当作 decode 次数，就会多算一次模型前向、一次状态追加和相应历史读取。$G=1$ 是很有用的边界检查：只有 prefill 产生首输出，后续 decode 为零。

多条无共享前缀的请求，状态容量与各自历史访问相加；批内权重却可能共享。请求长度不同时，应逐请求累积有效工作，再讨论 padding 和执行安排。真实记录中如果只有 API 返回 token 数，没有逐步调用和缓存恢复记录，上述公式只能构成带明确假设的代入结果，不能冒充观测到的实际执行。[封存 Chat 长度核算](../calculations/results/sealed-chat-known-prefill.md)正是按这一原则保留已知字段和未知路径。

## 2.3 历史状态表示与访问机制

全历史 KV 的容量随序列长度增长，累计读取又随生成次数增加。架构可以从不同位置改变这笔需求：减少每个历史位置的表示宽度，压缩或选择历史条目，或者把历史更新进固定大小的状态。这些选择影响的对象不同，也会产生不同的新增工作。比较时必须同时观察保存、选择、读取和更新。

### 2.3.1 多头注意力与 KV 共享

多头注意力允许不同查询子空间建立各自的历史关联。在标准 MHA 中，每个 Q 头对应自己的 K、V 头；MQA 让所有 Q 头共用一组 K、V；GQA 则把 Q 头分组，每组共享一组 K、V。它们首先改变的是历史表示的宽度，而不是序列长度。

先看一个只有四个查询头的单层例子。MHA 为四个查询头各存一份 K、V；GQA 可以让前两个查询头共享第一份 K、V，后两个共享第二份；MQA 则让四个查询头共用一份。若历史长度和头宽相同，需要保存的 KV 份数依次为四、二、一。因此，GQA 在这个例子中把历史保存量减半。四个查询头仍可给同一段历史打出四组不同的分数，这正是“共享历史表示”与“合并查询”之间的区别。

![图 2-3 查询头与共享历史的对应关系](ch02/figure-2-3-sharing.svg)

*图 2-3：四个查询头的教学例子。连线表示每个查询使用哪一组历史 K、V；三种结构都保留四个查询。图中组数用于解释共享关系，不是三个真实发布模型的配置。*

回到 Qwen3-8B：它让每四个查询头共用一组 KV，总计 32 个查询头、8 个 KV 头。如果给每个查询头单独保存 KV，容量会是当前配置的四倍；如果全部查询共享一组，则会是当前配置的八分之一。实际 GQA 配置保存 8192 个位置需要约 1.13 GiB。下面的容量图把这两个教学变体并列，是为了验证“保存量正比于 KV 组数”，而不是要求读者记住三组孤立的字节数。

这些状态容量的比例，不能直接套在全部注意力 FLOPs 上。32 个 Q 头仍产生不同的查询，每个查询仍需对历史评分并汇总 V。共享 K、V 减少其投影、保存与潜在读取，也为物理实现提供跨 Q 头复用机会，但不会把全部 QK／AV 交互自动按 KV 头数同比缩小。能否用更少的 KV 头满足任务质量，则需要训练和评测证据。

### 2.3.2 潜变量压缩与 MLA 执行路径

KV 共享减少并行表示的组数，MLA 则改变保存的表示本身。可以先把输入投影为低维潜变量 c，再通过上投影得到用于注意力的 K、V。若低维表示足以支撑模型能力，历史就有机会以 c 的形式保存。

更关键的是，执行时不一定要把全部历史潜变量显式展开。设 $K=cU_k$，则查询与键的点积可写为 $qK^{\mathsf T}=(qU_k^{\mathsf T})c^{\mathsf T}$。把键的上投影吸收到查询侧，便可直接对潜变量评分。V 的线性上投影也可在适当的矩阵结合次序下移到加权汇总之后。这些代数变换改变矩阵形状、中间表示和重复工作；门控、分支与数值格式仍需要按实际模型保留。

本章采用 Kimi K3 的 Gated MLA 作实例。其紧凑教学路径保留 512 维潜变量和参与 QK 的 64 维额外分支。报告使用 NoPE，不等于参考代码删掉了额外分支：没有施加旋转位置编码，与不存在这组计算维度是两回事。24 个 MLA 层、8192 历史、BF16 下，紧凑保存量为 $24\times 8192\times (512+64)\times 2$，即 216 MiB。

然而，仓库固定的 Hugging Face 参考代码缓存的是展开后的 K／V，同一长度的 MLA 历史约为 11.25 GiB。216 MiB 描述紧凑代数路径，11.25 GiB 描述该参考实现的展开缓存；不能把前者写成后者实际分配的内存，更不能拿两者构成一项未经测量的运行加速比。[两条 MLA 执行路径的计算](../calculations/results/k3-mla-expanded-b1-t8192-s0.md)分别保留了矩阵工作与状态口径。

MLA 还保留全局历史访问：潜变量比展开表示窄，历史条目数仍随 S 增长。它改变了每条历史的宽度，没有自动消除对全部历史评分的工作。此外，K3 的其余 KDA 层、短卷积状态和工作区尚未包含在这 216 MiB 中，整模型合计必须等各分支齐备。

### 2.3.3 局部窗口、历史压缩与稀疏索引

减少历史表示宽度之后，还可以改变保留哪些历史、每次访问哪些历史。局部窗口只关注最近的一段位置；压缩机制把若干位置合成较少的条目；稀疏选择先确定相关条目，再把它们送入主注意力。这三个动作可以组合，却不能合并成一个“稀疏率”。索引器为了找到少量条目，可能仍需扫描较大的索引历史。

DeepSeek-V4-Flash 的固定配置有 43 个主干层、4096 隐藏维度、64 个注意力头，每头维度 512。Q 先从 4096 维投影到 1024 维，再得到 $64\times 512$ 维查询；共享 KV 从 4096 维投影到 512 维；输出采用分 8 组的低秩投影。投影宽度并不必然等于隐藏维度，沿“hidden×hidden”估算所有矩阵会漏掉真实形状。

其主干包含 2 个纯窗口层、21 个 CSA 层和 20 个 HCA 层，窗口长度为 128。CSA 按压缩比 4 保存历史，并维护索引；HCA 按压缩比 128 保存更粗的历史。用 BF16 参考表示，CSA 每个完成的压缩条目含 512 维主状态，另有 128 维索引条目。已有 S 个位置时，完成条目数按 $\lfloor S/4\rfloor$ 计算；尚未完成的压缩块还需独立缓冲。

一次 CSA 查询的主注意力最多读取窗口加 512 个压缩条目，但索引打分仍扫描压缩索引历史。在 $S=8192$ 时，一个 CSA 层保留 2048 个压缩条目：主历史约 2 MiB、索引约 0.5 MiB，窗口约 0.125 MiB；主注意力选择的压缩条目最多约 0.5 MiB，索引扫描却仍需处理那 2048 个索引条目。HCA 则有 64 个完成条目，主历史约 0.0625 MiB，并访问窗口加这组粗粒度历史。

将 43 层相加，8192 历史下的窗口、压缩历史和索引约为 59.125 MiB；另有约 11.641 MiB 的 FP32 压缩器缓冲，合计约 70.8 MiB。最后查询的主注意力与索引载荷约 27.6 MiB。[状态分解](../calculations/results/state-deepseek-v4-flash-n8192-b1-native.md)将这些分项列开，因此能看出选择条目数、保存量和每步读取量并不相等。

压缩还需要持续更新。压缩器可以对每个新 token 都做投影，并在块完成时形成新条目；不能只在块边界计一次全部工作。128 边界可能同时触发不同层型的更新，平均写入量也不能替代边界峰值。仓库中固定 V4 增量路径对恢复前缀后的已知后缀逐 token 执行，甚至会计算被丢弃的中间 logits；这与并行 chunk prefill 是不同的调度。[缓存后缀续算记录](../calculations/results/v4-prefix-flash-6144-2048.md)保留了该差异。

### 2.3.4 线性注意力与有限状态递推

另一种路线是让历史进入有限大小的统计状态。作为直观起点，可以考虑 $S_t=S_{t-1}+k_tv_t^{\mathsf T}$、$o_t=q_t^{\mathsf T}S_t$ 这样的线性聚合。矩阵 S 汇总历史中键和值的关系，后续查询不必逐个取回全部 token。该形式只是解释有限状态的教学例子；带归一化的普通 Softmax 注意力不能无条件改写成这组等式。

KDA 使用更丰富的门控与 delta 更新。状态更新不仅写入新信息，还根据当前键对既有状态的预测形成修正，并通过衰减控制旧信息保留。直观上，它更新的是一张固定大小的关联矩阵，而不是不断追加一张逐 token 列表。有限状态是否足以支持精确检索、长期关联或其他任务，必须由相应模型的训练与质量记录验证。

K3 每个 KDA 层有 96 个头，每头递推矩阵为 $128\times 128$。按 FP32 保存，单层为 6 MiB，69 层为 414 MiB。这个量与历史长度无关，但并不小。若一次 decode 对每个递推矩阵理想地读取一次、写回一次，仅递推矩阵的读写就是 828 MiB；短卷积、投影、门控和其他状态还没有加入。省去全历史 KV 扫描，不等于状态访问变为零。

prefill 与 decode 的实现方式也不同。decode 可以采用单步递推；对一段已知输入，块式算法则把块内计算并行化，再在块之间传递状态。固定 KDA 参照实现的 8192-token、$chunk=64$ 算例中，每层中间 chunk state 为 384 MiB，已确认的最大同时存活缓冲子集约 1926 MiB。[块式状态与缓冲记录](../calculations/results/k3-kda-chunk-t8192-c64.md)包含尾块和非零初始状态检查。

1926 MiB 不是完整模型运行峰值，也不能乘以 69 个顺序执行层。它说明固定大小的最终递推状态，并不能替代 prefill 的临时工作区预算。融合、分块和缓冲寿命仍然决定实际执行代价。

### 2.3.5 混合注意力的状态构成

实际模型常把有限状态层与全局注意力层混合使用。这样既利用递推结构的历史压缩，也保留部分直接访问全局历史的能力。但整模型状态不再服从单一的“固定”或“线性增长”规则，而是多种分量之和。

K3 的配置为 69 个 KDA 层和 24 个 MLA 层，其中末尾额外的 MLA 使总数不能仅按 3:1 比例推算。8192 历史、紧凑 BF16 MLA、FP32 递推状态及给定 BF16 短卷积槽位下，三项分别为 216 MiB、414 MiB 与 19.4 MiB，合计约 649.4 MiB。若使用参考展开缓存，MLA 一项就变为 11.25 GiB，整体随之改变。[混合状态计算](../calculations/results/state-kimi-k3-n8192-b1-compact.md)为两条路径保留独立结果。

Qwen3.6-35B-A3B 同样需要按层型计算。其 30 个线性注意力层加 10 个完整注意力层，使每请求每历史 token 的全局 KV 为 20 KiB，另有固定 FP32 递推状态 60 MiB 和 BF16 卷积槽 1.875 MiB。8192 历史时，三项合计 221.9 MiB。下一节会用它讲 MoE，但这些状态差异来自注意力分支，不能都归因于专家计算。

## 2.4 条件计算与专家权重复用

前面主要改变历史状态，现在回到 FFN 的权重。稠密 FFN 对每个 token 使用同一组矩阵；MoE 把容量分散给多个专家，由路由器为每个 token 选择少数专家。它使“模型保存多少参数”与“一个 token 激活多少参数”分离，也让 batch 内不同 token 的选择影响实际权重访问集合。

### 2.4.1 稠密前馈网络与专家路由

一个典型 MoE 分支先从输入计算路由分数，选择 top-k 专家，再把 token 送入选中专家，最后按路由权重合并输出。有共享专家时，还会有一条所有 token 都参与的分支。专家本身通常仍由 gate、up、down 三个矩阵构成，因此可以沿上一节的 SwiGLU 计算逐个展开。

Qwen3.6-35B-A3B 的固定文本配置包含 40 层，隐藏维度 2048；每层 256 个路由专家，每 token 选 8 个，专家中间维度为 512，另有共享专家。一个路由专家包含 $3\times 2048\times 512=3,145,728$ 个参数，以 BF16 保存为 6 MiB。每层全部路由专家占 1.5 GiB，一个 token 选中的八个专家占 48 MiB。

设专家 e 实际收到 $t_e$ 个 token，其 gate/up 是 $[t_e,2048]\times [2048,512]$，down 是 $[t_e,512]\times [512,2048]$，主要矩阵工作为 $6t_e\times 2048\times 512$。全部路由专家的矩阵工作对 e 求和。路由器、共享分支、激活函数和收集合并仍需另计，不包含在这条专家矩阵公式里。

总参数决定可能需要保存的权重，逐 token 选中参数近似反映部分激活工作。名称中的 A3B 不能代替完整计算：注意力、路由、共享专家、输出头和其他算子仍会执行。仓库核对的基础文本参数为 34,660,610,688，统一 BF16 权重约 69.321 GB；视觉与 MTP 的权重和执行范围另列。[Qwen3.6 逐矩阵结果](../calculations/results/qwen36-prefill-8192.md)给出了完整组成。

### 2.4.2 激活计算与批内权重访问

即使激活参数相同，batch 内的权重读取也可能不同。假设 $B=64$，每个 token 选择 8 个专家，总共有 512 次 token–expert 分派。若均匀分到 256 个专家，每个专家平均接收 2 个 token，当前批次会访问全部路由专家；若所有 token 都集中到同 8 个专家，则每个专家接收 64 个 token，当前批次只访问 8 份专家权重。

这两种情况的专家矩阵有效 FLOPs 相同，因为 $t_e$ 的总和都是 512。按每个不同专家理想读取一次权重计算，每层访问量却从 1.5 GiB 降到 48 MiB，相差 32 倍。40 层合计的路由专家权重容量为 60 GiB，集中情形的批内选中集合合计为 1.875 GiB；容量仍是原来那 60 GiB，除非系统另行改变放置或卸载策略。

| $B=64$ 的路由情形 | 每层访问的不同专家 | 每专家 token 数 | 每层路由专家理想读取 |
| --- | ---: | ---: | ---: |
| 均匀分配 | 256 | 2 | 1.5 GiB |
| 集中于同 8 个专家 | 8 | 64 | 48 MiB |

因此，专家访问集合是介于单 token 激活参数与模型总参数之间的另一项关键信息。[均匀路由](../calculations/results/qwen36-decode-b64.md)与[集中路由](../calculations/results/qwen36-decode-b64-concentrated.md)计算保留了相同工作下的差异。真实实现还会受到矩阵行数、tile 补齐、路由聚合及内存层次影响，32 倍载荷差异不直接等于 32 倍速度差异。

对 Qwen3.6，已有 8192 历史的 $B=1$ decode 约需 7.33 GFLOPs，按所选参考路径计量。这个数小于本章 Qwen3-8B 基线的一步矩阵工作，却不能把全部差异都解释为 MoE：前者隐藏维度、层型和注意力状态也不同。只有先分解组件，再合成整模型，才不会把同时发生的架构变化误认为单一机制的效果。

### 2.4.3 共享专家与潜空间计算

更复杂的专家结构继续沿同一方法展开。DeepSeek-V4-Flash 每层有 256 个路由专家，每 token 选 6 个，另有 1 个共享专家；路由专家中间维度为 2048。单专家的 gate/up 为 $[t_e,4096]\times [4096,2048]$，down 为反向尺寸，参数为 25,165,824。前三层哈希路由与后续评分路由分开计量；哈希分支的参考执行仍可能包含不能从名称推断的路由计算。

共享专家意味着每个 token 还有共同工作。把 top-k 专家的工作相加之后，若忘记共享分支，就会低估激活计算与权重访问。全模型报告中的约 284B 总参数和 13B 激活参数也使用自己的定义；仅把专家矩阵相加，不能得到包含注意力、连接与输出模块的精确总数。

K3 的路由专家有 896 个，每 token 选 16 个，并在 3584 维潜空间中执行宽度 3072 的专家变换。主干输入进入潜空间、专家输出离开潜空间，都有额外投影；共享专家仍使用主干空间，首层 dense 与其他层的专家结构也要区分。路由概率在哪个维度施加、输出如何合并，同样会影响操作数与标量工作。[V4／K3 专家矩阵记录](../calculations/results/experts-kimi-k3-b64-balanced.md)逐层保存这些差异。

一旦专家放在不同设备，逻辑选择就会转化为 token 的分派、收集和跨设备等待。但逻辑路由本身没有指定物理放置。第六章先讨论专家和其他权重的多卡划分，第九章再比较 CPU／GPU 放置及 AF 分离。这里交付的是每个专家接收多少 token、对应哪些矩阵，以及哪些权重需要被访问。

> **实验 2-6 ★★〔延伸〕：专家矩阵与负载**
>
> 从 Qwen3.6 的 256 选 8 算例出发，对均匀与集中路由分别建立 $t_e$ 表。核对两者专家 FLOPs 相同，而批内不同专家权重集合相差 32 倍。再换成 V4 的 256 选 6 加共享专家，最后尝试 K3 的潜空间专家。
>
> 对每次修改都列出新增计算、被复用权重和路由／合并工作。矩阵有效 FLOPs 与 tile 补齐工作分别记录。若下一步要选择多卡方案，还需要补专家放置和 token 身份，单独的分派次数直方图不足以确定全部通信。

## 2.5 网络形状与计算组织

历史状态与专家选择改变了主要数据集合，网络的深度、宽度和连接方式则进一步决定这些工作以什么形状、什么顺序执行。相近的参数预算不保证相同的执行图，甚至相近的矩阵 FLOPs 也可能伴随不同的缓冲寿命和串行步骤。

### 2.5.1 深度、宽度与专家颗粒度

在粗略参数预算下，增加层数可以由减小宽度补偿，增加宽度也可以由减少层数补偿。但更深的模型增加了逐层依赖，并让每个保留历史的层都增加一份 KV 或递推状态；更宽的矩阵则改变了矩阵分块、片上容量需求和硬件利用机会。深窄和浅宽不是只看总参数就能互换的两个形状。

专家数量与宽度之间也有类似关系。Qwen3-235B 的真实基线有 128 个宽度 1536 的专家，每 token 选 8 个。教学变体改为 64 个宽度 3072 的专家，每 token 选 4 个，专家总参数预算和激活专家矩阵工作可以保持相同。可是 router 的输出维度改变，每专家接收的 token 数和 GEMM 形状也改变，因此完整模型并非严格等参。

本书的 16-token 算例中，两种配置的专家矩阵工作都约为 454 GFLOPs；变体的路由器更窄，完整参数因此略少。相同的专家预算被重新切成了不同数量、不同宽度的小矩阵。另一种 256 个宽度 768、选 16 个专家的教学变体同样保持专家预算，但路由参数又会增加。[专家颗粒度计算](../calculations/results/qwen235-granularity-baseline.md)按真实矩阵记录差额，不把“专家预算相同”写成“全部参数相同”。这些变体没有经过训练，质量与真实速度也没有由公式证明。

形状还约束多卡切分。128 个专家可以均匀分给八卡，但四个 KV 头不能在 $TP=8$ 时继续无复制地按完整头均分。常见实现需要复制或调整并行组合。整数可分只是必要的结构条件，逐卡峰值、通信、负载和实际矩阵效率仍要继续计算。第五章检查 tile 与执行，第六章才完成 TP／PP／EP 的分工。

### 2.5.2 残差连接与跨层状态

普通残差路径将子层输入与变换结果相加，使信息能够沿网络深度传递。它的参数量可能远小于 FFN，数据流作用却不能忽略。模型采用更复杂的连接时，需要保存的跨层表示、混合工作和临时缓冲都可能改变。

V4-Flash 的 mHC 使用 4 路残差状态，并通过混合与汇合连接注意力、FFN 和主干。四路残差不意味着每个子层都以 $4\times 4096$ 的隐藏维度计算：汇合后的子层输入仍是 4096 维。若直接把所有矩阵的 d 改成 16384，会大幅高估主体计算；若完全省去混合投影和归一化，又会漏算新增工作。

固定 8192-token 算例中，mHC 混合投影约为 555 GFLOPs，普通算术约为 149 GFLOPs，特殊函数独立记录。参考代码中的 Sinkhorn 归一化迭代在局部中间数据上推进，不能把迭代次数机械乘成 HBM 往返次数。最终 hc_head 处理新输入位置，词表头才按所选策略只处理最后位置。[mHC 子账](../calculations/results/hc-deepseek-v4-flash-b1-t8192.md)单独保留了这些边界。

K3 的 AttnRes 从网络深度上的块表示构造加权混合。它使当前层可以按内容选择来自较浅层的块表示，而不只接收紧邻上一子层的输出。块大小决定候选集合如何形成，逐层调度和精确数量留在配套记录中。这个堆栈属于本次 forward 的深度状态，每次调用重新建立，不是额外跨 token 保留的 KV。把它计入历史 cache，会错误地改变随生成长度增长的容量公式。[逐层调度记录](../calculations/results/k3-attn-res-b1-t8192.md)同时列出前缀累加、候选与缓冲。

![图 2-8 稠密层与 V4 层的数据流](ch02/figure-2-8-residual.svg)

### 2.5.3 多 token 预测与辅助计算

普通自回归主干对当前上下文产生下一个位置的预测。MTP 在训练目标或辅助结构中加入对更多位置的预测，可以为学习和推理提供额外路径。分析时必须区分三件事：训练时优化了哪些预测目标，发布的模型实际包含哪些模块，服务后端又启用了哪些模块。

作为推理草稿时，MTP 可以提供候选，但候选还要经过目标模型验证。一次辅助前向的 FLOPs 并不能告诉我们每轮最终接受多少 token，更不能直接得出加速比。草稿计算、目标验证、拒绝后的补偿以及状态回滚都属于完整推测执行，第八章会以有效输出重新计算收支。

本书固定的 V4 单次 MTP 算例由调用方提供主干特征与 token ID，只执行相应辅助块，没有再次执行主干。$B=1$、$T=1$ 时，矩阵工作为 1.80 GFLOPs，其中共享词表头为 1.06 GFLOPs。辅助块自有逻辑参数、checkpoint 载荷和共享嵌入／输出头分别计量，避免把共享权重重复加入常驻容量。[单次 MTP 计算](../calculations/results/v4-mtp-first-call.md)不推断草稿步数、接受率或时延。

类似的执行组织问题也出现在多模态生成中。Qwen3-Omni 的编码器、Thinker 与 Talker/code2wav 形成多个阶段；Fish Audio 使用 slow／fast AR 与 codec；Qwen-Image／FLUX 在 latent 空间迭代，视频生成还要处理时间维度。视频理解输入经过视觉编码，并不等于系统能够生成视频帧。MiniMax-H3 的注意力投影宽度也不能直接用 hidden 代替。[生成模型短例](../case-studies/generative-multimodal-models.md)保留各类固定配置与路径。

这些模型提醒我们：一次 forward、一次采样、一个输出 token 和一份最终媒体内容，可能是不同的计量单位。第二章建立组件与调用的资源模型，第三章再把编码、生成、迭代及实时输出组织成完整负载。

## 2.6 整模型需求与条件比较

前面已经建立三类结构变化：历史表示改变状态与访问，专家选择改变被激活的权重集合，网络组织改变矩阵形状和依赖。最后一步是把各部分合起来，在同一请求定义下检查容量与计算需求，并将质量证据放回比较条件。

### 2.6.1 模型组件与资源汇总

汇总计算时还要防止重叠。某个组件总数已经包含其内部矩阵，不能再把同一子项加一遍；一种 tile 口径替换有效矩阵项时，也应做替换而非相加。接口载荷若来自不同抽象层，可能描述同一份数据，必须先确定边界。一个可检查的汇总不仅有总数，还要能沿组件追到尺寸、调用与计量范围。

### 2.6.2 参数规模、数值精度与容量约束

容量筛选把模型需求与给定设备预算连接起来。对一张设备，先扣权重，再扣工作区和其他固定预留，剩余空间才能放请求状态。对普通等长、独立 KV 的简化情形，可写为：

$$
B_{\max}=\left\lfloor\frac{M_{\mathrm{device}}-M_{\mathrm{weight}}-M_{\mathrm{workspace}}}{M_{\mathrm{state/request}}}\right\rfloor
$$

若分子为负，连固定部分都装不下；如果状态包含随 batch 扩展的递推或卷积，也应计入每请求状态。真实运行峰值、并行复制和系统占用还会进一步改变可用空间。这个式子给出声明预算下的容量筛选，不是已经验证的服务并发。

Qwen3-8B 的 BF16 权重约 16.381 GB。设备预算取 24 decimal GB，固定工作区预留 2 GiB，每请求保留 8192-token BF16 KV，则计算上可放 4 条请求，加入第 5 条会超出预算。第一章“约 8B 权重约 16 GB”的估算，在这里被补成具体参数、状态与余量的计算。

70B 则使用固定的 DeepSeek-R1-Distill-Llama-70B，真实参数为 70,553,706,496。其 BF16 权重为 141.107 GB，每条 8192-token BF16 KV 为 2.5 GiB。在本书声明的分组低位宽方案中，保留嵌入、输出头和归一化等较高精度部分，并计入 scale 与打包尾部后，8-bit 方案约为 73.726 GB，4-bit 方案约为 39.500 GB。

因此，$70\times10^9\times0.5\ \mathrm{byte}=35\ \mathrm{GB}$只是理想载荷。实际方案并非每个参数都恰好占半个字节。80 decimal GB、2 GiB 固定预留下，8-bit 方案只能容纳 1 条 8K 请求，4-bit 方案可容纳 14 条；把历史增长到 32K，4-bit 方案只剩 3 条。[容量表](../calculations/results/llama70-capacity-8k.md)及[32K 对照](../calculations/results/llama70-capacity-32k.md)均采用相同的声明格式，没有声称已验证量化 checkpoint 的质量或吞吐。

![图 2-9 模型容量与架构形状](ch02/figure-2-9-capacity.svg)

*图 2-9：左侧按十进制 GB 分解一个请求的权重、状态和 2 GiB 固定预留，并给出指定容量下的算术并发；右侧比较专家颗粒度，只有基线为发布配置。容量与形状不会自动证明相同质量、可用吞吐或完整训练可行。*

约 30–32B、70B 和 235B 的部署范围也需要这样逐项计算。30B MoE 与 32B Dense 即便名称相近，全部常驻权重和每 token 工作也不是同一种含义。235B 的名义 BF16 权重约 470 GB，八张 80 GB 卡的总容量看似充足，但还需检查逐卡复制、状态和工作区；八张 24 GB 卡则是另一组容量条件。

所谓部署“甜点”，可能指能装下的可行点，也可能指满足延迟、吞吐与费用目标的经济点。模型团队选择某个规模的历史动机还涉及能力、训练数据和预算。容量计算不能倒推出“某一参数规模唯一为某种卡设计”的结论。

> **实验 2-7 ★〔核心〕：模型规模与硬件的适配范围**
>
> 固定 2 GiB 预留，复算 Qwen3-8B BF16 在 24 GB、8K 历史下的 4 条请求，以及 70B 4-bit 声明方案在 80 GB 下的 14 条请求。再将历史变为 32K，检查状态项增长与整数并发下降。
>
> 对 235B 的给定八卡放置结果，先看最忙一张卡，而不只看总剩余容量。最后改变数值精度或专家颗粒度，列出仍需补测的质量、工作区和执行效率；容量通过并不替代这些条件。

### 2.6.3 请求条件与模型比较

模型比较要同时固定资源输入和任务条件。固定 S、P、G、B 能对齐请求几何，却不保证不同分词器处理同样的文本；固定文本又可能产生不同 token 数。前一种对照适合隔离资源结构，后一种对照适合检查具体任务。二者应互相补充，而不强行合成一张无条件排行榜。

先做资源对照。取 $S=0$、$P=128$、$G=4$、$B=1$，即一次输入前向加三次 decode，最终保留 131 个已处理位置。本书已有四模型结果如下。[统一请求计算](../calculations/results/request-four-models-book.md)分别累积前向、历史增长、读取与写入。

| 模型 | 完整请求矩阵工作（TFLOPs） | 本次比较的关键口径 |
| --- | ---: | --- |
| Qwen3-8B | 1.83 | 有效因果矩阵工作，最后位置输出头 |
| V4-Flash | 3.40 | 主干有效注意力／专家工作，参考索引计算 |
| V4-Pro | 12.72 | 独立 Pro 配置，按自己的层型和选择上限计算 |
| Kimi K3 | 27.13 | 展开 MLA 与块式 KDA 数学口径 |

这些数包含不同模型的真实结构和所声明的参考路径。非矩阵算术、特殊函数、数值格式和实际硬件效率不同，表中 FLOPs 不能直接除以同一个峰值，得到可信的运行排名。特别是 K3 的整请求表使用展开 MLA；前面用于解释紧凑状态的路径不能未经重算就替换进这张表。

从表中至少可以提出一组可检查的问题：对给定长度，哪种状态表示更省容量？随着 G 增长，哪些历史会重复读取？MoE 的激活工作与常驻权重之间差多少？如果改成长输入、短输出，原来占比最高的需求是否改变？这些问题由逐项资源表回答，完整时延和系统设计则等待后续章节补入供给与执行。

> **实验 2-8 ★〔延伸〕：从请求长度计算模型需求**
>
> 使用[封存 Chat／Agent 记录](../experiments/ch02/02-08/README.md)中的已知长度，按 2.2 的规则计算输入与后续调用。四条原始 capture 共报告 753 个输入 token、489 个缓存 token 和 79 个返回 ID；这些汇总本身不能确定所有模型调用和恢复路径。
>
> 先计算可证字段对应的工作，再写出普通串行生成的条件假设。逐条请求处理首输出与 $G-1$ 次 decode，不把返回总数直接当作观测的 decode 次数。请求分布、工具等待与复用间隔将在第三章分析。

现有同消息实验把 Qwen3-8B 与 V4 Flash 放在同一组八道短语检索题上，两者均 8/8 精确答对并正常停止。但输入 token 并不相同：短文 Qwen 为 523 或 524，V4 为 501；较长一档 Qwen 为 2121 或 2122，V4 为 2036。“较长”只是相对本组短文，不是长上下文能力检验。

实验还使用不同部署：Qwen 为 BF16 权重与 KV、vLLM 路径；V4 为 MXFP4 专家 fallback、FP8 KV、SGLang、110 GiB CPU offload 和显式兼容适配。V4 复用此前八份原响应，Qwen 新增同消息结果。这些记录证明两种已测部署都完成了这个窄任务，没有证明一般能力相同，也不能从耗时判断纯架构速度。[配对检索记录](../experiments/ch02/02-09/paired-retrieval/README.md)将 Pro 与 K3 的匹配质量保持为未知。

![图 2-10 请求输入与计算状态映射](ch02/figure-2-10-request.svg)

*图 2-10：$S=0$、$P=128$、$G=4$ 的请求只有三次后续 decode。首输出来自输入阶段，最后输出尚未成为模型输入。下方列四模型的同请求矩阵工作；它们是资源推算，不能和右侧八题实测的输入长度或部署条件混成一次性能实验。*

> **实验 2-9 ★★〔延伸〕：请求条件下的模型选择**
>
> 从 Qwen3-8B 与 V4-Flash 的统一请求表出发，分别比较 prefill、单步 decode、整段生成、常驻权重和状态。把 G 改为 1，检查后续 decode 是否归零；再加入恢复前缀，检查状态恢复假设和 V4 增量路径。
>
> 使用八题配对结果填写质量条件：本题两者都通过，Pro／K3 未测。若更难任务使结论变化，需要新增匹配证据，不能继承其他模型分数。给出你的条件式选择，并说明哪项新测量最可能推翻它。

本章由一张计算图走到一份完整请求需求表。注意力改变历史的表达和访问，MoE 改变权重的选择与复用，网络形状、连接和辅助模块改变执行组织。每一种变化都可能减少某些需求，同时增加另一些工作。下一章在同一份表上加入请求长度分布、到达与交互、训练和 RL 循环，使单次模型需求成为随时间变化的系统负载。
